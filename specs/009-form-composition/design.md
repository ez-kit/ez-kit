# Композиция формы до 1.0

**Дата:** 2026-10-09
**Статус:** дизайн согласован (архитектура и API, поведение, шаги в JSX), план ещё не написан. `SchemaForm` — отдельная спека (§5).
**Пакеты:** `@ez-kit/form-core`, `@ez-kit/form-react`, `@ez-kit/form-shadcn`, `@ez-kit/form-heroui`

## 1. Зачем

Всё, что здесь решено, до 1.0 меняется дёшево, а после — только мажором. Аудит, с которого всё
началось, нашёл четыре дефекта такого рода:

1. **Контракт кита закрыт.** `FormFieldSlots` (12 видов полей) и `FormComponents` (7 слотов
   обвязки) — полные обязательные наборы. Любой новый вид поля или слот после 1.0 — ошибка
   компиляции в каждом внешнем ките, который написал `satisfies FormComponents`.
2. **Ничего не вытряхивается.** Импорт одного поля из корня кита стоит весь кит.
3. **Граф зависимостей допускает две копии TanStack**, а публичная поверхность выставляет имена,
   которые публичными быть не должны.
4. **Разнобой в именах:** `OptionsSource` против `OptionSource`, четыре имени для типа инстанса
   формы, `FormRenderer` для того, что на самом деле форма.

## 2. Замеры

Сборка esbuild из исходников, минификация, production. `react`, `react-dom` и `@tanstack/*` —
внешние; все зависимости китов включены, потому что за них платит приложение. Строки «только
`TextField`» симулируют чистый корень кита: импорт напрямую из `blocks/` и `createForm` с одним
полем.

| Вариант                                                 | min    | gzip   |
| ------------------------------------------------------- | ------ | ------ |
| shadcn — готовый `useForm` (сейчас)                     | 424 KB | 134 KB |
| shadcn — только `TextField` + `Button`/`Form`           | 76 KB  | 23 KB  |
| heroui — готовый `useForm` (сейчас)                     | 602 KB | 176 KB |
| heroui — только `TextField` + `Button`/`Form`           | 132 KB | 42 KB  |
| `form-react` — один `createForm` (= весь entry целиком) | 37 KB  | 11 KB  |

Внутри `form-react`: биндеры полей ~10 KB min, схемный рендерер ~10 KB min, источники опций ~5 KB
min. Обвязка поверх shadcn-формы с одним полем: `Section`+`GridItem` +0.3 KB gz, `ArrayField`+
`ArrayItem` +1.7 KB gz, `Wizard` +2.2 KB gz.

Два вывода определяют дизайн:

- **Вес даёт слой вида в китах** (`@base-ui/react`, `react-day-picker` + `date-fns`, Radix
  Select/Slider в shadcn; `react-aria` + `react-stately` в heroui), а не биндеры. Он вытряхивается
  сам, как только корень кита перестаёт его держать.
- **Корень кита держит один файл.** Из корня shadcn `stripHiddenValues` стоит 2.3 KB, а `TextField`
  — 424 KB: `TextField` реэкспортируется через `form.tsx`, где вызов `createForm(...)` на верхнем
  уровне и деструктуризация результата удерживают все компоненты.

Отсюда отказ от «определений» полей — пары биндер + вид, чтобы вытряхивались и биндеры. Все
биндеры вместе весят ~3 KB gz; ради этого пришлось бы сломать каждый экспорт китов.

## 3. Решения

### D1. Tree shaking даёт чистый корень, а не сабпути

- У китов остаётся один entry `"."`. Сабпутей сейчас нет: добавить сабпуть потом — аддитивно,
  убрать — мажор, так что YAGNI.
- Компоненты полей и обвязки экспортируются из корня кита **напрямую из `blocks/`**, никогда через
  модуль, который собирает готовую сборку.
- Готовая сборка создаётся под `/* @__PURE__ */` с **плоским** литералом-объектом — без spread
  (`AGENTS.md`: esbuild оставляет аннотированный вызов, если в аргументе есть spread) и без
  деструктуризации результата на верхнем уровне (дефект `createStoreCache()`). Как экспортировать
  `useForm` / `Form` / `FormProvider` раздельно и при этом с общим контекстом, решается прототипом
  на этапе плана и замером в `tree-shaking.test.ts`.
- `apps/docs/test/tree-shaking.test.ts` получает кейсы формы: форма из одного поля не тянет
  календарь, combobox и схемный рендерер; `{ Form }` из корня кита не тянет `SchemaForm`.
- Готовая сборка в корне кита остаётся — прецедент `DataGrid`. Привязка живёт в собственном модуле
  кита, никогда в `index.ts`.

### D2. Две фабрики с одним набором опций

```ts
createForm(options) // → { useForm, Form, FormProvider, withForm, withFieldGroup }
createSchemaForm(options) // → то же самое плюс SchemaForm
```

- `createSchemaForm` вызывает `createForm` с теми же опциями и добавляет `SchemaForm`. Регистрация
  полей по-прежнему происходит ровно один раз, поэтому `form.RatingField` в JSX и
  `{ type: 'rating' }` в документе не могут разойтись (инвариант спеки 008).
- `createForm` не ссылается на модуль схемы, поэтому JSX-приложение за него не платит.
- Два независимых набора по-прежнему возможны — двумя вызовами фабрик.

### D3. `FormRenderer` становится `SchemaForm`

Это `Form`, у которого дети берутся из документа: те же контролируемый и неконтролируемый режимы,
те же пропсы элемента, плюс `schema`, `translate`, `rules`, `keepHiddenValues` (изменения документа и пропса `blocks` — спека 010, §5). Имя
образует пару с `Form` и с `createSchemaForm` и совпадает с `schema` / `FormSchema` /
`defineFormSchema`. `JsonForm` отклонён: схему можно писать на TypeScript, а «JSON Forms» — это
существующая библиотека на JSON Schema, которой наш формат не является. Типы пропсов
переименовываются следом: `FormRendererControlledProps` → `SchemaFormControlledProps` и так далее.

~261 вхождение в 67 файлах, замена механическая.

### D4. Опции: всё необязательное, `form.X` типизирован по переданному

```ts
createForm({
	FormElement?,   // вид <form> из кита; без него — голый <form>
	fields?,        // поля, привязанные к значению, открытый реестр
	components?,    // открытый набор компонентов, знающих о форме
})
```

- **Два уровня, два правила.** Кит реализует контракт: типы пропсов каждого слота, проверка через
  `satisfies` (проверка лишних свойств по-прежнему ловит опечатку). Приложение собирает: любой
  поднабор, и `form.X` есть в типах только для переданного. Обязательного нет ни на одном уровне,
  так что новый слот после 1.0 — аддитивное изменение. Правило «необязательный уровень для слотов
  после 1.0» становится не нужно.
- **`fields`** — виды, привязанные к значению. Встроенные ключи получают свои bespoke-биндеры по
  имени; любой другой ключ получает generic-биндер и выводит id для документа
  (`RatingField` → `rating`). **`ArrayField` переезжает сюда**: он привязан к значению-массиву, и
  `name` сужается до путей массивов. `ArrayItem` идёт вместе с ним (как именно кит передаёт оба,
  решается в плане; кандидат — `/* @__PURE__ */ Object.assign(ArrayFieldView, { Item })`).
- **`components`** — открытый набор. Каждый ключ становится `form.<Ключ>` с типами пропсов этого
  компонента. Форму компонент получает из контекста (D6), поэтому это один и тот же компонент —
  используется ли он как `form.SaveBar` или рендерится напрямую как `<SaveBar />`.
- **`Section`, `GridItem`, `SubmitButton`** — обычные компоненты кита в `components`. В JSX они
  сейчас только пробрасывают пропсы (`createSection` / `createGridItem`), так что ничего не теряется.
- **Слот `Button` убирается.** Раньше из него собирался `form.SubmitButton`. Теперь кит поставляет
  готовый `SubmitButton`, написанный на `form.Submit` (D5). Побочный эффект: уходит и
  `ArrayScope.Button`, своя вёрстка массива берёт свои кнопки.
- **`Wizard`** кита — обычный компонент: в `components` для JSX (вёрстка поверх `form.Steps`,
  D18); схемный рендерер берёт его из `components` под этим именем, как сегодня (§5).
- **Запрещённые ключи.** Ключ, совпадающий с API инстанса (`Subscribe`, `state`, `reset`,
  `handleSubmit`, …, плюс наши `Field`, `NativeField`, `Array`, `Submit`, `Steps`, `Step`) или совпадающий между `fields` и `components`, —
  ошибка типов и dev-ошибка с именем ключа. Список выводится из типа инстанса TanStack, а не
  пишется руками, чтобы не устаревать при обновлении TanStack.
- **Guard'ы упрощаются.** Раз обязательного нет, предупреждения «забыт слот» уходят из
  `createForm`; рантайм-проверка остаётся только в схемном пути (документ использует слот, который
  никто не передал).
- `formFieldSlots` / `formComponents` переименовываются в **`allFormFields` / `allFormComponents`**:
  импорт такого набора — осознанное «всё», как `allDataGridFeatures`.

### D5. Встроенные примитивы на каждом инстансе

- **`form.Array`** — headless-примитив без изменений (спека 007).
- **`form.Submit`** — headless, render-prop: `{ canSubmit, isSubmitting, isDirty, formErrors, submit }`, где
  `submit` — это `form.handleSubmit`, `formErrors` — по D14, `isDirty` — по D17. Заменяет `form.SubmitButton` в роли примитива. Раз он отдаёт `submit`,
  кнопка на нём работает и вне `<form>`.
- Отдельной headless-_кнопки_ сабмита нет: `form.Submit` уже и есть эта точка расширения.
- **`form.Field` — наша привязка своего контрола**, без регистрации вида поля: render-prop с теми же
  пропсами, что получает поле из `defineFieldType` (`id`, `value`, `onChange` со значением,
  `onBlur`, `errors` — уже отфильтрованные правилом показа, `invalid`, `aria-*`, `data-field`, …) и
  с `validators` как у любого поля. Идёт через тот же биндер, что `form.TextField`, поэтому такое
  поле видят фокус на ошибке (D13), регистрация в шаге (D18) и снятие ошибок сервера при правке
  (D14). Подпись и вывод ошибки — на авторе; нужен один и тот же контрол в нескольких местах —
  `defineFieldType`. Аналог `Controller` / `useController` из react-hook-form; имя — как у Formik,
  Final Form и TanStack, потому что для частого пользователя библиотеки это основной путь.
- **`form.NativeField` — сырой `form.Field` TanStack** (`FieldApi` в render-prop) под новым именем.
  Нужен редко: мета, `pushValue` и прочее, чего наши пропсы не дают. Префикс говорит, что это
  уровень ниже: фокус на ошибке, регистрация в шаге и правило показа ошибок его не видят. Пример из
  документации TanStack, вставленный в `form.Field`, не компилируется (`field.state.value` в наших
  пропсах нет) — ошибка явная, не тихая. Переименование одинаковое везде: `group.Field` /
  `group.NativeField` в `withFieldGroup` и `form.FormGroup`, то же в записи массива. `form.AppField`
  TanStack не документируется: его место занимает `defineFieldType`.
- **`form.Steps` / `form.Step`** — headless-поток шагов (D18).

### D6. Контекст формы

- `<Form>` ставит контекст формы. **`FormProvider`** ставит его, не рендеря `<form>`: когда `<form>`
  ниже по дереву (`<Form form={form}>` в теле диалога) или его нет вовсе (строка таблицы).
- **`useFormContext` экспортирует пакет, а не сборка**, и возвращает **базовый** API (`Submit`,
  `Array`, `Subscribe`, `Field`, `NativeField`, `state`, `handleSubmit`, …) без зарегистрированных полей сборки.
  Хук из сборки создал бы цикл: `form.ts` импортирует `SaveBar`, чтобы зарегистрировать его, а
  `SaveBar` импортирует хук из `form.ts`, и TypeScript не может вывести тип ни того, ни другого
  (TS7022).
- **`useFormContext<TValues>()` — опциональный дженерик**, как `useFormContext<FormValues>()` в RHF.
  Он типизирует значения и базовый API (`state`, `Subscribe`, `Field`, `NativeField`, `FormGroup`,
  `Submit`, `setFieldValue`), а поля кита — только по `name` (`DeepKeys<TValues>`), без проверки,
  что такое поле зарегистрировано в сборке: набор полей задаёт `createForm` приложения, и второй
  дженерик под него вернул бы тот же цикл. Это **приведение типа, а не проверка**: окажись компонент
  в другой форме, TypeScript промолчит. Без дженерика — `unknown`, как раньше.
- Компонент, который называет пути в данных, — это кусок одной формы или переиспользуемый блок:
  для него `withForm` или `withFieldGroup`, которые проверяются в месте вставки. Дженерик хука —
  приём для мелочей вроде подсказки рядом с полем, и доки так его и подают.
- Это пересматривает решение спеки 007 «контекста формы нет». 007 отвергла контекст как способ
  добраться до полей из переиспользуемого списка; здесь поля по-прежнему приходят через замыкание и
  остаются строго типизированными, а контекст обслуживает только компоненты, не зависящие от
  конкретной формы, — случай, который 007 не рассматривала.

### D7. Хелперы композиции

- **`withForm`** — кусок одной формы, типизированный по всей её форме данных. `form` становится
  **необязательным** пропсом: передан — проверяется типами в месте вызова; не передан — берётся из
  контекста; нет ни того, ни другого — dev-ошибка.
- **`withFieldGroup`** — переиспользуемый блок, типизированный по своей форме данных (`Address`) и
  накладываемый на любую форму через `fields='shipping'` или карту полей. **Получает плоские
  поля**: `group.TextField name='street'` — тот же механизм относительного пути, что уже работает у
  `item.TextField` внутри записи массива. Без этого блок пишется на нативном TanStack, и хелпер на
  практике непригоден.
- **`withFieldGroup` получает `validators`** — схему в координатах блока, одну на весь объект. У
  `withFieldGroup` TanStack валидаторов нет; без них правило на весь блок («CVC подходит к карте»)
  пришлось бы вешать в каждом месте вставки.

  ```tsx
  export const CardFields = withFieldGroup({
  	defaultValues: { card: '', cvc: '' },
  	validators: { onChange: cardSchema }, // card, cvc — как у полей ниже
  	render: ({ group }) => (
  		<>
  			<group.TextField name='card' />
  			<group.TextField name='cvc' />
  		</>
  	),
  })

  <CardFields fields='payment' />                                  // → payment.card, payment.cvc
  <CardFields fields={{ card: 'billingCard', cvc: 'billingCvc' }} /> // → billingCard, billingCvc
  ```

  Ошибка с путём уходит в поле через реальный путь (префикс или карта полей). Ошибка без пути
  (refine на весь объект) — ошибка группы: блок получает её как `group.errors`, и в шаге тоже — в
  `stepErrors` она не дублируется (D18). Под капотом строковый `fields` — нативный `FormGroup` TanStack на этой
  ветке; карта полей — своя логика: объект собирается из полей по карте, проверяется схемой, ошибки
  раскладываются обратно по той же карте.

- **`withFieldGroup` получает свой сабмит**: `group.handleSubmit()` внутри блока и пропс
  `onGroupSubmit` в месте вставки, `value` типизирован по блоку. Секция, у которой кнопка
  «сохранить эту секцию» нужна везде, держит кнопку в себе, а страница решает только, куда её
  положить и что делать при сабмите:

  ```tsx
  <SecuritySection
  	fields='security'
  	onGroupSubmit={({ value }) => api.changePassword(value)}
  />
  ```

  `handleSubmit` проверяет только блок (его `validators` и поля) и зовёт `onGroupSubmit`, вся форма
  не отправляется. Со строковым `fields` это сабмит нативного `FormGroup`, с картой полей — своя
  логика поверх той же сборки значения. Нужна кнопка только на отдельных страницах — блок без кнопки,
  а страница оборачивает его в `form.FormGroup`.

- **`form.FormGroup` получает плоские поля** — `group.X` с путём относительно `name`, как у
  `withFieldGroup`. Тогда схема группы (TanStack отдаёт ей `values[name]` и ждёт относительные
  ключи) и имена полей записаны в одних координатах:

  ```tsx
  <form.FormGroup
  	name='payment'
  	validators={{ onChange: cardSchema }}
  >
  	{(group) => <group.TextField name='card' />}
  </form.FormGroup>
  ```

- **Координаты выбираются объектом, через который вызвано поле, а не деревом.** `form.X` — путь
  от корня, и схемы рядом с ним (форма, шаг) тоже от корня. `group.X` — путь относительно ветки
  (`form.FormGroup`, `withFieldGroup`), и схема группы относительная. Неявного префикса от предков
  нет: `form.TextField` создаётся один раз на форму и не может статически знать, что окажется над
  ним в дереве, — `name` стал бы `string`, а перенос компонента молча менял бы, куда пишутся данные.
  `form.TextField name='payment.card'` внутри `form.FormGroup name='payment'` работает, но в доках
  это антипример.
- **Где ставить правило (модель M2, change `form-schema-source-of-truth`).** Источник правды о
  данных — схема формы: сабмит всей формы запускает валидаторы формы и ни одной группы. Схема
  собирается из схем блоков, которые экспортируются как обычные константы. Группы (`validators`
  `withFieldGroup`, `form.FormGroup`) дают раннюю обратную связь и проверяют свой сабмит; ошибка,
  которую смонтированная группа уже показала, блокирует сабмит формы, а размонтированная группа
  уносит свои ошибки. Часть, которая есть не всегда (billing по галочке, шаг с `when`), — ветка схемы
  формы: `z.discriminatedUnion` по флагу или условный `superRefine`. Схема формы подключается на
  `onDynamic` с `validationLogic: revalidateLogic()` (оба кита экспортируют); `onSubmit` — для форм без
  условных частей. Одно правило на двух уровнях даёт одно сообщение: киты убирают повторы по тексту.
- `useFieldGroup` / `useFormGroup` реэкспортируются как раньше (они документированы в
  `composition.mdx`).
- Роли для доков: `withFieldGroup` переиспользует набор полей между формами; `withForm` разрезает
  одну форму на файлы и видит её целиком (шаг читает шаг 1); `form.FormGroup` — граница валидации и
  сабмита ветки внутри одной формы; `form.Step` — что на экране и что проверить перед «Далее» (D18).

### D8. Один публичный тип инстанса

`FormInstance<TValues, TFields, TComponents>` заменяет в публичной поверхности `KitFormApi`,
`BoundForm`, `RendererForm` и `BoundFieldApi`. Двенадцать дженериков валидаторов TanStack получают
значения по умолчанию; полная форма остаётся внутренней — она нужна `useForm` для вывода типов.
`BindableForm` / `SubmittableForm` остаются внутренними.

### D9. Граф пакетов

```
кит (heroui / shadcn)
  └─ @ez-kit/form-react              единственный пакет, от которого зависит кит
       ├─ @tanstack/react-form        dependency (не peer): версию выбираем мы
       ├─ @tanstack/form-core         dependency
       └─ @ez-kit/form-core           dependency
            └─ @tanstack/form-core    peer → удовлетворяется копией form-react
```

- `form-core` берёт из TanStack только типы; киты TanStack не импортируют вовсе. Значит, от TanStack
  зависит ровно один пакет, и копия одна.
- Киты убирают TanStack из peer и `@ez-kit/form-core` из dependencies; API `form-core` они
  реэкспортируют через `form-react`.
- Обновление TanStack — это релиз `form-react`. Киты зависят от `form-react` через `workspace:*`
  (после публикации — точная версия) при `updateInternalDependencies: "patch"`, поэтому каждый
  релиз `form-react` выпускает патч каждого кита, привязанный к нему, после того как CI прогнал кит
  на новой версии.
- `form-core` реэкспортирует только те типы TanStack, которые нужны его публичным сигнатурам. Мы —
  надстройка над TanStack: мажор TanStack — это наш мажор, и типы прямо это говорят, а не делают
  вид, что зависимость изолирована.
- Из доков установки уходит абзац «TanStack — peer dependency».

### D10. `form-core` — движок, не зависящий от фреймворка, и он публичный

Долгосрочная цель — сменить рендер (`form-vue`), поменяв адаптер, а не движок. Поэтому **сабпути
`internals` нет**: всё, что не зависит от фреймворка, — публичный API `form-core` с двумя
аудиториями. Приложения и бэкенд: формат документа, `parseFormSchema`, `buildValidator`,
`stripHiddenValues`, ошибки, словари. Авторы адаптеров: пути, обход дерева, `runFieldValidate`,
`compileCondition`, резолверы. Всё публичное замораживается на 1.0, поэтому каждый экспорт
осознанный; что не готово, остаётся неэкспортированным внутри модуля.

Правило для `AGENTS.md`: **логика, не зависящая от фреймворка, живёт в `form-core`; адаптер — только
привязка к своему фреймворку.** Вынос логики, которая уже нарушает правило, — отдельная спека из
§6.

### D11. Имена источников опций

- `OptionsSource` (ссылка документа, пишется под `optionsFrom`) → **`OptionSourceRef`**.
- В `form-core` по D10 переезжает только то, что не зависит от фреймворка: `OptionSourceRef`, форма
  входа `OptionSourceInput` (`params`, `query`, `values`) и форма результата `OptionSourceResult`
  (`options`, `loading`).
- Сам `OptionSource` (`SimpleOptionSource`, `SearchableOptionSource` с `useOptions` /
  `useSelectedOptions`) и `OptionSourceRegistry` **остаются в `form-react`**: это хуки React, внутри
  них живут `useQuery` и прочие хуки. У будущего `form-vue` будут свои composable-функции с теми же
  входом и результатом.

### D12. Паритет китов проверяется тестом

`apps/docs/test/kit-exports-parity.test.ts` строит `ts.Program` по собранным `.d.ts` обоих китов и
сравнивает все экспорты — и значения, и типы (найденное расхождение было именно в типах:
`ArrayFieldScope`, `ArrayItemScope`, `ArrayNode`). Законные различия перечислены с причиной.

### D13. Фокус на первой ошибке

- Включён по умолчанию, отключается опцией формы `focusOnError: false`.
- «Первое» определяется от состояния формы, а не от `aria-invalid`: после неудачного сабмита
  обходятся обёртки полей `[data-field]` в порядке DOM, берётся первое поле с ошибкой и фокусируется
  элемент с его `id` (тот же, на который указывает `label htmlFor`), иначе — первый фокусируемый
  элемент внутри обёртки. Так поиск не зависит от того, верно ли кит расставил ARIA (аудит нашёл
  `aria-invalid` на корне у radio group и slider в shadcn).
- Без `<form>` (`FormProvider`) поиск идёт по всему документу, но только по обёрткам этой формы —
  обёртка получает идентификатор формы (например, `data-form-id`).
- Пользовательский `onSubmitInvalid` вызывается после фокуса.
- Автоперехода на шаг с ошибкой нет (D18): фокус уходит на первую ошибку текущего шага.
- Поле в свёрнутом блоке или неактивной вкладке — ответственность вёрстки, описывается в доках.

### D14. Ошибки с сервера

- **Декларативный вход** — опция `useForm` и пропс `<Form>` / `<SchemaForm>`:
  `serverErrors: { fields?, form? }`. `fields` — пути формы (типизированы как `name`) → строка или
  массив строк; `form` — строка или массив строк.
- **Императивный вход** — `form.setServerErrors({ fields, form })`, тот же механизм.
- **Семантика:** ошибки применяются при смене значения `serverErrors` (по ссылке); ошибка поля
  снимается при первом изменении этого поля и не возвращается до нового значения `serverErrors`;
  все серверные ошибки сбрасываются при следующем сабмите; после применения срабатывает фокус по
  D13.
- **Хранение** — родной слот TanStack `errorMap.onServer`, так что киты выводят эти ошибки без
  изменений.
- **Общая ошибка формы** отдаётся в render-prop `form.Submit` как `formErrors: string[]` (всегда
  массив); туда же позже ляжет ошибка валидатора уровня формы.
- Имя `serverErrors`, а не `errors`: в форме уже есть `errors` (все ошибки, включая валидацию), а у
  этих — своя семантика снятия. Сравнение с другими библиотеками: RHF — `useForm({ errors })` с
  пометкой «server errors» в доках и `setError('root.serverError')`; Conform — `lastResult` с
  `fieldErrors` / `formErrors`; Final Form — `submitErrors` / `FORM_ERROR` / `dirtySinceLastSubmit`;
  TanStack — слот `onServer`.

### D15. Server actions и SSR — без нового API

- **Без JavaScript форма не работает**, и это явно записано в доках: поля китов — контролируемые
  компоненты, а массивы, условия и визард живут в JS.
- **Server action** — обычный `onSubmit`, вызывающий action через `startTransition`, плюс
  `serverErrors` из `useActionState`. `isSubmitting` гаснет раньше конца action, поэтому кнопке
  нужен `isPending` из хука — это показывает рецепт.
- **Валидация на сервере** — `form-core` без React (`buildValidator`, `stripHiddenValues`,
  `parseFormSchema`) или общая standard-schema.
- Новая страница доков «Server actions», живой пример в docs-приложении с настоящим action, e2e на
  отсутствие ошибок гидрации у формы, отрендеренной на сервере (`id` полей в `SchemaForm` — главный
  кандидат на расхождение).

### D16. Debounce и минимальная длина запроса у источников с поиском

- Между полем и источником — прослойка: кит получает введённый текст сразу, источник получает
  `query` с задержкой и только при достаточной длине.
- **Настраивается на источнике**, потому что это свойство бэкенда за ним:
  `{ useOptions, useSelectedOptions, debounce, minLength }`. Переопределение на поле —
  `searchable={{ debounce?, minLength? }}` (scalar-or-object), в схеме — то же в узле.
- **По умолчанию:** удалённый источник — `debounce: 300`, `minLength: 0` (пустой запрос остаётся
  валидным: первая страница, популярное); список в памяти — без задержки.
- **Контракт кита** аддитивно получает в `search` поля `minLength` и `belowMinLength`, чтобы кит
  показал подсказку вместо пустого списка.
- Снимаются оговорки «for now» в `contract.ts` и `options/source-types.ts`.

### D17. Dirty-состояние и reset

- `form.Submit` получает `isDirty` рядом с `canSubmit`, `isSubmitting`, `formErrors`. Готовый
  `SubmitButton` кита по `isDirty` сам **не** блокируется: форма создания должна отправляться и без
  правок — это решение приложения.
- Без нового API, рецептами в доках: `formApi.reset(value)` после успешного сохранения;
  асинхронные `defaultValues` (TanStack сам подхватывает новые значения, пока форма не тронута —
  `FormApi.update`, условие `!state.isTouched`); предупреждение об уходе со страницы через
  `beforeunload` + `isDirty`.
- Dirty на уровне поля в контракт кита не добавляется: ни один кит не рисует изменённое поле иначе.
- Общий хук защиты навигации не делается: у каждого роутера своя навигация.

### D18. Шаги в JSX: `form.Steps` и `form.Step`

Пошаговый поток нужен и без документа, поэтому он становится headless-примитивом инстанса, как
`form.Array`. Схемный визард и `Wizard` кита строятся поверх него.

**Анатомия.** `form.Steps` — только провайдер: его `children` — обычные узлы, без render-prop на
корне. Состояние шагов лежит во внешнем сторе, значение контекста стабильно, и каждый кусок
подписывается селектором только на свой срез.

```tsx
<form.Steps
	initial='account'
	onStepChange={(name) => track(name)}
>
	<form.Steps.List>
		{({ steps, current, goTo }) => (
			<MyStepper
				items={steps.map((step) => ({ ...step, label: t(`signup.steps.${step.name}`) }))}
				current={current}
				onSelect={goTo}
			/>
		)}
	</form.Steps.List>

	<form.Step name='account'>
		<form.TextField name='email' />
		<ProfileFields /> {/* withForm / withFieldGroup / form.ArrayField — тоже регистрируются */}
	</form.Step>

	<form.Step
		name='company'
		when={(v) => v.type === 'company'}
	>
		<form.TextField name='company.inn' />
	</form.Step>

	<form.Step
		name='payment'
		validators={{ onSubmit: termsSchema }} // от корня; только на «Далее», не на сабмите формы
	>
		<CardFields fields='payment' /> {/* свои validators, относительные */}
		<form.CheckboxField name='agree' /> {/* от корня */}
	</form.Step>

	<form.Steps.Controls>
		{({ canGoBack, isLast, isValidating, goBack, goNext }) => (
			<footer>
				{canGoBack && (
					<button
						type='button'
						onClick={goBack}
					>
						Назад
					</button>
				)}
				{isLast ? (
					<form.SubmitButton>Готово</form.SubmitButton>
				) : (
					<button
						type='button'
						onClick={goNext}
						disabled={isValidating}
					>
						Далее
					</button>
				)}
			</footer>
		)}
	</form.Steps.Controls>
</form.Steps>
```

| Часть                                                 | Подписан на                                                       | Отдаёт                                         |
| ----------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| `form.Step`                                           | «я активен» (при переходе перерисовываются два шага)              | рендерит детей только активного шага           |
| `form.Steps.List`                                     | список шагов, `current`                                           | `steps[i]: { name, invalid, visited }`, `goTo` |
| `form.Steps.Item` / `useStep(name)`                   | срез одного шага                                                  | `isCurrent`, `invalid`, `visited`, `goTo()`    |
| `form.Steps.Controls`                                 | `canGoBack`, `isLast`, `isValidating`, `stepErrors`, `formErrors` | `goBack`, `goNext`                             |
| `form.Steps.Subscribe` / `useSteps(selector, equal?)` | то, что выбрал селектор (обязателен)                              | любой срез стора шагов                         |

**Имена частей.** `List`, а не `Nav`: часть ничего не рендерит, `<nav>` в имени обещал бы элемент,
которого нет; `List` — общее имя такой части (`Steps.List` в Ark UI и Chakra, `Tabs.List` в Radix).
`Controls` — одна часть на обе кнопки, потому что им нужен общий `isLast`; делить её на
`PrevTrigger` / `NextTrigger`, как в Ark, незачем.

**Точечный рендер степпера.** `Steps.List` отдаёт весь массив, поэтому смена `current`, `visited` или
`invalid` у одного шага перерисовывает весь список. При 3–7 шагах это дёшево и остаётся путём по
умолчанию. Кому нужен точечный рендер, собирает степпер из `Steps.Item`:

```tsx
const names = useSteps((s) => s.names)

{names.map((name) => (
	<form.Steps.Item key={name} name={name}>
		{({ isCurrent, invalid, visited, goTo }) => <Dot … />}
	</form.Steps.Item>
))}
```

`Steps.Item` и `useStep(name)` подписаны на срез своего шага: смена текущего перерисовывает два
элемента, старый и новый. `names` — стабильная ссылка в сторе, пересоздаётся только когда меняется
набор шагов (регистрация или `when`), поэтому селектор `(s) => s.names` не ререндерит на каждое
обновление.

**Правило селекторов.** Сравнение по умолчанию — `Object.is`. Селектор, который собирает новый объект
или массив (`(s) => ({ a: s.a, b: s.b })`, `s.steps.map(…)`), ререндерит на каждое изменение стора;
для составных срезов — второй аргумент, `useSteps(selector, shallow)`, или отдельные вызовы на каждое
значение. Это сказано в доках `useSteps` и `Steps.Subscribe`.

**Список шагов без массива.** `form.Step` смонтирован всегда, прячется только его содержимое; он
регистрируется в `useLayoutEffect`, а эти эффекты у соседей идут в порядке дерева, поэтому порядок
шагов — порядок в JSX. Условный шаг — `when={(values) => …}`: шаг
остаётся на своём месте и пропускается. `{cond && <form.Step/>}` не поддерживается — такой шаг при
появлении встаёт в конец; это сказано в доках. Текущий шаг хранится по `name`. До регистрации список
пуст: на клиенте это не видно (layout-эффект до отрисовки), а для SSR есть `initial` — с ним
активный шаг рендерится уже на сервере. Контролируемый режим `step` / `onStepChange` — для
синхронизации с URL.

**Подписи — у степпера, не у шага.** `form.Step` — логика: что на экране и что проверить перед
«Далее». Подпись нужна только тому, кто рисует степпер, поэтому `Steps.List` отдаёт `name`, а
подпись степпер берёт сам — из словаря или функции перевода по `name`. `Wizard` кита в JSX
получает их пропсом `labels={{ account: 'Аккаунт' }}`. В схемном визарде подпись остаётся в `title`
узла: рендерер переводит её и отдаёт `Wizard` сам.

**Поля и группы шага — по монтированию.** `form.Step` даёт контекст регистрации; биндеры наших
полей (`form.X`, `group.X`, поля записи `form.ArrayField`) регистрируют полное имя в эффекте и
снимают при размонтировании, `form.FormGroup` и `withFieldGroup` с `validators` регистрируются как
группы. Шаг запоминает свой последний список, поэтому знает свои поля и тогда, когда неактивен.
`form.NativeField` не регистрируется — внутри шага пишут `form.X` или `form.Field`.

**`name`, и никакого `path`.** `name` — идентификатор шага для навигации (`goTo('payment')`, ключ в
степпере, `onStepChange`, URL); в значения формы не попадает. Ветки данных шаг не задаёт: имена
полей и объект формы от шагов не зависят, объект один и совпадает с DTO. Валидаторы шага
(`onChange` / `onBlur` / `onSubmit` и `Async`, как у TanStack) получают **всю форму** и пишутся от
корня, как поля `form.X` рядом: `z.object({ payment: cardSchema, agree: z.literal(true) })` — путь в
ошибке zod совпадает с `name` поля символ в символ. Ветка со своей относительной схемой — это
`form.FormGroup` или `withFieldGroup` внутри шага (D7). `path` был отклонён: поля писались от корня
(`payment.card`), а схема шага — от ветки (`card`), и на одном шаге жили две системы координат.

| Что                                  | Где                                                   | В `onSubmit` |
| ------------------------------------ | ----------------------------------------------------- | ------------ |
| значения полей                       | `form.state.values` — только DTO                      | да           |
| `touched` и ошибки полей             | мета полей TanStack, как обычно                       | нет          |
| ошибки валидаторов шага и групп      | мета полей по полным путям; без пути — группа или шаг | нет          |
| `current`, `visited`, шаги и их поля | отдельный стор `form.Steps`                           | нет          |
| `steps[i].invalid`                   | не хранится — селектор по ошибкам полей шага          | —            |

Состояние шагов в значения формы не кладётся: иначе оно попало бы в DTO, `isDirty` и `reset`.

**Навигация и порядок проверки.** По «Далее»:

1. Шаг берёт зарегистрированное: поля (полные пути) и группы (`withFieldGroup` с `validators`,
   `form.FormGroup`).
2. Синхронные валидаторы — все сразу и со всеми триггерами, как при сабмите: поля, группы (по
   своим относительным значениям), шаг и форма (по всей форме).
3. Асинхронные (`onSubmitAsync` шага, `onBlurAsync` поля, …) — только если синхронные прошли,
   чтобы не ходить на сервер с заведомо плохими данными.
4. Вердикт — только по ошибкам в зарегистрированных полях плюс ошибкам без пути у групп и шага
   (`stepErrors`). Ошибки, которые схема формы записала в поля следующих шагов, переход не
   блокируют и не показываются; ошибки валидатора шага в незарегистрированных полях
   отбрасываются. Это поведение сегодняшнего схемного визарда, перенесённое как есть.
5. Не прошло — поля шага помечаются тронутыми, фокус уходит на первую ошибку в порядке DOM (D13),
   `stepErrors` видны над кнопками, шаг становится посещённым и подсвечивается в `List`.

`steps[i].invalid` загорается только у посещённых шагов (шаг становится посещённым, когда с него
пытаются уйти), иначе форменная схема красила бы шаги, до которых пользователь ещё не дошёл.
`goBack` — без проверки. `goTo(name)` назад — свободно. Вперёд — по пропу `linear` у `form.Steps`
(по умолчанию `true`): сначала проверяется текущий шаг, как в `goNext`, и цель достижима, только если
каждый шаг между ними **прошёл** последнюю проверку (`passed`, отдельно от `visited` — «пытался уйти»)
и сейчас не содержит ошибок в своих полях. При `linear={false}` `goTo` переходит куда угодно без
проверки, а `goNext` по-прежнему проверяет шаг и не пускает с ошибками. Если текущий шаг перестаёт
подходить по `when`, текущим становится ближайший подходящий шаг перед ним, а без такого — первый.
Пропущенные по `when` шаги навигация обходит. Значения переживают размонтирование шага.

**Финальный сабмит.** Схема формы проверяет всё, и это единственный барьер (M2): группы — ни
активного, ни неактивных шагов — сабмит формы не запускает, поэтому правила блоков внутри шагов
должны быть и в схеме формы. Ошибка схемы на поле несмонтированного шага блокирует сабмит и видна,
когда шаг откроют: после попытки сабмита поле показывает ошибки без `touched`. Запускать ли на
финальном сабмите валидаторы самих `form.Step` тоже не запускаются: они — ранняя обратная связь на
«Далее», а правило, которое держит отправку (в том числе серверная проверка вроде `verifyCard`), живёт в
схеме формы или её `onSubmitAsync`. Ошибка на другом шаге — без автоперехода, пользователь сам решает, куда идти: шаг краснеет
в `List`, вернувшийся пользователь видит ошибки, потому что после попытки сабмита они показываются
независимо от `touched` — это правило показа для всех полей, а не только в шагах, иначе поля несмонтированного шага не получают пометку «тронуто».

**Ловушка пропущенных шагов.** Схема формы видит и данные шагов, пропущенных по `when`
(`company.inn` у физлица), и такая ошибка заблокирует сабмит. Это решается в схеме приложения —
`z.discriminatedUnion('type', […])` или условный `superRefine`; библиотека не угадает, что при каком
`type` обязательно. Рецепт — в доках.

**Дубли сообщений.** Группы и шаг — `onChange` / `onBlur` / `onSubmitAsync`, схема формы —
`onDynamic` с `revalidateLogic()`. Одно правило в обоих слоях показывается один раз: киты убирают
повторы по тексту. Одну схему не ставят на `onSubmit` и `onDynamic` сразу.

**Ошибки, не привязанные к полю.** Ошибка без пути до поля иначе не показал бы никто, а «Далее» она
блокирует. `Steps.Controls` отдаёт два списка: `stepErrors` — ошибки без пути у валидатора самого
текущего шага, и `formErrors` — ошибки без пути у валидаторов формы, как их отдаёт `form.Submit`.
Ошибки групп без пути в `stepErrors` не попадают: их показывает сама группа (`group.errors`), иначе
сообщение было бы дважды.

**Пропущенные шаги и DTO.** Значения шагов, пропущенных по `when`, остаются в объекте — как у
TanStack, где размонтированное поле значения не теряет; переключение туда-обратно сохраняет ввод.
Чистый DTO — выход схемы формы: `onSubmit={({ value }) => api.send(schema.parse(value))}`, где ветка
union для пропущенного случая не объявляет часть шага или отбрасывает её `.transform(() => undefined)`.
TanStack отдаёт в `onSubmit` сырое значение, поэтому `parse` пишется явно. Отдельной утилиты для
этого нет.

**Связь с остальным.** `withForm` выносит шаг в файл и видит всю форму; `withFieldGroup` —
переиспользуемый блок со своими правилами внутри шага; `form.FormGroup` — ветка со своей схемой
внутри шага или вне шагов, например для «сохранить секцию». `Wizard` кита — готовая вёрстка поверх
`Steps.List` и `Steps.Controls`, кладётся в `components`. Схемный визард (§5) переписывается на этот
же стор; у узла `step` в документе имени нет, рендерер именует шаги индексом, а свойство `path`
узла удаляется (сегодня оно только монтирует `FormGroup` без валидаторов и видимого эффекта не
даёт).

### Отклонено: dev-предупреждение для невыведенных ошибок `form.Array`

Предложение из спеки 007 (геттеры на `errors` / `invalid` в scope, предупреждение после попытки
сабмита) отклонено. `form.Array` — headless-примитив, и вывод ошибок — ответственность того, кто
собирает вёрстку на нём; готовый `form.ArrayField` кита выводит их сам. Лишняя сложность ради чужой
ошибки вёрстки не оправдана. Достаточно существующего предупреждения в `arrays/index.mdx`.

// Только то, что нужно проекту — src/shared/form.ts

import { createForm, FormElement, TextField, SelectField, ArrayField, SubmitButton, Section } from '@ez-kit/form-heroui'

export const { useForm, Form } = createForm({

### Сценарии

Минимальный JSX на каждый случай. Сборка — `src/shared/form.ts` из примера выше.

#### 1. Базовая форма: логин, пароль, подтверждение

```tsx
const loginSchema = z
	.object({
		login: z.string().min(3, 'Минимум 3 символа'),
		password: z.string().min(8, 'Минимум 8 символов'),
		confirm: z.string(),
	})
	.refine((v) => v.password === v.confirm, { path: ['confirm'], message: 'Пароли не совпадают' })

export function SignUpForm({ onSuccess }: { onSuccess: () => void }) {
	const signUp = useMutation({ mutationFn: api.signUp, onSuccess })

	return (
		<Form
			defaultValues={{ login: '', password: '', confirm: '' }}
			validators={{ onChange: loginSchema }} // ошибки zod ложатся в поля по path
			onSubmit={({ value }) => signUp.mutateAsync(value)}
			serverErrors={signUp.error?.body} // { fields: { login: 'Занят' } } — D14
		>
			{(form) => (
				<>
					<form.TextField
						name='login'
						label='Логин'
					/>
					<form.TextField
						name='password'
						label='Пароль'
						type='password'
					/>
					<form.TextField
						name='confirm'
						label='Повторите пароль'
						type='password'
					/>
					<form.SubmitButton>Зарегистрироваться</form.SubmitButton>
				</>
			)}
		</Form>
	)
}
```

Вся форма целиком переиспользуется как обычный React-компонент (`<SignUpForm onSuccess={…} />` и
на странице, и в модалке) — для этого хелперы не нужны. Они нужны, когда переиспользуется **часть**.

#### 2. Переиспользование части формы

| Нужно                                                         | Что брать        |
| ------------------------------------------------------------- | ---------------- |
| разрезать **одну** большую форму на файлы, кусок видит её всю | `withForm`       |
| один набор полей в **разных** формах, со своими правилами     | `withFieldGroup` |
| ветка **внутри** формы со своей проверкой и своим «Сохранить» | `form.FormGroup` |

**`withForm`** — кусок конкретной формы. Своих правил нет: валидацию даёт схема формы, кусок только
рисует поля и может читать любые значения формы.

```tsx
export const CredentialsPart = withForm({
	defaultValues: SIGN_UP_DEFAULTS, // тип всей формы
	render: ({ form }) => ( // form из контекста — D7
		<>
			<form.TextField name='password' type='password' />
			<form.TextField name='confirm' type='password' />
			<form.Subscribe selector={(s) => s.values.login}>{(login) => <p>Для {login}</p>}</form.Subscribe>
		</>
	),
})

<CredentialsPart /> // внутри <Form>, правила — из loginSchema
```

**`withFieldGroup`** — блок, который живёт в разных формах и проверяет себя сам. Имена и схема — в
координатах блока; куда он лёг, решает место вставки.

```tsx
const passwordPairSchema = z
	.object({ password: z.string().min(8), confirm: z.string() })
	.refine((v) => v.password === v.confirm, { path: ['confirm'], message: 'Пароли не совпадают' })

export const PasswordPair = withFieldGroup({
	defaultValues: { password: '', confirm: '' },
	validators: { onChange: passwordPairSchema }, // D7
	render: ({ group }) => (
		<>
			<group.TextField name='password' type='password' label='Пароль' />
			<group.TextField name='confirm' type='password' label='Повторите пароль' />
		</>
	),
})

// регистрация: поля на корне, ключи совпадают
<PasswordPair fields={{ password: 'password', confirm: 'confirm' }} />
// смена пароля: другие имена в данных
<PasswordPair fields={{ password: 'newPassword', confirm: 'newPasswordRepeat' }} />
// профиль: блок в ветке
<PasswordPair fields='security' /> // → security.password, security.confirm
```

С ним схема формы регистрации сводится к `z.object({ login: z.string().min(3) })`: пароли
проверяет блок.

**`form.FormGroup`** — ветка одной формы со своей схемой и своим сабмитом, без отправки всей формы.

```tsx
<Form
	defaultValues={PROFILE_DEFAULTS}
	onSubmit={({ value }) => api.saveProfile(value)}
>
	{(form) => (
		<>
			<form.TextField name='displayName' />

			<form.FormGroup
				name='security'
				validators={{ onChange: passwordPairSchema }} // относительная: password, confirm
				onGroupSubmit={({ value }) => api.changePassword(value)}
			>
				{(group) => (
					<form.Section title='Пароль'>
						<group.TextField
							name='password'
							type='password'
						/>{' '}
						{/* плоские поля — D7 */}
						<group.TextField
							name='confirm'
							type='password'
						/>
						<button
							type='button'
							onClick={() => group.handleSubmit()}
						>
							Сменить пароль
						</button>
					</form.Section>
				)}
			</form.FormGroup>

			<form.SubmitButton>Сохранить профиль</form.SubmitButton>
		</>
	)}
</Form>
```

«Сменить пароль» проверяет и отправляет только `security`; «Сохранить профиль» — всю форму.
Внутри `form.FormGroup` можно положить и `<PasswordPair fields='security' />` — тогда правило
придёт из блока, а группе останется только сабмит.

#### 3. Свой элемент в форме (не поле)

Компонент, которому нужна форма, но не значение: панель сохранения, счётчик ошибок, обёртка-секция.
Берёт форму из контекста; в `components` кладётся, только если удобно звать его как `form.X`.

```tsx
export function ErrorSummary() {
	const form = useFormContext()
	return (
		<form.Subscribe selector={(s) => s.submissionAttempts > 0 && !s.isValid}>
			{(show) => show && <Alert>Проверьте поля, отмеченные красным</Alert>}
		</form.Subscribe>
	)
}

createForm({ FormElement, fields: { TextField }, components: { SubmitButton, ErrorSummary } })

<form.ErrorSummary /> // или просто <ErrorSummary /> — работает одинаково
```

#### 4. Разовый свой контрол прямо в разметке

Один раз нужен контрол, которого нет в ките, и регистрировать новый вид поля ради него не хочется.
`form.Field` (D5) отдаёт те же пропсы, что получает зарегистрированное поле, — `id`, `value`,
`onChange` (значение, не событие), `onBlur`, `errors`, `invalid`, `data-field`, — поэтому разовый
контрол участвует в фокусе на ошибке (D13) и регистрируется в шаге (D18), как обычное поле.

```tsx
<form.Field
	name='seats'
	validators={{ onChange: z.number().min(1, 'Хотя бы одно место') }}
>
	{({ value, onChange, errors, invalid, ...field }) => (
		<>
			<SeatPicker
				{...field}
				value={value}
				onChange={onChange}
			/>
			{invalid && <p role='alert'>{errors.join(', ')}</p>}
		</>
	)}
</form.Field>
```

Подпись и вывод ошибки здесь свои. Сырой `FieldApi` TanStack остаётся как `form.NativeField`, но
фокус на ошибке и регистрация в шаге его не видят.

#### 5. Новый вид поля на проекте

Контрол нужен в нескольких местах — его регистрируют один раз, и он становится `form.X` с
типизированным `name`, а заодно типом `rating` в документе `SchemaForm` (спека 008).

```tsx
// src/shared/fields/rating-field.tsx
export const RatingField = defineFieldType<{ max: number }, number>()(
	({ value, onChange, props, label, errors, invalid, ...field }) => (
		<label>
			{label}
			<Stars {...field} value={value} max={props.max} onChange={onChange} />
			{invalid && <p role='alert'>{errors.join(', ')}</p>}
		</label>
	),
)

// src/shared/form.ts
export const { useForm, Form, withForm, withFieldGroup } = createForm({
	FormElement,
	fields: { TextField, RatingField },
	components: { SubmitButton },
})

// где угодно
<form.RatingField
	name='score' // только пути со значением number
	label='Оценка'
	max={5}
	validators={{ onChange: z.number().min(1, 'Поставьте оценку') }}
/>
```

Валидация у нового поля та же, что у встроенных: `validators` на поле, схема формы или группы по
его пути. Сам вид поля правил не несёт — правила принадлежат данным, а не контролу.

## 5. `SchemaForm` — только граница

`SchemaForm` ложится поверх всего, что решено здесь, поэтому его изменения — отдельная спека,
черновик в `specs/010-schema-form/draft.md` (опции `createSchemaForm`, один реестр, обобщённые
контейнеры, колонки). В этой спеке схемного пути касается ровно то, без чего он сломается или без
чего 009 не даёт результата:

- **Разделение фабрик (D2) и переименование (D3).** Без разделения `{ Form }` из корня кита тянет
  схемный рендерер, а чистый корень — главный результат 009. Переименование идёт в том же релизе,
  чтобы у пользователей схем была одна миграция, а не две.
- **Схемный визард переводится на стор `form.Steps` (D18)** без нового поведения документа: `Wizard`
  кита меняется на `current` / `goTo(name)`, и без этого перевода схемный путь сломается. Рендерер
  именует шаги индексом, свойство `path` узла `step` удаляется.
- Остальное в документе — как сегодня: `Section`, `GridItem` и `Wizard` рендерер берёт из
  `components` по этим именам, отсутствие — dev-ошибка схемного пути (D4); узлы `section` и
  `submit`, пропс `blocks` и резерв `row` остаются до спеки 010.

## 6. Вне рамок, зафиксировано

- **Вынос логики, не зависящей от фреймворка, в `form-core`** (D10) — своя спека до 1.0: `coerce`,
  `field-validate`, значения опций формы по умолчанию, значения опций и ключи параметров, вывод
  render-props поля, вывод id типа поля, логика шагов визарда, операции с ключами массива,
  раскладка схемы. Это задевает почти каждый файл адаптера, поэтому не смешивается с этой спекой.
- **`form-shadcn` переезжает в shadcn registry**, как `data-grid-shadcn`, после того как закроем
  функциональные вопросы: `private`, `ignore` в changesets, `build-registry.mjs`, registry item с
  зависимостью от `@ez-kit/form-react`, `npm deprecate` на опубликованные 0.2.0–0.3.2, переписанная
  страница установки. Тест паритета из D12 тогда сравнивает входные модули китов в репо, а не
  пакеты.
- **Виды полей — обсудить после** перестройки на headless-логику и `SchemaForm` (спека 010). После D4 новый вид
  поля — minor, а не мажор, так что к 1.0 это не блокер. Кандидаты: загрузка файла (высокая
  востребованность и сложность, вероятно, свой контракт источника загрузки), range slider, время /
  дата-время, OTP; rich text и цвет — через `custom-fields`.
- **Вывод списка ошибок в китах.** Поле получает `errors: string[]` — нормализованные
  `formatFieldErrors`, без дублей и уже отфильтрованные правилом показа; ошибок может быть
  несколько (валидатор поля и `refine` схемы формы падают одновременно). Киты выводят список
  по-разному: shadcn склеивает через `ERROR_SEPARATOR` в `blocks/field-shell.tsx`, heroui отдаёт
  массив своему компоненту, а у массива склеивает через `', '`. Свести к одному поведению — все
  ошибки, один разделитель, один элемент с `role='alert'` — и проверить вместе с проходом по
  доступности. Примеры в §4 выводят все ошибки через `errors.join(', ')`, как встроенные поля.
- Проход по доступности (блок 4 аудита).
- Замеры масштаба рендера (спека 006).

## 8. Тестирование

- **TDD на каждое изменение**, сначала красный тест, по правилу репо.
- **Типы:** `form.X` есть ровно для переданного; запрещённые ключи отклоняются; `withForm` с `form`
  и без; плоские поля `withFieldGroup` со строковым путём и с картой полей; базовый API
  `useFormContext`.
- **Поведение:** фокус на первой ошибке в порядке DOM, в том числе без `<form>` и при `aria-invalid`
  не на фокусируемом элементе; `serverErrors` — применение при смене ссылки, снятие при правке поля,
  сброс при сабмите, `formErrors` в `form.Submit`; debounce и `minLength` с переопределением на поле;
  `isDirty` в `form.Submit`; e2e на гидрацию формы с сервера.
- **Шаги (D18):** порядок по JSX и пропуск по `when`; регистрация полей через `withForm`,
  `withFieldGroup` и `form.ArrayField`, снятие при размонтировании; `goNext` блокирует невалидный
  шаг и фокусирует ошибку; валидатор шага от корня не красит чужие шаги; валидаторы групп в шаге
  участвуют в вердикте; `stepErrors` для ошибок без пути; `steps[i].invalid`
  неактивного шага; `goTo` вперёд — по `linear` и `passed`; `initial` рендерит шаг на сервере;
  при переходе перерисовываются только два `form.Step` и два `Steps.Item`; ссылка `names` не меняется,
  пока не меняется набор шагов; async-валидаторы шага не зовутся при синхронных ошибках; финальный
  сабмит валидаторы шагов не запускает.
- **`useFormContext<TValues>()` (D6):** значения и `name` полей типизированы по дженерику, без
  дженерика — `unknown`.
- **`withFieldGroup` сабмит (D7):** `group.handleSubmit` проверяет только блок и зовёт
