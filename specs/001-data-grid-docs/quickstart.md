# Quickstart: Authoring a Data-Grid Doc Page

**Branch**: `001-data-grid-docs` | **Date**: 2026-05-19

This is the operator handoff. It tells whoever picks up the implementation
how to add one page end-to-end in under 15 minutes. The full task list will
be generated by `/speckit-tasks`; this document is the standing reference
that any of those tasks should follow.

---

## Prereqs

```bash
pnpm install
pnpm docs:sandpack   # Regenerate Sandpack bundles. Mandatory after any package change.
```

You will need a terminal running `pnpm docs:dev` (in `apps/docs/`) for live
preview while you author.

## 0. One-time setup work for this feature

If not already done by a previous task:

1. Create the new MDX shortcode at
   `apps/docs/components/data-grid-docs-example.tsx` following
   [contracts/data-grid-docs-example.md](./contracts/data-grid-docs-example.md).
2. Register it in `apps/docs/components/mdx.tsx`:
   ```ts
   import { DataGridDocsExample } from './data-grid-docs-example'
   // …add to the components map exported from this file.
   ```
3. Create `apps/docs/content/docs/data-grid/meta.json` with the top-level
   group title and an empty `pages: []` array — pages get appended as
   they're authored.

## 1. Pick the page you're authoring

Find the page in [plan.md → Project Structure](./plan.md#project-structure)
under `apps/docs/content/docs/data-grid/`. Each line of that tree maps to
one mdx file you will create. Pick the next unwritten one.

## 2. Identify the manifest examples for the page

Open `apps/docs/shared/data-grid/examples/manifest.json` and find every
entry whose topic matches the page. The `id` field is what you reference.

Examples:

| Page | Manifest IDs |
|---|---|
| `sorting.mdx` | `base-sorting`, `sorting`, `sort-toolbar` |
| `filtering/date-range.mdx` | `filter-date-range` |
| `cells/custom-cell-types.mdx` | `custom-cell-types` |
| `controlled-state.mdx` | `controlled-state` |
| `fallbacks.mdx` | `fallbacks` |

## 3. Write the page

Follow [contracts/docs-page.md](./contracts/docs-page.md) exactly. Skeleton:

```mdx
---
title: <title — Title Case>
description: <30–200 char one-liner that contains the primary keyword>
---

# <title>

<One short paragraph stating what this surface is and when to reach for it.>

## Usage

<DataGridDocsExample exampleId='<manifest-id>' />

<Prose: when to use, how it composes with other surfaces, common gotchas.>

## Options

| Option | Type | Description |
|---|---|---|
| `…`    | `…` | … |

## Notes

- <Anything flavor-specific. If shadcn and heroui differ, say so.>

## See also

- [Related page](./other-page)

## Source

- `@ez-kit/data-grid-<pkg>` — `<repo-relative-path>`
```

Concept-only pages (Overview, Architecture, Theming, Migration,
Installation/*) MAY omit `<DataGridDocsExample />` and the Options table —
see the contract for the full rule.

## 4. Add the page to the parent `meta.json`

```jsonc
{
  "title": "Filtering",
  "pages": [
    "index",
    "operators",
    "panel",
    "date-range",   // <-- the page you just added
    "multi-value",
    "global"
  ]
}
```

## 5. Validate locally

```bash
pnpm --filter @ez-kit/docs lint
pnpm --filter @ez-kit/docs typecheck
pnpm --filter @ez-kit/docs test
pnpm --filter @ez-kit/docs build
```

All four MUST pass before considering the page done. `build` includes
`sandpack:build` and is the canonical FR-013 / SC-005 gate.

For the new component only, additionally run the Playwright visual test:

```bash
pnpm --filter @ez-kit/docs test:visual
```

If you intentionally changed how a documented surface renders, update the
snapshot with `pnpm --filter @ez-kit/docs test:visual:update` (only do this
when the change is the goal, not when something broke).

## 6. Cross-check against the success criteria

Before opening a PR for a batch of pages:

- [ ] SC-002: run `node -e` (or a small script) to compare
      `manifest.json` IDs against `embeddedExampleIds` referenced in the
      mdx tree. Every manifest ID MUST be referenced from at least one
      page.
- [ ] SC-003: every page whose `appliesTo` ∈ `{both, shadcn, heroui}` has
      a `<DataGridDocsExample />` (or an explicit "no live example —
      reason" note for Theming-style exceptions).
- [ ] SC-004: every documented capability appears for both flavors via the
      in-page toggle, OR the page explicitly says "X is not supported in
      flavor Y".
- [ ] SC-005: `pnpm docs:build` finishes with zero warnings.
- [ ] SC-006: search query smoke check — open the dev server, search for
      each of the FR-011 queries, confirm a data-grid page appears in the
      top results.
- [ ] SC-007: from the docs landing, click no more than 3 times to reach
      any documented page.

## 7. Commit

Conventional Commits — one logical group per commit:

```text
docs(data-grid): add filtering pages (operators, panel, date-range)
```

Per the constitution, no changeset is required for `apps/docs/` (it is a
private workspace package). Do not add one.

---

## Troubleshooting

- **Sandpack preview shows "Loading..." forever.** Re-run
  `pnpm docs:sandpack`. The bundles are regenerated only on demand.
- **TypeScript error on `<DataGridDocsExample exampleId="…" />`.** The
  `exampleId` type is `DataGridSandpackExampleId` — make sure the literal
  matches an `id` in `manifest.json`.
- **Build complains about a missing page in a `meta.json` `pages` array.**
  Either add the file or remove the entry. The contract requires 1:1
  agreement.
- **Both flavors show the same screenshot in the Playwright test.** The
  toggle is local state — Playwright must `click` the toggle and `await`
  the new bundle to load before taking the second screenshot.
