# Feature Specification: Config-Driven Forms (`FormSchema` v1)

**Date**: 2026-08-27 | **Status**: agreed, not implemented
**Packages**: `@ez-kit/form-core`, `@ez-kit/form-react`, `@ez-kit/form-shadcn`, `@ez-kit/form-heroui`

## 1. Summary

Add a **config-driven** rendering mode to the form packages: a plain-data `FormSchema`
describes a form, and one renderer turns it into the field components that already exist
on the form instance (`form.TextField`, `form.SelectField`, …). Writing a form in JSX and
describing it with a config become two entrances to the _same_ machinery — not two
implementations.

Motivation, in the order the value lands:

1. Large production forms are cheaper to describe as data than as JSX.
2. A config that is plain data can be produced by a visual builder.
3. It can be generated by an LLM and validated on the way in.
4. It can be delivered from a backend (BDUI) so a form changes without a deploy.

The kit contract (`FormComponents`) and the binding layer are reused unchanged, so both
`shadcn` and `heroui` support config-driven forms on day one.

## 2. Non-goals for v1

Deferred deliberately; each is additive and cannot break the v1 format:

- **Array fields** (repeatable rows). The relative-reference syntax they need _is_
  reserved in v1 (§5.3) so the rule language never has to change.
- `row` layout node and `rowSpan` — names reserved, not implemented (§4.4).
- Computed fields (`total = sum(items[].price)`).
- Visual builder, JSON Schema → `FormSchema` adapter, zod → `FormSchema` adapter.
- `resetOnHide` (§6).

## 3. Invariants

These are load-bearing. Everything below follows from them.

**I1 — Layout never affects data paths.** A container node contributes nothing to a
field's path. `name` is always the full path from the root of the form values. Moving a
field between sections, grid cells or steps changes neither `values`, nor validation, nor
the submitted payload. (The only future exception is inside an array node, §5.3.)

**I2 — A schema is pure data.** No React elements, no imported components, no functions —
_when the schema is meant to be serializable_. Anything non-serializable is either given a
serializable twin or is explicitly marked TS-only. Custom components are referenced by
**string key** resolved against a registry, never by import.

**I3 — No JavaScript in JSON.** Conditions delivered over the network are rule objects
evaluated by our own interpreter. `eval` / `new Function` on external data is out of scope
permanently: it demands `script-src 'unsafe-eval'`, it turns a data-write bug into script
execution, it cannot be round-tripped by a builder, and a backend cannot evaluate it.

**I4 — One source of validation.** Either the schema's constraints generate the validator
or the caller supplies `validators`; never both (§7.4).

**I5 — The kit owns the markup.** The renderer computes state and hands one flat props
object per unit; the kit renders the whole element tree. This extends the rule already
documented in `packages/form/react/react/src/contract.ts` to the new layout units.

## 4. The `FormSchema` format

### 4.1 Document

```ts
type FormSchema = {
	/** Format version. Present so BDUI payloads can evolve. v1 documents carry `1`. */
	version: 1
	children: Node[]
}
```

### 4.2 Node kinds

Every node carries a `type` discriminant. Built-in values:

| `type`                                                                                                              | kind      | notes                                       |
| ------------------------------------------------------------------------------------------------------------------- | --------- | ------------------------------------------- |
| the 8 `FormFieldType` values (`text`, `number`, `textarea`, `select`, `checkbox`, `switch`, `radiogroup`, `slider`) | field     | bound to `name`                             |
| `section`                                                                                                           | container | grid + optional heading                     |
| `step`                                                                                                              | container | one wizard step                             |
| `submit`                                                                                                            | leaf      | the submit button                           |
| `block`                                                                                                             | leaf      | custom, value-less markup from the registry |
| any other string                                                                                                    | field     | custom field from the registry (§8)         |

Reserved and rejected as custom-registry keys: all of the above.

### 4.3 Common properties

```ts
type CommonProps<TValues> = {
	label?: LocalizedText
	description?: LocalizedText
	/** Visible when this evaluates true (or when absent). */
	when?: Condition<TValues>
	/** Rendered disabled when this evaluates true. */
	disabledWhen?: Condition<TValues>
	/** Grid columns this node spans inside its section. Default 1. */
	colSpan?: number
}
```

Field nodes additionally carry `name`, their kind-specific options (mirroring the existing
`TextFieldProps`, `NumberFieldProps`, … in `field-props.ts`), an optional `defaultValue`
(§4.6) and an optional `validate` block (§7).

### 4.4 `section`

```ts
{
  type: 'section'
  title?: LocalizedText      // a section WITHOUT a title is legal — pure grouping
  description?: LocalizedText
  columns?: number           // grid columns for direct children, default 1
  children: Node[]
}
```

Children flow through the grid in array order; each occupies `colSpan` columns (default 1).
Nested sections are the way to build a different grid inside a section.

`row` and `rowSpan` are **reserved names** — no other feature may claim them. Adding them
later is purely additive: a `row` node inside a `columns` grid occupies a full grid line.

Rationale for choosing `columns`/`colSpan` over a `row` node in v1: `row` can be added
without breaking existing documents, whereas removing `columns` after release cannot.
`rowSpan` is additionally hazardous while row heights are content-driven (a validation
message makes a field taller), so it needs `grid-auto-rows` to be pinned first.

### 4.5 `step`

```ts
{
  type: 'step'
  title?: LocalizedText
  description?: LocalizedText
  /**
   * Optional data path. When present, the renderer drives this step through TanStack's
   * `useFormGroup({ name: path })` and gets `group.validate()` / `group.handleSubmit()`
   * for free. When absent (the default), the step's fields are collected by walking the
   * subtree and validated explicitly — which keeps step layout independent of the data
   * shape (I1).
   */
  path?: string
  children: Node[]
}
```

Steps live in the same tree as everything else, which is what lets a step carry `when` —
"skip the company-details step for an individual" is a first-class case, not a workaround.

Mixing `step` nodes with non-`step` siblings at the same level is a parse error.

### 4.6 `defaultValue`

A field node may carry `defaultValue`. In the TS mode defaults normally come from
`defaultValues`; in BDUI mode the schema is the only thing that knows a field exists, so
without this a backend-delivered field starts as `undefined`. When the caller does not pass
`defaultValues`, the renderer builds them from the schema.

Name chosen to match TanStack: `form-core@1.33.2` uses `defaultValues` on the form and
group, `defaultValue` on the field.

### 4.7 `submit`

```ts
{ type: 'submit', label?: LocalizedText, disabled?: boolean }
```

The submit button is a node so that a backend-delivered form can place and label it. It
renders through the existing `SubmitButton`. Inside a wizard, the wizard chrome owns
back/next; the final submit is this node placed in the last step (§10.3).

### 4.8 `LocalizedText`

```ts
type LocalizedText = string | { key: string; params?: Record<string, string | number> }
```

A string is finished copy; an object is a translation key resolved by the app through the
`translate` prop (§9.1). An object key with no `translate` supplied is a parse-time error,
not a blank label.

### 4.9 A complete example

```ts
const schema = defineFormSchema<Values>()({
	version: 1,
	children: [
		{
			type: 'section',
			title: 'Client',
			columns: 2,
			children: [
				{ type: FormFieldType.Text, name: 'firstName', label: 'First name' },
				{ type: FormFieldType.Text, name: 'lastName', label: 'Last name' },
				{
					type: FormFieldType.Select,
					name: 'clientType',
					label: 'Type',
					colSpan: 2,
					options: [
						{ value: 'person', label: 'Individual' },
						{ value: 'business', label: 'Company' },
					],
				},
			],
		},

		{
			type: 'section',
			title: 'Company details',
			when: { field: 'clientType', eq: 'business' },
			columns: 2,
			children: [
				{ type: FormFieldType.Text, name: 'inn', label: 'Tax ID', validate: { required: true, rule: 'ru-inn' } },
				{
					type: FormFieldType.Text,
					name: 'vat',
					label: 'VAT',
					when: { and: [{ field: 'clientType', eq: 'business' }, { not: { field: 'country', eq: 'RU' } }] },
				},
			],
		},

		{ type: 'submit', label: 'Save' },
	],
})
```

The same document as JSON — identical, because `FormFieldType` members _are_ those strings
and no functions were used:

```json
{
	"version": 1,
	"children": [
		{
			"type": "section",
			"title": "Client",
			"columns": 2,
			"children": [
				{ "type": "text", "name": "firstName", "label": "First name" },
				{ "type": "text", "name": "lastName", "label": "Last name" }
			]
		},
		{ "type": "submit", "label": "Save" }
	]
}
```

## 5. Conditions

### 5.1 The two inputs

```ts
type Condition<TValues> = Rule<TValues> | ((values: TValues) => boolean)
```

A **function** is only legal in a TS-authored schema — it comes from the caller's own
bundle. A **rule object** is legal everywhere and is the only form a network payload may
use. There is no third form (I3).

### 5.2 The rule language

```ts
type Rule<TValues> =
	| { field: FieldRef<TValues>; eq: unknown }
	| { field: FieldRef<TValues>; in: readonly unknown[] }
	| { field: FieldRef<TValues>; gt: number }
	| { field: FieldRef<TValues>; lt: number }
	| { field: FieldRef<TValues>; truthy: true }
	| { and: readonly Rule<TValues>[] }
	| { or: readonly Rule<TValues>[] }
	| { not: Rule<TValues> }
```

The operator set is closed on purpose: every operator added is an operator backends will
start emitting forever. Anything richer belongs in a named rule (§7.3) or a TS function.

Both forms compile to the same predicate:

```ts
function compileCondition<TValues>(c: Condition<TValues>): (values: TValues) => boolean
```

### 5.3 Field references, and the array reservation

```ts
type FieldRef<TValues> = DeepKeys<TValues> | `./${string}`
```

A bare path is resolved from the **root** of the values. A `./`-prefixed path is resolved
relative to the **current array item**. v1 ships no array node, so `./` never resolves and
is a parse error — but the syntax is claimed now, because changing the rule language after
documents exist in databases and backends is the one thing that cannot be done cheaply.

## 6. Visibility and data

Two behaviours, deliberately separated:

- **Validation of a hidden field is always off.** Not configurable. A required field the
  user cannot see must never make a form unsubmittable-without-explanation.
- **Whether a hidden field's value reaches `onSubmit`** is configurable:
  `<FormRenderer keepHiddenValues />`, default `false`.

Stripping happens **at submit time** by filtering the values against the computed
visibility tree — not by deleting from state when the field hides. Toggling a condition
back and forth therefore does not destroy what the user typed, and hiding causes no extra
state churn. The consequence is that re-showing a field shows its previous value; a true
reset (`resetOnHide`) is a separate future feature, not the default.

Prior art confirming the knob is real: react-hook-form's `shouldUnregister`, Formily's
`x-display: 'hidden' | 'none'`. TanStack has no equivalent option — only `form.deleteField`,
i.e. the primitive to implement it by hand.

## 7. Validation

### 7.1 Constraints in the schema

```ts
type FieldValidate = {
	required?: boolean
	min?: number // numeric value / slider
	max?: number
	minLength?: number // string length
	maxLength?: number
	format?: 'email' | 'url' | 'tel'
	/** Key into the named-rule registry (§7.3). */
	rule?: string
	/** Message overrides, per constraint key. */
	messages?: Partial<Record<string, LocalizedText>>
}
```

`pattern` is **not** part of the format. A regular expression from an untrusted source is a
ReDoS hazard, and a hung tab is a worse failure than a missing client-side check.

### 7.2 How the validator is produced

The renderer walks the tree and builds **one** validator for the whole form, attached at
form level. It implements the Standard Schema interface directly — it does **not** depend
on zod — so no new runtime dependency enters `@ez-kit/form-react`. TanStack already maps a
standard-schema's issues back onto fields by path, so nesting comes for free.

The generated validator is attached to `onChange` and `onSubmit`.

### 7.3 Named rules

Arbitrary logic stays reachable from BDUI without shipping code over the wire: the schema
names a rule, the app registers the implementation.

```tsx
<FormRenderer
	schema={schema}
	rules={{ 'ru-inn': (value) => isValidInn(value) || 'Invalid tax ID' }}
/>
```

A `rule` key with no registered implementation is a parse-time error.

### 7.4 Interaction with TanStack's own validation (I4)

TanStack accepts exactly one validator per trigger — a standard schema _or_ a function, not
both. So the modes are mutually exclusive rather than merged:

- schema carries `validate` blocks → the renderer generates and owns the validator;
- caller passes `validators` → theirs is used verbatim and schema constraints are ignored;
- **both** → a descriptive error in development. We do not silently pick a winner, and we do
  not merge two issue sets onto one path.

Field-level validators through the native `form.Field` are unaffected: TanStack runs field
and form level together, which is the supported escape hatch.

## 8. Registries

Three registries, all keyed by string, all passed to the renderer:

```tsx
<FormRenderer
	schema={schema}
	fields={{ rating: RatingField }} // custom FIELD — has a name, bound to a value
	blocks={{ 'promo-banner': PromoBanner }} // custom BLOCK — no name, renders nothing bound
	rules={{ 'ru-inn': isValidInn }} // named validation rules
/>
```

A custom field receives the same props as a built-in one, which is the entire point — id,
`data-field`, normalised `errors`, `invalid`, `onBlur`, `disabled` are all computed by the
binding layer:

```ts
type CustomFieldRenderProps<TValue = unknown> = FieldRenderProps & {
	value: TValue
	onChange: (value: TValue) => void
	/** The node's `props` object, passed through uninterpreted. */
	props: Record<string, unknown>
}
```

Parse-time errors: registering a key that collides with a reserved `type` (§4.2); a node
whose `type` is neither built-in nor registered (critical for BDUI — a backend sending a
field the frontend cannot render must fail loudly, not render a hole).

## 9. Renderer API

### 9.1 `FormRenderer`

Two modes, mirroring the existing `<Form>`:

```tsx
// Controlled — config-driven part inside a hand-written form, sharing one instance.
const form = useForm({ defaultValues, onSubmit })
<Form form={form}>
  <form.TextField name="email" label="Email" />
  <FormRenderer form={form} schema={dynamicPart} />
  <form.SubmitButton>Save</form.SubmitButton>
</Form>

// Uncontrolled — the renderer owns the form for the lifetime of the element.
<FormRenderer schema={schema} defaultValues={...} onSubmit={...} />
```

Props beyond the two modes:

| prop                          | purpose                                                                    |
| ----------------------------- | -------------------------------------------------------------------------- |
| `fields` / `blocks` / `rules` | registries (§8)                                                            |
| `components`                  | partial override of the kit's `FormComponents` for this render             |
| `translate`                   | `(key, params) => string`, resolves `LocalizedText` objects                |
| `keepHiddenValues`            | §6, default `false`                                                        |
| `validators`                  | caller-owned validation, mutually exclusive with schema constraints (§7.4) |

`components` being a partial override is what lets an app replace the wizard chrome or a
section heading without forking the kit.

### 9.2 `defineFormSchema`

```ts
export function defineFormSchema<TValues>(): <const S extends FormSchema<TValues>>(schema: S) => S
```

Curried because TypeScript has no partial generic inference: `TValues` is supplied
explicitly while the schema literal keeps being inferred. This is what makes `name`
checkable against `DeepKeysOfType<TValues, …>` per field kind — a `number` field pointing at
a string path is a compile error, which no comparable library offers.

Custom field types narrow `name` only to `DeepKeys<TValues>` in v1 (the value type is
unknown to us). A typed field registry that recovers the narrowing is a later addition.

### 9.3 `parseFormSchema`

```ts
export function parseFormSchema<TValues>(input: unknown, options): FormSchema<TValues>
```

Mandatory for any schema that did not come from the app's own bundle. Validates the
document shape, the `version`, reserved-name collisions, unknown `type`s, unknown `rule`s,
`./` references, duplicate `name`s, and `LocalizedText` keys without a `translate`.

Duplicate `name` in two places in the tree is an **error**, not a supported "render twice".

## 10. Wizard

### 10.1 Why the kit must draw it

Verified against the kits: **neither ships a stepper.** HeroUI v3 (3.0.5) has `ProgressBar`,
`ProgressCircle`, `Tabs`, `Breadcrumbs`, `Separator` — no stepper among its 71 components.
The `@shadcn` registry returns nothing for "stepper". So the chrome is assembled by hand in
each kit: for heroui in `src/components/ui/` (hand-written files are editable there — see
its `action-bar.tsx`), for shadcn in `src/blocks/` (its `components/ui/**` is vendored and
immutable per `AGENTS.md`).

### 10.2 The contract addition

One member, one flat props object, kit owns the tree (I5):

```ts
type WizardStep = {
	index: number
	title: LocalizedText | undefined
	description: LocalizedText | undefined
	status: 'complete' | 'current' | 'upcoming'
	/** Visited and failing validation. Never true for an unvisited step. */
	invalid: boolean
	/** Cannot be navigated to right now. */
	disabled: boolean
	goTo: () => void
}

type WizardRenderProps = {
	steps: WizardStep[]
	currentIndex: number
	canGoBack: boolean
	canGoNext: boolean
	isLastStep: boolean
	/** Validates the current step's fields, advances only if they pass. */
	goNext: () => void
	goBack: () => void
	submitting: boolean
	/** The current step's fields. */
	children: ReactNode
}
```

Two rules the renderer must honour so kits do not have to think:

- a step disabled by `when` is **removed from `steps` entirely** and indices are
  recomputed — otherwise the stepper claims "3 of 5" for a form with four reachable steps;
- `invalid` is computed only for visited steps, so an untouched wizard never opens red.

### 10.3 Submission

Wizard chrome owns back/next only. The final submit comes from a `submit` node placed in
the last step, so there is exactly one way to render a submit button and BDUI controls it
like everything else.

## 11. Kit contract additions

`FormComponents` grows by three members; both kits must implement all three or fail to
compile against `satisfies FormComponents`:

| member     | props                                       | responsibility                   |
| ---------- | ------------------------------------------- | -------------------------------- |
| `Section`  | `{ title, description, columns, children }` | heading + grid container         |
| `GridItem` | `{ colSpan, children }`                     | one grid cell                    |
| `Wizard`   | `WizardRenderProps`                         | stepper + navigation + step body |

No visual styling may leak into `@ez-kit/form-react` — the same constraint `AGENTS.md`
places on `data-grid/react/react`.

## 12. Re-exporting TanStack composition

`createForm` currently builds `withForm` and `withFieldGroup` via `createFormHook` and then
discards them, returning only `{ useForm, Form }`. They will be exported — but **not** as a
bare re-export.

Reason, verified in `createFormHook.d.ts@1.33.2`: inside `withForm`, the render prop is
typed `form: AppFieldExtendedReactFormApi<…>` — TanStack's type, parameterised by the
components we inject (we inject none). Our flat fields are attached afterwards in `useForm`
via `Object.assign` and live in `KitFormApi`. A bare re-export would therefore work at
runtime while `form.TextField` fails to type-check inside a composed block — a trap worse
than the missing export.

So `createForm` returns typed wrappers that re-declare `form` as `KitFormApi<…>`; there is
no runtime cost. `useFormGroup` / `useFieldGroup` are re-exported as-is (they yield a group
API, which correctly carries no injected fields), documented as native-`form.Field`
territory.

## 13. Packaging and size

The config layer ships **inside `@ez-kit/form-react`**, not as a separate package.
Tree-shaking removes it for JSX-only consumers (`sideEffects: false` is already set and the
layer executes nothing at module scope). The dependency argument that would have forced a
split is neutralised by §7.2 — the validator generator does not depend on zod.

A dedicated `size-limit` entry covers the config layer so its weight stays visible.

## 14. Testing

- **Rule compiler**: each operator, nesting, missing path, `./` rejected in v1.
- **Visibility**: hidden field is not validated; value stripped at submit by default and
  retained under `keepHiddenValues`; toggling a condition twice preserves input.
- **Validator generation**: constraints → Standard Schema; issues land on the right field
  paths; both-sources-supplied throws in dev.
- **Parser**: every error class in §9.3, each with a message naming the offending node.
- **Renderer**: a schema and its hand-written JSX equivalent produce the same DOM under
  both kits (the existing `test-kit.tsx` harness already supports this shape).
- **Typing**: `form-types.test.tsx`-style compile-time assertions — wrong-typed `name`,
  unknown option for a field kind, unknown `type`.
- **Wizard**: skipped step removes an index; `invalid` stays false until visited.
- **Docs**: at least one config-driven example under `apps/docs/shared/examples/form/`,
  rendering under both kits.

## 15. Compatibility and evolution

The v1 format is additive-safe by construction. Landing later without a breaking change:
`row` / `rowSpan`, array nodes (with `./` already reserved), `resetOnHide`, typed custom
field registry, `LocalizedText` variants, adapters (JSON Schema → `FormSchema`,
zod `.meta()` → `FormSchema`).

Per this repo's convention, pre-1.0 packages ship breaking changes as **minor**; array
support is planned as exactly such a minor addition.
