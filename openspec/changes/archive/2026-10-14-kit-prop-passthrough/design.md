# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/form-field-props/spec.md`.

Как устроено сейчас:

- Каждый из двенадцати биндеров в `packages/form/react/react/src/fields/*.tsx` деструктурирует
  фиксированный список пропсов (`TextFieldProps<TFormData>` в `field-props.ts`) и передаёт киту
  ровно его. Рендер-пропсы кита (`TextFieldRenderProps` и т. д. в `contract.ts`) перечисляют те же
  атрибуты второй раз.
- Кастомные поля (`fields/custom-field.tsx`) уже делят пропсы на «биндинг» и «автор»: ключи вне
  `BASE_FIELD_PROP_KEYS` собираются во вложенный мешок `props`, тип которого задаёт фантом
  `defineFieldType<TProps>`.
- Киты объявляют набор полей через `satisfies AllFormFieldSlots` (`sets.ts`), а бандлы
  типизируются `FormBundle<typeof allFormFields, …>` (`form.tsx`), поэтому литеральные типы
  компонентов кита доступны в типе экземпляра.
- Рендерер схемы (`schema/render-node.tsx`) вызывает `form.TextField` и прочие с `placeholder`,
  `type` (из `inputType`), `rows`, `min`, `max`, `step`.

## Goals / Non-Goals

**Goals:**

- Один механизм проброса для всех двенадцати встроенных полей, без перечисления атрибутов.
- Компонент кита — обычный React-компонент: никаких хелперов-обёрток, чтобы подставить свой.

**Non-Goals:**

- Менять кастомные поля (`defineFieldType`, мешок `props`) — они остаются как есть.
- Менять формат документа `SchemaForm`, `inputType` и `TextInputType` в `@ez-kit/form-core`.
- Добавлять `PasswordField` / `SearchField`.
- Менять `ArrayField`, `form.Field`, `form.NativeField`.

## Decisions

### Плоский проброс с выводом типа из параметров компонента кита

`form.<Field>` типизируется как пропсы биндинга плюс
`Omit<Parameters<TFields[Key]>[0], keyof <Field>RenderProps>`. Биндер собирает всё, что не
принадлежит ему, в `rest` и рендерит `<Kit {...rest} {...вычисленные} />`.

Альтернативы:

- **Мешок `props`, как у кастомных полей.** Единообразно, но каждый компонент кита пишет
  `{...props.props}`, а тип по-прежнему нужно объявлять фантомом. Мешок у кастомных полей
  оправдан тем, что документ схемы не должен перезаписать биндинг; здесь ту же защиту даёт порядок
  спреда и `Omit` в типе.
- **Фантом `__props` на слоте кита.** Требует обёртки на каждом компоненте; проект, подставивший
  свой `TextField`, должен о ней знать — это ломает сценарий «взял и подставил».

### Список ключей биндинга — рантайм-объект, сверенный с типом

Как уже сделано для `BASE_FIELD_PROP_KEYS`: объект ключей с
`satisfies Record<keyof …, true>`, по одному на «базу» и на «опции». Добавленный позже пропс
биндинга без записи в объект — ошибка компиляции, а не пропс, молча уехавший киту. Отбор —
`Object.hasOwn`, по той же причине, что в `custom-field.tsx`.

### Порядок спреда: автор первым, биндинг последним

Вычисленные пропсы перекрывают одноимённые авторские в рантайме; в типе эти ключи вырезаны
`Omit`, так что перекрытие срабатывает только при обходе типов (JS-вызов, `as any`, документ
схемы).

### Пропсы кита сверх контракта — только опциональные

Следует из того, что `satisfies FormFieldSlots` сравнивает компонент со слотом
`(props: <Field>RenderProps) => ReactNode`: компонент с обязательным лишним пропсом туда не
присваивается. Обходить это не будем: рендерер схемы и любой вызов без этого пропса не смогли бы
его передать.

### Раскладка пропсов — решение кита

- shadcn: `rest` целиком на `<Input>` / `<Textarea>` / примитив; пропсы оформления (`label`,
  `description`, `errors`, `invalid`, `data-*`) разбираются явно и идут в `FieldShell`.
- HeroUI: атрибуты, которые React Aria принимает на корне (`type`, `autoComplete`, `inputMode`,
  `maxLength`, …), — на корень; `placeholder` — на `<Input>`. Кит объявляет тип пропсов так, чтобы
  он соответствовал раскладке.

### Киты экспортируют тип пропсов каждого поля — `<Field>KitProps`

Атрибуты вроде `min` / `max` у `SliderField` и `DateField` документированы в таблицах, которые
`docs-option-names.test.ts` сверяет с реальным типом. После изменения их нет в типах
`@ez-kit/form-react`, поэтому governing type таблицы — тип пропсов кита. Имя с суффиксом
`KitProps`, потому что киты уже реэкспортируют потребительские `<Field>Props` из
`@ez-kit/form-react`. Тот же тип пригодится приложению, которое оборачивает поле кита.

### Рендерер схемы передаёт ключи узла как нетипизированные пропсы

Базовый контракт больше не знает `placeholder` / `min` / …, поэтому рендерер передаёт их через
один локально объявленный «мешок атрибутов узла» с явным приведением. Это временная дыра в типах
до переделки `SchemaForm`, помеченная комментарием в коде.

### `TextInputType` остаётся в core

Удаляется из `TextFieldRenderProps`, `TextFieldProps`, реэкспорта `@ez-kit/form-react` и обоих
китов. В `@ez-kit/form-core` остаётся экспортом — им типизирован `inputType` узла схемы.

## Risks / Trade-offs

- [Внешний кит, читавший `placeholder` / `min` / … из контракта, перестанет их получать в типах]
  → major-changeset с инструкцией миграции: объявить эти пропсы в своём компоненте.
- [Ручная аннотация `FormInstance<V>` по умолчанию берёт `AllFormFieldSlots` и теряет пропсы
  кита] → в доках писать второй параметр (`FormInstance<V, typeof allFormFields>`); алиас в ките —
  открытый вопрос ниже.
- [Пропсы, переданные документом схемы, не проверяются типами] → осознанно, до переделки
  `SchemaForm`; набор ключей тот же, что сейчас.
- [Разный UX передачи у встроенных (плоско) и кастомных (мешок `props`) полей] → задокументировать
  в `custom-kit` и `custom-fields`; унификация — вместе с `SchemaForm`.
- [Тип `Parameters<…>` по объединению пропсов (Select и др. — union по типу значения)] →
  пересечение `union & extras` распределяется корректно; закрепить тестом типов.

## Migration Plan

Один релиз, major для `@ez-kit/form-react`, `@ez-kit/form-shadcn`, `@ez-kit/form-heroui`.
Миграция для пользователей наших китов: заменить `TextInputType.X` на строку. Для авторов
внешних китов: объявить `placeholder` / `type` / `rows` / `min` / `max` / `step` в пропсах своих
компонентов. Откат — revert релиза; данных не затрагивает.

## Open Questions

- Нужен ли каждому киту экспорт алиаса экземпляра (`FormInstance` со своими полями). Не меняет
  механизм; можно добавить отдельно.
