# Design

## Context

Мотивация — в proposal.md. Требования — в `specs/data-grid-layout-presets/spec.md`.

Что есть сейчас:

- Четыре пресета в `packages/data-grid/react/react/src/layouts/` — компоненты без пропсов, читают
  грид из `useDataGridTable()`. Тулбар у всех собирается общими хуками `useToolbarStart` /
  `useToolbarEnd` из `layouts/toolbar-controls.tsx`. Эти хуки читают только ссылки на конфиг
  (`table.grid`, `table.options`) и намеренно не подписываются на состояние.
- `resolveActionBarVariant(table)` (`data-grid/action-bar-variant.ts`) уже возвращает
  разрешённый вариант: `table.grid.selection.bar?.variant ?? DEFAULT_ACTION_BAR_VARIANT`.
  `<ActionBar />` читает его сам, тем же способом.
- `GridBody` (`data-grid/data-grid.tsx`) рендерит `children ?? <core.Layout /> ?? <DataGridTable />`
  и не мемоизирован. Значит, перерисовка `<DataGrid>` с новым конфигом перерисовывает и пресет.
- Кит shadcn для `inline` при `open: false` возвращает `null`, для `floating` держит пустой
  sticky-якорь в DOM. HeroUI порталит плавающую панель в fixed-оверлей.
- `AGENTS.md` содержит пункт «A layout places `ActionBar` itself, and `selection.bar.variant`
  does not» в разделе «do not re-propose». Это изменение его пересматривает.

## Goals / Non-Goals

**Goals:**

- Одно место, где пресеты решают, куда ставить панель. Условие не копируется в четыре файла.
- Панель переезжает при смене варианта без ремоунта, если React это позволяет (см. решение 3).

**Non-Goals:**

- Не трогаем рендер панели в китах: ни резервирование места под inline-полосу, ни анимации.
- Не добавляем опций, пропсов и экспортов. Хук — внутренний для `layouts/`.
- Не меняем `GridBody`, `children` и `core.Layout`, зарегистрированный потребителем.
- Не переносим `variant` в проп `<DataGrid.ActionBar>`: это отклонено раньше и вне рамок.

## Decisions

### 1. Общий хук возвращает два слота, а не флаг

`layouts/action-bar-slots.tsx` экспортирует внутренний хук:

```tsx
function useActionBarSlots(): { top: ReactNode; bottom: ReactNode }
```

Он читает `resolveActionBarVariant(useDataGridTable())` и кладёт один `<ActionBar key=… />` в
`top` при `inline` или в `bottom` в остальных случаях. Второй слот получает `null`. Пресет
пишет `{actionBar.top}` над таблицей и `{actionBar.bottom}` в конце.

Почему не `const inline = useIsInlineActionBar()` и тернарник в каждом файле: тогда в четырёх
файлах окажется и условие, и два места `<ActionBar />`, и гарантия «ровно один экземпляр»
держалась бы на аккуратности каждого файла. Слоты держат её в одном месте: экземпляр создаёт
только хук. Форма повторяет соседние `useToolbarStart` / `useToolbarEnd`, которые тоже
возвращают `ReactNode` для пресета.

Почему не компонент-обёртка вроде `<PresetShell>` (то есть `GridShell`): обёртка забирает у
пресета весь порядок детей. Слоты оставляют порядок в JSX каждого пресета, и место
`ActionBar` по-прежнему видно в его разметке.

Хук не подписывается на состояние, по той же причине, что и `useToolbarControls`: вариант — это
конфиг, а не состояние. Подписка заставила бы весь пресет (`Body`, `Table`) перерисовываться на
каждое изменение выделения.

### 2. Место в каждом пресете

```
DefaultLayout:        Toolbar -> [top] -> Table -> Pagination -> [bottom]
BottomBarLayout:      Toolbar -> [top] -> Table -> BottomBar  -> [bottom]
FilterPanelLayout:    Toolbar -> ActiveFiltersBar -> [top] -> Table -> BottomBar -> [bottom]
PopoverFiltersLayout: Toolbar -> [top] -> Table(...) -> Pagination -> [bottom]
```

В `FilterPanelLayout` панель стоит после `ActiveFiltersBar`, а не между тулбаром и чипами. Чипы
описывают запрос и продолжают тулбар, где этот запрос задаётся. Панель действий работает со
строками, которые запрос вернул, и её место у этих строк. Иначе панель разрезала бы связку
«фильтр в тулбаре → его чип» и оторвала бы чипы от контрола, который их порождает.

### 3. Стабильный `key`, чтобы панель переезжала, а не ремоунтилась

Оба слота стоят среди детей одного фрагмента. React сопоставляет keyed-элементы по ключу во всём
массиве детей, поэтому `<ActionBar key='action-bar' />`, переехавший из позиции `top` в
`bottom`, должен быть перенесён, а не создан заново. Позиции `null` сохраняют индексы
остальных детей. Тест проверяет, что DOM-узел панели (или её состояние) переживает
переключение. Если на практике React всё же ремоунтит (например, из-за разной глубины в
`PopoverFiltersLayout`), это допустимо: выделение живёт в store таблицы, теряется только
эфемерное состояние кита, например открытое меню. Тогда тест ослабляется до сохранения
выделения, а причина записывается в docblock хука.

### 4. Переформулировка правила в `AGENTS.md`

Пункт «A layout places `ActionBar` itself…» переписывается так. Запрещены опции, которые
существуют **только** ради расположения (восемь удалённых опций, `GridShell` как неявная
девятая). Режим, который уже есть в конфиге и описывает поведение, пресет может учитывать,
чтобы поставить элемент туда, где ему место. Прецедент — `useToolbarControls`: он уже читает
`creating.mode`, чтобы решить, монтировать ли `CreateTrigger`. Своя раскладка остаётся
единственным, что решает за потребителя, и пресет её не переопределяет. Фраза «accepted cost
… below the table» удаляется. `GridShell` упоминается как история: он делал то же самое через
обёртку, отнимавшую у пресета порядок детей.

Последствие для `docs-option-names.test.ts` и `e2e-slots.test.ts` — никакого: не меняются ни
имена опций, ни слоты.

### 5. Changeset и semver

Пакеты в `0.x`. Ломающее изменение поведения оформляется как `minor` с заголовком
**Breaking**, по прецеденту `.changeset/presets-mount-only-entry-controls.md`. Пакеты:
`@ez-kit/data-grid-react` и `@ez-kit/data-grid-heroui` (её готовый `DataGrid` привязывает
`DefaultLayout`). Кит `@ez-kit/data-grid-shadcn` не упоминается: он в `ignore`, и
`check-changesets.mjs` такое отклонит. Коммит — `feat(data-grid)!:`.

## Risks / Trade-offs

- [Сдвиг таблицы при первом выделении] Inline-полоса shadcn при `open: false` — это `null`.
  Когда она стоит над таблицей, первое выделение вставляет полосу и сдвигает строки вниз прямо
  под курсором. Под таблицей сдвигалась только пагинация. → Так же ведёт себя рецепт «панель
  первой», который документация рекомендует сейчас, то есть это не новая регрессия для тех, кто
  уже ставит панель сверху. Резервирование места — решение кита и вне рамок изменения. В
  changeset это упоминается, чтобы никто не удивился.
- [Порядок табуляции] Inline-панель над таблицей идёт в порядке табуляции раньше строк. →
  Ожидаемо для видимой полосы в потоке: она появляется, только когда есть с чем работать
  (shadcn — `null` в закрытом состоянии). Для `floating` порядок прежний.
- [Вариант не обновился] Если `<DataGrid>` не перерисовывается при смене `selection.bar`,
  пресет не узнает о новом варианте: хук не подписан. → Смена `selection.bar` — это смена
  пропса `<DataGrid>`, она перерисовывает `GridBody`, а за ним и пресет. Сценарий из спеки
  проверяет это тестом через `rerender`.
- [Кто-то полагался на панель снизу] Поведение меняется у выпущенного `0.10.0`. → Ломающее
  изменение явно отмечено в changeset. Обход: своя раскладка с `<DataGrid.ActionBar />` в
  конце.

## Migration Plan

Миграция данных не нужна. Потребитель, которому панель нужна под таблицей при `inline`, пишет
свою раскладку и ставит `<DataGrid.ActionBar />` последним. Рецепт есть в changeset и на
странице `layout/presets.mdx`. Откат — revert коммита: изменение не трогает типы и API.
