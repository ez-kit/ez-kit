# Design

## Context

Список значений колонки сейчас живёт в мете как статический массив: `meta.cell.config.items` (из
`cell.config`) и `meta.filtering.items` (из `filtering.items`). Его читают:

- `resolveFilterItems` / `resolveOptionLabel` в `react/src/data-grid/filter-model.ts`: чистые
  функции, их вызывают `render-filter-input.tsx` и `filter-panel.tsx` при рендере;
- `cell.tsx`, `creating-row.tsx`, `auto-form.tsx`, которые передают `config: meta.cell.config`
  компонентам кита (`view` / `editing` / `creating` / `filtering` из реестра cell types);
- `SelectCell` и `BadgeCell` в обоих китах, которые ищут `config.items` по `String(value)`.

Хук нельзя вызвать ни из конфига, ни из чистой функции, ни по разу в каждой ячейке. Нужен
React-слой, который вызывает хук и отдаёт результат всем этим читателям. Мотивация в proposal.md,
поведение в specs.

## Goals / Non-Goals

**Goals:**

- Киты продолжают читать `config.items` и почти не меняются: грид подставляет туда уже
  разрешённый список.
- Чистые функции модели фильтра остаются чистыми: асинхронный источник приходит в них готовым
  снимком.
- Публичный контракт расширяется только аддитивно: новые необязательные поля и опции.

**Non-Goals:**

- Кэш данных справочника в гриде. Кэш, дедупликацию, `staleTime` и инвалидацию держит хук
  потребителя.
- Поиск, пагинация, `useItemLabels`, `filters` в параметрах: это следующая фича. Здесь только
  форма `params`, которая позволит добавить их без поломки.
- Асинхронные списки для своих cell types. Они могут читать store через публичный хук, но
  опции `useItems` / `getItem` есть только у `select` и `badge`.

## Decisions

### D1. Store источников на инстанс грида и ленивые runner'ы

```
  <DataGridRoot>
    +-- ItemsSourceHost                       (рендерится внутри контекста таблицы)
    |     +-- <SourceRunner key="warehouse:base#v1"  useItems={...} />
    |     +-- <SourceRunner key="warehouse:editing#v1" useItems={...} />
    |               | publish(snapshot) в эффекте
    |               v
    |     ItemsSourceStore: key -> { snapshot, subscribers, hook }
    |               ^ useSyncExternalStore
    +-- ячейки / фильтры / чипы / редактор:  useItemsSource(columnId, slot)
```

- **Ключ источника** — `columnId` и владелец списка: `base`, `filtering`, `editing` или
  `creating`. Владелец вычисляется по цепочке наследования из specs. Форма создания, которая
  наследует редактор, поэтому подписывается на ключ `editing`, а не заводит свой runner, и хук
  вызывается один раз.
- **Ленивость через refcount.** `useItemsSource` регистрирует подписчика в эффекте и снимает его
  при размонтировании. Host рендерит runner только для ключей, у которых есть подписчики. Скрытая
  колонка с закрытым фильтром не запускает запрос.
- **Runner** — компонент, который вызывает ровно один хук. Правила хуков соблюдены: хук
  вызывается безусловно на верхнем уровне компонента, а набор хуков между источниками различается
  через разные компоненты, а не через условие. Снимок публикуется в `useEffect` (запись в внешний
  store во время рендера запрещена). Если снимок не изменился поэлементно (`items`, `isLoading`,
  `error` по `Object.is`), подписчики не уведомляются.
- **Хуки потребителя работают внутри грида.** Runner сидит под контекстом таблицы, поэтому хук
  может вызывать `useDataGridState`, `useGridContext` и что угодно из окружения приложения. Так
  серверные счётчики доступны уже в этой фиче: хук сам читает текущие фильтры.

Альтернативы:

- **Вызов хука в каждом потребителе.** Отвергнуто: тысяча `useQuery`-observer'ов на странице, а
  результат один.
- **Promise-функция (`items: () => Promise`).** Отвергнуто: гриду пришлось бы самому решать кэш,
  дедупликацию, отмену и повторы.
- **Значения через `context`.** Отвергнуто: колонки не получают `GridContext`, запрос поднимается
  на уровень страницы и стартует сразу, а для каждого справочника пришлось бы заводить ключ через
  declaration merging.

### D2. Нестабильная ссылка на хук

Ключ runner'а дополняется версией идентичности хука (`#v1`, `#v2`, …). Если ссылка меняется,
runner перемонтируется с новым ключом. Это единственный корректный способ сменить хук без
нарушения правил хуков. В dev грид один раз предупреждает об этом для колонки (specs). Версии
считаются через `WeakMap<Function, number>` в store.

### D3. Подстановка разрешённого списка в `config`

`cell.tsx`, `creating-row.tsx` и `auto-form.tsx` больше не передают `meta.cell.config` как есть.
Они передают копию, где `items` — разрешённый список нужного владельца, а `useItems` и `getItem`
вырезаны. Встроенные `SelectCell` / `BadgeCell` и любые сторонние компоненты, которые читают
`config.items`, получают правильный список, ничего не зная про хук.

Рядом передаются новые необязательные поля:

- `CellViewCtx.itemStatus?: ItemStatus` и `CellViewCtx.item?: SelectItem | BadgeItem`: статус и
  найденный элемент значения (`resolved` / `pending` / `error` / `missing`);
- `FieldState.itemsLoading?: boolean` и `FieldState.itemsError?: unknown`: состояние списка
  вариантов для select редактора, формы создания и фильтра;
- `MultiSelectFilterProps.isLoading?: boolean` и `MultiSelectFilterProps.error?: unknown`.

`ItemStatus` — закрытое множество: const object плюс union одного имени, по правилам репозитория.
Все поля необязательны, поэтому внешний кит, написанный под `satisfies FullGridComponents`,
продолжает компилироваться.

### D4. Порядок подписи

Одна функция `resolveItem(value, sources)` для ячейки, чипа и триггера:

```
  base snapshot нашёл value         -> resolved(item из базы)
  getItem(row) вернул item          -> resolved(item из строки)      (только у ячейки)
  faceted-индекс нашёл value        -> resolved(item из строки)      (чип / триггер)
  base snapshot isLoading           -> pending
  base snapshot error               -> error
  иначе                             -> missing(raw)
```

Подписи берутся только из базового источника. Переопределения `filtering` / `editing` / `creating`
дают только варианты. Только у колонки без базы подписи берутся из источника того места, где
значение показано (specs).

### D5. Faceted и `getItem`: индекс по строкам, а не кэш

Для подписей faceted-вариантов и чипов строится `Map<value, item>`: для каждого значения берётся
`getItem` первой строки, где оно встречается. Строки берутся из faceted row model колонки, поэтому
у каждого faceted-значения строка есть. Индекс мемоизируется по ссылке на массив строк и
пересобирается вместе с ним. Это вычисление над данными таблицы, а не хранилище: инвалидировать
нечего.

### D6. Счётчики

`resolveFilterItems` меняет порядок слияния: `count` из источника сохраняется, а faceted
проставляет счётчик только варианту без него. Если источник счётчиков есть (включён faceted
или хотя бы один вариант несёт `count`), вариант без счётчика получает `0`. Иначе `count` остаётся
`undefined`. Предупреждение `faceted` + `manual` выводится в `createTableOptions` рядом с
проверкой `REQUIRED_FACETED_FEATURES`.

### D7. Модель фильтра остаётся чистой

`FilterTarget` получает необязательный снимок источника вариантов и базового источника. Компонент,
который вызывает `resolveFilter` (`render-filter-input.tsx`, `filter-panel.tsx`, хук
`useColumnFilters`), сначала читает снимки через `useItemsSource` и кладёт их в target.
`resolveFilter` при этом остаётся функцией без хуков, а тесты модели могут передавать снимки
напрямую.

### D8. Типы

```ts
type ItemsSourceParams = Record<never, never> // search / values / filters позже
type ItemsSourceResult<TItem> = { items: TItem[]; isLoading?: boolean; error?: unknown }
type ItemsSource<TItem> = (params: ItemsSourceParams) => ItemsSourceResult<TItem>
```

`SelectCellConfig` и `BadgeCellConfig` становятся объединением, в котором `items` или `useItems`
обязателен (сейчас обязателен `items`), с необязательным `getItem`. У `filtering`, `editing` и
`creating` колонки оба поля необязательны. Элемент в `useItems` у `badge` — `BadgeItem`, как у
`items`. `getItem` типизируется по `TRow` колонки, а `ColumnCellMeta` хранит его row-erased, как
другие функции колонки.

## Risks / Trade-offs

- [Один лишний рендер после ответа хука: снимок публикуется в эффекте] → Потребители видят
  `pending` на один кадр дольше. `getItem` закрывает это для ячеек, а для фильтра и редактора
  состояние загрузки и так ожидаемо.
- [Первый рендер всегда `pending`: подписчик регистрируется в эффекте, runner монтируется после
  первого коммита] → Если хук отдаёт данные синхронно из кэша TanStack Query, следующий кадр уже
  `resolved`. Документация рекомендует `getItem` там, где строка несёт подпись.
- [Видимая select-колонка всегда запускает хук через свои ячейки, ленивость её не спасает] → Это
  ожидаемо: подписи нужны сразу. Ленивость экономит запросы для скрытых колонок, закрытых фильтров
  и не открытых редакторов.
- [Подстановка `config.items` меняет то, что получает кастомный `cell.component` /
  `editing.component`] → Компонент получает разрешённый список вместо исходного. Для статического
  `items` это тот же массив. Для `useItems` это и есть то, что ему нужно.
- [Бюджет `size-limit` у `@ez-kit/data-grid-react`] → Store и runner небольшие, но бюджет
  проверяется задачей. Store не должен попадать в бандл грида без select/badge-колонок с
  `useItems` настолько, насколько это позволяет tree-shaking. `tree-shaking.test.ts` проверяет, что
  точки входа не изменились.

## Migration Plan

Изменения аддитивны, кроме двух исправлений поведения счётчиков (proposal, What Changes): грид с
`faceted` и `count` в `items` начнёт показывать счётчики источника, а значения без строк получат
`0`. Это описывается в changeset как исправление. Откат — revert PR.
