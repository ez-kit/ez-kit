# Design

## Context

Мотивация — в proposal.md, требования — в `specs/data-grid-disabled-features/spec.md`. Прямой
предшественник — изменение `infinite-pagination-unsliced`: оно закрыло тот же дефект для
`mode: 'infinite'` и разобрало механику TanStack, на которую опирается этот дизайн.

Конвейер строк TanStack Table v9 (`@tanstack/table-core` 9.2.4,
`core/row-models/coreRowModelsFeature.utils.js`):

```
data -> core -> filtered -> grouped -> sorted -> expanded -> paginated -> getRowModel()
```

Каждый этап устроен одинаково: модель берётся из слота `features` и кешируется в
`table._rowModels.<x>` при первом вызове, а затем пропускается, если стоит `manual<X>` или слота
нет. Включена ли фича в конфиге грида, TanStack не знает. Гейтом служит только флаг, а флаги
читаются на каждом вызове.

Что ядро передаёт сейчас (`create-table-options.ts`):

| Срез          | Гейт при выключенной фиче                          | Меняет строки?                             |
| ------------- | -------------------------------------------------- | ------------------------------------------ |
| pagination    | нет; `manualPagination` только для infinite/manual | да, всегда: состояние засевает ядро        |
| grouping      | `enableGrouping: false` — гасит только UI          | да, при засеве                             |
| columnFilters | `enableColumnFilters: false` — гасит только UI     | да, при засеве                             |
| sorting       | `enableSorting: false`                             | нет: модель проверяет `getCanSort`         |
| globalFilter  | `enableGlobalFilter: false`                        | нет: модель проверяет `getCanGlobalFilter` |
| expanded      | нет `getSubRows`                                   | нет: раскрывать нечего                     |
| rowPinning    | нет `enableRowPinning`                             | нет: тела делят строки только при нём      |

`@ez-kit/data-grid-react` читает `options.manualPagination` как признак серверного режима в
`aria-state.ts`: `hasPartialRowSet` и `hasTrustedRowTotal`. Для infinite это уже обойдено
чтением `grid.pagination.infinite`. `useDataGrid` пересобирает опции на каждом рендере и
явно зачищает ключи, которые резолвер перестал писать (`use-data-grid.ts`,
`previousOptionKeysRef`).

## Goals / Non-Goals

**Goals:**

- Одно правило на срез, выраженное флагом или колонкой, которые пересчитываются на каждом
  рендере. Тогда переключение на лету работает в обе стороны без особых случаев.
- Набор фич потребителя передаётся в TanStack как есть: ни слоты, ни их идентичность не
  трогаются.

**Non-Goals:**

- `aria-rowcount` при виртуализации — та же оговорка, что в предшественнике.
- Политика засевов раскладки колонок (`visibility.initialHidden`, `pinning.initialSide`): у них
  эффект засева и есть его смысл, `warnUnreachableSeed` остаётся как есть.
- `enableRowPinning` по умолчанию `true` в upstream: при выключенном закреплении `row.pin()` из
  кода по-прежнему меняет состояние. Строки от этого не меняются (тела не делят их), а UI
  закрепления нет. Это отдельный вопрос гейтинга API.
- Предупреждения о контролируемом `state.*`.
- Изменения в TanStack Table.

## Decisions

### 1. Пагинация: срез только в клиентском постраничном режиме

Ядро пишет `manualPagination` всегда, булевым значением:

```
isClientPaged    = hasPagination && mode !== 'infinite' && manual !== true
manualPagination = !isClientPaged
```

`rowCount` / `pageCount` по-прежнему передаются только в ветке `manual`. Ветки infinite и
manual сворачиваются в одно выражение.

Последствия при выключенной пагинации:

- `getRowCount()` возвращает длину pre-paginated модели, то есть все строки.
- `getPageCount()` формально считается, но его никто не читает: `Pagination` не рендерится.
- `autoResetPageIndex` выключен (см. риски).
- `createExpandedRowModel` раскрывает подстроки сам, как в infinite.

Безусловная запись ключа важна для headless-потребителей. Проба показала: при
`createTable` + `setOptions(prev => ({ ...prev, ...options }))` условный спред оставляет
`manualPagination: true` и `rowCount` от прежнего infinite- или manual-режима, и возврат в
клиентский режим перестаёт резать строки. React этого не видит благодаря зачистке ключей, но
опираться на неё не нужно.

Отвергнутые альтернативы — те же, что в предшественнике, плюс две:

- **Убирать `paginatedRowModel` из набора при выключенной пагинации.** Переход «выключено →
  включено» сработал бы: пустой кеш перепроверяется на каждом вызове. А «включено → выключено»
  нет: модель уже закеширована. К тому же ломается идентичность `options.features`.
- **Обёртка над слотом, читающая флаг на каждом вызове.** Работает в обе стороны и сохранила бы
  смысл `manualPagination` как «сервер», но дублирует штатный переключатель upstream, требует
  приватной опции, подменяет слот потребителя и зависит от `paginateExpandedRows`.
- **`pageSize: Infinity` в состоянии.** Пишет в состояние значение, которого автор не задавал:
  оно уходит в `onStateChange`, персист и контролируемый `state`, а при включении его пришлось бы
  восстанавливать.
- **React рендерит `getPrePaginatedRowModel()`.** Читателей `getRowModel()` десяток, а
  headless-потребитель всё равно получает срезанные строки.

### 2. Группировка: `manualGrouping: !hasGrouping`

Ядро отказывается от `manualGrouping`, когда группировка **включена**: флаг оставлял колонку
`__group__` пустой (комментарий у опций). При выключенной группировке колонки `__group__` нет,
и флаг делает ровно нужное: `getGroupedRowModel()` возвращает пре-группированную модель. Серверная
группировка (`grouping.getSubRows` + `createManualGroupedRowModel()`) требует включённой
`grouping` и не затрагивается. Флаг тоже пишется безусловно, булевым значением.

### 3. Колоночные фильтры: пропускающий `filterFn` плюс обёртка, сбрасывающая memo модели

`manualFiltering` в TanStack один на обе оси и при включённом поиске погасил бы и его.
`createFilteredRowModel` берёт функцию фильтра у колонки (`column_getFilterFn`), а глобальный
поиск — у таблицы (`globalFilterFn`). Поэтому решение из двух частей.

**Заглушка.** При `!hasColumnFiltering` `mapColumns` ставит каждой листовой колонке
`filterFn: () => true` поверх диспетчера операторов. Засеянный фильтр формально применяется, но
пропускает каждую строку; глобальный поиск не задет.

**Обёртка над слотом.** Одной заглушки мало: memo-зависимости `createFilteredRowModel` —
`[preFiltered, columnFilters, globalFilter]`, без `options.columns`. Смена `filterFn` при
переключении `filtering` на лету модель не пересчитывает: она остаётся устаревшей, пока не
изменятся данные, фильтры или поиск (выяснено при реализации, проба на живом экземпляре). У
группировки `options.columns` в зависимостях есть, поэтому решению 2 это не нужно.

Ядро заменяет `filteredRowModel` из набора потребителя обёрткой: она хранит экземпляр
внутренней модели и создаёт его заново, когда меняется `table.options.enableColumnFilters`.
Новый экземпляр — новый memo, поэтому первое же чтение после переключения пересчитывает строки
с актуальными функциями фильтра. Флаг читается на каждом вызове, как `manualPagination`, так
что работают оба направления. Лишний пересчёт бывает только в момент переключения.

Новый memo пропускает свой первый `onAfterUpdate`, а именно там upstream перематывает страницу
после изменения результата фильтра. Поэтому обёртка при переключении (но не при первой сборке)
сама вызывает upstream-овский `autoResetPageIndex` — иначе грид на пятой странице оказался бы на
пустой странице (найдено ревью). Сброс гейтится upstream так же, как всегда: только при клиентской
пагинации, поэтому спящий засев `pageIndex` у грида без пагинации не трогается.

Флагом служит существующий `enableColumnFilters`, а не приватная опция: ядро и так пишет его при
выключенной фильтрации. Теперь он пишется на каждом вызове булевым значением
(`enableColumnFilters: hasColumnFiltering`), чтобы слияние опций не оставило `false` от
прежнего режима. Явный `true` совпадает с дефолтом TanStack, а пер-колоночный
`enableColumnFilter: false` работает по-прежнему.

Обёртка кешируется по слоту потребителя (`WeakMap`), а собранный набор — по набору потребителя,
так что `options.features` сохраняет идентичность между рендерами, пока набор не меняется.
Идентичность набора потребителя при этом не сохраняется: в `options.features` лежит копия с
обёрткой. Прецедент есть — `sorting.fns` уже вливается в копию набора.

Почему не другие варианты:

- **Только заглушка.** Не переключается на лету — см. выше.
- **`manualFiltering`, когда обе оси выключены, плюс заглушка, когда выключена только
  колоночная.** Флаг читается на каждом вызове, но второй случай остаётся устаревшим при
  переключении, а требование спеки — оба.
- **Обёртка, сбрасывающая memo по идентичности `options.columns`.** React пересобирает колонки
  на каждом рендере, и модель фильтров пересчитывалась бы на каждом рендере.
- **Убрать функцию у колонки** (upstream пропускает колонку без функции): просто опущенный
  `filterFn` берёт из дефолтного определения колонки `'auto'`, а он резолвится в настоящую
  функцию и фильтрует. Явный `filterFn: undefined` перекрывает дефолт, но `column_getFilterFn`
  ищет его как имя в `filterFns` и в development пишет «is not registered» на каждом вызове.
- **Не передавать засеянные `columnFilters` в состояние** — противоречит решению 4 и политике
  засевов.

Фасеты применяют фильтры других колонок через ту же функцию и тоже получают пропуск. Фасеты
нужны только UI фильтра, которого при выключенной фиче нет. Dev-проверка «`filterFns` не в наборе»
(`create-table-options.ts`, «named filter functions vs. the `filterFns` slot») уже стоит под
`hasColumnFiltering` и не задета.

### 4. Засев выключенной фичи остаётся в состоянии без эффекта на строки

Это отличается от infinite, где засеянный `pageIndex` принудительно становится 0. Там режим
**активен**, и `pageIndex` в нём бессмыслен. Выключенная фича — **спящее** состояние, которое
станет активным при включении, и засев автора к этому моменту должен быть на месте.
Политика засевов («это то, что написал автор, молча отбросить хуже») соблюдается: засев не
отбрасывается и не правится, а предупреждение (решение 5) говорит, что он пока ни на что не
влияет.

### 5. Предупреждения о засеве — по образцу `warnUnreachableSeed`

Одно dev-предупреждение на срез, только по `config.initialState` автора:

| Засев                        | Предупреждаем, когда не включены |
| ---------------------------- | -------------------------------- |
| `initialState.pagination`    | `pagination`                     |
| `initialState.columnFilters` | `filtering`                      |
| `initialState.grouping`      | `grouping`                       |
| `initialState.sorting`       | `sorting`                        |
| `initialState.globalFilter`  | `globalFiltering`                |
| `initialState.expanded`      | ни `expanding`, ни `grouping`    |
| `initialState.rowPinning`    | закрепление строк                |

Предупреждение читает засев автора, а не собранный `initialState`: ядро само пишет туда
`pagination: { pageIndex: 0, pageSize }` и пины колонок, и о них предупреждать не о чем. Для
`expanded` группировка считается достаточной, потому что раскрытие управляет группами.
Сообщения вырезаются из production-сборки, как и соседние (`IS_DEV`).

### 6. ARIA читает режим: infinite → включена ли пагинация → флаг

Порядок проверок в `hasPartialRowSet` / `hasTrustedRowTotal`:

```
infinite?                     -> как сейчас (hasNextPage / hasPreviousPage)
!grid.pagination.enabled      -> полный набор: partial = false, итог доверенный
manualPagination === true     -> сервер: как сейчас
иначе                         -> клиент: как сейчас
```

`grid.pagination.enabled` уже равен `isPagedPagination` (`use-data-grid.ts`) и ложен и для
выключенной пагинации, и для infinite. Поэтому infinite проверяется первым. Без этой правки
решение 1 дало бы каждому гриду без пагинации `aria-rowcount="-1"` и молчащий статус числа
строк, включая все демо на узких наборах, которые сейчас корректны. `aria-row-index.tsx`
выключается сам (`enabled={partialRowSet}`), `pagination.tsx` выходит раньше по `enabled`.

### 7. Changeset — minor для `data-grid-core` и `data-grid-react`

Типы не меняются, но меняются наблюдаемые значения: `options.manualPagination` у каждого грида
без клиентской пагинации, `getFilterFn()` колонок при выключенной `filtering`, видимые строки
у гридов, которые полагались на засев выключенной фичи. Прецедент `infinite-pagination-unsliced`
шёл как minor по тем же основаниям. Текст называет регрессию (0.7.0, #246) и перечисляет
наблюдаемые значения. Кит shadcn в changeset не входит (правило репозитория).

## Risks / Trade-offs

- [Чужой код читает `options.manualPagination` как «сервер»] → в репозитории это два места в
  `aria-state.ts`, оба переводятся на режим (решение 6). Потребителю это называет changeset.
- [Headless-читатель `column.getFilterFn()` при выключенной `filtering` видит заглушку] →
  читать функцию фильтра колонки, которую нельзя фильтровать, незачем. Пункт есть в changeset.
- [Пока пагинация выключена, `autoResetPageIndex` выключен вместе с ней (`!manualPagination`)]
  → смена данных или фильтров в это время не сбрасывает сохранённый `pageIndex`, и при включении
  он может указать за последнюю страницу, на пустую страницу. Это та же ситуация, что
  сегодня у deep link на страницу, которой больше нет, а не новый класс. Принято: спящее
  состояние остаётся нетронутым (решение 4). Сбрасывать его при каждом изменении данных значило
  бы терять засев автора на первой же загрузке.
- [Faceted-модели не обёрнуты и после включения `filtering` на лету могут до первого изменения
  фильтров считать фасеты по заглушке] → фасеты читает только UI фильтра; первое же изменение
  фильтра пересчитывает их. Принято, чтобы не оборачивать ещё три слота.
- [Обёртка подменяет слот потребителя] → `table.options.features.filteredRowModel` больше не та
  функция, что в наборе потребителя. Читать её незачем; пункт есть в changeset.
- [Заглушка `filterFn` выполняется на каждой строке для каждого засеянного фильтра] → только
  при засеве и выключенной фиче, одна константная функция. Измеримой цены нет.
- [Документация продолжает описывать старое поведение, не называя имён] → вторая проверка по
  смыслу («first page», «slice», «one set covers both modes», засев при выключенной фиче), как
  требует правило репозитория об удалении поведения.

## Migration Plan

Потребителю ничего делать не нужно. Наборы без лишних моделей работают как прежде. Обходные
пути — второй набор без `paginatedRowModel` для гридов без пагинации, явный
`pagination: { pageSize: Infinity }` — после релиза можно удалить. Откат — revert изменения:
формат состояния и данных он не затрагивает.
