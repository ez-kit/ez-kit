# Design

## Context

Мотивация — в proposal.md (Why). Что есть в коде сейчас:

- `buildColumnInvariants` (`core/src/column-state/column-state.ts`) строит
  `{ forcedStart, forcedEnd, alwaysVisible }` из итогового списка колонок, системные включительно.
  `enforceColumnInvariants` правит `columnPinning` и `columnVisibility` и возвращает ту же ссылку,
  если менять нечего. Обе функции внутренние: инварианты — локальная переменная внутри
  `createTableOptions`, наружу из core не экспортируются.
- Инварианты применяются к seed `initialState` (`create-table-options.ts`, `enforceColumnInvariants`
  поверх `mergePinningSeed`) и через `constrain` в `buildSliceHandler` для `onColumnPinningChange` /
  `onColumnVisibilityChange`. `onColumnOrderChange` идёт без `constrain`.
- Controlled `state` в `useDataGrid` нормализуется (`normalizeControlledState`, только `loading`) и
  публикуется через `table_publishExternalState` в base atoms, мимо обработчиков срезов, а значит, и
  мимо инвариантов. Подписка на стор отфильтровывает эхо через `isControlledEcho`: срез считается
  эхом, если в сторе лежит **та же ссылка**, что в controlled-значении.
- `extractState` / `useExtractedState` берут срезы через общий `pickState`.
  `useExtractedState` кеширует результат по ссылкам входных срезов (`sameList`).
- В TanStack `table-core@9.2.4` колонка, которой нет в `columnOrder`, дописывается **в конец**
  (`table_getOrderColumnsFn`), а id в `columnPinning` без колонки пропускаются
  (`table_getStartLeafColumns`). Регион закрепления и порядок внутри него берутся из
  `columnPinning`, но `moveColumn` / `dropColumn` считают индексы по `getAllLeafColumns()`, то есть
  по `columnOrder`.

Проверенные ADR: 0004 (логическое закрепление колонок) — словарь `start` / `end` сохраняется.
0007 (контракт компонентов) не затрагивается: `table.grid` — это `GridOptions`, а не
`FullGridComponents`. 0003 и 0014 не затрагиваются: новых фич и подпутей нет.

## Goals / Non-Goals

**Goals:**

- Одно место, где описаны инварианты колонок, и одна пара операций над ними, через которую проходят
  и входы state, и выход persist.
- Controlled `state` подчиняется тем же инвариантам, что любая другая запись.

**Non-Goals:**

- Убирать forced-колонки из `onChange`, `onStateChange`, `useDataGridState`, `table.store.state`.
  Тогда внутренний стор и публичные значения разошлись бы, а controlled-эхо потребовало бы связки
  `strip(enforce(x)) === x` по ссылке (обсуждалось и отклонено, см. Decisions).
- Публичный хелпер, которым потребитель сам чистит значения из `onChange`. Устаревшие и лишние id
  безвредны, а для чистого persist есть утилиты.
- Версионирование и миграция сохранённых значений: это по-прежнему зона потребителя.

## Decisions

### 1. `table.grid.columnState { enforce, strip }`, а не экспорт функций (Durable)

Core добавляет в `GridOptions` поле `columnState` с двумя методами, замкнутыми на инварианты этой
таблицы. React (`useDataGrid`, `pickState`) вызывает их через `table.grid`.

- Альтернатива b: экспортировать `enforceColumnInvariants`, `stripForcedColumns` и выставить
  `table.grid.columnInvariants`. Отклонена: API растёт на три имени, форма инвариантов становится
  публичной и фиксируется semver, а единственный их потребитель — пакеты этого репозитория.
- Методы замкнуты на таблицу, поэтому вызывающему не нужно знать, какие колонки forced.

### 2. Срез на выходе только в утилитах persist (Durable)

Публичный state делится на два канала. Утилиты persist (`extractState` / `useExtractedState`) дают
значение «что выбрал пользователь» без forced-колонок. Низкоуровневый канал (`onChange.*`,
`onStateChange`, селекторы, `table.store.state`) отражает стор как есть.

- Альтернатива: срезать во всех callbacks. Отклонена. (1) Селекторы читают внутренний стор, и правд
  стало бы две. (2) Controlled-петля: потребитель возвращает срезанное значение, `enforce` строит
  новый массив, `isControlledEcho` не узнаёт эхо, и уведомления идут по кругу. Чтобы этого не было,
  нужна связка ссылок `strip(enforce(x)) === x` через WeakMap — инфраструктура ради косметики.
- Утилиты persist односторонние: восстановление идёт через `initialState`, где работает `enforce`,
  поэтому петли нет и стабильность ссылок обеспечивает уже существующий кеш `useExtractedState`.

### 3. Критерий среза — forced, а не «системная»

`strip` убирает `forcedStart ∪ forcedEnd` из `columnPinning` / `columnOrder` и `alwaysVisible` из
`columnVisibility`. Системная колонка с `initialSide` или `pinning: false` сохраняется: её положение
выбрал пользователь, и `enforce` его не восстановит. По тому же критерию срезаются статически
закреплённые пользовательские колонки (`pinning: 'start'`): они тоже следуют из конфига.

- Альтернатива: срезать по списку системных id. Отклонена: потерялся бы выбор пользователя для
  `initialSide`, а статически закреплённые пользовательские колонки остались бы шумом.

### 4. `enforce` восстанавливает `columnOrder`: start-колонки в нём, end-колонок в нём нет

В непустом `columnOrder` `forcedStart` стоят в начале, в порядке объявления: недостающие
вставляются, стоящие не на краю переставляются. `forcedEnd` из порядка **убираются**. Пустой
порядок не трогается.

TanStack дописывает каждую колонку, которой нет в непустом порядке, в конец и в порядке объявления.
Поэтому start-колонку нужно перечислить, иначе она уедет в конец. А end-колонку перечислять нельзя:
системные колонки объявляются последними (`buildColumnList`), и только их отсутствие держит их
последними, в том числе после колонки, которой не было на момент сохранения порядка. Перечисленная
`__actions__` встала бы перед такой колонкой (нашлось на ревью: `columnOrder: ['c', 'a']` давал
`[__selection__, c, a, __actions__, b]`).

Без восстановления восстановленный `['age', 'name']` поставил бы `__selection__` в конец
`getAllLeafColumns()`. Рендер был бы прав (регион берётся из `columnPinning`), но `moveColumn` /
`dropColumn` и ARIA-индексы считали бы от другого порядка, чем до сохранения.

- Альтернатива: дополнять порядок всеми id колонок перед расстановкой краёв. Отклонена: инварианты
  не знают id колонок групп, а id TanStack не всегда совпадает с `accessorKey`.
- Пользовательская колонка со статическим `pinning: 'end'` тоже не хранится в порядке и встаёт среди
  неупомянутых колонок в позиции объявления. Её регион задаётся `columnPinning`.

`constrain` добавляется и в `onColumnOrderChange`, чтобы `table.setColumnOrder(['name'])` вёл себя
как восстановление. Из-за этого обработчик есть у каждого грида с фичей порядка, даже без
`onChange.columnOrdering`.

### 4a. Forced-колонки всегда на краю своей стороны (Durable)

`enforce` ставит forced-колонки на внешний край и в `columnPinning`, и в `columnOrder`, даже когда
вход уже содержит их в другом месте. Причина нашлась на тесте-свойстве `enforce(strip(s)) == s`:
TanStack `column.pin('end')` дописывает колонку **после** `__actions__`, так что до этого изменения
пользовательская колонка, закреплённая справа, вставала снаружи колонки действий. Это расходилось с
замыслом `mergePinningSeed` («`__actions__` stays at the end»), а сохранённое значение без forced-id
не могло бы сказать, с какой стороны от них стояла колонка.

- Альтернатива: оставить порядок, который дал TanStack, и ослабить гарантию круга до «та же
  сторона». Отклонена: после перезагрузки колонка, закреплённая справа, перескакивала бы левее
  `__actions__`.
- Видимое следствие: колонка, закреплённая справа, теперь встаёт левее колонки действий. Это
  исправление, и оно описывается в changeset.

### 5. Controlled publish: `enforce` с кешем по ссылке входа

В `useDataGrid` controlled-значение после `normalizeControlledState` проходит через
`table.grid.columnState.enforce`. Результат для каждого из трёх срезов кешируется по ссылке входного
среза: пока потребитель передаёт ту же ссылку, публикуется тот же исправленный массив. В эхо-фильтр
передаётся **исправленное** значение, потому что именно оно лежит в сторе.

Сценарий из спеки: потребитель передал `{ start: [] }` → в сторе `[__selection__]`, и то же
значение лежит в `controlledStateRef` → эхо-фильтр видит в сторе ровно то, что отдал потребитель
(после исправления) → `onStateChange` молчит. Это тот же приём, что у нормализации `loading`:
исправление входа — не изменение. Срез потребителя может остаться `{ start: [] }`, и это нормально:
следующий жест пользователя придёт в `onStateChange` уже с системными id.

- Альтернатива: один раз сообщить исправленное значение. Отклонена: потребитель, который сохраняет
  `onStateChange`, получил бы запись без участия пользователя, а эхо-фильтр пришлось бы сравнивать с
  сырым значением, а не с тем, что лежит в сторе.

Кеш ключуется по паре «ссылка входного среза + `columnState.signature`». Объект `columnState`
пересобирается на каждом рендере вместе с опциями, поэтому его идентичность ничего не говорит.
А конфиг может добавить или убрать forced-колонку, пока потребитель передаёт ту же ссылку. Тот же
ключ входит в кеш `useExtractedState` (нашлось на ревью).

`enforce` вызывается внутри `useDataGrid` и не меняет порядок фаз: seed по-прежнему публикуется во
время первого рендера, дальше — в layout effect.

### 6. `ExtractableTable` получает опциональный `grid`

`Pick<CoreDataTable, 'store'> & { draft?; grid?: { columnState? } }`. Голый `createTable` и
`useDataGrid` подходят оба. Без `grid` значение отдаётся как раньше: это держит контракт «принимает
что угодно со `store`».

## Risks / Trade-offs

- [Значение `extractState` меняется для существующих потребителей: из него пропадают системные id]
  → Восстановление старых и новых значений даёт один и тот же вид (спека, «Ранее сохранённые
  значения»). Минорная версия и абзац в changeset. Код, который ищет `__selection__` в сохранённом
  значении, по контракту утилит никогда не был нужен.
- [`enforce(strip(s)) == s` верно, только если forced-колонки стоят на краях] → Решение 4a делает это
  верным для любого состояния в сторе: `enforce` стоит на каждом входе. Фиксируется тестом-свойством
  на состояниях, полученных через `pin`, `moveColumn`, `dropColumn` и `setColumnPinning`.
- [Controlled-петля, если кеш ссылок сломается] → Тест, в котором потребитель зеркалит
  `onStateChange` в `useState`, считает вызовы и ререндеры.
- [`constrain` на `onColumnOrderChange` задевает горячий путь перетаскивания колонок] → `enforce` для
  порядка, содержащего все id, возвращает ту же ссылку после одного прохода по `forced*`. Это
  несколько id, а не все колонки.

## Migration Plan

Миграции нет: старые значения восстанавливаются как раньше. Откат — revert изменения. Перед
архивированием change решения 1, 2 и 4a переносятся в новый ADR
`openspec/decisions/0015-persist-excludes-config-derived-column-state.md`, а одноабзацное правило со
ссылкой на него добавляется в AGENTS.md (раздел «Settled data-grid API decisions»).
