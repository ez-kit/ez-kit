# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/form-steps/spec.md`. Исходный дизайн — D18 в
`specs/009-form-composition/design.md`. Этот change реализует его с решениями, принятыми поверх M2.

Что уже есть в `packages/form/react/react/src`:

- **Члены инстанса** собираются в `create-form.tsx` через `Object.assign(form, native,
{ FormGroup, setServerErrors }, fieldComponents, components)`. `form.Submit` и `form.Array`
  строятся в `build-field-components.tsx`. `Steps` / `Step` перечислены вручную в
  `reserved-keys.ts` с пометкой «stage 6».
- **Все связанные поля проходят через одну точку** — `createFieldBinding` в `field-binding.tsx`,
  то есть `form.AppField`. Это `form.X`, `group.X`, поля записей `form.ArrayField` и `form.Field`.
  `form.NativeField` идёт мимо неё.
- **Группы.** Нативные группы проходят через `useFormGroup` (`form-group.tsx`), map-группы — через
  `createMapGroup` (`map-group.ts`). Сабмит-проход групп — `validateGroups(form, accept)`,
  собственные ошибки map-групп — `hasOwnErrorsIn(form, accept)`, оба в `group-registry.ts`.
- **Движок проходов map-группы** (`map-group.ts`) уже умеет то, что нужно валидаторам шага:
  - слоты `onMount` / `onChange` / `onBlur` / `onSubmit` и их async-варианты;
  - async только после sync, debounce, отмена устаревших проходов;
  - раскладка ошибок по путям и ошибки без пути в `errorMap` формы под своим ключом, который
    `formErrors` пропускает;
  - подписка на изменения и blur своих путей, сброс при `reset`.
- **Схемный визард** (`schema/form-wizard.tsx`) проверяет шаг так: помечает поля тронутыми, затем
  `form.validate('submit', { filterFieldNames })`, и выносит вердикт по ошибкам полей шага. С
  `revalidateLogic` причина `'submit'` запускает и `onDynamic`.
- **Показ ошибок:** `shownFieldErrors` показывает их после касания поля или после попытки сабмита.
  Поэтому ошибки схемы на полях будущих шагов не видны, пока не было сабмита.
- **Фокус:** `focusFirstFieldWithErrors(form, within)`.

## Goals / Non-Goals

**Goals:**

- Headless-поток без единого элемента разметки от пакета: всё рисует приложение или кит.
- Точечные подписки: переход перерисовывает два шага и два элемента степпера.
- Один механизм валидации для map-групп и шагов, без второй копии движка.

**Non-Goals:**

- Схемный визард и `Wizard` кита — отдельная задача. Их код в этом change не меняется.
- Вёрстка степпера, анимации переходов, синхронизация с URL сверх `step` / `onStepChange`.
- `{cond && <form.Step/>}`: не поддерживается, в доке сказано, что условный шаг задаётся через
  `when`.

## Decisions

### Стор шагов — TanStack Store, тот же, что под формой

На каждый `form.Steps` создаётся один стор — `createStore` из `@tanstack/react-store`, который
`@tanstack/react-form` и так ставит в дерево. Значение контекста — сам стор, его ссылка стабильна.
Чтение идёт через `useSteps(selector, equal)` поверх `useSelector(store, selector, { compare })`.
`useSelector` построен на `useSyncExternalStoreWithSelector`, поэтому селектор, возвращающий
новый объект, не вызывает бесконечный цикл: при равенстве по `compare` (по умолчанию `Object.is`)
возвращается прежний результат. Первая версия держала свой стор на `useSyncExternalStore` — он
повторял то, что уже есть в зависимостях, и заменён.

Состояние:

- `order` — имена в порядке регистрации;
- `names` — видимые имена, новая ссылка только при смене набора;
- `current`;
- `visited` и `passed` — множества имён;
- `fields` — для каждого шага запомненный список полей;
- `groups` — для каждого шага его группы;
- `validating`.

Альтернатива — `Store` из `@tanstack/store`. Он есть в дереве транзитивно, но под pnpm его
пришлось бы объявить зависимостью, а `@tanstack/react-store` в пакете не используется. Стор на
30 строк дешевле новой зависимости и закрывает всё, что здесь нужно.

### Регистрация шагов, полей и групп

- **Шаги.** `form.Step` регистрирует себя в `useLayoutEffect`. У соседей эти эффекты идут в
  порядке дерева, поэтому порядок шагов совпадает с порядком в JSX. `when` вычисляется селектором
  по значениям формы, и от него зависят `names`. Начальное состояние берётся из `initial`, так что
  на сервере `form.Step` с этим именем рендерит детей ещё до регистрации.
- **Поля.** `createFieldBinding` читает `StepContext` (имя шага или ничего) и в layout-эффекте
  добавляет полное имя поля в `fields[step]`. Cleanup убирает имя, **только если шаг всё ещё
  текущий**: так поле, которое пропало внутри живого шага, уходит из списка, а поле, размонтированное
  потому что шаг перестал быть текущим, остаётся. Когда шаг снова становится текущим, его список
  собирается заново при монтировании. Вне `form.Step` контекста нет, и регистрация ничего не делает.
- **Группы.** `useFormGroup` и `createMapGroup` регистрируют в шаге свой `ValidatedGroup.owner`.
  Нативная группа добавляет ещё и своё имя в `fields[step]`: её мета лежит в `fieldMeta[name]`, и
  её ошибки без пути должны участвовать в вердикте.

### Валидаторы шага — на обобщённом движке map-группы

Из `createMapGroup` выделяется `createValidatedScope({ form, errorKey, validators, value, knows,
toAbsolute, watches })`. Map-группа становится его клиентом с прежними параметрами. Её тесты
обязаны остаться зелёными без правок — это и есть проверка рефакторинга.

Шаг — второй клиент:

- `value` — значения всей формы;
- `knows` — имя зарегистрировано в шаге;
- `toAbsolute` — тождество;
- `watches` — поля шага;
- `errorKey` — `onStep:<name>`.

Ошибки на путях вне шага отбрасываются (поведение D18). Ошибки без пути — это `stepErrors`.
Фильтр `formErrors` в `fields/submit.tsx`, который сейчас пропускает `onGroup:`, пропускает и
`onStep:`.

Скоуп шага подключается, пока шаг видим. Шаг, пропущенный по `when`, отключается и очищает свой
результат. В реестр сабмита формы скоуп шага **не** регистрируется: сабмит формы его не запускает
(M2). Его ошибки, уже записанные в мету, учитываются в `canSubmit` по обычным правилам TanStack.

Альтернатива — писать проходы шага заново. Получилась бы вторая копия логики отмены, debounce и
раскладки, которая уже дважды исправлялась в map-группе (T6-1, T6-2).

### `goNext` — сабмит шага

1. Если идёт проверка (`validating`), ничего не делать. Шаг отмечается посещённым.
2. Поля шага помечаются тронутыми (как в схемном визарде).
3. Синхронный слой:
   - `form.validate('submit', { filterFieldNames: inStep })` — поля и валидаторы формы, ограниченные
     полями шага;
   - `validateGroups(form, inStepGroup)` — группы шага;
   - сабмит-проход скоупа шага.

   Проход скоупа сам запускает async-слоты только после чистых sync-слотов. Async-валидаторы полей
   и формы — забота TanStack внутри `validate`.
   `form.validate` вызывается с `dontUpdateFormErrorMap: true`. Без этого TanStack записывает в
   `errorMap` формы весь результат схемы, включая поля шагов впереди. Со схемой на `onDynamic` до
   первого сабмита эту запись никто не пересчитывает, и кнопка сабмита на последнем шаге остаётся
   заблокированной (найдено e2e, закреплено тестом «leaves no stale verdict on the steps ahead»).
   Нынешний схемный визард этого не замечает: его схема на `onChange` пересчитывается на каждом
   изменении.

4. Вердикт:
   - в `fields[step]` нет ни одной меты с ошибками;
   - у шага нет ошибок без пути;
   - `hasOwnErrorsIn(form, inStepGroup)` ложно.
5. Прошло — шаг попадает в `passed`, текущим становится следующий видимый. Не прошло — шаг убирается
   из `passed`, фокус на первой ошибке внутри шага.

`goTo(target)`:

- позади — переход без проверки;
- впереди при `linear` — сначала `goNext`-проверка текущего, затем каждый шаг между текущим и целью
  должен быть в `passed` и не иметь ошибок в `fields[step]` (селектор по мете);
- при `linear={false}` — переход без проверки.

`goBack` — без проверки. Пропущенные по `when` шаги навигация обходит.

`passed` хранится отдельно от `visited`. `visited` означает «пытался уйти», и на нём нельзя
строить достижимость — это ровно дыра нынешнего схемного визарда (`isReachable`).

### `invalid`, `stepErrors`, `formErrors`

- `invalid(step)` — производное: `visited.has(step)` и у одного из полей `fields[step]` есть ошибки.
  В сторе не хранится.
- `stepErrors` — `formatOwnErrors` от собственных ошибок скоупа текущего шага.
- `formErrors` — те же сообщения, что `form.Submit` отдаёт под этим именем. Источник один, так что
  они не расходятся.

### Текущий шаг исчез

Это делает эффект на `names`: если `current` нет в `names`, текущим становится ближайший видимый
шаг перед ним по `order`, а без такого — первый видимый. В контролируемом режиме вызывается только
`onStepChange`.

### Сброс формы

Шаги подписываются на те же хуки сброса, что и map-группы (`onResetOf`). При `reset` `visited` и
`passed` очищаются, текущим становится `initial` или первый видимый шаг.

### Типы и члены инстанса

- `form.Steps` — компонент со статическими частями `List`, `Item`, `Controls`, `Subscribe`. Они
  собираются одним `/* @__PURE__ */ Object.assign` с плоским литералом, как у `DataGrid`, чтобы
  импорт одной части не тянул остальные.
- `form.Step` — компонент.
- `useStep` и `useSteps` экспортируются из пакета и китов. Они читают ближайший `form.Steps`, вне
  него бросают именованную ошибку.
- Валидаторы `form.Step` типизированы по данным формы, `when` — `(values: TFormData) => boolean`.
- Ручной список `Steps` / `Step` в `reserved-keys.ts` заменяется ключами реальных членов.

### Документация

- Новая страница `form/steps.mdx` с пятью примерами:
  - базовый поток;
  - условный шаг с union и `schema.parse` в `onSubmit`;
  - блоки (`withFieldGroup`, `form.FormGroup`) внутри шага;
  - `linear={false}`;
  - свой степпер на `Steps.Item`.
- Таблицы опций классифицируются в `page-type-map.ts`.
- Без внутренних комментариев в примерах.
- D18 правится под решения: нет `stripSkippedSteps`, нет `verifyCard` на шаге, проп `linear`,
  состав `stepErrors`, добавлен `formErrors`, правило «текущий шаг исчез».

### Исправления по ревью

- **Ход проверки и поколения.** У контроллера есть счётчик поколений: его увеличивают каждый переход и
  каждый сброс. Проверка шага переводит поток, только если за время проверки поколение не сменилось.
  Цель (`neighbour`, `reachable`) вычисляется после проверки, а не до неё. Отменённый проход скоупа
  (`run` вернул `false`) не засчитывается как пройденный.
- **Падение проверки.** Исключение в проверке шага перехватывается: шаг считается не прошедшим, ошибка
  выводится через `console.error` с именем шага. Отклонённый промис наружу не уходит.
- **Контролируемый режим.** Каждый переход, о котором попросил пользователь, вызывает `onStepChange`.
  Дедупликация осталась только у автоматических переходов из `refresh`, которые срабатывают на каждое
  изменение стора; `syncStep` её сбрасывает.
- **StrictMode.** Cleanup `connect` возвращает `registering = true`, а снятие шага с регистрации больше
  не переключает текущий шаг. Двойной монтаж не теряет `initial`.
- **Списки шага.** При входе на шаг сбрасываются и его поля, и его группы. Поля считаются по числу
  смонтированных привязок, так что два биндинга одного имени не снимают друг друга.
  `useStepGroup` перерегистрирует группу, когда меняется её владелец, а в dev предупреждает, если
  владельца нет.
- **Скоуп шага** создаётся только при наличии `validators`, читает их через функцию (а не Proxy) и
  перезапускает проход `onChange` при изменении любого значения формы: валидатор шага видит всю форму.
- **`onMount` шага** запускается при каждом входе шага на экран, после эффектов его детей, когда поля
  уже зарегистрированы. Так ведёт себя `FormGroup` в мастере из документации TanStack (группа
  монтируется вместе с шагом) и наша map-группа (`Mount` при монтировании блока). Скоуп при этом живёт,
  пока шаг подходит: триггеры `onChange` и `onBlur` и ошибки шага не зависят от экрана.
- **React 18.** Все layout-эффекты шагов — `useIsomorphicLayoutEffect` из `@tanstack/react-form`:
  через `useStepField` их вызывает каждое связанное поле, и обычный `useLayoutEffect` дал бы
  предупреждение React 18 на каждое поле при SSR. Это закрепляет `steps-ssr.test.tsx` в окружении `node`
  (в jsdom есть `window`, и проверка там бессмысленна).
- **Предупреждения в dev:** два шага с одним именем; шаг, смонтированный после потока (он встаёт в
  конец списка).
- **Async-валидаторы полей и формы** на «Далее» следуют правилу TanStack для своего уровня (пропускаются,
  если синхронная проверка того же поля или формы нашла ошибку). Строгий гейт «async только после всех
  sync» действует для валидаторов шага: `scope.run(..., { async: syncClean })`.

## Risks / Trade-offs

- **[Рефакторинг движка map-группы может сломать её поведение]** → Тесты map-группы (`map-group.test.tsx`,
  T6-1, T6-2, R82, R83) прогоняются без правок до того, как подключается шаг.
- **[Код шагов попадает в каждую форму из `createForm`, даже без шагов]** → Принято сознательно,
  ради типизации членов инстанса, как у `form.Array`. Измерено при реализации:
  - `form-react` целиком вырос с 14,53 до 16,93 кБ brotli, бюджет поднят с 17 до 19,5 кБ (размер +
    15%);
  - форма с одним полем стала 0,49 корня shadcn и 0,54 корня HeroUI.

  Поэтому порог в `tree-shaking.test.ts` поднят с половины до 0,6 (константа `ONE_FIELD_SHARE`).
  Отсутствие календаря, комбобокса и схемного рендерера проверяется отдельно, как и раньше.
  Альтернатива — `Steps` / `Step` как отдельный импорт из кита — была рассмотрена и отклонена.

- **[Регистрация в `createFieldBinding` стоит каждому полю один эффект, даже вне шагов]** → Вне
  `form.Step` контекст пуст, и эффект возвращается сразу. Бюджет `size-limit` и
  `tree-shaking.test.ts` проверяются в задаче.
- **[Под `StrictMode` двойной монтаж убирает и возвращает поля в списке шага]** → Cleanup убирает
  имя только у текущего шага, а повторный монтаж возвращает его. Отдельный тест под `StrictMode`.
- **[Поле, отрисованное через `form.NativeField`, шаг не видит]** → Так задумано в D18. В доке
  сказано писать `form.X` или `form.Field`.
- **[Ошибки схемы на полях шага, пропущенного по `when`, блокируют сабмит]** → Решается в схеме
  приложения (union). Рецепт — на странице шагов.
- **[Под `StrictMode` в dev поле, смонтированное после неудачного сабмита, теряет ошибки схемы до
  следующего изменения]** → Это поведение TanStack (см. архив `form-schema-source-of-truth`). e2e
  не опираются на него.

## Migration Plan

Только добавление. Публичные API не меняются, кроме того что `Steps` / `Step` становятся реальными
членами вместо зарезервированных имён. Нужен minor-changeset для трёх пакетов. Откат — убрать
члены и модуль, движок map-группы при этом остаётся обобщённым.
