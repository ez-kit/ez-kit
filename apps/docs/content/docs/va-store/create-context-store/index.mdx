Wraps a Valtio proxy in React context. Each `<Provider>` creates its own proxy instance (via `useRef`), so the same factory can power multiple isolated subtrees. There are no selectors — `useSnapshot` tracks the properties you actually read.

This page is the guide — what the pieces are for and how they behave. Every signature, prop and option is listed on [API reference](./create-context-store/api).

## Basic usage

Write the store as a plain Valtio proxy, hand the factory to `createContextStore`, and wrap the subtree in the returned `Provider`.

<LivePreview
	path='va-store/counter'
	title='Counter'
/>

The example above keeps its actions on the proxy (the idiomatic Valtio pattern), so components only ever read from `useSnapshot()`. You can also mutate the proxy directly — see [reading and writing](#reading-and-writing) below.

The factory is seeded through a single `defaultValue` envelope — type its parameter with the exported `ContextStoreInit<T>` helper. `defaultValue` is required on the `Provider` when your seed has required fields, and optional otherwise.

```tsx
<counterStore.Provider defaultValue={{ initialCount: 10 }}>
	<App />
</counterStore.Provider>
```

The factory runs **once per mount** (held in a `useRef`), so changing `defaultValue` after the first render won't recreate the proxy.

## Reading and writing

Four ways in, for four different jobs. The rule underneath all of them: **read from snapshots, mutate the source proxy.**

| You want                                           | Use           |
| -------------------------------------------------- | ------------- |
| state to render, re-render when read fields change | `useSnapshot` |
| the raw proxy to write to, without subscribing     | `useStore`    |
| both, inside JSX                                   | `Subscribe`   |
| to write from a subtree that renders nothing of it | `Store`       |

```tsx
const snap = counterStore.useSnapshot()   // read
const state = counterStore.useStore()     // write: state.count += 1

<counterStore.Subscribe>{({ snap, store }) => <button onClick={() => (store.count += 1)}>{snap.count}</button>}</counterStore.Subscribe>

<counterStore.Store>{(store) => <button onClick={() => (store.count += 1)}>increment</button>}</counterStore.Store>
```

There is no selector to get right here: Valtio tracks the properties a component actually reads off the snapshot, so a component that renders `snap.count` never re-renders when `snap.label` changes.

<Callout type='warn'>
	`useStore()` is the **raw handle**, not a read. Reading state is `useSnapshot()` — the same split as
	[`@ez-kit/zu-store`](../zu-store/create-context-store), where the raw handle is also `useStore()` and reads go through
	`useSelector()`. Mutate the proxy in event handlers and effects, not during render.
</Callout>

`Subscribe` subscribes, `Store` does not — that is the whole difference between the two render props. Reach for `Store` when a subtree writes but renders nothing from the store, so a counter ticking elsewhere no longer drags it through a re-render.

<Callout type='warn'>
	**Breaking change.** `useContextStore()` has been renamed to `useStore()`. Across every `@ez-kit` store package
	`useStore()` now means the same thing — the raw handle, no subscription — while reading keeps a manager-specific name:
	`useSnapshot()` here, `useSelector()` in [`@ez-kit/zu-store`](../zu-store/create-context-store). Rename
	`store.useContextStore()` → `store.useStore()`; reads through `useSnapshot()` are unaffected.
</Callout>

## Controlled fields

By default a store is fully self-contained: `defaultValue` seeds it and nothing outside can reach in again. The `value` prop opens exactly as much of that up as you ask for — **the controlled fields are precisely the keys present in `value`**, nothing more.

<LivePreview
	path='va-store/controlled'
	title='Mirror and fully controlled fields side by side'
/>

### `defaultValue` vs `value`

They answer different questions and are meant to be used together.

|                     | `defaultValue`                    | `value`                                |
| ------------------- | --------------------------------- | -------------------------------------- |
| Question it answers | "what should this be built from?" | "what is this equal to right now?"     |
| Owner               | the store                         | the parent                             |
| Applied             | once, at creation                 | at creation, then on every real change |
| Scope               | whatever the factory does with it | exactly the keys listed                |

For a key present in both, `value` wins on mount. Keys absent from `value` still seed from `defaultValue` and then live their own life:

```tsx
<store.Provider
	defaultValue={{ count: 1, label: 'boot' }}
	value={{ count: 99 }}
>
	{/* count === 99 (value won), label === 'boot' (seeded, uncontrolled) */}
</store.Provider>
```

### Mode 1 — a mirror

`value` alone is a **mirror**: the field flows in from outside and nothing inside the store writes it. This is the right shape for a theme, a locale, a `userId`, server data from react-query, or a router param.

```tsx
<store.Provider
	defaultValue={{}}
	value={{ theme, userId }}
>
	<App />
</store.Provider>
```

### Mode 2 — two-way control

`value` **plus** `onValueChange` is full two-way control: children mutate the proxy, the callback hands the changed slice up, and the parent feeds a new `value` back down.

```tsx
const handleValueChange = useCallback((next: Partial<State>) => {
	if (next.count !== undefined) setCount(next.count)
}, [])

<store.Provider
	defaultValue={{}}
	value={{ count }}
	onValueChange={handleValueChange}
>
	<App />
</store.Provider>
```

### Choosing between them

The deciding question is simply: **does anything inside the store write this field?** If it does and you did not pass `onValueChange`, the mutation still lands — the store just drifts away from `value` until the prop next changes, at which point it is overwritten. That is deliberate, not a bug, but it is rarely what you want.

<Callout type='warn'>
	`onValueChange` receives **only the controlled keys that actually changed**, not the whole state and not the whole
	`value`. Writes the Provider itself just pushed down from `value` are not echoed back. Object-typed fields are emitted
	from the **snapshot**, never the live proxy — a parent never gets a mutable handle that could write past the
	Provider's own write path.
</Callout>

The payload is built by **key presence**, so a field that legitimately changed _to_ `undefined` or `null` arrives as a present key. The `next.count !== undefined` check above is fine for a non-nullable `count`; for a nullable controlled field, test presence instead:

```ts
if ('selectedId' in next) setSelectedId(next.selectedId)
```

### This is not `<input value>`

A controlled DOM input reasserts its `value` on every render. This Provider syncs when the **`value` prop actually changes**, per key — not on every render.

The difference matters. "The prop always wins" would clobber any local mutation on the very next parent render, which would make the mirror-only mode useless and turn every unrelated parent re-render into a store reset. Syncing on change instead lets a local write to a controlled field survive until the parent genuinely says otherwise.

Passing an inline object literal (`value={{ count }}`) is therefore fine: the identity is fresh every render, but the Provider compares **key by key**, so an unchanged `count` writes nothing.

## Class-based stores

Valtio stores are often classes. Controlled fields work with them, with a few sharp edges worth knowing.

**Private fields are not controllable, and that is fine.** TypeScript's `private` members are excluded from `keyof`, so they never appear in `Partial<TState>`. You cannot list them in `value`, and the type does not break because of it — encapsulation survives contact with the feature.

**Accessor setters just work.** Because the sync writes through `Object.assign` on the proxy, a `set` accessor is invoked automatically. You do **not** need [`controlled.set`](./create-context-store/api#the-controlled-option) for it:

```ts
class UsersStore {
	private internal: readonly string[] = []

	get users(): readonly string[] {
		return this.internal
	}

	set users(next: readonly string[]) {
		this.internal = next // runs on every sync from `value`
	}
}
```

`controlled.set` is for the other shape — stores whose writes go through a **method** rather than an accessor:

```ts
class UsersStore {
	users: readonly string[] = []

	setUsers(next: readonly string[]): void {
		this.users = next
	}
}

const store = createContextStore(() => proxy(new UsersStore()), {
	controlled: { users: { set: (s, next) => s.setUsers(next) } },
})
```

<Callout type='warn'>
	**Getter-only properties are a silent trap.** A property with a getter and no setter still appears in `keyof`, so
	listing it in `value` **type-checks cleanly** — and then the write is silently discarded at runtime. Nothing throws
	and nothing warns; the field simply never changes. Derived values belong in the store, not in `value`.
</Callout>

<Callout type='error'>
	**Do not use `#private` fields in a Valtio store class.** This is a Valtio-wide constraint rather than anything to do
	with controlled fields: methods and getters run with `this` bound to the proxy, which is not the class instance that
	owns the private slot, so any access to `this.#field` throws `TypeError: Cannot read private member #field from an
	object whose class did not declare it`. Use TypeScript's `private` instead — it gives you the same compile-time
	encapsulation and keeps the field a plain own property the proxy can carry.
</Callout>

## Traps worth knowing

### Deriving `value` on the fly

This is the single most common one:

```tsx
<store.Provider value={{ users: transform(dto) }}>
```

`transform(dto)` returns a **new reference every render**, so the default `Object.is` sees a change every time the parent renders and writes to the proxy on every one of them.

The fix is a per-field comparator, declared once via the [`controlled` option](./create-context-store/api#the-controlled-option). `shallowEqual` is re-exported from this package for exactly this:

```ts
import { createContextStore, shallowEqual } from '@ez-kit/va-store'

const store = createContextStore(createMyStore, {
	controlled: { users: { equals: shallowEqual } },
})
```

The architectural alternative is worth considering too: keep the **raw** source in the controlled field and derive `users` inside the store. Then the controlled value is a stable reference from the server and there is nothing to compare deeply.

### Callbacks in `value`

Passing a callback through `value` is supported on purpose. A callback handed in via `defaultValue` is captured on the first render and keeps that first render's closure forever — so a `handleSubmit` in a multi-step form will read stale props by the time it fires. Routing it through `value` keeps it fresh.

The catch: **memoise it**, or a new function identity on every parent render will look like a real change and sync on every render.

```tsx
const handleSubmit = useCallback(() => {
	submit(step, formData)
}, [step, formData])

<store.Provider
	defaultValue={{}}
	value={{ handleSubmit }}
>
```

### The merge is shallow

`value` replaces each controlled key **wholesale**. It does not merge into it.

```tsx
// This replaces `filters` entirely — a previously set `filters.sort` is gone.
<store.Provider value={{ filters: { search: 'abc' } }}>
```

Two Valtio specifics follow from that:

- The replacement object is written with `Object.assign` onto the proxy, so **Valtio wraps it in its own proxy for you**. You do not need to call `proxy()` on the nested value yourself.
- A reference to the **old** nested object captured earlier is now orphaned. It is still a live proxy, but it is no longer attached to the store, so writing to it changes nothing that anyone renders.

```ts
const staleFilters = store.filters // captured before the sync
// …value pushes a new `filters` down…
staleFilters.search = 'xyz' // writes to an orphan — the store is unaffected
```

### Removing a key from `value`

A key that disappears from `value` simply stops being controlled. It keeps whatever value it last had — **there is no revert to `defaultValue`**.

"Disappears" means the key is genuinely absent. `value={{ count: undefined }}` still **controls** `count` — the key is present, so it is written, and `count` becomes `undefined`. Drop the key rather than blanking it.

### Consuming outside a `Provider`

Using `useSnapshot`, `useStore`, `Subscribe`, or `Store` outside a `Provider` throws:

```
Error: Missing Provider for createContextStore
```

This is deliberate — there is no implicit module-level fallback, because the whole point of `createContextStore` is per-tree isolation. Wrap the consuming subtree in a `Provider`.
