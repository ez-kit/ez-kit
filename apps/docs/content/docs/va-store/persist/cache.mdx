title: Cached stores
description: One store that is BOTH cached and persisted — kept alive across unmount/remount AND mirrored to the URL or storage, under a single StoreProvider.
---

`withPersist` attaches its capability to the proxy itself, inside the factory — so it composes with [`createCachedStore`](../cache) exactly the way it composes with `createContextStore`: call it inside the factory function you hand to `createCachedStore`. A single store can be **both** kept alive in the cache **and** synced to the URL or storage — composed, not bolted together.

A cache-hit returns the same already-bound proxy, so its persist binding (and any in-progress edits) survive a remount within `gcTime` — the substrate is never re-read on the way back.

## Wiring it up

Two pieces: a cached store group whose factory wraps the proxy in `withPersist`, and a single `StoreProvider` that mounts **both** the persist engines and the cache.

```tsx
import { createStoreCache, pipe, StoreProvider } from '@ez-kit/va-store'
import { withPersist } from '@ez-kit/va-store/persist'
import { localStorageAdapter } from '@ez-kit/va-store/persist/storage'
import { reactRouterAdapter } from '@ez-kit/va-store/persist/url/react-router'
import { urlField } from '@ez-kit/va-store/persist/url'
import { proxy } from 'valtio'

type FiltersState = { q: string; page: number }

// An isolated cache, threaded into the StoreProvider below.
const cache = createStoreCache()

// Cached AND persisted: the cache keeps the proxy alive; `withPersist` mirrors its fields to the URL.
const filtersStore = cache.createCachedStore<FiltersState>(
	() =>
		pipe(
			proxy<FiltersState>({ q: '', page: 1 }),
			withPersist({
				fields: (field) => [field((s) => s.q, urlField()), field((s) => s.page, urlField())],
			}),
		),
	{ name: 'filters' },
)

// One StoreProvider mounts the persist engines (`persist`) and the cache (`cache`) at once.
function App({ children }: { children: React.ReactNode }) {
	return (
		<StoreProvider
			persist={[reactRouterAdapter, localStorageAdapter()]}
			cache={cache}
		>
			{children}
		</StoreProvider>
	)
}

function FiltersPanel() {
	return (
		<filtersStore.Provider id='main'>
			<Controls />
		</filtersStore.Provider>
	)
}
```

`StoreProvider` composes the two layers in the right order — the persist engines outermost, the cache inside — so a cached store's `withPersist` capability always resolves the engines published above it. Omit either prop to skip that layer: no `persist` → no engines; no `cache` → no cache boundary (a plain `StoreProvider persist={[…]}` is the modern replacement for a bare `PersistProvider`).

<Callout type="info">
	A non-cached `createContextStore(() => pipe(proxy(…), withPersist()))` is request-scoped — a fresh proxy per
	`Provider` mount, persisted but not kept alive. Add the cache only when the store should outlive its
	`Provider`. See [createCachedStore](../cache) for the keep-alive lifecycle.
</Callout>

## First-present-wins still holds

When a cached, dual-source store is first created, the same [first-present-wins on cold start](./combined#first-present-wins-on-cold-start) rule applies — a shared `?q=` link beats a restored storage value. On a cache-remount the proxy already carries its hydrated state, so no source re-seeds; the kept-alive value wins, exactly as keep-alive intends.

That does **not** mean a cached store is cut off from its source while nothing renders it. The plugin's lifetime is the cache entry's, not the `Provider`'s, so the binding stays live between mounts: an external change — the back button, another tab — lands on the cached proxy even with no `Provider` mounted, and the returning screen renders it. What never happens on the way back is a re-seed that would discard local, unpersisted state.
