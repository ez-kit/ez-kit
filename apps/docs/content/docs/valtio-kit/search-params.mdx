# Search params sync

Mirror a Valtio store into the URL's query string and back, in both directions. Mutating the store updates the URL; navigating (deep link, Back/forward, an external write) updates the store. The proxy stays **synchronous and snappy** — the URL is a throttled, rehydratable projection of it.

```bash
pnpm add @ez-kit/valtio-kit valtio
```

Router and validator integrations are optional peers — install only what you use (`react-router`, `next`, `zod`, `qs`).

## Mental model

Valtio is the **source of truth**; the URL is a **mirror**.

- **proxy → URL**: a `subscribe` watches the store; changed fields are coalesced into one navigation per tick (throttled, `replace` by default).
- **URL → proxy**: the adapter's reactive read pushes external URL changes back into the store, writing only the diff — pulls never write the URL, so Back/forward and third-party writes are safe.
- **Identity-preserving writes**: fields are addressed by **path** (`filters.price.min`). A URL pull assigns only the **leaf** — nested objects, class instances, and computed getters keep their identity. The engine never replaces a whole subtree.
- **Loop breaking**: each direction writes only when the value differs in a normalized form. Parsers carry a round-trip contract so the feedback loop terminates.

A single coordinator — `StoreSearchParamsProvider` — is the only component that reads and writes the URL. It connects every store, merges their owned keys, and preserves foreign keys it doesn't own.

## Two ways to declare fields

You bring your own proxy and declare which fields sync. There are two fronts on one engine:

| Front | You write | Best for |
| --- | --- | --- |
| [Decorators](#decorators-class-stores) — `@searchParam` + `withSearchParams` | classes | entity models, composition, inheritance |
| [Accessor](#accessor-plain-proxies) — `field()` + `withSearchParamsFields` | plain `proxy({…})` | quick stores; no build-time decorator support |

Both produce the same path-based descriptors and feed the same engine, so layouts, history, adapters, and SSR behave identically. For request-scoped SSR, wrap either in [`createSearchParamsStore`](#ssr-createsearchparamsstore).

## Decorators (class stores)

Decorate the fields you want synced. The property name becomes the URL key, and the parser is **auto-resolved from the field's value** — so primitives need no parser at all.

```tsx
import { searchParam, withSearchParams } from '@ez-kit/valtio-kit/search-params'
import { proxy } from 'valtio'

class Filters {
	@searchParam() q = ''
	@searchParam() page = 1          // number parser auto-resolved
	@searchParam() inStock = false   // boolean parser auto-resolved
}

export const filters = withSearchParams(proxy(new Filters()))

// mutate the proxy directly
filters.q = 'boots'
filters.page = 2
```

`withSearchParams` takes an **already-created** proxy and returns it, augmented with a `$searchParams` control. Because you bring the proxy, it composes with the rest of the valtio ecosystem (`proxyWithHistory`, `derive`, valtio-yjs, …).

### Composition & inheritance

Nested class instances are discovered automatically — no decorator on the composed field needed. Paths nest to match the shape, and inherited fields come along via the prototype chain.

```tsx
class Price {
	@searchParam() min = 0
	@searchParam() max = 100
}
class Filters {
	@searchParam() q = ''
	price = new Price()           // composed — auto-recursed
}
class ProductFilters extends Filters {
	@searchParam() onSale = false // inherited q + price.* come too
}

withSearchParams(proxy(new ProductFilters()))
// URL keys: q, price.min, price.max, onSale
```

The walk recurses only into objects whose class declares `@searchParam` fields; `Date`, `Map`, `Set`, arrays, and plain objects are treated as leaves. Cyclic graphs terminate safely.

## Accessor (plain proxies)

No classes, no build-time decorator support required. Pass a builder that declares each field with a typed selector; the parser type follows the selected leaf, and you get autocomplete on the store shape.

```tsx
import { field, withSearchParamsFields, paramString } from '@ez-kit/valtio-kit/search-params'
import { proxy } from 'valtio'

const store = proxy({ filters: { q: '', page: 1 } })

withSearchParamsFields(store, (field) => [
	field((s) => s.filters.q, paramString()), // explicit parser
	field((s) => s.filters.page),             // auto-resolved (number)
])
// URL keys: filters.q, filters.page
```

The selector supports **direct property access only** (`s => s.a.b.c`) — it's recorded to derive the path, not executed for its value.

## TypeScript & build setup

`@searchParam` uses **Stage 3 (standard) decorators** with `Symbol.metadata`. No `reflect-metadata`, no `emitDecoratorMetadata`.

```jsonc
// tsconfig.json — TypeScript ≥ 5.2
{
	"compilerOptions": {
		"target": "ES2022",
		// Do NOT set experimentalDecorators — Stage 3 is the default and what this package needs.
		// "experimentalDecorators": false
	}
}
```

- **`experimentalDecorators` must be off** (or absent). The legacy decorator mode is incompatible.
- **`Symbol.metadata`** is read at bind time. Modern bundlers (esbuild/Vite, swc, Babel `@babel/plugin-proposal-decorators` v2023-05, tsc) emit it. On runtimes without it, add a one-line polyfill at your entry:

```ts
;(Symbol as { metadata?: symbol }).metadata ??= Symbol.for('Symbol.metadata')
```

- **Decorators are applied in your code**, so your bundler must transpile them. If you can't enable Stage 3 decorators, use the [accessor API](#accessor-plain-proxies) instead — it needs **no transpilation** and is fully equivalent.

<Callout type="info">
	Same engine, two fronts: `@searchParam` for classes, `field()` for plain proxies. Pick per project; mix per
	store if you like.
</Callout>

## Parsers

A parser converts one typed leaf to/from a URL string. Reads never throw into render — invalid input falls back to the field's default.

| Parser | Type | Notes |
| --- | --- | --- |
| `paramString()` | `string` | identity |
| `paramNumber()` | `number` | finite numbers; non-finite omitted |
| `paramBoolean()` | `boolean` | also reads `1`/`0` |
| `paramBigInt()` | `bigint` | decimal string |
| `paramDate()` | `Date` | ISO string |
| `paramEnum(values)` | `T` | rejects values outside the set |
| `paramArray(item)` | `T[]` | delimited list of an inner parser |
| `paramJson()` | `T` | JSON value (plain objects/arrays) |

```ts
import { paramEnum, paramArray, paramString } from '@ez-kit/valtio-kit/search-params'

const sort = paramEnum(['asc', 'desc'] as const)
const tags = paramArray(paramString())
```

Each parser satisfies a round-trip contract — `parse(stringify(v))` deep-equals `v` — which lets the engine break the proxy⇄URL loop by comparing serialized forms. Provide an `equals` on a custom parser if `Object.is` isn't right for your type.

### Auto-resolution

When you omit a parser, one is picked from the field's **runtime value** at bind time:

| Value brand | Parser |
| --- | --- |
| `string` | `paramString()` |
| `number` | `paramNumber()` |
| `boolean` | `paramBoolean()` |
| `bigint` | `paramBigInt()` |
| `Date` instance | `paramDate()` |
| array (non-empty) | `paramArray(<item>)`, item inferred from the first element |

Anything else — `null`, `undefined`, a plain object, `Set`/`Map`, an empty array, or a class instance with no `@searchParam` fields — **throws at bind** with the field name and asks for an explicit parser:

```ts
@searchParam({ parser: paramJson() }) coords = { lat: 0, lng: 0 } // plain object → explicit
@searchParam() createdAt = new Date()                              // Date → auto
```

### Zod validation

`zodParam(schema)` turns any Zod schema into a parser — parsing **is** validation, and a failed parse gracefully falls back to the default.

<LivePreview path='valtio-kit/search-params-zod' title='Zod-validated rating (1–5)' />

```ts
import { zodParam } from '@ez-kit/valtio-kit/search-params/validators/zod'
import { z } from 'zod'

const rating = zodParam(z.coerce.number().int().min(1).max(5))
```

## Key placement

By default a field's URL key is its **joined path** — collision-free across nested shapes:

```
filters.price.min  →  ?filters.price.min=0
```

Two options override that, on both fronts (`@searchParam({ … })` or `field(…, { … })`):

| Option | Effect | Example |
| --- | --- | --- |
| `key` | rename the **leaf** segment (keeps the ancestor prefix) | `{ key: 'query' }` on `filters.q` → `?filters.query` |
| `absolute` | pin an **exact top-level** key, ignoring ancestors | `{ key: 'q', absolute: true }` on `filters.search.q` → `?q` |

```tsx
class Search {
	@searchParam({ key: 'q', absolute: true }) query = ''
}
// wherever Search is nested, it always writes ?q=…
```

`absolute` is what lets a deeply-nested field own a short, shareable key regardless of where its class sits. Collisions from `absolute` are your call — the engine flags only statically-known duplicates at bind. `absolute` applies to the `flat` layout; under `json`/`qs` the nesting is the structure, so it's ignored (with a dev warning).

## Layouts

A layout maps the persisted fields onto URL keys. Pass one as `layout`; the default is `flat()`.

### `flat()` — one key per field

The default. Each field gets its own query key (`?q=boots&page=2`), so arbitrary components can read individual params with `useSearchParams().get('q')`. Pass `{ prefix }` to namespace keys.

<LivePreview path='valtio-kit/search-params-flat' title='Flat layout — q + page' />

### `json(key)` — whole state under one key

Packs every field into one canonical-JSON param, mirroring field paths as a nested object of stringified leaves. Compact and collision-free for multiple stores, at the cost of single-param interop.

<LivePreview path='valtio-kit/search-params-json' title='JSON layout — one key carries everything' />

```ts
import { json } from '@ez-kit/valtio-kit/search-params'

layout: json('state') // ?state={"view":"grid","compact":"false"}
```

### `qs()` — arrays & nesting

The `qs()` encoder (opt-in subpath, requires `qs`) serializes nested paths into bracket keys like `filters[price][min]=0`, instead of JSON-encoding them.

<LivePreview path='valtio-kit/search-params-qs' title='qs encoder — array fields' />

```ts
import { qs } from '@ez-kit/valtio-kit/search-params/encoders/qs'

layout: qs()
```

<Callout type="info">
	`flat()` is the mode that lets arbitrary components read individual params. `json()`/`qs()` trade that for
	compactness and multi-store isolation.
</Callout>

## History control

URL writes default to `history: 'replace'` so high-frequency fields (text inputs) don't spam the history stack. Override per write with the `$searchParams` control attached to the proxy. Several mutations inside one call coalesce into a **single** history entry:

<LivePreview path='valtio-kit/search-params-history' title='push vs replace' />

```ts
// advancing a wizard: one Back-button-able entry, even with several changes
store.$searchParams.push(() => {
	store.step = 'review'
	store.touched = true
})

// going back: replace, don't stack
store.$searchParams.replace(() => (store.step = 'profile'))
```

Set a different default for the whole store with the `history` option, and tune write frequency with `throttleMs`. `clearOnDefault` (on by default) omits a param when its value equals the field default, keeping URLs clean.

## SSR (`createSearchParamsStore`)

The request-scoped, SSR-correct form. It fuses the [`createContextStore`](./create-context-store) lifecycle with the sync engine: the proxy is created per `<Provider>` and **seeded synchronously from the URL** — `defaultValue` first, then URL overrides — identically on server and client. The first paint already reflects the URL: no flash, no hydration mismatch.

Fields come from `@searchParam` decorators on the factory's instance, or from an accessor `fields` builder:

<LivePreview path='valtio-kit/search-params-ssr' title='Synchronous URL seed — opens on ?tab=billing' />

```tsx
import { createSearchParamsStore, flat, paramString, paramNumber } from '@ez-kit/valtio-kit/search-params'
import { proxy } from 'valtio'

// accessor form
const filtersStore = createSearchParamsStore<{ q: string; page: number }>(
	() => proxy({ q: '', page: 1 }),
	{ fields: (field) => [field((s) => s.q, paramString()), field((s) => s.page, paramNumber())], layout: flat() },
)

// or class form — omit `fields`, decorators are discovered on the instance
class Filters {
	@searchParam() q = ''
	@searchParam() page = 1
}
const classStore = createSearchParamsStore(() => proxy(new Filters()))
```

It returns the same surface as `createContextStore` — `Provider`, `useStore`, `useSnapshot`, `Item`. Each `Provider` is an isolated instance, so two never collide.

## Router adapters

The core is router-agnostic. An adapter is a tiny object exposing the reactive read and the writer as hooks; the coordinator does all merging.

### react-router

```tsx
import { reactRouterAdapter } from '@ez-kit/valtio-kit/search-params/routers/react-router'

<StoreSearchParamsProvider adapter={reactRouterAdapter}>{children}</StoreSearchParamsProvider>
```

Works with react-router v6/v7 (`BrowserRouter` / data routers).

### Next.js

```tsx
import { nextAdapter } from '@ez-kit/valtio-kit/search-params/routers/next'

<StoreSearchParamsProvider adapter={nextAdapter}>{children}</StoreSearchParamsProvider>
```

For the App Router, writes go through `router.replace`/`push`; client-held Valtio state survives the RSC refetch.

### Writing an adapter

Any router fits by implementing three members:

```ts
import type { RouterAdapter } from '@ez-kit/valtio-kit/search-params'

const myAdapter: RouterAdapter = {
	useSearchParams: () => /* reactive URLSearchParams */,
	useUpdater: () => (next, { history }) => {/* navigate to ?next, push|replace */},
	getSnapshot: () => /* non-reactive URLSearchParams for the throttled flush */,
}
```

The live demos on this page use exactly this contract with an in-memory adapter, so each example owns an isolated URL instead of driving the page address bar.

## Caveats

- **Decorators need transpilation** in your toolchain (Stage 3 + `Symbol.metadata`). No build step for decorators? Use the accessor API — it's equivalent and needs none.
- **Auto-resolution can't read your TS types**, only runtime values — `null`/`undefined`/plain objects/`Set`/`Map`/empty arrays/class leaves need an explicit `parser`.
- **A parser on a class-instance node throws at bind** — sync its fields individually (that's what composition is for) rather than blobbing the whole instance.
- **Non-canonical custom parsers can loop** — honor the round-trip contract (or supply `equals`). `json`/`qs` use stable ordering for you.
- **`json`/`qs` break single-param interop** — use `flat()` when other components need to read individual keys.
- **Next App Router** lacks true shallow routing; `nextAdapter` re-runs server components on write. Client Valtio state survives the refetch.
