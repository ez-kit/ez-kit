# Recipes & caveats

Practical patterns built from the pieces in the rest of this section, followed by the caveats worth internalizing.

## URL as tabs

Persist the active tab so a deep link opens the right panel and Back/forward works. Use `paramEnum` to reject unknown values, and [`createSearchParamsStore`](./valtio-kit/search-params/ssr) so the first server paint is correct:

```tsx
class TabsState {
	@searchParam({ parser: paramEnum(['overview', 'billing', 'team'] as const) })
	tab: 'overview' | 'billing' | 'team' = 'overview'
}
const tabsStore = createSearchParamsStore(() => proxy(new TabsState()))
```

This is exactly the [SSR demo](./valtio-kit/search-params/ssr) — it opens on `?tab=billing`.

## Filters + pagination

Keep filters and the current page in the URL together, on the default [`flat()` layout](./valtio-kit/search-params/layouts) so any component can read `?q` or `?page`. Reset `page` to 1 when a filter changes:

```tsx
class Catalog {
	@searchParam() q = ''
	@searchParam() page = 1
	setQuery(value: string) {
		this.q = value
		this.page = 1 // new query → back to first page
	}
}
```

Wrap both writes in `$searchParams.replace(() => store.setQuery('boots'))` so the pair lands as one URL update — see the [decorators demo](./valtio-kit/search-params/decorators).

## Wizard steps with real history

Advancing a wizard should be Back-button-able; going back shouldn't stack. Mix `push` and `replace` per action via the [history control](./valtio-kit/search-params/history):

```ts
store.$searchParams.push(() => (store.step = 'review')) // creates a history entry
store.$searchParams.replace(() => (store.step = 'profile')) // rewrites it
```

## Multiple isolated stores

Render any number of stores under one `StoreSearchParamsProvider`; the coordinator merges their keys and preserves foreign ones. Namespace each so they don't collide — distinct field names, a `prefix` on `flat()`, or a per-store `json()` key:

```tsx
const filters = createSearchParamsStore(() => proxy(new Filters()), { layout: flat({ prefix: 'f.' }) })
const table = createSearchParamsStore(() => proxy(new TableState()), { layout: flat({ prefix: 't.' }) })
```

## Caveats

- **Decorators need transpilation** in your toolchain (Stage 3 + `Symbol.metadata`). No build step for decorators? Use the [accessor API](./valtio-kit/search-params/fields) — it's equivalent and needs none. Full setup: [TypeScript](./valtio-kit/search-params/typescript).
- **Auto-resolution can't read your TS types**, only runtime values — `null`/`undefined`/plain objects/`Set`/`Map`/empty arrays/class leaves need an explicit [`parser`](./valtio-kit/search-params/parsers).
- **A parser on a class-instance node throws at bind** — sync its fields individually (that's what [composition](./valtio-kit/search-params/decorators#composition) is for) rather than blobbing the whole instance.
- **Non-canonical custom parsers can loop** — honor the round-trip contract (or supply `equals`). `json`/`qs` use stable ordering for you.
- **`json`/`qs` break single-param interop** — use [`flat()`](./valtio-kit/search-params/layouts) when other components need to read individual keys.
- **Next App Router** lacks true shallow routing; `nextAdapter` re-runs server components on write. Client Valtio state survives the refetch.
