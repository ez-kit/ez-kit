# `createContextStore`

Wraps a Valtio proxy in React context. Each `<Provider>` creates its own proxy instance (via `useRef`), so the same factory can power multiple isolated subtrees. There are no selectors — `useSnapshot` tracks the properties you actually read.

## Signature

```ts
type ContextStoreInit<TDefaultValue> = { defaultValue: TDefaultValue }

function createContextStore<TState extends object, TDefaultValue = undefined>(
	factory: (init: ContextStoreInit<TDefaultValue>) => TState,
): {
	Provider: (props: PropsWithChildren<{ defaultValue: TDefaultValue }>) => ReactElement
	useSnapshot: (options?: { sync?: boolean }) => Snapshot<TState>
	useContextStore: () => TState
	Item: (props: { children: (arg: { snap: Snapshot<TState>; store: TState }) => ReactElement }) => ReactElement
}
```

> **Rule of thumb:** read from snapshots (`useSnapshot`), mutate the source proxy (`useContextStore`).

<Callout type='warn'>
	**Breaking change.** `useStore()` has been **removed**. It used to return the raw mutable proxy — that is now
	`useContextStore()`. There is no alias for reads either: `useSnapshot()` is the only read path. Migrate
	`store.useStore()` → `store.useContextStore()` when you were writing, and → `store.useSnapshot()` when you were
	reading.
</Callout>

The factory is seeded through a single `defaultValue` envelope — type its parameter with the exported `ContextStoreInit<T>` helper. `defaultValue` is required on the `Provider` when your seed has required fields, and optional otherwise.

## API

### `Provider`

Creates and provides the proxy. The factory runs **once per mount** (held in a `useRef`), so changing `defaultValue` after the first render won't recreate it. Pass your seed through the single `defaultValue` prop.

```tsx
<counterStore.Provider defaultValue={{ initialCount: 10 }}>
	<App />
</counterStore.Provider>
```

### `useSnapshot(options?)`

Returns Valtio's readonly snapshot. The component re-renders only when the properties it actually reads change — no selector required.

```tsx
const snap = counterStore.useSnapshot()
return <span>{snap.count}</span>
```

Valtio's options pass straight through. Use `{ sync: true }` for synchronous re-renders (e.g. text inputs that must stay in lockstep):

```tsx
const snap = counterStore.useSnapshot({ sync: true })
```

### `useContextStore()`

Returns the raw, **mutable** proxy — the write path. It does **not** subscribe the calling component, so pair it with `useSnapshot()` when the same component also renders that state. Mutate it directly to update state:

```tsx
const state = counterStore.useContextStore()

const onClick = () => {
	state.count += 1
}
```

<Callout type='info'>
	The name matches [`@ez-kit/zu-store`](../zu-store/create-context-store), where `useContextStore()` likewise hands back
	the raw store handle (there, the Zustand `StoreApi`). Reads differ per kit: `useStore(selector)` in zu-store,
	`useSnapshot()` here. Mutate the proxy in event handlers and effects, not during render.
</Callout>

You can also feed it to Valtio's vanilla utilities:

```tsx
import { subscribe } from 'valtio'

const state = counterStore.useContextStore()

useEffect(() => subscribe(state, () => console.log('changed')), [state])
```

<Callout type='warn'>
	The React Compiler ESLint ruleset (`react-hooks/immutability`) flags mutating any value returned from a hook, so it
	warns on `state.count += 1`. Either keep actions on the proxy (as in the live example) or disable the rule at the
	mutation site with `// eslint-disable-next-line react-hooks/immutability`.
</Callout>

### `Item`

Render-prop alternative to `useSnapshot`. Its child receives `{ snap, store }` — `snap` for reads (auto-tracked) and `store` (the raw proxy) for writes — so a single `Item` can both render and mutate without a separate `useContextStore()` consumer.

```tsx
<counterStore.Item>
	{({ snap, store }) => (
		<button
			onClick={() => {
				store.count += 1
			}}
		>
			{snap.count}
		</button>
	)}
</counterStore.Item>
```

## Errors

Using `useSnapshot`, `useContextStore`, or `Item` outside a `Provider` throws:

```
Error: Missing Provider for createContextStore
```

This is deliberate — there is no implicit module-level fallback, because the whole point of `createContextStore` is per-tree isolation. Wrap the consuming subtree in a `Provider`.
