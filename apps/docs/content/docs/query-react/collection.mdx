`useCollectionQuery` executes a collection source under your existing `QueryClientProvider`.
It does not own list state or render UI. Import it from `@ez-kit/query-react/collection`.

For a guided walkthrough of reading, all four mutations and grid adaptation, see
[Lists and CRUD](/docs/qc-react/lists). The API contracts are described below.

## Sources and arbitrary parameters

```tsx
import { createCollectionSource, useCollectionQuery } from '@ez-kit/query-react/collection'

const source = createCollectionSource({
	key: ['users'],
	getAll: {
		prepareArgs: (params: { teamId: string; offset: number; limit: number }) => ({
			path: { teamId: params.teamId },
			query: { offset: params.offset, limit: params.limit },
		}),
		fetcher: fetchUsers,
		getItems: (response) => response.items,
		getTotal: (response) => response.total,
	},
})
const users = useCollectionQuery({
	source,
	mode: 'pages',
	params: { teamId, offset: 0, limit: 20 },
})
```

`params` is inferred from the source. It can use your own filter, sort and pagination shape.
The hook forwards it without modifying it. Include every response-affecting input, including
tenant identity, in prepared arguments or the base key. Fetchers receive a separate `{ signal }`
transport argument; generated clients remain responsible for URL, query and body placement.

`items` is the projected collection and `total` is optional. `query` is the native active query
result, including loading, disabled, placeholder, refetch and error states. Projections consume
selected observer data; they do not replace the original cached response.

## Mutations

```tsx
update: {
  prepareArgs: (input: { id: string; name: string }) => ({
    path: { id: input.id }, body: { name: input.name },
  }),
  fetcher: updateUser,
  options: {
    onSuccess: (saved, input) => console.log(saved.id, input.id),
  },
}
// In a consumer:
await users.update.mutateAsync({ id: '42', name: 'Alice' })
```

Only configured `create`, `update`, `delete` and `deleteMany` operations are available. Each is a
native mutation result: use `mutate`, `mutateAsync`, `isPending`, `error`, `data`, `variables` and
`reset`. There is no `execute` method. Each operation has its own input, fetcher argument, result,
error and optimistic-context types. The error default respects TanStack's registered default error.

Preparation runs inside `mutationFn`, after `onMutate`. Lifecycle callbacks receive the original
input. Preparation failures enter the native error lifecycle, and enabled retries repeat preparation.
Keep preparation pure; put stable operation IDs in the input rather than generating them on retry.
Handle `mutateAsync` rejections in event handlers. Bulk deletion requires an explicit fetcher;
the hook does not loop over single deletion or infer partial success.

## Invalidation and native options

Generated keys use separate `list` and `infinite` families beneath the base key. Successful
mutations invalidate both families without waiting for background refresh. Slow or failed refreshes
do not turn successful persistence into failed persistence. User lifecycle promises are still awaited.

Use `invalidate: false`, `{ additional: [{ queryKey: ['users-count'] }] }`, or
`{ replace: [...] }` at source or operation level. Operation policies override or extend source rules.
Each additional filter selects a separate family; one queryKey array remains one composite key.

Native read descriptors provide `query(params)`, `getItems` and optional `getTotal`; native mutation
descriptors provide `mutation` options. These preserve external keys and variable types. Supply an
explicit invalidation policy for native sources. Fetcher and native mutation descriptors are distinct:
a native mutation already defines its input and does not take another `prepareArgs`.

Automatic invalidation is attached at hook scope and survives observer unmount. Per-call callbacks
retain TanStack's observer-dependent lifetime. Mutation errors are not converted into form errors here;
a UI connector can adapt them at its own boundary.

## Infinite-only collections

A source can define only `getInfinite`; `getAll` is not required. Use `mode: 'infinite'` and the
parameters inferred for that operation. `prepareArgs` creates collection arguments, while
`preparePageArgs({ args, pageParam })` creates each request. `initialPageParam` and `getNextPageParam`
retain native cursor types. Cursors do not change collection identity.

The hook projects loaded pages into `items`; call `query.fetchNextPage()` and observe
`query.hasNextPage`, `query.isFetchingNextPage` and `query.isFetchNextPageError`. Existing items remain
on next-page failure. `total` is undefined for infinite reads; custom metadata remains in native page
data. The hook adds no scroll observer. A source supporting both modes can switch without remounting.

## Reuse conventions and connect a grid

`createCollectionSourceFactory` defines shared `list`, `infinite` and `mutations` defaults. Supply
entity fetchers to the returned factory; expanded operations override supplied properties. An
operation's `options` replaces the options object rather than deep-merging callbacks. An application
factory can specialize an entity type once when a generic response envelope needs it.

Use `createGridSourceFromCollection` from `@ez-kit/qc-react/data-grid` to map table parameters and action
contexts to a collection source. `withQuery(bundle)` then consumes that dataSource. The collection
has no grid dependency; tables still own applied filters, page resets and form sessions.
See [the connector guide](/docs/qc-react) for grid integration.

Fetcher mutations default `mutationKey` to `[...baseKey, operationName]`. Include tenant ownership
in the base key when switching between tenant-specific sources: a mutation already dispatched for
one tenant keeps that scope when the hook switches to a differently keyed source. Explicit mutation
keys override this default. Native mutation descriptors preserve supplied keys and TanStack's normal
observer behavior; changing callbacks under the same key does not create an isolated operation scope.

## Conditional capabilities and required configuration

When a permission or feature flag conditionally adds a mutation, the corresponding result
remains optional: check `users.delete` before calling it, or use `users.delete?.mutate(input)`.
Likewise, narrow a conditionally present read before selecting its mode. A configured read
can still use `enabled: false` to pause requests without removing the capability.

Generated reads require `key`; native reads require explicit `invalidate` (including `false`).
A shared factory can omit a read convention, but the entity operation must then supply all
of that read's preparation and projection fields. Incomplete definitions are type errors.

Mutation `onSuccess` inherits global or keyed QueryClient defaults when the source does not
provide its own callback. A local callback replaces the inherited one, following TanStack's
precedence; automatic invalidation follows the effective callback.

## Per-component query options

Keep shared defaults in the source and override loading behavior at the hook call:

```tsx
const users = useCollectionQuery({
	source: usersSource,
	mode: 'pages',
	params,
	queryOptions: {
		enabled: isOpen,
		staleTime: 30_000,
		refetchOnWindowFocus: false,
	},
})
```

The same option works in `mode: 'infinite'`. Supplied properties override source options;
other source settings remain unchanged. Supported options are `enabled`, `staleTime`, `gcTime`,
`retry`, `retryDelay`, `retryOnMount`, `refetchInterval`, `refetchIntervalInBackground`,
`refetchOnMount`, `refetchOnWindowFocus`, `refetchOnReconnect`, `networkMode`, `throwOnError`
and `notifyOnChangeProps`. Native callbacks retain the source's response and error types.

The source still owns `queryKey`, `queryFn`, `select`, initial data and infinite cursor handling.
They cannot be overridden here. These settings apply only to the active read, not to mutations.
Disabling an observer retains TanStack's normal behavior: cached data remains available and
manual `query.refetch()` can still fetch.

## Selecting another shape in a shared factory

An entity can change the selected response shape without changing the cached response or
repeating the request convention:

```tsx
const makeUsersSource = createCollectionSourceFactory({
	list: {
		prepareArgs: (params: { offset: number; limit: number }) => ({ query: params }),
		getItems: (response: { items: User[]; total: number }) => response.items,
		getTotal: (response) => response.total,
	},
})

const namesSource = makeUsersSource({
	key: ['user-names'],
	getAll: {
		fetcher: fetchUsers,
		options: { select: (response) => response.items.map((user) => user.name) },
		getItems: (names) => names, // string[], inferred from select
	},
})
```

Providing `select` requires an explicit `getItems` for the new shape. The inherited `getTotal`
is discarded; supply a new one if the selected data still contains a total. Without it, the
collection total is `undefined`. The operation's entire `options` object replaces shared
options, as with other factory overrides.

For infinite reads, select the native `InfiniteData` envelope and project each selected page:

```tsx
getInfinite: {
  fetcher: fetchUsersPage,
  options: {
    select: data => ({
      ...data,
      pages: data.pages.map(page => page.items.map(user => user.name)),
    }),
  },
  getItems: names => names, // selected page: string[]
}
```

Keep the `pages` / `pageParams` structure. `getNextPageParam` still receives original API pages;
`getItems` receives selected pages. Prefetching and cache access continue to use the raw response.

## Safe selection and changing capabilities

Without `select`, `getItems` and `getTotal` receive the raw API response. A projection annotation
cannot change that response type. If a selector changes the response shape, it must be present
whenever the projection expects that shape. This applies to both standalone sources and shared
factories, including infinite pages.

```tsx
// Keep the selector present; branch inside it so the output shape stays consistent.
options: {
  select: response => compact
    ? response.items.map(user => user.name)
    : response.items.map(user => `${user.name} (${user.id})`),
},
getItems: names => names,
```

A conditional selector can also return an explicit union of raw and selected data, provided the
projection handles both shapes. An optional selector cannot promise that only selected data arrives.

Every generated fetcher operation requires a source `key`, including mutations alongside native
reads. Native reads still require their own explicit invalidation policy; supplying a base key
does not infer their query keys.

When a conditional mutation disappears, it is omitted from the hook result. Already dispatched
work retains the last connected operation's retry function, lifecycle callbacks and invalidation.
Reconfiguring an available native operation still follows TanStack's key/observer behavior.

### Native projections and inherited totals

Native reads also infer the input of `getItems` and `getTotal` from their query options. Both plain
options objects and TanStack's `queryOptions` / `infiniteQueryOptions` helpers are supported.

If conditional selection broadens the input type, an inherited raw-only `getTotal` needs a
compatible replacement. Handle both forms or use `getTotal: () => undefined` when no total is needed.
A definitely present selector continues to discard inherited projections as described above.

The packages require TanStack Query **5.105.3 or later within v5**. Public declaration checks run
against that exact minimum version as well as the workspace's development dependencies.

A plain source keeps the relationship between its native query options and `getItems` or
`getTotal`. The projection must accept the data produced by the query, including any `select`.
Infinite projections consume one page of the selected infinite data.

Plain native descriptors passed directly to `useCollectionQuery` have the same consumer option
types as sources built by the helpers. An omitted option remains available for local overrides,
and a source's literal `enabled: false` can be overridden with `queryOptions: { enabled: true }`.
Callback options infer the native query's data type. The runtime whitelist still prevents
consumers from replacing source-owned keys, fetchers or selection.
