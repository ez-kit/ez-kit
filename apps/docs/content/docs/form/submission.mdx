`<Form>` renders the `<form>` element and wires its `onSubmit` to `form.handleSubmit()`, preventing the browser's navigation and stopping the event from bubbling out of a form nested inside another. Nothing else is claimed: what happens to the values is yours.

## `onSubmit`

The handler is an option of the form, not a prop of the button:

```tsx
<Form
	defaultValues={{ email: '', password: '' }}
	onSubmit={async ({ value, formApi, meta }) => {
		await save(value)
	}}
>
```

`value` is the form's values, typed by `defaultValues`. `formApi` is the instance, for the cases where the handler has to reach back into the form — resetting it after a successful save, or reading a field it was not given. `meta` carries whatever was passed to `handleSubmit(meta)`, which is how one form ends up with a "save" and a "save and publish" button that differ only in what the handler is told.

It runs **only after validation has passed**. `handleSubmit` first marks every field touched — which is what makes a required-but-never-focused field show its error on the first submit attempt — then runs the field validators, then the form's, and returns early if either produced an issue. On that early return the form [moves focus to the first field with an error](#focus-on-the-first-error), then calls `onSubmitInvalid` if you passed one — the hook for announcing the failure, or for anything else the early return should do.

An exception thrown from the handler is not swallowed: `isSubmitting` is cleared, the form is marked unsuccessful, and the error propagates out of `handleSubmit`. Since `<Form>` calls it as `void form.handleSubmit()`, an unhandled rejection there is an unhandled rejection in the page — catch what you expect to fail, and see the next section for the failure worth modelling properly.

To submit from outside the element — a dialog footer, a toolbar, a keyboard shortcut — call `form.handleSubmit()` yourself, or use [`form.Submit`](#formsubmit); see also [Native API](/docs/form/native-api).

## Submit state

Two pieces of state describe a submission, and `form.SubmitButton` is already subscribed to both. It reads the form from context, so it needs `<Form>`, `<SchemaForm>` or a [`FormProvider`](/docs/form/composition#formprovider) above it.

`isSubmitting` is true from the moment validation passes until the handler settles. `canSubmit` is the form's own answer to "would submitting be meaningful right now": true while the form is pristine and has never been submitted — otherwise the very first submit could never happen — and thereafter true only when the form is valid, not validating and not already submitting.

So the button disables itself while a request is in flight and again whenever the form is invalid, and there is nothing to wire. Its `disabled` prop only ever _adds_ a reason of your own; it cannot force the button enabled. What it does not do is change its own label — that is content, and content is yours:

```tsx
<form.Subscribe selector={(state) => state.isSubmitting}>
	{(isSubmitting) => <form.SubmitButton>{isSubmitting ? 'Saving…' : 'Save'}</form.SubmitButton>}
</form.Subscribe>
```

Reaching for `form.Subscribe` here rather than reading `form.state.isSubmitting` is the general rule, explained in [Reactivity](/docs/form/reactivity).

## `form.Submit`

`form.SubmitButton` is the kit's button. The primitive under it is `form.Submit`, a headless render prop that subscribes to the submit state and hands it out, so a control of your own — a link, a menu item, a button from a design system the kit does not wrap — gets the same behaviour:

```tsx
<form.Submit>
	{({ canSubmit, isSubmitting, submit }) => (
		<MyButton
			isDisabled={!canSubmit || isSubmitting}
			onPress={() => void submit()}
		>
			{isSubmitting ? 'Saving…' : 'Save'}
		</MyButton>
	)}
</form.Submit>
```

| Key            | Type                  | Notes                                                                                                                                                     |
| -------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `canSubmit`    | `boolean`             | The form's own answer to "would submitting be meaningful right now" — see above.                                                                          |
| `isSubmitting` | `boolean`             | True from the moment validation passes until the handler settles.                                                                                         |
| `isDirty`      | `boolean`             | Whether the user has changed any field. It stays `true` after the value is changed back; to compare with the defaults, read `form.state.isDefaultValue`.  |
| `formErrors`   | `string[]`            | The form-level errors as display strings: the form validators', then a server's [`form` messages](#server-errors). Field-level issues are not among them. |
| `submit`       | `() => Promise<void>` | `form.handleSubmit`. A control built on it works outside a `<form>` element too, where a submit button cannot.                                            |

### Outside the `<form>` element

`submit` is what makes a button on `form.Submit` independent of the DOM. Put the button in a dialog footer, a toolbar or a sticky bar that is not a descendant of the `<form>`, give the tree a [`FormProvider`](/docs/form/composition#formprovider) so the button can find the form, and it submits:

```tsx
<FormProvider form={form}>
	<form.TextField
		name='email'
		label='Email'
	/>
	<form.SubmitButton>Save</form.SubmitButton>
</FormProvider>
```

The kit's `SubmitButton` is written on `form.Submit`. Inside a `<form>` it is an ordinary submit button and the element's own handler runs; with no `<form>` above it, a click calls `submit` instead, and only one of the two paths ever fires.

## Focus on the first error

After a submit that fails validation, focus moves to the first field with an error — first **in page order**, not in the order of `defaultValues`. Which element inside the field takes it: the one carrying the field's `id`, if it can take focus; otherwise the first focusable element inside the field; otherwise the field's wrapper, if that can. So a text field focuses its text box, and a radio group whose kit puts the `id` on a container focuses its first radio.

It does not depend on a `<form>` element. The walk covers the whole page and keeps only the fields stamped with this form's `data-form-id`, so a form under [`FormProvider`](/docs/form/composition#formprovider) with no `<form>` behaves the same, and two forms with the same field names never reach into each other. A [custom kit](/docs/form/custom-kit#fields) has to put `data-form-id` beside `data-field` for its fields to take part.

A field that is hidden — in a collapsed section, on an inactive tab — ignores focus. It is skipped, and the next field with an error takes focus instead; if none can, focus stays where it was. The form does not open what hides a field: revealing it is the layout's business.

`focusOnError: false` turns all of this off — an option of `useForm`, and a prop of an uncontrolled `<Form>` or `<SchemaForm>`. It also governs the focus that follows [server errors](#server-errors). `onSubmitInvalid` runs after the focus has moved, either way.

## Server errors

A taken username, a declined card, a stale version — the failures only the backend can see often come back as the **answer** to a request that already went out: the handler ran, and the server replied with what it rejected. `serverErrors` puts that answer on the form, on the fields it names:

```tsx
<Form
	defaultValues={{ username: '', email: '' }}
	serverErrors={state.serverErrors}
	onSubmit={({ value }) => {
		startTransition(() => {
			action(value)
		})
	}}
>
```

That is the [server actions](/docs/form/server-actions) recipe, where the answer arrives as `useActionState`'s state. The shape is:

```ts
type ServerErrors<TFormData> = {
	fields?: { [TPath in DeepKeys<TFormData>]?: string | readonly string[] | undefined }
	form?: string | readonly string[] | undefined
}
```

`fields` is keyed by a field's full path — the `name` you gave it, `address.city` or `members[1].email` — and takes one message or several. `form` is for a message about the form as a whole. An `undefined` entry is ignored, so zod's `flatten().fieldErrors` fits as it is.

`serverErrors` is an option of `useForm`, and a prop of an uncontrolled `<Form>` or `<SchemaForm>`. A controlled `<Form form={form}>` does not take it — pass it to your own `useForm`, so it has one source. `form.setServerErrors(errors)` is the same mechanism called directly, for an answer that arrives in your own code:

```tsx
const form = useForm({
	defaultValues: { username: '' },
	onSubmit: async ({ value }) => {
		const response = await signUp(value)
		if (response.errors) form.setServerErrors(response.errors)
	},
})
```

When errors are applied:

- **Each field named shows its messages at once**, through the kit's error component with `aria-invalid` set, like any other error. Applying them marks the field touched, so the display rule does not hide them.
- **The first field with an error takes focus**, by the [rule above](#focus-on-the-first-error), unless `focusOnError` is `false`. Errors that name no field move nothing.
- **A `form` message reaches [`form.Submit`](#formsubmit)'s `formErrors`** and does not disable submitting.

And when they go:

- **A field's error stays while the user moves in and out of the field**, and goes the first time its value changes. It does not come back for that value — typing the rejected username again does not restore the message; only the server can say it again.
- **Every server error goes on the next submit**, and on `form.reset()`.
- Until it goes, a field's server error makes the form invalid, so `canSubmit` is `false` and the kit's button is disabled — the same as any field error, and the reason the error clears on the first edit. A `form` message never disables it.
- **An error for a field that is not mounted is kept**, and shows when the field mounts, by the same rules. It does not block submitting while nothing shows it.

The prop is applied on mount and whenever its value changes **by reference** — the same object again applies nothing, so an error the user has since edited away stays gone. Pass the server's answer as it is (`state.serverErrors` changes once per result), or memoise any reshaping of it: a literal built inline is a new object on every render, and every render would apply it again — restoring a message the user edited away, marking the fields touched again and moving focus back. It is applied in an effect, so errors present on the first render appear once the page has hydrated, not in server-rendered HTML.

One limitation: the errors are kept by path, and a field's error goes once the value at its path changes. So after an entry of an array is removed or moved, an error on a later row is dropped — or, if the row that now sits at that path holds the same value, shown on that row instead. Two empty rows, or a duplicate-address error, are exactly the case where the values match.

### The two options

| Option         | Type                                   | Notes                                                                                                |
| -------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `focusOnError` | `boolean`                              | Focus the first field with an error after an invalid submit, and after server errors. On by default. |
| `serverErrors` | `ServerErrors<TFormData> \| undefined` | Errors a server reported. Applied on mount and when the reference changes.                           |

## A server check as a validator

A server check can also run **as validation**, before the handler: a uniqueness lookup that should keep `onSubmit` from running at all, rather than a response to a request it made.

The seam for that is a **validator**, not the `onSubmit` handler. The handler's return value is ignored; `validators.onSubmit` and `validators.onSubmitAsync` are the two whose result TanStack maps back onto fields. Return `undefined` and submission proceeds to the handler; return an object with a `fields` map and it does not:

```tsx
<Form
	defaultValues={{ email: '', password: '' }}
	validators={{
		onSubmitAsync: async ({ value }) => {
			const conflict = await createAccount(value)
			return conflict ? { fields: { email: 'That address is already registered' } } : undefined
		},
	}}
	onSubmit={({ value }) => {
		// Only reached when the request above reported nothing.
	}}
>
```

Each key of `fields` is a field name, and its message goes into that field's submit-time error slot — where the flat fields already look, so it renders through the kit's error component with `aria-invalid` and `aria-describedby` set, exactly like a schema issue. It is visible immediately because submitting has just marked every field touched. A `form` key may sit alongside `fields` for a message about the form as a whole; that one belongs to no field, so nothing renders it for you — read it from `form.Submit`'s `formErrors` and put it where you want it.

The message then clears itself. Editing the rejected field runs its own change validation, and a field that now passes drops its stale submit-time error. That is not cosmetic: an unresolved error keeps the form invalid, and an invalid form keeps `canSubmit` false — without the clearing, one server rejection would disable the button for good.

Because the request is a validator, `isSubmitting` is already true while it awaits, and the button is disabled for the whole round trip.

**Which one?** Both put a server's message on a field. A server **validator** runs as part of submitting: the handler does not run until it answers, and its error stops the submission like any validation error. Server **errors** are a response you put on the form afterwards — the submission went through, and this is what came back. A [server action](/docs/form/server-actions) is the second shape, since the request _is_ the submission; a check that must pass before anything is saved is the first.

## Hidden values and the submitted payload

A field that is not on screen has usually stopped being part of the answer, and the value it holds should not travel with the submission.

In a [config-driven form](/docs/form/schema#visibility-and-the-submitted-payload) this is handled: a field hidden by a `when` condition is stripped from the value at submit time, `keepHiddenValues` opts out, and a controlled caller applies `stripHiddenValues(schema, value)` at the top of their own handler because `SchemaForm` has no seam to wrap.

In the JSX API there is no `when` and therefore nothing to compute visibility from — hiding a field means not rendering it, and that is a decision only your component knows about. Unmounting a field resets its meta but deliberately **leaves its value in form state**, so that a field toggled away and back does not lose what the user typed. The consequence is that the value still reaches `onSubmit`, and dropping it is an explicit act: omit the key when you build the request, or call `form.deleteField(name)` when the field goes away.

## Initial values that arrive late

Editing an existing record means the form is often mounted before the record is loaded, and this package adds no API for it: `<Form>` splits its props into the `<form>` element's DOM attributes and TanStack Form's options, then hands the options over untouched. Everything below is TanStack's behaviour, not ours, and its [async initial values guide](https://tanstack.com/form/latest/docs/framework/react/guides/async-initial-values) is the fuller account.

Three approaches, in the order they are worth trying:

**Pass `defaultValues` as they arrive.** TanStack re-applies the options on every render, and replaces the form's values when `defaultValues` changes — but only while the form is still untouched. That proviso is the whole reason this is safe: data landing a moment after mount fills the fields, while a response landing after the user has started typing cannot overwrite their work. Render the form with empty defaults and swap them in when the request resolves.

**Call `form.reset(values)`** when you want the change to apply regardless — after a successful save, or when the user explicitly discards their edits. It replaces the values and leaves the form pristine, so `isDirty` is `false` again. It also makes `values` the baseline `isDefaultValue` compares against — but only until the next render. TanStack re-applies the options it was rendered with, a reset form is untouched, and so a `defaultValues` still holding the old record puts the old values back the next time the component renders, silently undoing the save. Feed the saved value back as `defaultValues`, from state, so the options and the reset agree:

```tsx
const [saved, setSaved] = useState(record)
const form = useForm({
	defaultValues: saved,
	onSubmit: async ({ value, formApi }) => {
		await save(value)
		setSaved(value)
		formApi.reset(value)
	},
})
```

The recipe seeds `useState` with `record`, so it assumes the record is there when the form mounts: render the form once the data has resolved, or key it by the record's id so a different record starts a fresh one.

`formApi.reset(value, { keepDefaultValues: true })` is the alternative when nothing reads `isDefaultValue`: the values stay and `isDirty` is `false`, while the baseline remains the original `defaultValues`, so `isDefaultValue` reads `false` from then on.

**Remount with `key`** when the form should genuinely start over: `<Form key={recordId} …>` gives each record its own form instance, and switching records throws away the previous one's state instead of reconciling it. This is the blunt option, and the right one when reconciling would be wrong.

## Warn before leaving with unsaved changes

`isDirty` is what a "you have unsaved changes" prompt reads. The browser's own prompt on closing or reloading the tab is a `beforeunload` listener, attached only while the form is dirty — read the flag through `form.Submit` (or `form.Subscribe`) and hand it to a component that owns the effect:

```tsx
function LeaveGuard({ when }: { when: boolean }): ReactNode {
	useEffect(() => {
		if (!when) return
		const warn = (event: BeforeUnloadEvent): void => {
			event.preventDefault()
		}
		window.addEventListener('beforeunload', warn)
		return () => {
			window.removeEventListener('beforeunload', warn)
		}
	}, [when])
	return null
}
```

Render it anywhere inside the form:

```tsx
<form.Submit>{({ isDirty }) => <LeaveGuard when={isDirty} />}</form.Submit>
```

Navigation inside the app never fires `beforeunload`; blocking a route change is the router's business, through its own blocker, with the same `isDirty` as the condition.
