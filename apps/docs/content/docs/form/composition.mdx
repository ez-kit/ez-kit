A form long enough to be worth building is a form long enough to want cutting into pieces: an address block that appears twice, a step you render in three different flows, a section a colleague owns. TanStack Form ships four helpers for that, and all four are re-exported by your kit — but only one of them needed changing on the way, and the reason is worth understanding before you pick between them.

## The problem a block has

Pull a group of fields out into its own component and it loses the form. Hand the form back as a prop and the question becomes: what type is that prop?

Not `any` — the whole value of these fields is that `name='shipping.city'` is a compile error the moment `shipping` stops having a `city`. The type has to carry both the form's data shape and the flat field components hanging off the instance.

The type is `FormInstance`, exported by every kit. It takes the form's value type, and by default describes the kit's full bundle — every built-in field kind and all four components:

```tsx
import type { FormInstance } from '@ez-kit/form-shadcn'

function AddressBlock({ form, path }: { form: FormInstance<Checkout>; path: 'billing' | 'shipping' }) {
	return (
		<form.TextField
			name={`${path}.city`}
			label='City'
		/>
	)
}
```

Any instance `useForm` returns for a `Checkout` is accepted, whatever validators it was given — they stay on the instance and do not have to be restated in the prop's type. The price is that the prop's type no longer knows them: through a `FormInstance`, everything typed from a validator or the submit meta is `any` — `state.errors`, `state.errorMap`, `getAllErrors()`, field-level errors, `options.validators`, `options.onSubmitMeta` and the meta `handleSubmit` takes. Values and field names stay fully typed. The same openness works in reverse: a `FormInstance` is accepted by a `withForm` block that declared validators of its own, so a block that relies on its errors being typed should be handed the instance `useForm` returned, not one passed through a `FormInstance` prop.

A form built from a subset names its own shape once: `FormInstance<V, typeof fields, typeof components>`, with `NoRegistry` standing for a set left empty. A block typed with the one-argument form asks for the kit's full bundle, so an instance that registered fewer fields is not assignable to it.

The example is a checkout with a billing and a shipping address. `AddressBlock` is written once, takes `form` plus the path it should write into, and is rendered twice. Inside it, `form.TextField` is the same component, checked against the same value type, as at the top level.

That example declares its `form` prop by hand — deliberately, because it is rendered under two kits at once and so cannot import either kit's `withForm`. In your own app you would not: `withForm` infers the type for you.

## `withForm`

`withForm` builds a block from form options plus a render function, and infers the `form` prop's type from the options:

```tsx
import { withForm } from '@ez-kit/form-shadcn'

const AddressBlock = withForm({
	defaultValues: DEFAULT_CHECKOUT,
	props: { path: 'billing' as AddressPath, heading: '' },
	render: ({ form, path, heading }) => (
		<fieldset>
			<legend>{heading}</legend>
			<form.TextField
				name={`${path}.street`}
				label='Street'
			/>
			<form.TextField
				name={`${path}.city`}
				label='City'
			/>
		</fieldset>
	),
})
```

The form options are **required, not decorative**. `defaultValues` — or another option that pins the shape — is the only place the block's data type can be inferred from. A block written as `withForm({ render })` infers `unknown`, which collapses the set of writable field names to `never`: no `name` compiles inside it, and no real form is assignable to it from outside. Always declare a block against the form data it belongs to.

Extra props go through the `props` option, which is also their inference site; they are not inferred from the render function's own parameter.

There is no runtime here. `withForm` hands the options straight to TanStack, which only closes over `render`.

### Why it had to be retyped

TanStack types the render prop's `form` as an API parameterised by the components injected into `createFormHook`. This adapter injects **none** — the kit's primitives reach the fields by closure instead — so TanStack's own type describes an instance with no `TextField` on it, and `form.TextField` inside a block would fail to compile while working perfectly at runtime.

So `withForm` is wrapped, and the single thing the wrapper changes is that declared type: it names the kit's own form instance — the type `useForm` returns, with the validators the block's options declare — rather than TanStack's component-less one. A block therefore sees exactly the instance it is handed. The reasoning is written out in full at the top of `packages/form/react/react/src/composition.ts`.

That wrapping is what puts `withForm` on the kit rather than on the adapter's general surface: it is produced by `createForm({ fields, components })` together with `useForm`, `Form` and `FormProvider` (and by `createSchemaForm`, which adds `SchemaForm`), so you import it from `@ez-kit/form-shadcn` or `@ez-kit/form-heroui` alongside them.

## `withFieldGroup`

`withForm` ties a block to **one form's** shape. `withFieldGroup` is the other half of the pair, for a block that should be reusable across **different** forms: it is written against the group's own shape — `Address` — and mapped onto a parent path at the call site.

```tsx
<AddressGroup
	form={form}
	fields='shipping'
/>
```

The same block then serves any form that has an `Address` somewhere in it, under whatever name.

The trade is deliberate and is the thing to weigh when choosing between the two. A group's render prop receives a **group API**, and a group API carries the native `group.Field`, not the flat field components — because a group has no idea what the surrounding form's value type is, which is exactly the freedom you asked for. Inside a field group you are in [native API](/docs/form/native-api) territory.

Because of that, `withFieldGroup` needed no retyping and is re-exported as TanStack builds it. It still comes from your kit, since `createForm` returns it — and the parent `form` prop of the component it produces already accepts a `FormInstance`, that type being an intersection over TanStack's.

## The two hooks

`useFieldGroup` is the hook behind `withFieldGroup`: it takes the parent form and a `fields` mapping and returns the same group API, for when you want a group inside a component you are already writing rather than a standalone block. `useFormGroup` scopes a subtree of one form — a named branch with validators of its own — and returns a group API for that branch.

Neither is touched by this package, so both are re-exported **verbatim** from `@tanstack/react-form` by `@ez-kit/form-react`, and from there by each kit. Import them from your kit like everything else:

```ts
import { useFieldGroup, useFormGroup } from '@ez-kit/form-shadcn'
```

The [TanStack Form documentation](https://tanstack.com/form/latest/docs/framework/react/quick-start) is the reference for their options; nothing here changes them.

## Components that know about the form

A block is tied to the shape of one form. Many components are not: a save bar, an error summary, a "discard changes" button need the form's _state_ and _submit_, not its field names. They read the form from context.

`<Form>` and `<SchemaForm>` set that context, and `useFormContext()` returns the form's **base API** — `Subscribe`, `state`, `handleSubmit`, `Submit`, `Array`, `Field` — without the fields a bundle registered, and with the values typed `unknown`. It is exported by the package and by each kit, not by the bundle, so it can be used from a component the bundle itself registers.

```tsx
import { useFormContext } from '@ez-kit/form-shadcn'

function ErrorSummary() {
	const form = useFormContext()

	return (
		<form.Subscribe selector={(state) => state.errors}>
			{(errors) => (errors.length > 0 ? <p role='alert'>{errors.length} problems</p> : null)}
		</form.Subscribe>
	)
}
```

Register it in `components` and it is `<form.ErrorSummary />` with its own props; leave it out and render `<ErrorSummary />` directly. It is the same component either way, which is why `createForm` attaches components as they are rather than binding them to an instance.

```tsx
export const { useForm, Form } = createForm({
	FormElement,
	fields: allFormFields,
	components: { ...allFormComponents, ErrorSummary },
})
```

### `FormProvider`

When you own the `<form>` element, or there is none, `<Form>` is not in the tree and nothing sets the context. `FormProvider` sets it without rendering a `<form>`:

```tsx
const form = useForm({ defaultValues: { email: '' }, onSubmit })

return (
	<FormProvider form={form}>
		<form
			onSubmit={(event) => {
				event.preventDefault()
				void form.handleSubmit()
			}}
		>
			<form.TextField
				name='email'
				label='Email'
			/>
		</form>
		<form.SubmitButton>Save</form.SubmitButton>
	</FormProvider>
)
```

A component that reads the form from context — `form.SubmitButton`, `form.ErrorSummary`, your own — throws `useFormContext() must be called inside <Form>, <SchemaForm> or <FormProvider>` without one. A hand-written `<form>` does not count. Here the submit button sits outside the `<form>` element and still works: it is built on [`form.Submit`](/docs/form/submission#formsubmit), which hands out `submit`.

## Choosing

Reuse a block within **one form's** shape — an address at two paths, a step in a wizard over the same data — and `withForm` is the one to reach for, because it keeps the flat fields.

Reuse a block across **different forms** and `withFieldGroup` is the only one that can, at the cost of writing its fields natively.

And if the block is only ever rendered once, it does not need either: a plain component taking `form: FormInstance<Values>`, as the example's `AddressBlock` does, is less machinery for the same result.

<Callout>
	A `FormSchema` has an analogue in nested `section` and `step` nodes, but it is not the same mechanism. Those group
	fields for **layout and visibility** inside one document; they do not produce a reusable, separately typed unit that
	several forms can render. See [Config-driven forms](/docs/form/schema).
</Callout>
