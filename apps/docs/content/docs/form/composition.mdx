Reusing a whole form needs no helper: it is a component, and you render it twice. The helpers are for reusing a **part** of one — and which part you have decides which helper you want:

| You need                                                         | Use              |
| ---------------------------------------------------------------- | ---------------- |
| to cut **one** large form into files, a part that sees all of it | `withForm`       |
| one set of fields in **different** forms, with its own rules     | `withFieldGroup` |
| a branch **inside** a form with its own check and its own "Save" | `form.FormGroup` |

All three come from your kit — `withForm` and `withFieldGroup` are returned by `createForm` beside `useForm` and `Form`, and `form.FormGroup` hangs off every form instance — so import them from `@ez-kit/form-shadcn` or `@ez-kit/form-heroui` like everything else.

## `withForm`

`withForm` builds a part of **one** form: a block typed by the whole form's data, with the same flat fields the form has. It has no rules of its own — it is a file boundary, not a validation one.

```tsx
import { withForm } from '@ez-kit/form-shadcn'

const AddressBlock = withForm({
	defaultValues: DEFAULT_CHECKOUT,
	props: { path: 'billing' as AddressPath, heading: '' },
	render: ({ form, path, heading }) => (
		<fieldset>
			<legend>{heading}</legend>
			<form.TextField
				name={`${path}.street`}
				label='Street'
			/>
			<form.TextField
				name={`${path}.city`}
				label='City'
			/>
		</fieldset>
	),
})
```

The `form` prop is optional:

- **Passed** — `<AddressBlock form={form} path='shipping' heading='Shipping' />` — and it is checked where the block is placed: a form over another shape does not compile.
- **Omitted** — `<AddressBlock path='shipping' heading='Shipping' />` — and the block reads the form above it, from `<Form>`, `<SchemaForm>` or `FormProvider`. That is a **cast, not a check**, exactly like [`useFormContext<V>()`](#typing-the-values): nothing verifies that the form above has the block's data.
- **Neither** — no prop and no form above — and the block throws ``withForm(): the block needs a form — pass `form`, or render it inside <Form>, <SchemaForm> or <FormProvider>.`` on its first render, in every environment.

The form options are **required, not decorative**. `defaultValues` — or another option that pins the shape — is the only place the block's data type can be inferred from. A block written as `withForm({ render })` infers `unknown`, which collapses the set of writable field names to `never`: no `name` compiles inside it, and no real form is assignable to it from outside. Always declare a block against the form data it belongs to.

Extra props go through the `props` option, which is also their inference site; they are not inferred from the render function's own parameter.

The `form` the render function receives is typed as the kit's own form instance — the type `useForm` returns, with the validators the block's options declare — rather than TanStack's, which describes an instance without the flat fields; that is what makes `form.TextField` compile inside a block.

### A plain component is enough once

If a part is only ever rendered once, it needs no helper either. A plain component that takes the form as a prop typed `FormInstance<Values>` — exported by every kit — is less machinery for the same result, and any instance `useForm` returns for those values is accepted, whatever validators it was given. The price is that the prop's type no longer knows them: through a `FormInstance`, everything typed from a validator or the submit meta is `any`, while values and field names stay fully typed. A form built from a subset names its own shape once: `FormInstance<V, typeof fields, typeof components>`.

## `withFieldGroup`

`withFieldGroup` builds a block written in **its own** coordinates — typed by its own shape, not by any form's — and placed into any form that has that shape somewhere. Its `render` receives a `group` carrying every field your bundle registered, with names relative to the block: `group.TextField name='password'`, `group.ArrayField`, your own registered fields, `group.Field` and `group.NativeField`.

```tsx
import { withFieldGroup } from '@ez-kit/form-shadcn'

const PasswordPair = withFieldGroup({
	defaultValues: PASSWORD_PAIR_DEFAULTS,
	validators: { onChange: passwordPairSchema },
	render: ({ group }) => (
		<>
			<group.TextField
				name='password'
				type='password'
				label='Password'
			/>
			<group.TextField
				name='confirm'
				type='password'
				label='Repeat password'
			/>
		</>
	),
})
```

### Placing it

Where the block lies is said by `fields`, at the place:

- **A path** — `<PasswordPair fields='security' />` — puts it on a branch: `password` is `security.password`.
- **A map** — `<PasswordPair fields={{ password: 'password', confirm: 'confirm' }} />` — names a path for each of the block's keys, so its fields can sit anywhere in the form, the root included.

The form is the one above the block, as for `withForm`, or the one you pass as `form`. With `form`, `fields` is checked against it: a path to a branch of another shape, or a map naming a path whose value does not fit, does not compile. Without it, `fields` is a cast — any path, or a map that names every key of the block.

### Its own rules

`validators` take the TanStack slots — `onMount`, `onChange`, `onBlur`, `onSubmit`, their async variants and debounces — each either a Standard Schema over the block's own shape, one per object, or a function of `{ value }`. The schema is written in the block's coordinates whatever placement it gets:

- an issue **with a path** — `confirm` — lands on the real field: `security.confirm` under a path, `confirm` under the map above;
- an issue **without one** — a refine over the whole object — is the block's own, and reaches `render` as `group.errors`, a `string[]`.

### Its own submit

`group.handleSubmit()`, called inside the block, submits the block: it checks the block's fields and its `validators`, then calls the `onGroupSubmit` the block was placed with, with `value` typed by the block. It does **not** submit the form. Invalid, it focuses the block's first field with an error, as the form's `focusOnError` says.

```tsx
<SecuritySection
	fields='security'
	onGroupSubmit={({ value }) => api.changePassword(value)}
/>
```

So a section that needs a "Save this section" button wherever it goes keeps the button inside itself, and each page decides only where the section lies and what its submit does.

<Callout type='warn'>
	**Breaking:** `group.handleSubmit()` inside a `withFieldGroup` block used to submit the whole form, as TanStack's
	field group does. It now submits the block only. To submit the form from inside a block, call
	`group.form.handleSubmit()`.
</Callout>

### `withFieldGroup` options

| Option          | Type                                      | Notes                                                               |
| --------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| `defaultValues` | `TGroup`                                  | The block's own shape — the inference site for its type.            |
| `props`         | `object`                                  | The block's extra props, inferred from here. Required at the place. |
| `validators`    | `GroupValidators<TGroup>`                 | The block's own rules, in its coordinates.                          |
| `render`        | `(props: { group } & props) => ReactNode` | The block's body.                                                   |

### Placing a block

| Prop            | Type                                       | Notes                                                                                                                                |
| --------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `form`          | `FormInstance<TFormData>`                  | Optional. Passed, `fields` is checked against it; omitted, the form above.                                                           |
| `fields`        | path, or `{ [key in keyof TGroup]: path }` | Where the block lies: a branch, or a path per key.                                                                                   |
| `onGroupSubmit` | `({ value, meta }) => unknown`             | Called when `group.handleSubmit()` finds the block valid. `meta` is `undefined` when `handleSubmit()` is called without an argument. |

## `form.FormGroup`

`form.FormGroup` is a branch **inside** one form with its own check and its own submit — the right tool when a section needs a "Save" on one page only, or a rule that belongs to this form rather than to a reusable block.

```tsx
<form.FormGroup
	name='payment'
	validators={{ onChange: cardSchema }}
	onGroupSubmit={({ value }) => api.savePayment(value)}
>
	{(group) => (
		<>
			<group.TextField
				name='card'
				label='Card'
			/>
			<group.TextField
				name='cvc'
				label='CVC'
			/>
		</>
	)}
</form.FormGroup>
```

Its `group` carries the bundle's flat fields, named relative to `name`: `group.TextField name='card'` writes `payment.card`. That is what puts the group's schema and its fields in one set of coordinates — TanStack hands the group's validators `values[name]`, so the schema's keys are relative too.

`group.handleSubmit()` is a group submit: it checks the branch's fields, the blocks mounted inside it and the group's own `validators`, then calls `onGroupSubmit`; the form's `onSubmit` is not called. `group.errors` holds the group's own messages — those its validators report with no path — as strings; `group.state.meta.errors` is TanStack's raw value and can hold a record of every issue by path, which is not fit to display.

## Coordinates come from the object, not the tree

A field's path is read from the object you called it through — never from what sits above it in the tree:

- `form.X` is **absolute**, inside a group too — and so are the schemas beside it: the form's, and a step's.
- `group.X` is **relative** to the group's branch, `form.FormGroup` and `withFieldGroup` alike — and so is the group's schema.

There is no implicit prefix. `form.TextField` is created once per form and cannot know what will render above it; if it took a prefix from its ancestors, its `name` could only be typed `string`, and moving a component would silently change where its data is written.

So `form.TextField name='payment.card'` inside `form.FormGroup name='payment'` works — it writes `payment.card` — but do not write it: the field and the group's schema then name the same value in two coordinates. Inside a group, write `group.TextField name='card'`.

## Where a rule goes

- **The block owns it** — a card number's format, two passwords that must match — and it goes in the block's `validators`, so it travels with the block to every form.
- **It depends on the place** — billing is required only when it differs from shipping — and it goes on a `form.FormGroup` or in the form's schema, at that place.
- **The form's schema on `onSubmit`** is the last barrier.
- **One validating group per branch.** A `form.FormGroup` and a block placed on the same name share one group state, so when both carry `validators`, the later pass erases the other's own errors. Put the place's rule in the form's schema, or keep the outer group without validators as _Change password_ above does. In development, two validating groups on one name log an error.

A whole-form submit runs every mounted group's validators too: a block that fails, even untouched, blocks the form's `onSubmit` — which is why _Save profile_ above stops on the password pair. The same rule on two levels is fine on different triggers — the group's on `onChange` or `onBlur`, the form's on `onSubmit` — and when both report it, the field shows the message once.

## Server errors and group submits

A group submit — `group.handleSubmit()` on a `form.FormGroup`, a `withFieldGroup` block or `useFormGroup` — clears the [server errors](/docs/form/submission#server-errors) of the fields inside the group, and only those: form-level messages and other fields' errors stay, because the group submit does not send the form. Invalid, it focuses the group's first field with an error.

## The two hooks

`useFieldGroup` is the hook behind `withFieldGroup`: it takes the parent form and a `fields` path or map and returns the field group, for when you want a group inside a component you are already writing rather than a standalone block. `useFormGroup` is the hook behind `form.FormGroup`: it scopes a named branch of one form, with validators of its own. Neither carries the flat fields — inside, fields are written with `group.Field` (your own control, bound, `name` relative to the group) or `group.NativeField`, as [Native API](/docs/form/native-api#groups-and-array-entries) describes.

Both hooks are this package's own, wrapping TanStack's: they take the instance `useForm` returns as their `form`, not a TanStack `FormApi`, and a group cannot be another group's `form`. `@ez-kit/form-react` exports them, and each kit re-exports them:

```ts
import { useFieldGroup, useFormGroup } from '@ez-kit/form-shadcn'
```

`useFieldGroup` takes `form`, `fields` and an optional `defaultValues`. `useFormGroup` takes `form` plus TanStack's form-group options — `name`, `validators`, `onGroupSubmit` and the rest — and the [TanStack Form documentation](https://tanstack.com/form/latest/docs/framework/react/quick-start) is the reference for those. Its group also has `errors`, and its `handleSubmit` is the group submit described above.

## Components that know about the form

A block is tied to the shape of one form. Many components are not: a save bar, an error summary, a "discard changes" button need the form's _state_ and _submit_, not its field names. They read the form from context.

`<Form>` and `<SchemaForm>` set that context, and `useFormContext()` returns the form's **base API** — `Subscribe`, `state`, `handleSubmit`, `Submit`, `Array`, `Field`, `NativeField` — without the fields a bundle registered, and with the values typed `unknown`. It is exported by the package and by each kit, not by the bundle, so it can be used from a component the bundle itself registers.

```tsx
import { useFormContext } from '@ez-kit/form-shadcn'

function ErrorSummary() {
	const form = useFormContext()

	return (
		<form.Subscribe selector={(state) => state.errors}>
			{(errors) => (errors.length > 0 ? <p role='alert'>{errors.length} problems</p> : null)}
		</form.Subscribe>
	)
}
```

Register it in `components` and it is `<form.ErrorSummary />` with its own props; leave it out and render `<ErrorSummary />` directly. It is the same component either way, which is why `createForm` attaches components as they are rather than binding them to an instance.

```tsx
export const { useForm, Form } = createForm({
	FormElement,
	fields: allFormFields,
	components: { ...allFormComponents, ErrorSummary },
})
```

### Typing the values

`useFormContext` takes an optional type argument. `useFormContext<Values>()` types the same base API over `Values`, and adds the kit's **built-in** fields with their value-typed `name` — `form.TextField name` accepts only the string paths of `Values`:

```tsx
type SignUp = { email: string; age: number }

function EmailHint() {
	const form = useFormContext<SignUp>()

	return (
		<form.Subscribe selector={(state) => state.values.email}>{(email) => <p>Signing up as {email}</p>}</form.Subscribe>
	)
}
```

It is **a cast, not a check**: nothing verifies that the form above has these values, or that the bundle registered the built-in field you call. Fields and components you registered yourself are not on it, since naming them would need the bundle, and a component the bundle registers cannot import it. Call it with a concrete type; a component that names paths in one form's data is better written with `withForm` or `withFieldGroup`, which are checked where they are placed.

### `FormProvider`

When you own the `<form>` element, or there is none, `<Form>` is not in the tree and nothing sets the context. `FormProvider` sets it without rendering a `<form>`:

```tsx
const form = useForm({ defaultValues: { email: '' }, onSubmit })

return (
	<FormProvider form={form}>
		<form
			onSubmit={(event) => {
				event.preventDefault()
				void form.handleSubmit()
			}}
		>
			<form.TextField
				name='email'
				label='Email'
			/>
		</form>
		<form.SubmitButton>Save</form.SubmitButton>
	</FormProvider>
)
```

A component that reads the form from context — `form.SubmitButton`, `form.ErrorSummary`, your own — throws `useFormContext() must be called inside <Form>, <SchemaForm> or <FormProvider>` without one. A hand-written `<form>` does not count. Here the submit button sits outside the `<form>` element and still works: it is built on [`form.Submit`](/docs/form/submission#formsubmit), which hands out `submit`.

## Choosing

Each helper has one role:

- **`withFieldGroup`** reuses a set of fields across forms, with its rules and, when it needs one, its submit.
- **`withForm`** cuts one form into files, and each part sees the whole form — a later part can read what an earlier one wrote.
- **`form.FormGroup`** is the validation and submit boundary of a branch inside one form.
- **`form.Step`**, coming next, will say what is on screen and what to check before _Next_.

<Callout>
	A `FormSchema` has an analogue in nested `section` and `step` nodes, but it is not the same mechanism. Those group
	fields for **layout and visibility** inside one document; they do not produce a reusable, separately typed unit that
	several forms can render. See [Config-driven forms](/docs/form/schema).
</Callout>
