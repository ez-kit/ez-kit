# Fields

Every field is **complete**: it renders its own label, description, input and error message, and wires the accessibility attributes that tie them together. You give it a `name` and a `label`.

<KitExample exampleId='form-fields' />

## Shared props

| Prop          | Type        | Notes                                                                                       |
| ------------- | ----------- | ------------------------------------------------------------------------------------------- |
| `name`        | typed path  | **Required.** Narrowed to paths whose value type matches the field.                         |
| `label`       | `ReactNode` | Omit it and no label element is rendered.                                                   |
| `description` | `ReactNode` | Helper text, linked via `aria-describedby`.                                                 |
| `disabled`    | `boolean`   |                                                                                             |
| `required`    | `boolean`   | Marks the control required. It does **not** validate — see [Validation](./form/validation). |

## `form.TextField`

Single-line text. Accepts `placeholder` and `type`.

```tsx
import { TextInputType } from '@ez-kit/form-shadcn'
;<form.TextField
	name='email'
	label='Email'
	placeholder='you@example.com'
	type={TextInputType.Email}
/>
```

`type` is the `TextInputType` enum — `Text`, `Email`, `Password`, `Tel`, `Url`, `Search` — rather than a bare string, so a typo cannot slip through.

## `form.NumberField`

Binds to a `number`. Accepts `placeholder`, `min`, `max`, `step`.

```tsx
<form.NumberField
	name='age'
	label='Age'
	min={0}
	max={130}
/>
```

An empty control is `undefined` in form state, not `NaN` — "no number entered" is genuinely a different thing from "not a number", and `undefined` is what a schema like `z.number()` will correctly reject as missing.

## `form.TextareaField`

Multi-line text. Accepts `placeholder` and `rows`.

```tsx
<form.TextareaField
	name='bio'
	label='Bio'
	rows={4}
/>
```

## `form.SelectField`

Binds to a `string`. Options are a flat list, identical across kits:

```tsx
<form.SelectField
	name='role'
	label='Role'
	placeholder='Pick a role'
	options={[
		{ label: 'Viewer', value: 'viewer' },
		{ label: 'Admin', value: 'admin', disabled: true },
	]}
/>
```

Each option is a `SelectOption`: `{ label, value, disabled? }`. Both kits render a real listbox widget (Radix for shadcn, React Aria for HeroUI), not a native `<select>` — the flat list is what shields you from that difference.

An empty string means "nothing selected", so the placeholder shows.

### Numeric option values

An option `value` may be a **string or a number**, and `name` is checked against it: a field bound to a `number` path takes numeric options, one bound to a `string` path string ones. Mixing the two is a compile error, not a lookup that quietly finds nothing.

```tsx
// `countryId: number` in the form values
<form.SelectField
	name='countryId'
	label='Country'
	options={[
		{ label: 'Germany', value: 49 },
		{ label: 'France', value: 33 },
	]}
/>
```

Form state holds the option's value **verbatim** — `49`, never `'49'` — so a submitted payload carries the entity id a backend expects. The kits themselves stay string-only at the DOM edge (Radix requires string item values, and reserves `''` for "nothing selected"); the binding layer stringifies the options on the way down and maps the string a kit reports back to the option it came from. That is a lookup, never `Number(value)`, so a string-valued `'42'` stays a string.

The same holds for `form.RadioGroupField`, `form.MultiSelectField` (a `number[]` path) and `form.CheckboxGroupField`, and for the equivalent schema nodes. `parseFormSchema` rejects a delivered document that mixes string and number values in one list: `1` and `'1'` are distinct option values that collide the moment a kit renders them as keys.

### Options that arrive later

When an app fetches its options, `options={data ?? []}` is ambiguous: an empty list can mean "still fetching" or "the backend genuinely offers nothing", and both render as an empty dropdown. Pass `loading` to say which:

```tsx
const { data, isPending } = useQuery({ queryKey: ['roles'], queryFn: fetchRoles })
;<form.SelectField
	name='role'
	label='Role'
	options={data ?? []}
	loading={isPending}
/>
```

While `loading` is true both kits disable the control and show a **skeleton** in place of its value — a single bar in a select or multi-select trigger, a short list of placeholder rows in a radio or checkbox group, which have no trigger to put one in. That is also what covers an edit form: a value loaded from the server (`role: 'admin'`) arrives before the option that carries its label, and a skeleton reads better than a blank trigger.

`loading` is accepted by all four option-bearing fields — `form.SelectField`, `form.MultiSelectField`, `form.RadioGroupField`, `form.CheckboxGroupField` — and defaults to `false`. It is a **rendering** concern, not part of the schema: a statically authored `options` array in a `FormSchema` is never loading, and `@ez-kit/form-core` knows nothing about it.

Failure is deliberately not in the contract: there is no `error` or `onRetry` prop. A retry button inside a select popover is awkward UI and multiplies badly across the four widgets, and the code that supplies the options is already the right place to surface a failed fetch — a toast from `onError`, an error boundary, a message beside the form.

## `form.CheckboxField`

Binds to a `boolean`.

```tsx
<form.CheckboxField
	name='newsletter'
	label='Send me the newsletter'
/>
```

## `form.SwitchField`

Binds to a `boolean`, like `form.CheckboxField` — same props, no extras. Reach for the switch when the control toggles a setting that takes effect immediately (notifications, dark mode), and the checkbox when it records a choice the form submits later (accept terms, subscribe).

```tsx
<form.SwitchField
	name='notifications'
	label='Enable notifications'
	description='Toggle email and in-app alerts.'
/>
```

Both kits render a real switch widget with a moving thumb (Radix for shadcn, React Aria for HeroUI), so its on/off state reads at a glance.

## `form.RadioGroupField`

Binds to a `string`. Like `form.SelectField` it takes a flat `options` list, but it lays every choice out at once instead of hiding them behind a trigger — use it for a small, fixed set the user should see in full:

```tsx
<form.RadioGroupField
	name='plan'
	label='Plan'
	options={[
		{ label: 'Free', value: 'free' },
		{ label: 'Pro', value: 'pro' },
		{ label: 'Enterprise', value: 'enterprise', disabled: true },
	]}
/>
```

Each option is the same `SelectOption` shape as `form.SelectField`: `{ label, value, disabled? }`. The value in form state is the selected option's `value`; an empty string means nothing is selected.

## `form.MultiSelectField`

Binds to a **`string[]`** — the multi-value counterpart of `form.SelectField`, taking the same flat `options` list:

```tsx
<form.MultiSelectField
	name='tags'
	label='Tags'
	placeholder='Pick a few'
	options={[
		{ label: 'Design', value: 'design' },
		{ label: 'Engineering', value: 'engineering' },
	]}
/>
```

The value is always a list — `[]` when nothing is chosen, never `undefined` — and `onChange` reports the whole new selection rather than a toggle.

**A separate field, not a `multiple` flag on `form.SelectField`.** Its value has a different type, and that is what keeps `name` narrowed to `string[]` paths here and to `string` paths there. The kits differ underneath and it does not matter: HeroUI uses its own `Select` in `selectionMode='multiple'`, shadcn a popover of checkboxes (Radix's select is single-selection only).

## `form.CheckboxGroupField`

Binds to a `string[]` as well, but lays every choice out at once — the multi-value counterpart of `form.RadioGroupField`:

```tsx
<form.CheckboxGroupField
	name='interests'
	label='Interests'
	options={[
		{ label: 'Code', value: 'code' },
		{ label: 'Design', value: 'design' },
	]}
/>
```

It is **one field**, not one per box: a single `name` holding the list of checked values. A lone `form.CheckboxField` remains what it was — one boolean, for "I agree".

The four selection fields line up as a grid — collapsed or expanded, one value or many:

|                                   | one value         | many values          |
| --------------------------------- | ----------------- | -------------------- |
| collapsed (trigger plus a popup)  | `SelectField`     | `MultiSelectField`   |
| expanded (every choice on screen) | `RadioGroupField` | `CheckboxGroupField` |

## `form.SliderField`

Binds to a `number`, like `form.NumberField`, but picks the value along a track instead of typing it. Accepts `min`, `max`, `step` — reach for it when the range is bounded and the exact digit matters less than the feel of "more or less".

```tsx
<form.SliderField
	name='volume'
	label='Volume'
	description='Drag the thumb to set a value between 0 and 100.'
	min={0}
	max={100}
	step={5}
/>
```

| Prop   | Type     | Notes                                    |
| ------ | -------- | ---------------------------------------- |
| `min`  | `number` | Track start. Defaults to `0` if omitted. |
| `max`  | `number` | Track end.                               |
| `step` | `number` | Granularity of each move.                |

A slider has no "empty" position: when the form value is not yet a number the thumb rests at `min` (or `0` when `min` is omitted), so the control always shows a definite value. Both kits render a real slider widget with a draggable thumb (Radix for shadcn, React Aria for HeroUI).

## `form.DateField`

Binds to a **`YYYY-MM-DD` string**, never a `Date`. A calendar date has no time and no zone, and a string is the only representation that survives `JSON.stringify` — which is what lets the same field be described by a [schema](./form/schema) delivered from a backend.

```tsx
<form.DateField
	name='startsOn'
	label='Starts on'
	min='2026-01-01'
	max='2026-12-31'
/>
```

| Prop          | Type     | Notes                                         |
| ------------- | -------- | --------------------------------------------- |
| `min`         | `string` | Earliest selectable day, `YYYY-MM-DD`.        |
| `max`         | `string` | Latest selectable day.                        |
| `placeholder` | `string` | Shown on the trigger while nothing is picked. |

`min` / `max` bound what the picker _offers_; they are not validation. To reject an out-of-range value use `validate: { min, max }` in a schema — those constraints take the same `YYYY-MM-DD` strings, and ISO dates compare correctly as text.

Each kit renders its own picker: shadcn a `Popover` holding its `Calendar` (react-day-picker), HeroUI its React Aria `DatePicker` with a segmented input. Both convert to and from the string at their own edge — no date library reaches your form state.

## `form.DateRangeField`

Binds to a **`{ start, end }` object** of two `YYYY-MM-DD` strings, under a single `name`:

```tsx
<form.DateRangeField
	name='stay'
	label='Stay'
	min='2026-01-01'
/>
```

A range is a separate field rather than a flag on `form.DateField` because its value has a different shape — which is what keeps `name` checked against your form's type in both cases.

**The value appears only once both ends are picked.** A half-picked range lives inside the picker; form state holds either a complete range or nothing, so validation, `onSubmit` and a `when` rule never have to handle `{ start, end: undefined }`.

## `form.SubmitButton`

Subscribed to the form's `canSubmit` and `isSubmitting`, so it disables itself while the form is invalid or in flight. The `disabled` prop can only add to that, never override it.

```tsx
<form.SubmitButton>Save</form.SubmitButton>
```

## `Form`

The `<form>` element, already wired to `handleSubmit`, with `noValidate` set so the browser's own bubbles stay out of the way. It accepts the usual `<form>` props **except `onSubmit`**, which it owns — in uncontrolled mode `onSubmit` is TanStack's, called with the validated values.

```tsx
<Form
	defaultValues={{ email: '' }}
	className='max-w-sm'
>
	{(form) => (
		<form.TextField
			name='email'
			label='Email'
		/>
	)}
</Form>
```

See [Getting started](./form/getting-started) for both modes.

## Styling hooks

The field layer emits these and styles none of them — that is the kit's job:

| Attribute         | Where        | Value                                                                                                                                                |
| ----------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data-field`      | field root   | the field's `name`                                                                                                                                   |
| `data-field-type` | field root   | `text` / `number` / `textarea` / `select` / `multiselect` / `checkbox` / `checkboxgroup` / `switch` / `radiogroup` / `slider` / `date` / `daterange` |
| `data-invalid`    | field root   | `true` while the field has errors, absent otherwise                                                                                                  |
| `data-form`       | the `<form>` | always present                                                                                                                                       |

So targeting one field, or every field of a kind, is plain CSS:

```css
[data-field='email'] {
	grid-column: span 2;
}
[data-field-type='checkbox'] {
	flex-direction: row;
	align-items: center;
}
[data-invalid] label {
	color: var(--destructive);
}
```

## Fields we do not ship yet

Date-picker and combobox are planned. Until then, build them with [the native API](./form/native-api) — it composes with the flat fields in the same form.
