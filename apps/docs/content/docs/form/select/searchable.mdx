---
title: Searchable select and multiselect
description: A select or multiselect that queries as the user types — and still shows the labels of values the current results do not contain.
---

Everything in [Option sources](/docs/form/select/option-sources) assumes a source returns **the whole list**. That assumption is doing more work than it looks: because the list is complete, the option carrying the value in form state is always on it, so the kit can draw its label by finding the matching entry.

Server-side search breaks that permanently. The source now returns only the **page matching the last query**. Form state holds `city: 4821`, the current results are Lisbon and Porto, and no option carries `4821` — so the control renders blank, forever. It is the transient "the value arrived before its option" case from [`loading`](/docs/form/select#options-that-arrive-later) made permanent.

Add `searchable` to a `select` — or a `multiselect` — that already names a source:

```tsx
<form.SelectField
	name='address.city'
	optionsFrom='cities'
	optionsParams={{ country }}
	searchable
/>
```

```json
{
	"type": "select",
	"name": "address.city",
	"searchable": true,
	"optionsFrom": { "source": "cities", "dependsOn": { "country": "address.country" } }
}
```

There is no new node `type`. The value and its shape are unchanged and only the presentation differs — the same reasoning that kept numeric option values on `select` instead of spawning a second kind.

The flag reads the same on either side, and the source it needs is registered once for both.

## Why a source grows a second hook

A searchable source answers two questions instead of one:

```tsx
function useCitySearch({ params, query }) {
	const results = useQuery({
		queryKey: ['cities', params, query],
		queryFn: () => api.searchCities(params, query),
		enabled: query !== undefined,
	})
	return { options: (results.data ?? []).map(toOption), loading: results.isPending }
}

function useCitiesByValue({ values }) {
	const rows = useQuery({
		queryKey: ['cities', 'byId', values],
		queryFn: () => api.getCities(values),
		enabled: values.length > 0,
	})
	return { options: (rows.data ?? []).map(toOption), loading: rows.isPending }
}

const optionSources = {
	cities: { useOptions: useCitySearch, useSelectedOptions: useCitiesByValue, minLength: 2 },
}
```

`useOptions` answers "what matches what was just typed". `useSelectedOptions` answers "what is the option behind the value already in form state" — the only one of the two that can label a selection the current page does not contain.

This is not an invention: react-admin pays exactly the same price, with a `getMany(ids)` call alongside `getList`. Two questions genuinely need two answers, and a single endpoint that tried to serve both would have to guess which one it was being asked.

`values` is an **array**, which is what lets one source serve both kinds of field: a `select` sends its single value as a one-element array, a `multiselect` sends its whole selection. A source written for one works unchanged for the other.

## The kit never learns there are two queries

`SchemaForm` calls both hooks and merges their results — search results first, any selected option the search did not return appended, deduped by value — before handing one `options` list to the kit. `loading` is true while **either** hook is loading, and while the typed text is waiting out the [debounce](#debounce-and-minimum-length) on its way to the source.

So from a kit's side nothing changed: it is still "find the option whose value matches". A kit gets one new key — the identical one on `SelectFieldRenderProps` and `MultiSelectFieldRenderProps`:

```ts
/** Present only for a searchable field; `undefined` means a plain one. */
search:
	| {
			query: string
			onQueryChange: (query: string) => void
			minLength: number
			belowMinLength: boolean
	  }
	| undefined
```

Its presence _is_ the mode switch. `query` is the typed text, at once — what the input shows; the source sees it later, debounced. `minLength` and `belowMinLength` exist for one hint: while the text is too short to search, the list holds only the selected options, and where the kit would say "No matches" it says how much more to type instead. `SchemaForm` owns the query — it must, since it is what feeds the source — so the kit stays fully controlled, exactly as it is for every value in the contract. A kit must **never filter `options` itself**: that filtering already happened, server-side, and a second pass would hide rows the search deliberately returned.

## Existing sources are unaffected

The source type is now a union:

```ts
type OptionSource = ((input: OptionSourceInput) => OptionSourceResult) | SearchableOptionSource
```

Every source written against the plain function shape stays valid, and a plain function remains the right answer for any source that returns its whole list. `query` on the input is additive — a source that never reads it simply ignores it.

Both members of the object form are **hooks**, so both must be named `use…` functions, for the same reason a plain source must be: React and `eslint-plugin-react-hooks` identify a hook by its name. Declare them as named functions and reference them in the registry literal; `source.useOptions(input)` as a member call is fine for the lint rule.

A `searchable` field whose source is the plain function form throws at render, naming the field — it has no way to resolve a selected label, and a silent blank control is a worse answer than an error.

## Debounce and minimum length

The renderer, not the source, decides when the typed text becomes a query. Two settings govern it:

- **`debounce`** — milliseconds without typing before the source sees the text. One request per pause, rather than one per keystroke.
- **`minLength`** — the shortest text the source sees. Below it the source receives `query: undefined`.

For a field over an option source the defaults are **300 ms** and **no minimum**, so a source sees the first character after a pause. A searchable field over an in-memory `options` list filters on every keystroke — no debounce, no minimum — since filtering it costs nothing; the field-level settings below apply to it too.

Set them on the source, where they belong to the endpoint they protect:

```tsx
const optionSources = {
	cities: { useOptions: useCitySearch, useSelectedOptions: useCitiesByValue, debounce: 250, minLength: 2 },
}
```

or per field, where one field needs a different answer. The object form of `searchable` is itself "on", and each key it sets wins over the source's:

```tsx
<form.SelectField
	name='address.city'
	optionsFrom='cities'
	searchable={{ minLength: 3 }}
/>
```

```json
{
	"type": "select",
	"name": "address.city",
	"searchable": { "minLength": 3 },
	"optionsFrom": { "source": "cities" }
}
```

While the typed text is below the minimum:

- **The source gets `query: undefined`** — "no search", not an empty string. Don't fetch a result page for it: `enabled: query !== undefined` in the source above is that check. A source that fetches on `undefined` anyway asks for a page nobody will see.
- **The listed results are dropped and the selection stays.** The options from `useSelectedOptions` remain, so a chosen label never disappears while the user types over it.
- **The kit shows a hint** — "Type at least 2 characters" — where it would otherwise say there are no matches. It is part of the empty state, so while a selected option keeps the list non-empty no hint is shown.
- **The search hook's `loading` is ignored**: nothing is being searched for, and a query hook disabled for an absent query — TanStack Query's `isPending` — would otherwise report loading for as long as the text stays short. `useSelectedOptions`'s `loading` still counts.

A [creatable](/docs/form/select/creatable) field's "Add …" row follows the typed text at once, below the minimum and through the debounce alike — it offers what is in the box, not what the source last saw.

## Searchable multiselect

`searchable` works the same way on a `multiselect`, and needs no change to the source:

```tsx
<form.MultiSelectField
	name='address.cities'
	optionsFrom='cities'
	optionsParams={{ country }}
	searchable
/>
```

```json
{
	"type": "multiselect",
	"name": "address.cities",
	"searchable": true,
	"optionsFrom": { "source": "cities", "dependsOn": { "country": "address.country" } }
}
```

Both examples **start with two cities already chosen**. Nothing has been typed, so the search has returned nothing at all — and both chips read "Lisbon" and "Porto" rather than `4821` and `4825`. That is the whole reason `useSelectedOptions` exists: with a server-side search the current selection is normally off the current page of results, and a chip showing a raw id is exactly the blank-trigger failure of the single-value case, once per value.

`useSelectedOptions` receives the field's **whole value array** here, where a `select` sends a single-element one. Nothing else differs — the same registry entry serves both fields, even in the same form.

**After a selection the query resets to empty**, in both kits. The term that produced the new chip has been consumed by it, and leaving it in the box would silently narrow the next search; the kits agree on this so a form behaves the same whichever one renders it. Removing a chip updates form state immediately and leaves the query alone.

## Scope

`searchable` is legal on `select` and `multiselect` — the two kinds that draw one control standing for the selection.

- **`radiogroup` and `checkboxgroup`** render every option inline. There is no trigger to type into and no page to narrow, so the flag is meaningless there and always will be. `parseFormSchema` rejects it.
- A `searchable` field with a **static `options` list** is filtered in `SchemaForm`, by a case-insensitive substring of the label and with no configuration. Everything else on this page — the second hook, the merged-in selection, the cleared query — is about a _source_, which is what you need the moment matching has to be anything more particular than that. See [Creatable select](/docs/form/select/creatable) for the static case.

## What still holds

Everything `optionsFrom` already did applies unchanged. Most visibly, **changing a parameter still clears the dependent field** — pick a country, pick a city, then change the country: the city goes, rather than lingering behind a control that looks empty and being submitted against the wrong country. A multiselect clears to `[]`, dropping every chip at once. The typed query is cleared with it either way, since "berl" is a search of the wrong catalogue once the country moved.
