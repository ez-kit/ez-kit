# Basic concepts

This page names the moving parts. Nothing here is a how-to; every later page builds on the words defined below.

## Three layers, one machine

The package is split across three layers, and the split is not bookkeeping — it is what makes the same example render under two different UI kits.

`@ez-kit/form-core` is framework-agnostic. It owns the **document**: the `FormSchema` format, the field kinds, the shared `SelectOption` shape, the named validation rules, and the normalisation of validator errors into plain strings. It imports no React and renders nothing, which is what lets a schema be produced by a backend, stored in a database, or generated by a tool that has never heard of React.

`@ez-kit/form-react` is the behaviour: binding a field to form state, tracking submit state, wiring `id` / `aria-labelledby` / `aria-describedby`, deciding when an error is shown. It contains **zero visual styling** — no inline styles, no class names. What it emits are `data-*` attributes and a call into the kit.

The kit — `@ez-kit/form-shadcn` or `@ez-kit/form-heroui` — owns every pixel. A field's entire element tree comes from the kit through a `FormComponents` contract, which is why a React Aria kit can nest its label and error _inside_ the field root while a plain-DOM kit keeps them as siblings, and why neither arrangement is hard-coded anywhere in the react layer.

Two consequences worth carrying forward. First, you install exactly one kit and it pulls the other two in; the kit re-exports the whole consumer surface, so it is the only import specifier you ever write. Second — and this trips people up — **a field's props are not a kit component's props**. `label`, `description`, `required` and the rest are the react layer's vocabulary; the kit decides what markup they become. That boundary is the whole subject of [Custom kit](/docs/form/custom-kit).

## The form instance is a superset

`useForm` is TanStack Form's `useForm`. `<Form>` calls it for you. What comes back is TanStack's own instance with flat field components **attached to it** — nothing is wrapped, proxied or hidden:

```tsx
form.TextField // added by this package
form.Field // TanStack's, untouched
form.handleSubmit // TanStack's, untouched
form.state // TanStack's, untouched
```

There is no adapter and no escape hatch to reach for, because you never left. Any TanStack Form documentation, recipe or plugin applies to this object as written. [Native API](/docs/form/native-api) is the mapping.

## A field is complete

`<form.TextField name='email' label='Email' />` is not an input. It renders the label, the input, the description, the error message once validation fails, and the accessibility wiring that ties them together — `id`, `for`, `aria-invalid`, `aria-labelledby`, `aria-describedby`, `role='alert'`. There is no `value`, no `onChange`, no `onBlur` to pass: the field reads and writes form state itself.

TanStack's own `form.Field` render prop is still there and still works. The difference is what you own:

```tsx
// the flat field: name + label, and the chrome is done
<form.TextField name='email' label='Email' />

// form.Field: you render everything, including label and error
<form.Field name='email'>
	{(field) => (
		<input
			value={field.state.value}
			onChange={(e) => field.handleChange(e.target.value)}
			onBlur={field.handleBlur}
		/>
	)}
</form.Field>
```

Reach for `form.Field` when you need a control the package does not ship. If you want the flat fields' layout and error handling _around_ your own control, the answer is a kit, not a render prop.

## Values and state are different things

`form.state.values` is the data — what `onSubmit` receives. Everything else on `form.state` is machinery about the data: `isDirty`, `canSubmit`, `isSubmitting`, `isValid`, per-field `meta` with its errors and its touched flag.

Reading either one _reactively_ is a topic of its own, because `form.state` in a component body is a snapshot: it does not re-render the component when the value changes. That is a deliberate design of TanStack Form's store rather than an oversight, and the tool for it — `form.Subscribe` — is covered in [Reactivity](/docs/form/reactivity).

## `name` is typed, and that is why `children` is a function

`name` is not a loose string. It is narrowed to the paths in your form data **whose value type matches the field kind**, so `<form.NumberField name='email' />` against `{ email: string }` is a compile error, and so is a misspelt path.

That checking is what dictates the shape of `<Form>` in its uncontrolled mode:

```tsx
<Form defaultValues={{ email: '', age: 0 }}>
	{(form) => (
		<form.TextField
			name='email'
			label='Email'
		/>
	)}
</Form>
```

`children` is a render prop, not plain JSX under a context provider, because **React context cannot carry the `TFormData` generic**. A `createContext` call fixes its value type at module scope; the form's data type is only known at the call site. An instance handed down through context would arrive with `TFormData` erased, degrading every `name` back to `string` and every `value` to `unknown`. The reason is written down beside the type itself, in `packages/form/react/react/src/form-props.ts`.

In the controlled mode you call `useForm` yourself, so you already hold the typed instance and `children` is ordinary JSX. Which mode to pick is a lifetime question, answered in [Getting started](/docs/form/getting-started#controlled-when-the-instance-is-needed-outside).

## Two entry points, one machine

There are two ways in, and they run the same code underneath.

**JSX** — `<Form>` plus flat fields. Everything JavaScript can express is available: inline validators, arbitrary conditions, `form.Subscribe`, your own components between the fields.

**The document** — a `FormSchema` handed to `<FormRenderer>`. The renderer walks the document and renders it through the _same_ bound field components the JSX API exposes, so both produce the same DOM. There is one implementation, not two.

The boundary between them is worth stating plainly rather than discovering later. A document is data — it survives `JSON.stringify`, which means it can be delivered by a backend, stored in a table, or produced by a visual builder. That is also its limit:

- **Validation is named rules only.** `validate: { required: true, format: 'email' }`, plus rules you register yourself. An arbitrary JavaScript predicate is deliberately not expressible — a document that carried executable code would not be safe to accept over the wire.
- **Conditions are declarative.** `when` and `disabledWhen` cover showing, hiding and disabling against other field values. There is no `form.Subscribe` in a document; the renderer handles re-rendering itself.
- **Some things exist only on the document side.** Wizards are the notable case: `step` nodes and the step chrome are a renderer feature, and there is no `<Step>` component in the JSX API.

Neither entry point is the fallback for the other. Reach for the document when the form's shape is data — long forms, backend-delivered forms, forms a non-developer edits. Reach for JSX when the form's shape is code. The format is described in full in [Config-driven forms](/docs/form/schema).
