title: Config-driven forms
description: Describe a form as plain data — a FormSchema — and render it with SchemaForm. The same machinery as the JSX API, entered from the other side.
---

A **`FormSchema`** is a form written as data instead of JSX:

```ts
{ version: 1, children: [ /* nodes */ ] }
```

`<SchemaForm>` walks that document and renders it through the _same_ bound field components the JSX API exposes — `form.TextField`, `form.SelectField`, `form.SubmitButton`. A config-driven form and a hand-written one produce the same DOM, because there is only one implementation.

Why bother describing a form as data:

- large forms are cheaper to maintain as a list of nodes than as a page of JSX;
- data can be produced by a visual builder, or generated by an LLM and checked on the way in;
- data can be **delivered by a backend**, so a form changes without a frontend deploy.

Everything a schema needs — `SchemaForm` and the format alike — comes from your kit, which re-exports the schema-authoring API of `@ez-kit/form-core` so the kit stays the only package you install:

```ts
import { defineFormSchema, FormFieldType, SchemaForm, parseFormSchema } from '@ez-kit/form-shadcn'
```

## The document

`children` is a flat array of **nodes**, each discriminated by `type`:

| `type`                                                                                                                         | kind      | what it is                                                 |
| ------------------------------------------------------------------------------------------------------------------------------ | --------- | ---------------------------------------------------------- |
| `text` `number` `textarea` `select` `multiselect` `checkbox` `checkboxgroup` `switch` `radiogroup` `slider` `date` `daterange` | field     | one bound input; carries `name`                            |
| `block`                                                                                                                        | either    | a component from `components`, with `children` a container |
| `array`                                                                                                                        | container | a repeatable group of fields bound to a list               |
| any other string                                                                                                               | field     | a custom field, resolved from the field registry           |

Those twelve field strings are exactly the members of the `FormFieldType` enum, so `FormFieldType.Text` and `'text'` are the same value.

### Common node properties

A field node may carry:

| property       | meaning                                                              |
| -------------- | -------------------------------------------------------------------- |
| `label`        | `LocalizedText` — finished copy, or `{ i18n, params }`               |
| `description`  | `LocalizedText`                                                      |
| `when`         | rendered only when this condition holds                              |
| `disabledWhen` | rendered disabled when this condition holds                          |
| `colSpan`      | grid columns the node spans in its container's grid — an integer 1–4 |

A block carries only `when` and `colSpan` of these: what its component shows is in its `props`.

A `date` node carries `min`, `max` and `defaultValue` as `YYYY-MM-DD` strings; a `daterange` node's `defaultValue` is `{ start, end }` of two such strings, and its value reaches `onSubmit` in that same shape under one `name`. Dates are strings on purpose — a `Date` does not survive `JSON.stringify`, and a calendar date has no time zone to lose. See [Fields](./form/fields) for what each kit renders.

A `select`, `multiselect`, `radiogroup` or `checkboxgroup` node adds `options`: a `{ value, label, disabled? }` list whose `label` is `LocalizedText` like every other label in the format, so a delivered document can name a translation key instead of shipping copy in one language. `SchemaForm` resolves them before the kit sees them — a kit only ever receives finished strings.

An option `value` is a **string or a number**, and the node's `name` is checked against it: a `number`-valued path takes numeric options (a `number[]` one for `multiselect` / `checkboxgroup`), a string-valued path string ones. That is what makes a backend-authored document over integer entity ids expressible — the id stays a number all the way into form state and back out of `onSubmit`. One list carries one scalar type; see [Numeric option values](/docs/form/select#numeric-option-values).

A field node adds `name` (the full path from the root of the form values — never affected by which block it sits in), its kind-specific options, an optional `defaultValue` and an optional `validate` block. It may also carry `required`, which is the _marker_ the kit renders next to the label — enforcement is `validate.required`, and the two are deliberately separate so a field can be marked without being checked, or checked without being marked.

### Blocks

A **block** is a component from the bundle's `components`, written as data — the same component JSX reaches as `form.<Name>`:

```ts
{ type: 'block', component: 'Section', props: { title: 'Client' }, children: [ … ] }
{ type: 'block', component: 'SubmitButton', props: { children: 'Save' } }
```

- `component` names a key of `components`: the kit's `Section` and `SubmitButton`, or any component you registered yourself.
- `props` reach the component flat, under the names JSX uses — `title` for `Section`, `children` for `SubmitButton`. A `{ i18n }` value among them is translated first; see [Localisation](#localisation).
- `children` makes the block a container: they are document nodes, rendered and handed to the component as its `children`. A block without them is a leaf, and its `children`, if any, come from `props`.
- `when` hides the block and everything inside it.

A delivered document chooses a block's props, so a component a document can name should treat them as untrusted input — the same way it would treat any value from a server. `parseFormSchema` holds them to what JSON can carry, so no function or class instance gets through, but it cannot know which strings a component would be unwise to render as markup or as a link.

### Columns

`columns` (an integer **1–4**) lays out a container's children on a grid. It goes on any node with children — a block, an `array` (where it lays out the fields of each entry) or the document itself — and the renderer puts the kit's `Grid` **inside** the container, with each child in a `Grid.Item`. A child takes one column unless it sets `colSpan`.

`columns` and `colSpan` outside 1–4 are a parse error rather than a silent fallback: a document that asked for six columns and got one is a layout nobody can explain. So is a `colSpan` whose container sets no `columns`, which would otherwise do nothing. Nest a container to build a different grid inside a cell.

### `defaultValue`

Fields may carry their own `defaultValue`. When you pass no `defaultValues` to `SchemaForm`, it builds them from the schema — which is the only way a backend-delivered field can start out as anything but `undefined`. A `defaultValues` you pass yourself always wins.

The **schema** carries the form's value type, so `onSubmit`'s `value` is typed whether or not you pass `defaultValues` — which matters most for a backend-delivered document, the case that has no `defaultValues` to state it with. A schema built by `defineFormSchema<Values>()` or by `parseFormSchema<Values>()` says `Values`; one assembled as a bare object literal says nothing, and `value` arrives as `unknown` until you annotate it. Passing `defaultValues` as well is still checked against the same type.

## TypeScript and JSON are the same document

`defineFormSchema` is curried, because TypeScript has no partial generic inference — the value type is given explicitly while the literal is still inferred:

```ts
const schema = defineFormSchema<Values>()({
	version: 1,
	children: [
		{
			type: 'block',
			component: 'Section',
			props: { title: 'Client' },
			columns: 2,
			children: [
				{ type: FormFieldType.Text, name: 'firstName', label: 'First name' },
				{ type: FormFieldType.Text, name: 'lastName', label: 'Last name' },
			],
		},
		{ type: 'block', component: 'SubmitButton', props: { children: 'Save' } },
	],
})
```

That buys real checking: `name` is narrowed **per field kind** against your value type, so a `number` field pointing at a string path is a compile error, and an option that belongs to another kind does not type-check.

The same document as JSON is character-for-character the same data — no functions were used, and the `FormFieldType` members _are_ those strings:

```json
{
	"version": 1,
	"children": [
		{
			"type": "block",
			"component": "Section",
			"props": { "title": "Client" },
			"columns": 2,
			"children": [
				{ "type": "text", "name": "firstName", "label": "First name" },
				{ "type": "text", "name": "lastName", "label": "Last name" }
			]
		},
		{ "type": "block", "component": "SubmitButton", "props": { "children": "Save" } }
	]
}
```

This is the whole point of the format: authoring in TypeScript and delivering over the wire are the same thing, not two dialects.

The TS spelling adds exactly one thing: compile-time checking. Everything else — conditions, validation, layout — is the same data either way, so a form you prototype in TypeScript can be moved into a database verbatim.

## Conditions

`when` and `disabledWhen` take a **rule object**:

```ts
{ field: 'clientType', eq: 'business' }
{ and: [{ field: 'clientType', eq: 'business' }, { not: { field: 'country', eq: 'RU' } }] }
```

The operator set is closed on purpose — every operator added is one backends will emit forever:

| rule                               | true when                             |
| ---------------------------------- | ------------------------------------- |
| `{ field, eq: value }`             | the field equals `value`              |
| `{ field, in: [...] }`             | the field is one of the listed values |
| `{ field, gt: n }` / `{ lt: n }`   | numeric comparison                    |
| `{ field, truthy: true }`          | the field is truthy                   |
| `{ and: [...] }` / `{ or: [...] }` | all / any of the nested rules         |
| `{ not: rule }`                    | the nested rule does not hold         |

`field` is a path from the root of the values — or, **inside an array item**, a `./`-prefixed path relative to that item: `{ field: './kind', eq: 'company' }` means _this_ entry's `kind`, whatever index it ended up at. An absolute path still reaches the form root from inside an item, so a row can depend on a top-level field. Only one level of relativity exists — there is no `../` — and a `./` written outside an array item is rejected, because there is no item for it to resolve against. See [Arrays](/docs/form/arrays).

### A predicate instead of a rule

A TypeScript-authored schema may write the condition as a plain function, because that function comes from your own bundle. Anywhere a rule object is accepted — `when` and `disabledWhen`, on a field or a block — a `(values) => boolean` is accepted too:

```ts
const schema = defineFormSchema<Values>()({
	version: 1,
	children: [
		{
			type: 'block',
			component: 'Section',
			props: { title: 'Company details' },
			// The rule spelling — serialisable, and what a backend would send:
			// when: { and: [{ field: 'clientType', eq: 'business' }, { field: 'revenue', gt: 1_000_000 }] },
			// The predicate spelling — `values` is typed as `Values`:
			when: (values) => values.clientType === 'business' && values.revenue > 1_000_000,
			children: [{ type: FormFieldType.Text, name: 'inn', label: 'Tax ID' }],
		},
	],
})
```

Runtime behaviour is identical: `SchemaForm` subscribes to the form's values and re-evaluates the predicate on every change, exactly as it does a compiled rule, so visibility, the "hidden fields are never validated" rule and the stripping of hidden values all work the same way.

What you give up is everything that depends on the schema being data:

- **`parseFormSchema` rejects it** — `Condition must be a rule object`. That is the line between the two modes, and it is the reason a predicate is only ever reachable in a schema you authored yourself.
- `JSON.stringify` silently drops the key, so a document with a predicate cannot be stored, sent, or round-tripped through a visual builder.

Use a predicate for logic that is genuinely local and awkward as data; keep to rule objects for anything a backend might one day own.

### Why there is no JavaScript in the JSON

A condition arriving over the network is **data interpreted by our own compiler**, never code. `eval` and `new Function` are out of scope permanently:

- they require `script-src 'unsafe-eval'`, throwing away a real CSP;
- they turn any bug that writes into your schema store into remote script execution;
- a visual builder cannot round-trip arbitrary code, and a backend cannot evaluate it.

Anything richer than the operator table belongs in a **named rule** (below) or, when the schema is TS-authored, in a function.

## Validation

Constraints live on the field node:

```ts
{ type: FormFieldType.Text, name: 'email', label: 'Email', validate: { required: true, format: 'email' } }
```

| key                       | effect                                                     |
| ------------------------- | ---------------------------------------------------------- |
| `required`                | empty (`undefined`, `null`, `''`, `false`, `[]`) fails     |
| `min` / `max`             | numeric bounds, or `YYYY-MM-DD` bounds for a date          |
| `minLength` / `maxLength` | string length, or how many items a multi-value field holds |
| `format`                  | `'email'`, `'url'` or `'tel'`                              |
| `rule`                    | key into the named-rule registry                           |
| `messages`                | `LocalizedText` override per constraint key                |

Constraints are checked in that order and stop at the first failure, so a field reports one message rather than a pile.

There is no `pattern`. A regular expression from an untrusted source is a ReDoS hazard, and a hung tab is a worse failure than a missing client-side check.

`SchemaForm` walks the tree once and builds **one** validator for the whole form, implementing the standard-schema interface directly — no zod, no new runtime dependency — and attaches it to `onChange` and `onSubmit`. TanStack maps its issues back onto fields by path, so nesting comes for free.

### One source of validation

This is all **uncontrolled-mode** machinery: `SchemaForm` can only own a validator when it is the one calling `useForm`. Pass your own `form` and the schema's `validate` blocks are inert — build the validator yourself with `buildValidator`.

TanStack accepts exactly one validator per trigger, so the two modes are mutually exclusive:

- the schema carries `validate` blocks → `SchemaForm` generates and owns the validator;
- you pass `validators` → yours is used verbatim and schema constraints are ignored;
- **both** → `SchemaForm` throws, naming the conflict. There is no silent winner and no merging of two issue sets onto one path.

Field-level validators through `form.NativeField` still compose with either mode — TanStack runs field-level and form-level validators together.

### Named rules

Logic that cannot be expressed as data stays reachable from a delivered document: the schema _names_ a rule, your app registers the implementation.

```tsx
<SchemaForm
	schema={schema}
	rules={{ 'ru-inn': (value) => isValidInn(value) || 'Invalid tax ID' }}
/>
```

A rule returns `true` when the value passes, or the message to show. A `validate.rule` with no registered implementation throws when the validator is built — on mount, not on the user's first keystroke.

`rules` is meaningful in **uncontrolled** mode only, for the same reason `validate` is: `SchemaForm` builds the validator only when it is the one calling `useForm`. A controlled caller builds their own instance, so they build their own validator too — call `buildValidator(schema, { rules })` — re-exported by your kit — and pass the result as `validators.onChange` / `validators.onSubmit`.

## Visibility and the submitted payload

Two behaviours, deliberately separated:

- **A hidden field is never validated.** Not configurable — a required field the user cannot see must never make a form unsubmittable with no explanation.
- **Whether a hidden field's value reaches `onSubmit`** is a choice: stripped by default, kept with `keepHiddenValues`.

Stripping happens _at submit time_, by filtering the values against the computed visibility tree — not by deleting state when a field hides. Toggle a condition back and forth and what the user typed is still there.

```tsx
<SchemaForm schema={schema} keepHiddenValues onSubmit={…} />
```

`keepHiddenValues` exists **only in uncontrolled mode**, and that asymmetry is not an oversight: in controlled mode you own `onSubmit`, and `SchemaForm` has no seam to wrap it in — TanStack's own `useForm` re-applies your original options into the instance on every render, so any wrapper would lose that race. The escape hatch is explicit instead:

```ts
import { stripHiddenValues } from '@ez-kit/form-shadcn'

const form = useForm({
	defaultValues,
	onSubmit: ({ value }) => save(stripHiddenValues(schema, value)),
})

<SchemaForm form={form} schema={schema} />
```

v1 strips top-level keys only: a hidden field addressed by a dotted path (`company.inn`) still reaches `onSubmit` inside its parent object.

## Registries

Three registries, in two places. **Fields and components are registered once, on `createSchemaForm`** — the same registration that makes `form.RatingField` and `form.PromoBanner` available in JSX — while rules are a prop on `SchemaForm`:

```ts
export const { SchemaForm } = createSchemaForm({
	FormElement,
	fields: { ...allFormFields, RatingField }, // custom FIELD — has a name, bound to a value
	components: { ...allFormComponents, PromoBanner }, // a block — no name, no binding
})
```

```tsx
<SchemaForm
	schema={schema}
	rules={{ 'ru-inn': isValidInn }} // named validation rules
/>
```

A **custom field** is referenced from a document by its `type`, which its component name derives: `RatingField` → `rating`. It receives exactly what a built-in field receives — `id`, `data-field`, normalised `errors`, `invalid`, `onBlur`, `disabled`, all computed by the binding layer — plus `value`, `onChange` and the node's own `props`, passed through uninterpreted. Getting that binding for free is the entire reason a custom field goes through a registry instead of being written inline.

There is **one** registration site, deliberately: a field registered on the factory is reachable from JSX _and_ from a document, so the two can never disagree about what `rating` means. `SchemaForm` took a per-form `fields` prop in earlier versions; it is gone, and passing one is now a type error.

A **block** is a `{ type: 'block', component: 'PromoBanner' }` node; it holds no value and receives only its `props`, and its component is found by the same key JSX uses. `Grid` is the one key a block cannot name: the renderer inserts it for `columns`, so the document says `columns` instead.

Registering a field whose type id collides with a reserved node type — `section`, `step`, `submit`, `block`, `array` or any of the twelve field types — throws when the factory (`createForm` or `createSchemaForm`) runs, so a `SectionField` that would shadow `section` is rejected at startup rather than on the first document that uses it. A node whose `type` is neither built-in nor registered is an error too, never a silently skipped hole: a backend sending a field the frontend cannot render must fail loudly.

A document also needs the **components** it draws with, and `createSchemaForm` does not require them: a block needs the component it names, `columns` needs `Grid`, an `array` needs `ArrayField` in `fields`. The same holds for every field kind: a `date` node needs `DateField` in `fields`, and a custom `rating` node needs a registered component that derives the `rating` id. When one is missing, `SchemaForm` throws a named error — "the document has a block "SubmitButton", but no SubmitButton component was passed in components", "the document has a date field, but no DateField was passed in fields" — before it renders anything. It walks the whole document first, so a block or a field hidden by `when` fails at mount instead of mid-flow.

Custom types are declared to the type system as the second parameter of `defineFormSchema`:

```ts
const schema = defineFormSchema<Values, 'rating'>()({ version: 1, children: [{ type: 'rating', name: 'score' }] })
```

Keeping that set closed is what preserves the checking on built-in nodes — an open `type: string` member would swallow every mistyped built-in.

## Steps

A document has no steps. `step` stays a reserved node type, and `parseFormSchema` rejects a node that uses it. A form split into steps is written in JSX, with [`form.Steps` and `form.Step`](/docs/form/steps).

## Backend-driven UI

A schema from your own bundle is trusted. A schema from anywhere else — a database, an API, an LLM — goes through `parseFormSchema` **first**:

```ts
import { FormSchemaError, parseFormSchema } from '@ez-kit/form-shadcn'

try {
	const schema = parseFormSchema<Values>(await res.json(), {
		fieldTypes: Object.keys(fields),
		components: Object.keys(components),
		rules: Object.keys(rules),
		optionSources: Object.keys(optionSources),
		hasTranslate: true,
	})
	// …render it
} catch (error) {
	if (error instanceof FormSchemaError) {
		reportBadSchema(error.message, error.path)
	}
	throw error
}
```

The parser is the trust boundary. It rejects, throwing `FormSchemaError` with the offending node's path (`children[1].children[0]`) on the first violation:

- a non-object document, a missing `children` array, an unsupported `version`;
- a node with no `type`, an unknown `type`, a container with no `children`;
- a `section` or `submit` node — the error names the block that replaced it;
- a field with no `name`, or a `name` used twice in the tree (a duplicate is an error, not a supported "render twice");
- a `validate.rule`, a block `component` or an `optionsFrom` source that is not registered;
- a field type colliding with a reserved node type;
- a block naming `Grid`, carrying `label`, `description` or `disabledWhen`, taking `children` both as nodes and in `props`, or carrying `props` that JSON cannot represent;
- a malformed rule, a `./` field reference, or a **function** condition — which cannot survive `JSON.parse` anyway, but a hand-built object must still be told it is not a serialisable document;
- a `LocalizedText` that is neither a string nor `{ i18n }`, or a translation key with no `translate` registered;
- an options-bearing node carrying neither `options` nor [`optionsFrom`](/docs/form/select/option-sources) — or both — an option missing its `value` or `label`, an option `value` that is neither a string nor a number, or one list mixing the two;
- an `optionsFrom` whose `dependsOn` names a relative (`./`) field reference, or whose `params` carry something `JSON.stringify` would not survive (a function, `undefined`, `NaN`, a `Date`);
- a `multiselect` / `checkboxgroup` `defaultValue` that is not an array of option values, or whose entries disagree with the option value type;
- a date `min` / `max` / `defaultValue` that is not a real `YYYY-MM-DD` day, or a `daterange` default missing an end;
- `columns` / `colSpan` outside 1–4, `columns` on a node with no children, or a `colSpan` whose container sets no `columns` or fewer columns than it spans;
- a `step` node.

Passing the registries' keys in the options is what lets the parser check a delivered document against _this_ app's capabilities, which is the check that matters: the backend can only send what the frontend can actually render.

`SchemaForm` deliberately does not call the parser for you. Parsing is a step you take at the boundary where the document arrives — once, where you can log it and fall back — not on every render.

## Localisation

`label`, `description`, `validate.messages`, a select's **option labels** and a block's **props** all take `LocalizedText`: a plain string is finished copy, an object `{ i18n, params }` is a translation key resolved by the `translate` prop. A block translates only its top-level props — a `{ i18n }` nested deeper is passed through as data.

```tsx
<SchemaForm
	schema={schema}
	translate={(key, params) => t(key, params)}
/>
```

A key with no `translate` supplied is a parse-time error, not a blank label.

## SchemaForm props

| prop                                         | mode         | purpose                                                     |
| -------------------------------------------- | ------------ | ----------------------------------------------------------- |
| `schema`                                     | both         | the document to render                                      |
| `form`                                       | controlled   | your own instance; `SchemaForm` binds into it               |
| `rules`                                      | uncontrolled | named validation rules — see below                          |
| `translate`                                  | both         | resolves `LocalizedText` keys                               |
| `keepHiddenValues`                           | uncontrolled | keep hidden fields in the submitted value (default: strip)  |
| `defaultValues`, `onSubmit`, `validators`, … | uncontrolled | everything `useForm` takes — `SchemaForm` owns the instance |

Anything else you pass lands on the `<form>` element.

In **controlled** mode `SchemaForm` binds into an instance you already own, which is how a config-driven part sits inside a hand-written form; in **uncontrolled** mode mounting the element _is_ creating the form, so closing the dialog it lives in throws the state away with it.
