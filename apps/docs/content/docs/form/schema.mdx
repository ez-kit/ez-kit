# Config-driven forms

A **`FormSchema`** is a form written as data instead of JSX:

```ts
{ version: 1, children: [ /* nodes */ ] }
```

`<FormRenderer>` walks that document and renders it through the _same_ bound field components the JSX API exposes — `form.TextField`, `form.SelectField`, `form.SubmitButton`. A config-driven form and a hand-written one produce the same DOM, because there is only one implementation.

Why bother describing a form as data:

- large forms are cheaper to maintain as a list of nodes than as a page of JSX;
- data can be produced by a visual builder, or generated by an LLM and checked on the way in;
- data can be **delivered by a backend**, so a form changes without a frontend deploy.

Everything a schema needs — the renderer and the format alike — comes from your kit, which re-exports the schema-authoring API of `@ez-kit/form-core` so the kit stays the only package you install:

```ts
import { defineFormSchema, FormFieldType, FormRenderer, parseFormSchema } from '@ez-kit/form-shadcn'
```

## The document

`children` is a flat array of **nodes**, each discriminated by `type`:

| `type`                                                                                           | kind      | what it is                                          |
| ------------------------------------------------------------------------------------------------ | --------- | --------------------------------------------------- |
| `text` `number` `textarea` `select` `checkbox` `switch` `radiogroup` `slider` `date` `daterange` | field     | one bound input; carries `name`                     |
| `section`                                                                                        | container | optional heading plus a column grid                 |
| `step`                                                                                           | container | one wizard step                                     |
| `submit`                                                                                         | leaf      | the submit button                                   |
| `block`                                                                                          | leaf      | value-less markup, resolved from the block registry |
| any other string                                                                                 | field     | a custom field, resolved from the field registry    |

Those ten field strings are exactly the members of the `FormFieldType` enum, so `FormFieldType.Text` and `'text'` are the same value.

Every node may carry:

| property       | meaning                                                             |
| -------------- | ------------------------------------------------------------------- |
| `label`        | `LocalizedText` — finished copy, or `{ key, params }`               |
| `description`  | `LocalizedText`                                                     |
| `when`         | rendered only when this condition holds                             |
| `disabledWhen` | rendered disabled when this condition holds                         |
| `colSpan`      | grid columns the node spans inside its section — an integer **1–4** |

A `date` node carries `min`, `max` and `defaultValue` as `YYYY-MM-DD` strings; a `daterange` node's `defaultValue` is `{ start, end }` of two such strings, and its value reaches `onSubmit` in that same shape under one `name`. Dates are strings on purpose — a `Date` does not survive `JSON.stringify`, and a calendar date has no time zone to lose. See [Fields](./form/fields) for what each kit renders.

A `select` or `radiogroup` node adds `options`: a `{ value, label, disabled? }` list whose `label` is `LocalizedText` like every other label in the format, so a delivered document can name a translation key instead of shipping copy in one language. The renderer resolves them before the kit sees them — a kit only ever receives finished strings.

A field node adds `name` (the full path from the root of the form values — never affected by which section or step it sits in), its kind-specific options, an optional `defaultValue` and an optional `validate` block. It may also carry `required`, which is the _marker_ the kit renders next to the label — enforcement is `validate.required`, and the two are deliberately separate so a field can be marked without being checked, or checked without being marked.

A `section` adds `title`, `description`, `columns` (an integer **1–4**, default 1) and `children`. A `step` adds `title`, `description`, `children` and an optional `path`. A `submit` node takes `label` and `disabled`.

`columns` and `colSpan` outside 1–4 are a parse error rather than a silent fallback: a document that asked for six columns and got one is a layout nobody can explain. Nest sections to build a different grid.

### `defaultValue`

Fields may carry their own `defaultValue`. When you pass no `defaultValues` to the renderer, it builds them from the schema — which is the only way a backend-delivered field can start out as anything but `undefined`. A `defaultValues` you pass yourself always wins.

`defaultValues` is also the inference site for the form's value type, exactly as in the JSX API: pass it and `onSubmit`'s `value` is typed; leave it out and it arrives as `unknown`.

## TypeScript and JSON are the same document

`defineFormSchema` is curried, because TypeScript has no partial generic inference — the value type is given explicitly while the literal is still inferred:

```ts
const schema = defineFormSchema<Values>()({
	version: 1,
	children: [
		{
			type: 'section',
			title: 'Client',
			columns: 2,
			children: [
				{ type: FormFieldType.Text, name: 'firstName', label: 'First name' },
				{ type: FormFieldType.Text, name: 'lastName', label: 'Last name' },
			],
		},
		{ type: 'submit', label: 'Save' },
	],
})
```

That buys real checking: `name` is narrowed **per field kind** against your value type, so a `number` field pointing at a string path is a compile error, and an option that belongs to another kind does not type-check.

The same document as JSON is character-for-character the same data — no functions were used, and the `FormFieldType` members _are_ those strings:

```json
{
	"version": 1,
	"children": [
		{
			"type": "section",
			"title": "Client",
			"columns": 2,
			"children": [
				{ "type": "text", "name": "firstName", "label": "First name" },
				{ "type": "text", "name": "lastName", "label": "Last name" }
			]
		},
		{ "type": "submit", "label": "Save" }
	]
}
```

This is the whole point of the format: authoring in TypeScript and delivering over the wire are the same thing, not two dialects.

The TS spelling adds exactly one thing: compile-time checking. Everything else — conditions, validation, layout — is the same data either way, so a form you prototype in TypeScript can be moved into a database verbatim.

## Conditions

`when` and `disabledWhen` take a **rule object**:

```ts
{ field: 'clientType', eq: 'business' }
{ and: [{ field: 'clientType', eq: 'business' }, { not: { field: 'country', eq: 'RU' } }] }
```

The operator set is closed on purpose — every operator added is one backends will emit forever:

| rule                               | true when                             |
| ---------------------------------- | ------------------------------------- |
| `{ field, eq: value }`             | the field equals `value`              |
| `{ field, in: [...] }`             | the field is one of the listed values |
| `{ field, gt: n }` / `{ lt: n }`   | numeric comparison                    |
| `{ field, truthy: true }`          | the field is truthy                   |
| `{ and: [...] }` / `{ or: [...] }` | all / any of the nested rules         |
| `{ not: rule }`                    | the nested rule does not hold         |

`field` is a path from the root of the values. A `./`-prefixed path is **reserved** for array items, which v1 does not ship — it is rejected today so the rule language never has to change once documents exist in databases.

### A predicate instead of a rule

A TypeScript-authored schema may write the condition as a plain function, because that function comes from your own bundle. Anywhere a rule object is accepted — `when` and `disabledWhen`, on a field, a `section` or a `step` — a `(values) => boolean` is accepted too:

```ts
const schema = defineFormSchema<Values>()({
	version: 1,
	children: [
		{
			type: 'section',
			title: 'Company details',
			// The rule spelling — serialisable, and what a backend would send:
			// when: { and: [{ field: 'clientType', eq: 'business' }, { field: 'revenue', gt: 1_000_000 }] },
			// The predicate spelling — `values` is typed as `Values`:
			when: (values) => values.clientType === 'business' && values.revenue > 1_000_000,
			children: [{ type: FormFieldType.Text, name: 'inn', label: 'Tax ID' }],
		},
	],
})
```

Runtime behaviour is identical: the renderer subscribes to the form's values and re-evaluates the predicate on every change, exactly as it does a compiled rule, so visibility, the "hidden fields are never validated" rule and the stripping of hidden values all work the same way.

What you give up is everything that depends on the schema being data:

- **`parseFormSchema` rejects it** — `Condition must be a rule object`. That is the line between the two modes, and it is the reason a predicate is only ever reachable in a schema you authored yourself.
- `JSON.stringify` silently drops the key, so a document with a predicate cannot be stored, sent, or round-tripped through a visual builder.

Use a predicate for logic that is genuinely local and awkward as data; keep to rule objects for anything a backend might one day own.

### Why there is no JavaScript in the JSON

A condition arriving over the network is **data interpreted by our own compiler**, never code. `eval` and `new Function` are out of scope permanently:

- they require `script-src 'unsafe-eval'`, throwing away a real CSP;
- they turn any bug that writes into your schema store into remote script execution;
- a visual builder cannot round-trip arbitrary code, and a backend cannot evaluate it.

Anything richer than the operator table belongs in a **named rule** (below) or, when the schema is TS-authored, in a function.

## Validation

Constraints live on the field node:

```ts
{ type: FormFieldType.Text, name: 'email', label: 'Email', validate: { required: true, format: 'email' } }
```

| key                       | effect                                            |
| ------------------------- | ------------------------------------------------- |
| `required`                | empty (`undefined`, `null`, `''`, `false`) fails  |
| `min` / `max`             | numeric bounds, or `YYYY-MM-DD` bounds for a date |
| `minLength` / `maxLength` | string length bounds                              |
| `format`                  | `'email'`, `'url'` or `'tel'`                     |
| `rule`                    | key into the named-rule registry                  |
| `messages`                | `LocalizedText` override per constraint key       |

Constraints are checked in that order and stop at the first failure, so a field reports one message rather than a pile.

There is no `pattern`. A regular expression from an untrusted source is a ReDoS hazard, and a hung tab is a worse failure than a missing client-side check.

The renderer walks the tree once and builds **one** validator for the whole form, implementing the standard-schema interface directly — no zod, no new runtime dependency — and attaches it to `onChange` and `onSubmit`. TanStack maps its issues back onto fields by path, so nesting comes for free.

### One source of validation

This is all **uncontrolled-mode** machinery: the renderer can only own a validator when it is the one calling `useForm`. Pass your own `form` and the schema's `validate` blocks are inert — build the validator yourself with `buildValidator`.

TanStack accepts exactly one validator per trigger, so the two modes are mutually exclusive:

- the schema carries `validate` blocks → the renderer generates and owns the validator;
- you pass `validators` → yours is used verbatim and schema constraints are ignored;
- **both** → `FormRenderer` throws, naming the conflict. There is no silent winner and no merging of two issue sets onto one path.

Field-level validators through the native `form.Field` still compose with either mode — TanStack runs field-level and form-level validators together.

### Named rules

Logic that cannot be expressed as data stays reachable from a delivered document: the schema _names_ a rule, your app registers the implementation.

```tsx
<FormRenderer
	schema={schema}
	rules={{ 'ru-inn': (value) => isValidInn(value) || 'Invalid tax ID' }}
/>
```

A rule returns `true` when the value passes, or the message to show. A `validate.rule` with no registered implementation throws when the validator is built — on mount, not on the user's first keystroke.

`rules` is meaningful in **uncontrolled** mode only, for the same reason `validate` is: the renderer builds the validator only when it is the one calling `useForm`. A controlled caller builds their own instance, so they build their own validator too — call `buildValidator(schema, { rules })` — re-exported by your kit — and pass the result as `validators.onChange` / `validators.onSubmit`.

## Visibility and the submitted payload

Two behaviours, deliberately separated:

- **A hidden field is never validated.** Not configurable — a required field the user cannot see must never make a form unsubmittable with no explanation.
- **Whether a hidden field's value reaches `onSubmit`** is a choice: stripped by default, kept with `keepHiddenValues`.

Stripping happens _at submit time_, by filtering the values against the computed visibility tree — not by deleting state when a field hides. Toggle a condition back and forth and what the user typed is still there.

```tsx
<FormRenderer schema={schema} keepHiddenValues onSubmit={…} />
```

`keepHiddenValues` exists **only in uncontrolled mode**, and that asymmetry is not an oversight: in controlled mode you own `onSubmit`, and the renderer has no seam to wrap it in — TanStack's own `useForm` re-applies your original options into the instance on every render, so any wrapper would lose that race. The escape hatch is explicit instead:

```ts
import { stripHiddenValues } from '@ez-kit/form-shadcn'

const form = useForm({
	defaultValues,
	onSubmit: ({ value }) => save(stripHiddenValues(schema, value)),
})

<FormRenderer form={form} schema={schema} />
```

v1 strips top-level keys only: a hidden field addressed by a dotted path (`company.inn`) still reaches `onSubmit` inside its parent object.

## Registries

Three registries, all keyed by string, all props on the renderer:

```tsx
<FormRenderer
	schema={schema}
	fields={{ rating: RatingField }} // custom FIELD — has a name, bound to a value
	blocks={{ 'promo-banner': PromoBanner }} // custom BLOCK — no name, no binding
	rules={{ 'ru-inn': isValidInn }} // named validation rules
/>
```

A **custom field** is referenced by its `type` and receives exactly what a built-in field receives — `id`, `data-field`, normalised `errors`, `invalid`, `onBlur`, `disabled`, all computed by the binding layer — plus `value`, `onChange` and the node's own `props`, passed through uninterpreted. Getting that binding for free is the entire reason a custom field goes through a registry instead of being written inline.

A **block** is a `{ type: 'block', component: 'promo-banner' }` node; it holds no value and receives only its `props`.

Registering a key that collides with a reserved node type — `section`, `step`, `submit`, `block` or any of the eight field types — throws when the renderer mounts. A node whose `type` is neither built-in nor registered is an error too, never a silently skipped hole: a backend sending a field the frontend cannot render must fail loudly.

Custom types are declared to the type system as the second parameter of `defineFormSchema`:

```ts
const schema = defineFormSchema<Values, 'rating'>()({ version: 1, children: [{ type: 'rating', name: 'score' }] })
```

Keeping that set closed is what preserves the checking on built-in nodes — an open `type: string` member would swallow every mistyped built-in.

## Wizards

When the document's **top-level** children are `step` nodes, it is a wizard: the renderer shows one step at a time and asks your kit for the chrome (`Wizard` in the kit contract — neither shadcn nor HeroUI ships a stepper, so each kit draws its own). Steps live in the same tree as everything else, so a step can carry `when` — "skip the company step for an individual" is a first-class case.

A step's `title` and `description` are resolved by the renderer before the kit sees them — `WizardStep` types both as `ReactNode`, so a kit never has to know what a translation key is. Mixing `step` nodes with non-`step` siblings at the same level throws, in the parser and at render time alike: the loose nodes would otherwise be silently dropped.

Four behaviours the renderer settles so no kit has to:

- **Which fields a step owns is decided by layout, never by a data path.** `goNext` collects the field names in the step's own subtree and runs the form-level validators scoped to exactly those, so a step's "next" can never write errors onto fields further along. A step's optional `path` does not change that scope: it mounts a `useFormGroup` binding for the step and nothing more.
- **A step never opens red on arrival.** The schema's constraints compile into a _form-level_ `onChange` validator, which sees every field in the document — including ones the user has not reached. A step is marked `invalid` only once the user has tried to _leave_ it, and arriving on a step the user has never left clears the errors its fields were carrying.
- **A step hidden by `when` is removed from the list and the remaining steps are renumbered**, so a stepper never reports "3 of 5" for a form with four reachable steps. If the step on screen hides itself, the wizard falls back to the nearest earlier visible step rather than to the start.
- **The final submit is not wizard chrome.** Put a `submit` node in the last step; it renders like any other node.

## Backend-driven UI

A schema from your own bundle is trusted. A schema from anywhere else — a database, an API, an LLM — goes through `parseFormSchema` **first**:

```ts
import { FormSchemaError, parseFormSchema } from '@ez-kit/form-shadcn'

try {
	const schema = parseFormSchema<Values>(await res.json(), {
		fieldTypes: Object.keys(fields),
		blocks: Object.keys(blocks),
		rules: Object.keys(rules),
		hasTranslate: true,
	})
	// …render it
} catch (error) {
	if (error instanceof FormSchemaError) {
		reportBadSchema(error.message, error.path)
	}
	throw error
}
```

The parser is the trust boundary. It rejects, throwing `FormSchemaError` with the offending node's path (`children[1].children[0]`) on the first violation:

- a non-object document, a missing `children` array, an unsupported `version`;
- a node with no `type`, an unknown `type`, a container with no `children`;
- a field with no `name`, or a `name` used twice in the tree (a duplicate is an error, not a supported "render twice");
- a `validate.rule` or a block `component` that is not registered;
- a registry key colliding with a reserved node type;
- a malformed rule, a `./` field reference, or a **function** condition — which cannot survive `JSON.parse` anyway, but a hand-built object must still be told it is not a serialisable document;
- a `LocalizedText` that is neither a string nor `{ key }`, or a translation key with no `translate` registered;
- a `select` / `radiogroup` with no `options` array, or an option missing its `value` or `label`;
- a date `min` / `max` / `defaultValue` that is not a real `YYYY-MM-DD` day, or a `daterange` default missing an end;
- `columns` / `colSpan` outside 1–4;
- `step` nodes mixed with non-`step` siblings.

Passing the registries' keys in the options is what lets the parser check a delivered document against _this_ app's capabilities, which is the check that matters: the backend can only send what the frontend can actually render.

`FormRenderer` deliberately does not call the parser for you. Parsing is a step you take at the boundary where the document arrives — once, where you can log it and fall back — not on every render.

## Localisation

`label`, `description`, `title`, `validate.messages` and a select's **option labels** all take `LocalizedText`: a plain string is finished copy, an object `{ key, params }` is a translation key resolved by the `translate` prop.

```tsx
<FormRenderer
	schema={schema}
	translate={(key, params) => t(key, params)}
/>
```

A key with no `translate` supplied is a parse-time error, not a blank label.

## Renderer props

| prop                                         | mode         | purpose                                                     |
| -------------------------------------------- | ------------ | ----------------------------------------------------------- |
| `schema`                                     | both         | the document to render                                      |
| `form`                                       | controlled   | your own instance; the renderer binds into it               |
| `fields` / `blocks`                          | both         | the custom-field and block registries above                 |
| `rules`                                      | uncontrolled | named validation rules — see below                          |
| `translate`                                  | both         | resolves `LocalizedText` keys                               |
| `keepHiddenValues`                           | uncontrolled | keep hidden fields in the submitted value (default: strip)  |
| `defaultValues`, `onSubmit`, `validators`, … | uncontrolled | everything `useForm` takes — the renderer owns the instance |

Anything else you pass lands on the `<form>` element.

In **controlled** mode the renderer binds into an instance you already own, which is how a config-driven part sits inside a hand-written form; in **uncontrolled** mode mounting the element _is_ creating the form, so closing the dialog it lives in throws the state away with it.
