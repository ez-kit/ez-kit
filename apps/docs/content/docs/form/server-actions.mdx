**The form needs JavaScript.** These are not plain HTML forms: the kits' fields are controlled components, and validation, arrays, conditions and steps all live in JavaScript, so a server action here is the endpoint the form calls, not a no-JavaScript fallback.

What a press does **before** the page has hydrated is the browser's own submit. By default the kits render a `<form>` with no `method`, and their inputs carry `name`, so that submit is a **GET** to the current URL with every field's value in the query string — and from there in the browser history and the server's logs. A password field makes that a credential in a URL. Give the form `method='post'` — `<Form>` and `<SchemaForm>` pass it through to the `<form>` element in both kits — so an early press sends the values in a request body, which nothing on the page reads; or keep the submit control disabled until the page has hydrated.

## The recipe

Three pieces, all React's own: the action, `useActionState` to hold what it returned, and `startTransition` to call it.

```ts
'use server'

import { buildValidator } from '@ez-kit/form-core'

import { signUpSchema } from './sign-up-schema'

import type { SignUpValues } from './sign-up-schema'
import type { ServerErrors } from '@ez-kit/form-shadcn'

export type SignUpResult = {
	serverErrors?: ServerErrors<SignUpValues>
	ok?: true
}

type IssuePath = readonly (PropertyKey | { readonly key: PropertyKey })[]

const TAKEN_USERNAMES = new Set(['admin', 'root'])

const MALFORMED_REQUEST = 'The request could not be read. Reload the page and try again.'

const validator = buildValidator(signUpSchema)

function isSignUpValues(values: unknown): values is SignUpValues {
	return (
		typeof values === 'object' &&
		values !== null &&
		'username' in values &&
		typeof values.username === 'string' &&
		'email' in values &&
		typeof values.email === 'string'
	)
}

function toFieldPath(path: IssuePath): string {
	return path
		.map((segment) => (typeof segment === 'object' ? segment.key : segment))
		.reduce<string>((joined, key) => {
			if (typeof key === 'number') return `${joined}[${String(key)}]`
			return joined === '' ? String(key) : `${joined}.${String(key)}`
		}, '')
}

export async function signUp(_previous: SignUpResult, values: unknown): Promise<SignUpResult> {
	if (!isSignUpValues(values)) {
		return { serverErrors: { form: MALFORMED_REQUEST } }
	}

	const result = await validator['~standard'].validate(values)

	if (result.issues) {
		const fields = Object.fromEntries(result.issues.map((issue) => [toFieldPath(issue.path ?? []), issue.message]))
		return { serverErrors: { fields } }
	}

	if (TAKEN_USERNAMES.has(values.username.trim().toLowerCase())) {
		return { serverErrors: { fields: { username: 'That username is taken' } } }
	}

	return { ok: true }
}
```

The document it validates against is shared with the form:

```ts
import { defineFormSchema, FormFieldType } from '@ez-kit/form-core'

export type SignUpValues = {
	username: string
	email: string
}

export const signUpSchema = defineFormSchema<SignUpValues>()({
	version: 1,
	children: [
		{
			type: FormFieldType.Text,
			name: 'username',
			label: 'Username',
			defaultValue: '',
			validate: { required: true, minLength: 3, maxLength: 32 },
		},
		{
			type: FormFieldType.Text,
			name: 'email',
			label: 'Email',
			inputType: 'email',
			defaultValue: '',
			validate: { required: true, maxLength: 254, format: 'email' },
		},
		{ type: 'block', component: 'SubmitButton', props: { children: 'Sign up' } },
	],
})
```

The action returns a `serverErrors` object in the shape the form takes — field messages under `fields`, keyed by path, and an optional `form` for a message about the form as a whole — and the component hands it straight back to `<Form>`:

```tsx
'use client'

import { startTransition, useActionState } from 'react'

import { Form } from '@ez-kit/form-shadcn'

import { signUp } from './sign-up'

export function SignUp() {
	const [state, action, isPending] = useActionState(signUp, {})

	return (
		<Form
			method='post'
			defaultValues={{ username: '', email: '' }}
			serverErrors={state.serverErrors}
			onSubmit={({ value }) => {
				startTransition(() => {
					action(value)
				})
			}}
		>
			{(form) => (
				<>
					<form.TextField
						name='username'
						label='Username'
						validate={{ required: true, minLength: 3, maxLength: 32 }}
					/>
					<form.TextField
						name='email'
						label='Email'
						type='email'
						validate={{ required: true, maxLength: 254, format: 'email' }}
					/>
					<form.SubmitButton disabled={isPending}>Sign up</form.SubmitButton>
				</>
			)}
		</Form>
	)
}
```

`onSubmit` runs only once the form's own validation has passed, and the value it passes is a plain object, which an action accepts as it is — no `FormData` to unpack. `action` is called inside `startTransition`, which is what `useActionState`'s dispatch requires outside a `<form action>`.

**The button reads `isPending`.** `form.SubmitButton` already disables itself while `isSubmitting` is true, but that flag ends when `onSubmit` returns, and `onSubmit` returns as soon as the action has been _started_. The request is still in flight; `isPending` from `useActionState` is the flag that covers it. `disabled` on the kit's button adds a reason without overriding its own.

## What `serverErrors` does

A field's message shows at once — the field is marked touched so the display rule does not hide it — and the first field with an error, in page order, takes focus. It stays while the user tabs in and out, goes the first time the field's value changes, and does not come back for that value. Every server error goes on the next submit or reset of the instance `useForm` returns. An answer that arrives after the user kept editing applies to the field's current value, not the submitted one, and moves focus into the field. A `form` message reaches `form.Submit`'s `formErrors` and does not disable submitting. [Submission](/docs/form/submission#server-errors) has the full rules and the imperative `form.setServerErrors`.

Two consequences of how the prop is read:

- **It is applied when its reference changes.** `state.serverErrors` from `useActionState` changes exactly once per action result, which is what the prop expects — pass it as it is. If you reshape the action's result first, memoise the result (`useMemo` on `state`): a literal built inline is a new object on every render, and every render would then apply it again — restoring a message the user has edited away, marking the fields touched again and moving focus back.
- **It is applied after hydration**, in an effect. Errors that arrive with the first render — a `useActionState` seeded with a previous result — are not in the server-rendered HTML; they appear when the page hydrates.

## Validating on the server

An action is a public endpoint: anything can POST to it, with any payload, so it validates again whatever the browser already checked. Two things the browser's checks never had to do come first:

- **Check the payload's shape.** `buildValidator` checks the document's constraints, not the values' types — a `username` that arrives as a number passes `required` and skips `minLength`. The action above narrows `values` from `unknown` before it validates, and answers anything else with a form-level error rather than throwing. A standard schema that checks types (zod, valibot) does both at once.
- **Bound every length.** A `format` check is a regular expression, and a regular expression over unbounded input is CPU an attacker can spend; on a public endpoint give each field a `maxLength`, which is checked before `format`.

`@ez-kit/form-core` runs without React, so the rules a document declares run on the server unchanged:

- `buildValidator(schema)` compiles a document's `validate` blocks into a [standard-schema](https://github.com/standard-schema/standard-schema) validator — call its `'~standard'.validate(values)` and map each issue's path onto `fields`, as `toFieldPath` above does — joined, so a nested field's error lands on `address.city` rather than on `address`.
- `stripHiddenValues(schema, values)` drops what a `when` condition hid, so the server sees the payload the form would have submitted.
- `parseFormSchema(json)` checks a document that arrived as data before it is trusted.

Import them from `@ez-kit/form-core` rather than from the kit, and add it to your dependencies: the kit packages are client modules, and a `'use server'` file cannot call into one. Types are erased, so `import type { ServerErrors }` from the kit is fine.

A shared standard schema — zod, valibot, arktype — works the same way: validate with it in the action, and hand the same schema to the form's `validators`.
