# `@ez-kit/form-*`

A thin layer over [TanStack Form](https://tanstack.com/form) that hands you **fields, not plumbing**.

`useForm` here is a **superset** of TanStack Form's: the instance it returns carries flat, ready-wired field components, while the entire native API stays on that same object.

```tsx
const form = useForm({
	defaultValues: { email: '', password: '' },
	onSubmit: ({ value }) => save(value),
})

<form.Form>
	<form.TextField name='email' label='Email' />
	<form.SubmitButton>Save</form.SubmitButton>
</form.Form>
```

Each field renders its own label, description, input and error message. No `<Field>` render prop, no manual `value` / `onChange` / `onBlur` wiring, no error plumbing — unless you want it, in which case [the native API](./form/native-api) is right there.

## The packages

| Package               | Role                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------ |
| `@ez-kit/form-core`   | Framework-agnostic: field kinds, the shared `SelectOption` shape, validator-error normalisation. |
| `@ez-kit/form-react`  | The DI contract and field layer. Contains **zero visual styling** — only `data-*` attributes.    |
| `@ez-kit/form-shadcn` | The shadcn flavour.                                                                              |
| `@ez-kit/form-heroui` | The HeroUI v3 flavour.                                                                           |

You install exactly one of the two flavours; it pulls the rest in.

## Why the layering

`@ez-kit/form-react` knows how to bind a field to form state, normalise errors and track submit state — but it owns no pixels and no markup. Each field's entire element tree is supplied by a kit through a `FormComponents` contract, so a React Aria kit can nest its label and error inside the field root while a plain-DOM kit keeps them as siblings. That is what lets the **same example render under either kit**, and it is why you can [build your own kit](./form/custom-kit) without forking anything.

## What's in the box

| Export                                        | Purpose                                                            |
| --------------------------------------------- | ------------------------------------------------------------------ |
| [`useForm`](./form/getting-started)           | The extended hook. Everything below hangs off its result.          |
| [`form.TextField` and friends](./form/fields) | Five base fields: text, number, textarea, select, checkbox.        |
| `form.SubmitButton`                           | Subscribed to `canSubmit` / `isSubmitting`, so it disables itself. |
| `form.Form`                                   | A `<form>` wired to `handleSubmit`.                                |
| [`createForm`](./form/custom-kit)             | The factory a UI kit calls to bind its own components.             |

## Validation

There is **no custom resolver**. Validation is pure pass-through of TanStack Form's native [standard-schema](https://github.com/standard-schema/standard-schema) support — hand it a zod, valibot or arktype schema and it just works. See [Validation](./form/validation).

## Not included yet

Switch, radio-group, date-picker and combobox fields, a schema-driven auto-form, and `extendForm` (registering your own field type) are planned but not shipped. Today, a field type we do not cover is written with [the native API](./form/native-api).
