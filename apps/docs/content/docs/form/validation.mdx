# Validation

There is **no resolver here**. `@ez-kit/form` adds nothing to TanStack Form's validation — it passes your validators through untouched, then renders whatever errors come back through the kit's error component.

That means everything in the [TanStack Form validation guide](https://tanstack.com/form/latest/docs/framework/react/guides/validation) applies verbatim.

## Schema validation

Hand `validators.onChange` any [standard-schema](https://github.com/standard-schema/standard-schema) validator — zod, valibot, arktype:

```tsx
import { z } from 'zod'

const schema = z.object({
	email: z.email('Enter a valid email address'),
	age: z.number().min(18, 'You must be at least 18'),
	terms: z.literal(true, { error: 'You have to accept the terms' }),
})

const form = useForm({
	defaultValues: { email: '', age: 0, terms: false as boolean },
	validators: { onChange: schema },
	onSubmit: ({ value }) => save(value),
})
```

## Named rules: validation without JavaScript

A [`FormSchema`](/docs/form/schema) may arrive as JSON, from a backend or a builder, and JSON holds no functions. So the document does not carry validators — it carries **constraints with names**, and `buildValidator` compiles them into a single standard-schema validator that TanStack consumes exactly like your zod one.

Seven constraints make up a field's `validate` block: `required`, the bounds `min` and `max`, the length bounds `minLength` and `maxLength`, a `format` of `'email'`, `'url'` or `'tel'`, and a `rule` naming a registered function — alongside `messages`, which overrides the wording per constraint. They run in that order and stop at the first failure, so a field shows one message rather than a pile. [Config-driven forms](/docs/form/schema#validation) documents each of them; what matters here is what the set does **not** contain.

There is no `pattern`. A regular expression arriving from a source you do not control is a ReDoS hazard, and a hung tab is a worse outcome than a missing client-side check. There is no predicate either — no `refine`, no cross-field callback, no checksum — because there is no way to spell one in a document without shipping executable code inside data.

What replaces both is indirection: the document _names_ a rule and the application supplies it.

```tsx
<FormRenderer
	schema={schema}
	rules={{ 'ru-inn': (value, values) => isValidInn(value) || 'Invalid tax ID' }}
/>
```

A rule receives the field's value and the whole form's values, and returns `true` or the message to show. Both halves of that arrangement are deliberate: the backend can compose new forms out of rules the frontend already ships, and it cannot make the frontend run anything the frontend did not already contain. A `validate.rule` naming a rule nobody registered throws when the validator is built — on mount, not on the user's first keystroke — so a mistyped name is a loud failure rather than a constraint that silently never fires.

`rules` is meaningful in uncontrolled mode only. A controlled caller owns the form instance, so it owns the validator too: call `buildValidator(schema, { rules })` yourself and pass the result as `validators.onChange`. [Config-driven forms](/docs/form/schema#one-source-of-validation) explains why the two modes cannot be mixed.

## When validation runs

Pick the trigger with the key you use:

```tsx
validators: {
	onChange: schema,   // as the user types
	onBlur: schema,     // when the field loses focus
	onSubmit: schema,   // only on submit
}
```

Async validators (`onChangeAsync`, `onBlurAsync`) and `onChangeAsyncDebounceMs` work exactly as in TanStack Form.

## Per-field validators

The flat fields do not take a `validators` prop — validation is declared on the form, which is where a schema naturally lives. For a rule that belongs to one field only, use a form-level function validator returning the `fields` map:

```tsx
const form = useForm({
	defaultValues: { username: '' },
	validators: {
		onChange: ({ value }) =>
			value.username.length < 3 ? { fields: { username: 'At least 3 characters' } } : undefined,
	},
})
```

…or drop to [the native `form.Field`](./form/native-api), which accepts its own `validators`.

## How errors are rendered

Whatever a validator produces — a standard-schema issue object, a plain string, an `Error` — is normalised to display strings before it reaches your kit. Empty and `null` slots are dropped, so a field with nothing renderable is not marked invalid.

The same helper is exported if you need it in a custom field:

```ts
import { formatFieldErrors, hasFieldErrors } from '@ez-kit/form-shadcn'

formatFieldErrors([{ message: 'Required' }, undefined, 'Too short'])
// → ['Required', 'Too short']
```

When a field has at least one error, its root gets `data-invalid`, the input gets `aria-invalid`, and the error element is linked through `aria-describedby`.

## `required` is not validation

The `required` prop on a field marks the control required for assistive technology and native form semantics. It does **not** produce an error message — that is the validator's job. Set both when you want both.
