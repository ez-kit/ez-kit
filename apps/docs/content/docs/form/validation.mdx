# Validation

There is **no resolver here**. `@ez-kit/form` does not wrap or rewrite your validators — it passes them through untouched, then renders whatever errors come back through the kit's error component.

That means everything in the [TanStack Form validation guide](https://tanstack.com/form/latest/docs/framework/react/guides/validation) applies verbatim. What the package adds sits beside that rather than in front of it: the [`validate` prop](#per-field-validators) on a field, and the constraints a [document](#named-rules-validation-without-javascript) declares — two spellings of one small constraint vocabulary, both compiled into ordinary TanStack validators.

## Schema validation

Hand `validators.onChange` any [standard-schema](https://github.com/standard-schema/standard-schema) validator — zod, valibot, arktype:

```tsx
import { z } from 'zod'

const schema = z.object({
	email: z.email('Enter a valid email address'),
	age: z.number().min(18, 'You must be at least 18'),
	terms: z.literal(true, { error: 'You have to accept the terms' }),
})

const form = useForm({
	defaultValues: { email: '', age: 0, terms: false as boolean },
	validators: { onChange: schema },
	onSubmit: ({ value }) => save(value),
})
```

## Named rules: validation without JavaScript

A [`FormSchema`](/docs/form/schema) may arrive as JSON, from a backend or a builder, and JSON holds no functions. So the document does not carry validators — it carries **constraints with names**, and `buildValidator` compiles them into a single standard-schema validator that TanStack consumes exactly like your zod one.

Seven constraints make up a field's `validate` block: `required`, the bounds `min` and `max`, the length bounds `minLength` and `maxLength`, a `format` of `'email'`, `'url'` or `'tel'`, and a `rule` naming a registered function — alongside `messages`, which overrides the wording per constraint. They run in that order and stop at the first failure, so a field shows one message rather than a pile. [Config-driven forms](/docs/form/schema#validation) documents each of them; what matters here is what the set does **not** contain.

There is no `pattern`. A regular expression arriving from a source you do not control is a ReDoS hazard, and a hung tab is a worse outcome than a missing client-side check. There is no predicate either — no `refine`, no cross-field callback, no checksum — because there is no way to spell one in a document without shipping executable code inside data.

What replaces both is indirection: the document _names_ a rule and the application supplies it.

```tsx
<FormRenderer
	schema={schema}
	rules={{ 'ru-inn': (value, values) => isValidInn(value) || 'Invalid tax ID' }}
/>
```

A rule receives the field's value and the whole form's values, and returns `true` or the message to show. Both halves of that arrangement are deliberate: the backend can compose new forms out of rules the frontend already ships, and it cannot make the frontend run anything the frontend did not already contain. A `validate.rule` naming a rule nobody registered throws when the validator is built — on mount, not on the user's first keystroke — so a mistyped name is a loud failure rather than a constraint that silently never fires.

`rules` is meaningful in uncontrolled mode only. A controlled caller owns the form instance, so it owns the validator too: call `buildValidator(schema, { rules })` yourself and pass the result as `validators.onChange`. [Config-driven forms](/docs/form/schema#one-source-of-validation) explains why the two modes cannot be mixed.

## When validation runs

Pick the trigger with the key you use:

```tsx
validators: {
	onChange: schema,   // as the user types
	onBlur: schema,     // when the field loses focus
	onSubmit: schema,   // only on submit
}
```

Async validators (`onChangeAsync`, `onBlurAsync`) and `onChangeAsyncDebounceMs` work exactly as in TanStack Form.

## Per-field validators

Every flat field takes a `validate` prop, and it carries **the same `FieldValidate` object** a schema field node carries — the same constraints, in the same order, through the same engine in `@ez-kit/form-core`:

```tsx
<form.TextField
	name='email'
	label='Email'
	validate={{ required: true, format: 'email' }}
/>
<form.NumberField
	name='age'
	label='Age'
	validate={{ min: 18, max: 120 }}
/>
<form.MultiSelectField
	name='tags'
	label='Tags'
	options={TAGS}
	validate={{ maxLength: 2, messages: { maxLength: 'Pick at most two' } }}
/>
```

The prop attaches to the field's `onChange` — the hook the document side attaches its generated validator to — so both entry points fail at the same moment, and both are gated for _display_ by the same `isTouched` check. `validate.required` implies the visual `required`, so the asterisk needs no second prop.

It **layers on** the form's own `validators` rather than replacing them: both run on every change. They share the field's single `onChange` error slot, so while both fail it is the field's own message that shows, and the form-level one appears as soon as the field's constraints are satisfied.

### The two keys the JSX spelling omits

`rule` and `LocalizedText` messages only mean something to a document, so neither is available here. Both are compile errors.

**`rule`** names an entry in a registry because JSON cannot carry code. JSX can, so there is no registry on this side to look a name up in, and a string indirection would be the worst of the spellings available to you — write the check as a TanStack field validator, or as a standard-schema validator on the form. A `rule` that arrives past a cast throws, naming the field.

**`messages`** takes plain strings here. Resolving a `{ key, params }` message needs a `translate`, and `translate` is a prop of `<FormRenderer>`, not of `<Form>` or `useForm`; rather than invent a second translate channel for the JSX API, the type asks for the finished copy you already hold.

### When a form-level validator is the right answer instead

The constraint set is fixed and deliberately small — `required`, the bounds `min` and `max`, the length bounds `minLength` and `maxLength`, and `format`. It is the vocabulary a **document** must be able to express as data, not a validation library, and the JSX side offers it so that the two entry points say the same things rather than so that it can grow.

Anything outside that set — a regular expression, a cross-field check, a predicate of your own — belongs in a standard-schema validator on the form, or in a form-level function validator returning the `fields` map:

```tsx
const form = useForm({
	defaultValues: { username: '' },
	validators: {
		onChange: ({ value }) =>
			value.username.length < 3 ? { fields: { username: 'At least 3 characters' } } : undefined,
	},
})
```

…or drop to [the native `form.Field`](./form/native-api), which accepts its own `validators`.

## How errors are rendered

Whatever a validator produces — a standard-schema issue object, a plain string, an `Error` — is normalised to display strings before it reaches your kit. Empty and `null` slots are dropped, so a field with nothing renderable is not marked invalid.

The same helper is exported if you need it in a custom field:

```ts
import { formatFieldErrors, hasFieldErrors } from '@ez-kit/form-shadcn'

formatFieldErrors([{ message: 'Required' }, undefined, 'Too short'])
// → ['Required', 'Too short']
```

When a field has at least one error, its root gets `data-invalid`, the input gets `aria-invalid`, and the error element is linked through `aria-describedby`.

## `required` is not validation

The bare `required` prop on a field marks the control required for assistive technology and native form semantics. It does **not** produce an error message — that is the validator's job. It stays visual-only on purpose: a caller whose validation lives in a zod schema on the form needs to render the marker without this package second-guessing their validator.

To _enforce_ it, write `validate={{ required: true }}`, which implies the marker — so the two are never both needed, and the pair is not two spellings of one prop.
