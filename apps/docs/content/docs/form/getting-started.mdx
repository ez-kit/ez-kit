# Getting started

## 1. Install a flavour

Pick the UI kit you already use. It pulls in `@ez-kit/form-react` and `@ez-kit/form-core` for you.

```bash
# shadcn
pnpm add @ez-kit/form-shadcn

# …or HeroUI (its packages are peer dependencies)
pnpm add @ez-kit/form-heroui @heroui/react @heroui/styles
```

Neither kit ships a stylesheet — your app owns its theme. Add one `@source` line to the CSS
file you already have so Tailwind v4 generates the kit's classes, since it does not scan
`node_modules`:

```css
@source '../node_modules/@ez-kit/form-shadcn/dist/**/*.js';
/* …or */
@source '../node_modules/@ez-kit/form-heroui/dist/**/*.js';
```

Full per-kit details — Tailwind setup, theming, peer dependencies — live in [Installation](./form/installation/shadcn).

## 2. Render a form

`<Form>` takes everything TanStack Form's `useForm` takes — `defaultValues` is what types the whole form — and hands the instance to its children. It **is** the `<form>` element: it calls `preventDefault` for you, so `onSubmit` here is TanStack's, called with the validated values.

```tsx
import { Form } from '@ez-kit/form-shadcn'
;<Form
	defaultValues={{ email: '', password: '' }}
	onSubmit={async ({ value }) => {
		await api.signUp(value)
	}}
>
	{(form) => (
		<>
			<form.TextField
				name='email'
				label='Email'
				placeholder='you@example.com'
			/>
			<form.TextField
				name='password'
				label='Password'
				type={TextInputType.Password}
			/>
			<form.SubmitButton>Create account</form.SubmitButton>
		</>
	)}
</Form>
```

`children` is a function, not plain JSX, and that is load-bearing: React context cannot carry the `TFormData` generic, so an instance passed down through context would degrade every `name` to a bare `string`. The render prop is what keeps the type checking below.

## 3. Mind the lifetime

The form lives exactly as long as the element that created it. Unmount `<Form>` — close a dialog, switch a record — and its values, errors and submit state go with it; mount it again and you get a clean form, with no `reset` call anywhere.

That is why a dialog belongs in this mode, with `<Form>` **inside** the dialog and wrapping both its body and its footer:

```tsx
<Dialog
	open={open}
	onOpenChange={setOpen}
>
	<Dialog.Content>
		<Form
			defaultValues={{ email: '' }}
			onSubmit={async ({ value }) => {
				await save(value)
				setOpen(false)
			}}
		>
			{(form) => (
				<>
					<Dialog.Body>
						<form.TextField
							name='email'
							label='Email'
						/>
					</Dialog.Body>
					<Dialog.Footer>
						<form.SubmitButton>Save</form.SubmitButton>
					</Dialog.Footer>
				</>
			)}
		</Form>
	</Dialog.Content>
</Dialog>
```

The submit button sits in the footer and is still a native `type='submit'` inside its own `<form>`.

<Callout type='warn'>
	Whether reopening resets the form depends on your dialog: one that renders its content conditionally (`open && …`)
	remounts `<Form>` and resets it for you, while one that keeps the content mounted and hides it with CSS does not. In
	that second case give `<Form>` a `key` — `key={recordId}`, or a counter bumped on open — so React recreates the
	instance.
</Callout>

## Controlled: when the instance is needed outside

Sometimes something outside the markup has to read the form — a parent guarding the close button with `form.state.isDirty`, a wizard step, a toolbar button. Then call `useForm` yourself and hand the instance to `<Form>`; `children` is plain JSX in this mode.

```tsx
import { Form, useForm } from '@ez-kit/form-shadcn'

const form = useForm({ defaultValues: { email: '' }, onSubmit })

;<Form
	form={form}
	className='space-y-4'
>
	<form.TextField
		name='email'
		label='Email'
	/>
	<form.SubmitButton>Save</form.SubmitButton>
</Form>
```

The two modes are mutually exclusive — passing `form` together with `defaultValues` is a compile error — and the mode is fixed for the lifetime of the component, since switching remounts the form. Note the trade-off you take on here: the instance now lives as long as **the component that called the hook**, so inside a dialog you own the reset.

## Type safety

`name` is not a loose string. It is narrowed to the paths in your form data **whose value type matches the field**, so a mismatch is a compile error rather than a runtime surprise:

```tsx
// inside <Form defaultValues={{ email: '', age: 0 }}>

<form.TextField name='email' label='Email' />    // ✅
<form.NumberField name='age' label='Age' />      // ✅
<form.NumberField name='email' label='Email' />  // ❌ 'email' is a string, not a number
<form.TextField name='emial' label='Email' />    // ❌ no such path
```

## What each field renders

A single `<form.TextField name='email' label='Email' description='Work address' />` produces the label, the input, the description and — once validation fails — the error message, with the accessibility wiring already done:

```html
<div
	data-field="email"
	data-field-type="text"
	data-invalid="true"
>
	<label
		id="email-label"
		for="email"
		>Email</label
	>
	<p id="email-description">Work address</p>
	<input
		id="email"
		name="email"
		aria-invalid="true"
		aria-labelledby="email-label"
		aria-describedby="email-description email-error"
	/>
	<p
		id="email-error"
		role="alert"
	>
		Enter a valid email address
	</p>
</div>
```

The `data-*` attributes are the styling hooks; the visible elements all come from your kit. See [Fields](./form/fields) for the full prop reference.
