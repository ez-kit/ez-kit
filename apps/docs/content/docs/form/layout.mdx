A form of any size stops being a list of fields and becomes groups of them: a heading, two or three columns, one field that needs the full width. That is all `Section` and `Grid` do. They are **pure layout** — putting a field inside a section or a grid changes neither its `name`, nor the path its value lives at, nor its validation, nor whether it is submitted. Move a field between cells and the payload is byte-identical.

Both entry points reach the same kit components, so the DOM matches whichever way you write it.

## Sections

A section draws an optional heading and description above its children. It knows nothing of columns: put a grid inside it when its fields should sit side by side.

```tsx
<form.Section
	title='Company'
	description='Three columns — the name takes two of them.'
>
	<form.Grid columns={3}>
		<form.TextField
			name='company'
			label='Company'
		/>
	</form.Grid>
</form.Section>
```

### `form.Section`

| Prop          | Type        | Notes                                                                            |
| ------------- | ----------- | -------------------------------------------------------------------------------- |
| `title`       | `ReactNode` | Omit it and no heading element is rendered — a section without a title is legal. |
| `description` | `ReactNode` | Sub-heading text under the title.                                                |
| `children`    | `ReactNode` | **Required.** Fields, a grid, further sections.                                  |

## The grid

`form.Grid` lays its direct children out on a `columns`-wide grid. Every child occupies one column; to take more, wrap it in `form.Grid.Item`:

```tsx
<form.Grid columns={3}>
	<form.Grid.Item colSpan={2}>
		<form.TextField
			name='company'
			label='Company'
		/>
	</form.Grid.Item>
	<form.TextField
		name='vatId'
		label='VAT id'
	/>
</form.Grid>
```

Only write `Grid.Item` where a wider span is wanted: an unwrapped child is already a cell of its own, and wrapping it with no `colSpan` changes nothing but the markup.

`colSpan` is geometry, not state — a `Grid.Item` binds no field and wraps anything, a nested section included.

### `form.Grid`

| Prop       | Type        | Notes                                                                               |
| ---------- | ----------- | ----------------------------------------------------------------------------------- |
| `columns`  | `number`    | Grid columns for the direct children. Default 1, integer 1–4; anything else clamps. |
| `children` | `ReactNode` | **Required.** Fields, grid items, sections.                                         |

### `form.Grid.Item`

| Prop       | Type        | Notes                                                                                      |
| ---------- | ----------- | ------------------------------------------------------------------------------------------ |
| `colSpan`  | `number`    | Columns to span. Default 1, integer 1–4; a value above the grid's `columns` fills the row. |
| `children` | `ReactNode` | **Required.**                                                                              |

## Nesting

A different grid inside a cell is another grid — usually inside its own section. The inner one is a child of the outer like any other, so it takes a `Grid.Item` when it should span more than one column:

```tsx
<form.Grid columns={3}>
	<form.Grid.Item colSpan={3}>
		<form.Section title='Billing address'>
			<form.Grid columns={4}>…</form.Grid>
		</form.Section>
	</form.Grid.Item>
</form.Grid>
```

There is no depth limit and no interaction with field names: `street` inside two sections is still `street`.

## The same thing as data

A document writes the section as a block and puts `columns` on it; the renderer inserts the grid **inside** the block. The span goes on the node itself, because a node cannot wrap itself:

```ts
{
	type: 'block',
	component: 'Section',
	props: { title: 'Company' },
	columns: 3,
	children: [
		{ type: FormFieldType.Text, name: 'company', label: 'Company', colSpan: 2 },
		{ type: FormFieldType.Text, name: 'vatId', label: 'VAT id' },
	],
}
```

Those are the two structural differences between the spellings. `SchemaForm` wraps the children of any container that sets `columns` in the kit's `Grid`, and **every** one of them in a `Grid.Item` with the node's `colSpan`; in JSX you write the grid yourself, and the item only where you need it.

`columns` is not a `Section` thing: it goes on any block with children, on an `array` (laying out the fields of each entry) and on the document itself. A `colSpan` under a container with no `columns` is a parse error rather than a silent no-op. See [Blocks](/docs/form/schema#blocks) and [Columns](/docs/form/schema#columns) for the full rules.

A block carries `when`, so a hidden section hides a whole group at once — with its fields' values stripped from the payload, exactly as if each were hidden on its own.

## Styling hooks

Both kits stamp the same attributes, so app CSS can reach the layout without forking a kit:

| Attribute                    | Element                        |
| ---------------------------- | ------------------------------ |
| `data-slot='form-section'`   | The section wrapper.           |
| `data-slot='form-grid'`      | The grid holding the children. |
| `data-slot='form-grid-item'` | One cell.                      |

## What layout is not

- **Not a value path.** A section contributes nothing to a field's `name` — nesting is visual only. Group values under a key by naming the fields `address.city`, not by wrapping them.
- **Not a reuse unit.** A block of fields you render more than once is a component; see [Composition](/docs/form/composition) for `withForm` and `withFieldGroup`.
- **Not a step flow.** A section is on screen with the rest of the form; showing one part at a time is [`form.Steps`](/docs/form/steps).
