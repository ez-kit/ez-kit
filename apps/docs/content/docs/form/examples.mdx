Four forms, each one a whole feature rather than a fragment, and most shown twice: once written in
TSX, once as a `FormSchema` document rendered by `SchemaForm`. Both versions are live — the
document is a real `<SchemaForm schema={…} />`, not a code block — because the two are the same
machinery entered from different sides, and the only convincing way to say so is to run both.

Scroll for the shape closest to your problem. Each case names the guide that explains it properly;
this page is deliberately short on prose and long on working forms.

## A complete form

Every field kind the kits ship, laid out in sections on the column grid: text, number, textarea,
select, multiselect, checkbox, checkbox group, switch, radio group, slider, date and date range,
with validation on the fields where it matters. It is the page to skim when you want to know what a
field actually looks like in your kit before deciding to use it.

Sections are the layout unit in both spellings: a `Section` block or `form.Section` holds a grid of
`columns` (1–4), and each child may claim a `colSpan`. [Fields](/docs/form/fields) covers what each kind accepts, and
[Validation](/docs/form/validation) the constraints used here.

## A step flow

A form split into steps is still one form — one set of values, one submit — with
[`form.Steps` and `form.Step`](/docs/form/steps) deciding which step is on screen and what "Next"
checks before it lets the user leave.

Two behaviours are worth watching in the example rather than taking on trust:

- **"Next" checks the step, not the form.** It marks the step's own fields touched and validates
  them, so the user hears about an empty email before reaching the end, and never about a field
  further along.
- **A step hidden by `when` drops out of the flow.** Pick the other account type and the company
  step disappears from the stepper; its values stay in the form state until `schema.parse` drops
  them in `onSubmit`.

## A dependent cascade

A country select that decides what the city select can offer. The list is not known until the form
is being filled in, so it cannot be written into the document at all — the document names a
**source** and the app decides what that name fetches. A source is a React hook, which is what lets
your existing data layer do the caching, deduplication and cancellation instead of this package
reimplementing them.

Watch the city value clear the moment the country changes: the new list is not waited for and the
old value is not checked against it, because a stale `{ country: 'de', city: 'msk' }` reaching
`onSubmit` is the worse outcome. [Option sources](/docs/form/select/option-sources) explains the
registry, `params` and `dependsOn`.

## A form in a dialog

The interesting part is not the dialog — it is the form instance's lifetime. The form lives exactly
as long as the element that created it, so `<Form>` goes **inside** the dialog and wraps both its
body and its footer. Closing the dialog throws the values, errors and submit state away with it, and
opening it again gives a clean form with no `reset` call anywhere. Put the dialog inside the form and
you get the opposite: state that outlives the interaction the user thought they had abandoned.

[Getting started](/docs/form/getting-started#3-mind-the-lifetime) covers the rule and where it bites.

The document version relies on the same property: in uncontrolled mode, mounting `SchemaForm` _is_
creating the form.
