The twelve field kinds a kit ships are the floor of `createForm({ fields })`, not its ceiling. `fields` is an **open registry**: spread the kit's own slots beside a component of your own, and the bundle that comes back has a thirteenth field on it — bound to form state, validated, and addressable from a schema document — without forking the kit.

```tsx
import { createForm, defineFieldType, formComponents, formFieldSlots } from '@ez-kit/form-shadcn'

const RatingField = defineFieldType<{ max: number }, number>()(({ value, onChange, props, ...field }) => (
	<Stars
		{...field}
		value={value}
		max={props.max}
		onChange={onChange}
	/>
))

export const { useForm, Form, FormRenderer, withForm, withFieldGroup } = createForm({
	components: formComponents,
	fields: { ...formFieldSlots, RatingField },
})
```

`<form.RatingField name='score' max={5} />` now compiles, `name` is narrowed to the paths whose value is a `number`, and `max` is required.

## `defineFieldType`

`defineFieldType` is curried, and the currying is what lets you pin the two type parameters explicitly while the component keeps its own inferred type:

```tsx
defineFieldType<TProps, TValue>()(component)
```

- **`TProps`** — the props the _author_ writes at the call site, and which arrive nested under `props`. Defaults to an untyped bag.
- **`TValue`** — the value the field binds to. This is what narrows `name`: with `TValue = number`, `<form.RatingField name='email' />` is a compile error. `TValue` defaults to `unknown`, which still rejects a path that does not exist but narrows nothing — a field declared without one is unnarrowed, not unchecked.

Both markers are **type-only**. `defineFieldType` returns its argument untouched, so nothing it adds reaches the bundle and the component's identity stays your own.

### What the component receives

Everything a built-in field receives — `id`, `name`, `label`, `description`, `errors`, `invalid`, `onBlur`, `disabled`, `required`, `data-field`, `data-field-type`, all computed by the binding layer (see [the kit contract](/docs/form/custom-kit#fields)) — plus three more:

| Prop       | Meaning                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| `value`    | The bound value, typed as `TValue`.                                                                          |
| `onChange` | `(value: TValue) => void`. Receives **the value**, never a DOM event — the same rule every kit slot follows. |
| `props`    | The author's own props, typed as `TProps`, in a **nested** bag rather than spread flat beside the binding.   |

The nesting is deliberate. A schema document's node carries its author props under `node.props`, and a delivered document must never be able to overwrite `label`, `disabled`, `name` or `validate` by naming them — a flat bag would let a backend-driven payload silently break the binding. The JSX call site still writes them flat, and the binder collects every key outside the base props back into `props`.

Getting that binding for free, rather than wiring `form.AppField` by hand, is the entire reason a custom field goes through the registry instead of being written inline.

## The name derives the document type id

A registry key resolves to a document `type` by one rule: **drop a trailing `Field`, lowercase the rest.**

`RatingField` → `rating`. So the same registration that produced `form.RatingField` also makes this node render:

```ts
const schema = defineFormSchema<Values, 'rating'>()({
	version: 1,
	children: [{ type: 'rating', name: 'score', label: 'Score', props: { max: 5 } }],
})
```

There is **one** registration site, deliberately: a field registered on the factory is reachable from JSX _and_ from a document, so the two can never disagree about what `rating` means. See [Schema-driven forms](/docs/form/schema#registries) for the document side.

### Why the derivation runs this way and not the other

The rule maps a component name to an id, never an id back to a component name. That direction is forced, not a preference: the reverse is lossy. The built-in `radiogroup` would have to yield `RadioGroupField`, and nothing in the string says where the capital `G` goes — `RadiogroupField` is just as good a guess. Going forwards, `RadioGroupField` → `radiogroup` is one unambiguous answer; the twelve built-ins each round-trip to their own `FormFieldType` member, which the package asserts from both lists.

Two ways the derivation can go wrong, both of which throw at `createForm` rather than on the first document that hits them:

- **Two keys deriving one id.** `RatingField` and `Rating` both derive `rating`.
- **An id that collides with a reserved node type.** A slot named `SectionField` derives `section` and would silently shadow the container node; so would `StepField`, `SubmitField` or `BlockField`. A key that collides with one of the form's own non-field components — `SubmitButton`, `Section`, `GridItem`, `ArrayField`, `Array` — throws for the same reason.

Replacing a built-in _at its own key_ is not an error: handing `fields` your own `TextField` beside the other eleven is the point of an open registry.

## One bundle per `createForm` call

<Callout type='warn'>
	Every `createForm` call builds its **own** bundle, with its own internal context. Mixing pieces across two calls —
	`<Form>` from one bundle, `form.TextField` from another — breaks **at runtime, with no type error**, because each
	call makes its own `createFormHookContexts()` and a field from one cannot find the provider from the other.
</Callout>

So call it once, in one module, and export the result from there. The failure mode is easy to reach by accident:

```tsx
// ❌ two calls — `form.RatingField` below belongs to a different context than `<Form>`
import { Form } from '@ez-kit/form-shadcn' // the kit's ready-made bundle
const { useForm } = createForm({ components: formComponents, fields: { ...formFieldSlots, RatingField } })
```

```tsx
// ✅ one call, one module, one bundle
export const { useForm, Form, FormRenderer, withForm, withFieldGroup } = createForm({
	components: formComponents,
	fields: { ...formFieldSlots, RatingField },
})
```

A kit's own `Form` / `useForm` / `FormRenderer` exports come from the kit's single `createForm` call. The moment you make your own bundle, that one becomes the bundle your app uses — import `Form` from your module, not from the kit.

## Blocks are not fields

A **custom field** has a `name` and is bound to a value. A [**block**](/docs/form/schema#registries) has neither: it is a `{ type: 'block', component: 'promo-banner' }` node that receives only its `props`, and it is registered as a `blocks` prop on `FormRenderer`, not on the factory. If what you are adding renders a value the user edits, it is a field; if it is markup the document wants to place, it is a block.
