The flat fields are **added to** the TanStack Form instance, not layered over it. Next to them sit a field for a control of your own and TanStack's field itself, and the rest of the native API is on the same object, unchanged:

| Member               | What it is                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| `form.Field`         | Binds a control of your own like a registered field: `value`, `onChange`, `errors`, `invalid`, `id`. |
| `form.NativeField`   | TanStack's render-prop field, with its `FieldApi`.                                                   |
| `form.Subscribe`     | Selector-based subscription — see [Reactivity](/docs/form/reactivity).                               |
| `form.handleSubmit`  | Submit programmatically.                                                                             |
| `form.state`         | The current snapshot (not reactive on its own).                                                      |
| `form.setFieldValue` | …and the rest of the imperative API.                                                                 |

## `form.Field`

Use it whenever you need a control we do not ship — a segmented picker, a slider, a colour input. It is bound exactly like a registered field, and its render prop gets what a [custom field](/docs/form/custom-fields) gets, minus the `props` bag:

```tsx
<form.Field
	name='seats'
	label='Seats'
	validate={{ min: 1 }}
>
	{({ value, onChange, onBlur, errors, invalid, label, description, ...field }) => (
		<div>
			<span>{label}</span>
			<MySegmentedControl
				{...field}
				value={value}
				onChange={onChange}
				onBlur={onBlur}
				invalid={invalid}
			/>
			{invalid && <p role='alert'>{errors.join(', ')}</p>}
		</div>
	)}
</form.Field>
```

| Render prop                     | What it carries                                                                        |
| ------------------------------- | -------------------------------------------------------------------------------------- |
| `value`, `onChange`             | The field's value, and a setter that takes the value itself rather than an event.      |
| `onBlur`                        | Marks the field touched.                                                               |
| `errors`, `invalid`             | Display strings and `errors.length > 0`.                                               |
| `id`, `name`                    | The id for the focusable control, and the field's path.                                |
| `data-field`, `data-field-type` | The field's `name`, and `'field'` — the same styling hooks a registered field carries. |
| `data-form-id`                  | The form's id; spread it with `data-field` so focus-on-error can find this control.    |
| `label`, `description`          | What you passed, handed back for you to render.                                        |
| `disabled`, `required`          | What you passed; `validate.required` implies `required`.                               |

`label` and `description` are content for you to render, not DOM attributes — take them out before spreading the rest onto an element, as above, or they land on it as attributes.

It validates through `validate`, like every field of this package: `required`, `min`, `max`, `minLength`, `maxLength`, `format` and `messages`. A rule that needs a standard schema or a function belongs on the form or on a group, or on [`form.NativeField`](#formnativefield). `errors` arrive filtered by the same display rule every field follows: empty until the field is touched or a submit was attempted.

You own the chrome here — label, description and error rendering are up to you. A control you need in several places is a field type of its own: [`defineFieldType`](/docs/form/custom-fields).

## `form.NativeField`

TanStack's own render-prop field, with the whole `FieldApi` in the render prop — reach for it when you need what `form.Field` does not hand out: the field's meta, `pushValue` and the rest of the `FieldApi`, or TanStack's own `validators`:

```tsx
<form.NativeField name='notes'>
	{(field) => (
		<textarea
			value={field.state.value}
			onChange={(event) => {
				field.handleChange(event.target.value)
			}}
			onBlur={field.handleBlur}
		/>
	)}
</form.NativeField>
```

It is a level below this package: what this package does around fields does not see it. It takes no part in assembling the render props — no `errors` filtered by the display rule, no `data-field`, no `id` — so all of that is yours. TanStack's own examples write `form.Field` with a `FieldApi` render prop; paste them into `form.NativeField`, not `form.Field`, where they fail to compile.

## Groups and array entries

The pair exists wherever a form hands you a scope. A [group](/docs/form/composition) carries `group.Field` and `group.NativeField`, and an [array entry](/docs/form/arrays) carries `item.Field` and `item.NativeField`, with the same meaning as on the form. Their `name` is relative to the group or the entry.

`group.NativeField` and `item.NativeField` hand over the root form's `FieldApi`, so `field.name` is the absolute path — `address.city`, `tags[0].label` — not the relative one you wrote. The names in `onChangeListenTo` / `onBlurListenTo` are relative too, and are mapped the same way.

## Reading state

`form.state` read in a component body is a snapshot, not a subscription: the component will not re-render when the value changes. Anything you render from form state goes through `form.Subscribe`, which is the subject of [Reactivity](/docs/form/reactivity).

## Submitting from elsewhere

`<Form>` wires submission for you, but nothing stops you calling it yourself — from a toolbar button, a keyboard shortcut, a dialog footer that sits outside the element:

```tsx
<button
	type='button'
	onClick={() => void form.handleSubmit()}
>
	Save
</button>
```

And if you would rather own the `<form>` element entirely, skip `<Form>` — take the instance from `useForm` and render your own:

```tsx
<form
	onSubmit={(event) => {
		event.preventDefault()
		event.stopPropagation()
		void form.handleSubmit()
	}}
>
	<form.TextField
		name='email'
		label='Email'
	/>
</form>
```

The flat fields do not care which element they sit in — they bind to the form instance, not to the DOM node. Components that read the form from context — `form.SubmitButton` and any component you registered in `components` — are different: they need `<Form>`, `<SchemaForm>` or a [`FormProvider`](/docs/form/composition#formprovider) above them, and a hand-written `<form>` is not one.

## Composition helpers

Your kit ships `withForm`, `withFieldGroup` and `form.FormGroup` for a part of a form, and the hooks `useFieldGroup` and `useFormGroup` behind the last two. A `withForm` or `withFieldGroup` block placed without a `form` prop takes the form above it. The groups — a `withFieldGroup` block and `form.FormGroup` — carry the bundle's flat fields as well as `group.Field` and `group.NativeField`, all named relative to the group. They have a page of their own: [Composition](/docs/form/composition).
