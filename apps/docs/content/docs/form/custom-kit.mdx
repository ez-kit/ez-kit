`@ez-kit/form-shadcn` and `@ez-kit/form-heroui` are not special. Each is a folder of components that implement one contract, plus a single file that hands them to one factory. Your design system can do the same.

## The idea

`@ez-kit/form-react` owns the behaviour — binding a field to form state, normalising errors, tracking submit state — and **no pixels and no DOM structure at all**. It hands you one flat props object per field and you build the whole element tree:

```tsx
export function TextField({
	id,
	name,
	label,
	value,
	onChange,
	onBlur,
	errors,
	invalid,
	...field
}: TextFieldRenderProps) {
	return (
		<div {...field}>
			<label htmlFor={id}>{label}</label>
			<input
				id={id}
				name={name}
				value={value}
				onBlur={onBlur}
				onChange={(event) => {
					onChange(event.target.value)
				}}
				aria-invalid={invalid}
			/>
			{invalid && <p role='alert'>{errors.join(', ')}</p>}
		</div>
	)
}
```

Write one of those per slot, hand the lot to `createForm`, and your consumers get the same `<Form>` / `form.TextField` / `form.SubmitButton` API as either shipped flavour. The full slot list and the factory call are [below](#the-contract).

### Why the kit owns the markup

An earlier version of this contract asked kits for chrome primitives — `FieldRoot`, `Label`, `Description`, `ErrorText` — and assembled them itself, in one fixed order, as siblings of the input.

That works for a plain-DOM system like shadcn and breaks a React-Aria-based one like HeroUI v3, where a field is a **context**:

```tsx
<TextField isInvalid>
	<Label /> {/* takes the control's id from the root */}
	<Input />
	<Description /> {/* routed into aria-describedby by the root */}
	<FieldError /> {/* reads validation state from the root */}
</TextField>
```

Rendered outside that root, `FieldError` has nothing to read and `Label` has nothing to point at — the wiring can only be faked, and the kit's own slot styling never applies. So the contract inverts: the shared layer stops rendering, and each kit expresses its natural anatomy.

## The contract

A kit hands the factory three things: the `<form>` element (`FormElement`), the field kinds (`fields`) and the form-aware components (`components`). The twelve field kinds and the array frame — which carries its entry view as `ArrayField.Item` — go to `fields`; the four components the form needs around them — the submit button, the two layout primitives and the wizard chrome — go to `components`. Eighteen pieces in all, written in two files. The first, `src/sets.ts`, gathers them into the two bags:

```tsx
import type { AllFormComponents, AllFormFieldSlots } from '@ez-kit/form-react'

export const allFormFields = {
	TextField,
	NumberField,
	TextareaField,
	SelectField,
	CheckboxField,
	SwitchField,
	RadioGroupField,
	SliderField,
	MultiSelectField,
	CheckboxGroupField,
	DateField,
	DateRangeField,
	ArrayField: Object.assign(ArrayFieldView, { Item: ArrayItemView }),
} satisfies AllFormFieldSlots

export const allFormComponents = { SubmitButton, Section, GridItem, Wizard } satisfies AllFormComponents
```

The second, `src/form.tsx`, holds only the prebuilt bundle:

```tsx
import { createForm, createSchemaForm } from '@ez-kit/form-react'

import type { FormBundle, SchemaFormBundle } from '@ez-kit/form-react'

type KitFormBundle = FormBundle<typeof allFormFields, typeof allFormComponents>
type KitSchemaFormBundle = SchemaFormBundle<typeof allFormFields, typeof allFormComponents>

const kit: KitFormBundle = /* @__PURE__ */ createForm({
	FormElement,
	fields: allFormFields,
	components: allFormComponents,
})
const schemaKit: KitSchemaFormBundle = /* @__PURE__ */ createSchemaForm({
	FormElement,
	fields: allFormFields,
	components: allFormComponents,
})

export const useForm: KitFormBundle['useForm'] = (options) => kit.useForm(options)
export const withForm: KitFormBundle['withForm'] = (options) => kit.withForm(options)
// …`withFieldGroup`, `Form` and `SchemaForm` delegate the same way
```

Both calls are annotated `/* @__PURE__ */` with flat, spread-free arguments, and every export **delegates inside a function body** instead of reading a property of the bundle at the top level. That is what lets a bundler drop the whole bundle for an app that imports a single field: `export const Form = kit.Form` would be a top-level property read, anchor the bundle, and with it every component it registers. The kit's root also exports every component directly from its own file, never through `form.tsx`, for the same reason.

### Two levels of contract

- **A kit implements the slots.** Each slot has a props type, and `satisfies AllFormFieldSlots` / `satisfies AllFormComponents` checks that the kit ships every one and that each takes the props the slot promises. `satisfies` — rather than a type annotation, which would erase your components' own prop types — also does the excess-property check, so a misspelt key is a compile error.
- **An app assembles any subset.** Nothing is required at any level: every key of `FormFieldSlots` and `FormComponents` is optional, `createForm()` alone compiles, and `form.X` exists in the types for exactly what was passed. A new slot added after 1.0 is therefore additive. A document that reaches a component nobody passed does not warn: `SchemaForm` throws a named error when it mounts with the document, before it renders anything, so a document that names a `Wizard` the factory was not given fails before the first render rather than when the user reaches a step.

```tsx
export const { useForm, Form, withForm } = createForm({
	FormElement,
	fields: { TextField, NumberField },
	components: { SubmitButton },
})
```

### The options

| Option        | Type                                     | Notes                                                                                                                                                 |
| ------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FormElement` | `(props: FormElementProps) => ReactNode` | The `<form>` element `<Form>` and `<SchemaForm>` render. A plain `<form>` when omitted. It must put every prop it receives on a real `<form>`.        |
| `fields`      | `FormFieldRegistry`                      | The field kinds, keyed by component name. Each key becomes `form.<Key>`; a key that is not a built-in is a custom field, bound by the generic binder. |
| `components`  | `FormComponentRegistry`                  | Any components, each attached as `form.<Key>` with its own props. The four the kit contract names are also what `SchemaForm` draws with.              |

<Callout type='warn'>
	**Pass the kit's `FormElement` whenever you call `createForm` yourself.** Without it the form renders a bare `<form>`,
	and on HeroUI that loses React Aria's form context: the fields still render, but `isInvalid` and the error wiring stop
	reaching them, silently and with no type error. Both kits export `FormElement` for this reason.
</Callout>

`components` is an open set. A component of your own — `{ SaveBar }` — becomes `<form.SaveBar />` with its own prop types, and is the same component whether it is rendered as `form.SaveBar` or directly as `<SaveBar />`, because it reads the form from context rather than from a closure. That context is set by `<Form>`, `<SchemaForm>` or [`FormProvider`](/docs/form/composition/with-form#components-that-know-about-the-form); a hand-written `<form>` around an instance from `useForm` is not enough.

A key that equals a member the form instance already owns (`Subscribe`, `state`, `reset`, `handleSubmit`, and our own `Field`, `Array`, `Submit`, …), or that appears in both `fields` and `components`, is a type error and throws at `createForm`, naming the key.

Every custom entry in `fields` is checked against what the generic binder hands it. A component registered without `defineFieldType` has to take the default `CustomFieldRenderProps`; typing its value is what [`defineFieldType`](/docs/form/custom-fields) is for. A misspelt built-in key (`TextFeild`) is a compile error, not a custom field.

Neither shipped kit's `form.tsx` is anything beyond the file above, and both export `allFormFields` and `allFormComponents` beside each component and the bundle. That is what lets an app spread the kit's sets beside a field of its own and call `createForm` itself — see [Custom fields](/docs/form/custom-fields).

### Fields

These twelve, with the array frame, are the `fields` registry. Every field kind receives the same base props:

| Prop                            | Meaning                                                                                                                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `data-field`, `data-field-type` | Spread onto your root so CSS, tests and e2e can find the field.                                                              |
| `data-form-id`                  | The form's id. Spread onto the same root as `data-field`, so focus-on-error can tell this form's fields from another form's. |
| `id`, `name`                    | `id` goes on the focusable control.                                                                                          |
| `label`, `description`          | `ReactNode`; `null`/`undefined` when the consumer passed none.                                                               |
| `errors`, `invalid`             | Already normalised display strings; `errors` is empty when valid.                                                            |
| `onBlur`                        | Must reach the control — blur validation depends on it.                                                                      |
| `disabled`, `required`          | `boolean \| undefined`.                                                                                                      |

#### Per-kind props

On top of that, per kind:

| Component            | Value props                                                                                        |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| `TextField`          | `value: string`, `onChange(value)`                                                                 |
| `NumberField`        | `value: number \| undefined`, `onChange(value)`                                                    |
| `TextareaField`      | `value: string`, `onChange(value)`                                                                 |
| `SelectField`        | `value: string`, `onChange(value)`, `options`, `loading`, `search?`                                |
| `MultiSelectField`   | `value: readonly string[]`, `onChange(value)`, `options`, `loading`, `search?`                     |
| `CheckboxField`      | `checked: boolean`, `onChange(checked)`                                                            |
| `SwitchField`        | `checked: boolean`, `onChange(checked)`                                                            |
| `RadioGroupField`    | `value: string`, `onChange(value)`, `options`, `loading`                                           |
| `CheckboxGroupField` | `value: readonly string[]`, `onChange(value)`, `options`, `loading`                                |
| `SliderField`        | `value: number` — always concrete, never empty — `onChange(value)`                                 |
| `DateField`          | `value: string \| undefined` (`YYYY-MM-DD`), `onChange(value)`                                     |
| `DateRangeField`     | `value: DateRangeValue \| undefined` — reported only once both ends are picked — `onChange(value)` |

<Callout type='warn'>
	`onChange` receives **the value**, not a DOM event. That is what keeps the contract identical across kits whose
	primitives disagree — some hand you an event, some a value, some a React Aria callback. Unwrapping is the kit's job.
</Callout>

#### Kit props

The contract names no input attribute — no `placeholder`, `type`, `rows`, `min`, `max` or `step`. A component that renders one declares it in its own props, beside the render props:

```tsx
type TextFieldKitProps = {
	placeholder?: string | undefined
	type?: 'text' | 'email' | 'password' | undefined
	variant?: 'flat' | 'bordered' | undefined
}

export function TextField({
	value,
	onChange,
	placeholder,
	type,
	variant,
	...field
}: TextFieldRenderProps & TextFieldKitProps) {
	// …
}
```

- **What you declare is what `form.TextField` accepts.** A component's props beyond its render props become props of the bound field, read off the component's own parameter — no helper, no registration. Under the kit above, `variant='outlined'` is a compile error, and so is a prop the component does not declare. A field set typed with the contract's own signatures (`AllFormFieldSlots`, which a bare `FormInstance<V>` assumes) accepts none — name the set, `FormInstance<V, typeof fields>`, to keep them.
- **They must be optional.** `satisfies FormFieldSlots` rejects a component that requires a prop beyond the contract: the schema renderer, and every call site that omits it, could not supply it.
- **The computed props win.** The author's props reach your component first and the binding's after them, so `value`, `onChange`, `id`, `name` and the rest are always the binding's — and none of them can be written on `form.TextField` to begin with.

A document reaches the same props: the schema renderer passes a field node's `placeholder`, `rows`, `min`, `max` and `step` under those names, and `inputType` as `type`. That path is unchecked — a component that does not declare one still receives it. Both shipped kits declare all of them, and export the type of each field's kit props as `<Field>KitProps`.

#### `search`

`SelectField` and `MultiSelectField` receive `search` only when the field is [searchable](/docs/form/select/searchable); `undefined` means a plain listbox, and its presence is the mode switch. The object has four members:

- **`query`** — the typed text, at once: what the input shows. The source sees it later, [debounced](/docs/form/select/searchable#debounce-and-minimum-length).
- **`onQueryChange`** — report each change of the input. Call `onQueryChange('')` after a selection, so the next search starts fresh.
- **`minLength`** — the shortest text the source is given, for the hint.
- **`belowMinLength`** — the typed text is shorter than `minLength`: nothing is searched, and `options` holds only the selected options.

Never filter `options` yourself — the renderer already did, or the server did. The one thing `belowMinLength` asks of a kit is the empty state: where it would say "No matches", say how much more to type instead ("Type at least 2 characters"). While a selected option keeps the list non-empty there is no empty state, and both shipped kits show no hint.

### Form level

The `<form>` element is the `FormElement` option, which receives the full `<form>` props. The rest are `components`, starting with the submit button:

| Component      | Props                   | Renders                                                                                                              |
| -------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `SubmitButton` | `disabled?`, `children` | The submit button, built on `form.Submit` and the context, so it also works under a `FormProvider` with no `<form>`. |

### Layout and wizard

Three more `components`, which the _document_ side leans on hardest, though `Section` and `GridItem` are equally reachable from JSX as `form.Section` / `form.GridItem` — see [Layout](/docs/form/layout). The array frame — `ArrayField` in `fields`, with its entry view as `ArrayField.Item` — is documented with the feature it serves, in the [arrays API](/docs/form/arrays/api).

| Component  | Props                                                                                                         | Renders                                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `Section`  | `title`, `description`, `columns`, `children`                                                                 | A heading plus a `columns`-wide grid. `columns` is `undefined` for one column; clamp it into 1–4 with `clampToGridRange`.         |
| `GridItem` | `colSpan`, `children`                                                                                         | One cell of that grid. `undefined` spans one column.                                                                              |
| `Wizard`   | `steps`, `currentIndex`, `canGoBack`, `canGoNext`, `isLastStep`, `goNext`, `goBack`, `submitting`, `children` | The stepper chrome around the current step's fields. Every step's `status` / `invalid` / `disabled` / `goTo` is already resolved. |

Tailwind extracts class names statically, so `grid-cols-${columns}` would drop the utility from your build — both shipped kits map the four supported counts to literal class names instead.

## Two shapes, two implementations

**Plain DOM (shadcn).** Chrome is siblings of the control, wired by explicit ids. Because that shape is uniform, the kit factors it into one internal `FieldShell` — but that is the _kit's_ choice, not the contract's:

```tsx
export function TextField({ value, onChange, id, name, onBlur, ...field }: TextFieldRenderProps) {
	return (
		<FieldShell
			id={id}
			{...field}
		>
			{(binding) => (
				<Input
					id={id}
					name={name}
					value={value}
					onBlur={onBlur}
					onChange={(event) => {
						onChange(event.target.value)
					}}
					aria-invalid={field.invalid}
					{...binding}
				/>
			)}
		</FieldShell>
	)
}
```

**React Aria (HeroUI).** Chrome is nested inside the root, and the library owns the ids:

```tsx
export function TextField({
	value,
	onChange,
	id,
	name,
	onBlur,
	label,
	description,
	errors,
	...field
}: TextFieldRenderProps) {
	return (
		<HeroTextField
			value={value}
			onChange={onChange}
			name={name}
			{...fieldRoot(field)}
		>
			<FieldLabel label={label} />
			<Input
				id={id}
				onBlur={onBlur}
			/>
			<FieldDescription description={description} />
			<FieldErrorText
				errors={errors}
				invalid={field.invalid}
			/>
		</HeroTextField>
	)
}
```

## What you must not forget

- **Spread `data-field`, `data-field-type` and `data-form-id` onto your root.** They are the only structural convention the contract keeps, and kit CSS, tests and e2e selectors rely on them. `data-form-id` is what focus-on-error reads: after an invalid submit it walks the page's `[data-field]` wrappers and keeps only the ones carrying the submitting form's id, so two forms with the same field names never reach into each other. A kit that spreads the render props gets it for free; one that picks them must add it, or its fields are skipped.
- **Put `id` on the focusable control** and make sure a click on the label focuses it — via `htmlFor`, or via your library's own labelling.
- **Route `onBlur` to the control.** Dropping it silently disables `onBlur` validators.
- **Render errors only when `invalid`.** `errors` is empty otherwise.
- **Handle `loading` on the four option-bearing fields.** `SelectField`, `MultiSelectField`, `RadioGroupField` and `CheckboxGroupField` each receive `loading: boolean` — a plain boolean, never `undefined`, so there is no absent case to collapse. While it is true the list has not arrived and an empty `options` says nothing about what there will be to choose from: keep the control non-interactive and put a skeleton where its value would go. A widget with no trigger (radio group, checkbox group) has nowhere to put a single skeleton — the shipped kits render a short list of placeholder rows instead. There is intentionally **no** `error` or `onRetry` in the contract; a failed fetch is the consuming app's to report.
- **Map `invalid` to whatever your system wants** — `aria-invalid`, `isInvalid`, a `data-` attribute.
- **Render `Section`'s heading only when `title` is given.** A section without one is legal and means grouping alone; the same goes for `description`.

## Boolean props and `exactOptionalPropertyTypes`

The contract declares optional inputs as `T | undefined` rather than `?:`, so nothing is ever silently absent. Several third-party primitives reject an explicit `undefined` under `exactOptionalPropertyTypes` — spread conditionally at that edge:

```tsx
<Primitive {...(disabled !== undefined ? { disabled } : {})} />
```

## Worked examples

The two shipped kits are the reference implementations, and they deliberately solve the problem differently:

- [`packages/form/react/shadcn/src/blocks`](https://github.com/ez-kit/ez-kit/tree/main/packages/form/react/shadcn/src/blocks) — one shared `FieldShell` over Radix-based primitives.
- [`packages/form/react/heroui/src/blocks`](https://github.com/ez-kit/ez-kit/tree/main/packages/form/react/heroui/src/blocks) — React Aria compositions, chrome nested inside the field root.

Reading both is the fastest way to see which parts of the contract are load-bearing.
