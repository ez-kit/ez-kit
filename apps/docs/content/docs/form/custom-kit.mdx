# Custom kit

`@ez-kit/form-shadcn` and `@ez-kit/form-heroui` are not special. Each is a folder of components that implement one contract, plus a single file that hands them to one factory. Your design system can do the same.

## The idea

`@ez-kit/form-react` owns the behaviour — binding a field to form state, normalising errors, tracking submit state — and **no pixels and no DOM structure at all**. It hands you one flat props object per field and you build the whole element tree:

```tsx
export function TextField({
	id,
	name,
	label,
	value,
	onChange,
	onBlur,
	errors,
	invalid,
	...field
}: TextFieldRenderProps) {
	return (
		<div {...field}>
			<label htmlFor={id}>{label}</label>
			<input
				id={id}
				name={name}
				value={value}
				onBlur={onBlur}
				onChange={(event) => {
					onChange(event.target.value)
				}}
				aria-invalid={invalid}
			/>
			{invalid && <p role='alert'>{errors.join(', ')}</p>}
		</div>
	)
}
```

Write one of those per slot, hand the lot to `createForm`, and your consumers get the same `<Form>` / `form.TextField` / `form.SubmitButton` API as either shipped flavour. The full slot list and the factory call are [below](#the-contract).

### Why the kit owns the markup

An earlier version of this contract asked kits for chrome primitives — `FieldRoot`, `Label`, `Description`, `ErrorText` — and assembled them itself, in one fixed order, as siblings of the input.

That works for a plain-DOM system like shadcn and breaks a React-Aria-based one like HeroUI v3, where a field is a **context**:

```tsx
<TextField isInvalid>
	<Label /> {/* takes the control's id from the root */}
	<Input />
	<Description /> {/* routed into aria-describedby by the root */}
	<FieldError /> {/* reads validation state from the root */}
</TextField>
```

Rendered outside that root, `FieldError` has nothing to read and `Label` has nothing to point at — the wiring can only be faked, and the kit's own slot styling never applies. So the contract inverts: the shared layer stops rendering, and each kit expresses its natural anatomy.

## The contract

Seventeen components: twelve fields, two form-level pieces, two layout primitives and the wizard chrome. Registering them is one object:

```tsx
import { createForm } from '@ez-kit/form-react'

import type { FormComponents } from '@ez-kit/form-react'

const components = {
	TextField,
	NumberField,
	TextareaField,
	SelectField,
	CheckboxField,
	SwitchField,
	RadioGroupField,
	SliderField,
	MultiSelectField,
	CheckboxGroupField,
	DateField,
	DateRangeField,
	Button,
	Form: FormElement,
	Section,
	GridItem,
	Wizard,
} satisfies FormComponents

export const { useForm, Form, FormRenderer, withForm, withFieldGroup } = createForm({ components })
```

`satisfies FormComponents` — rather than a type annotation, which would erase your components' own prop types — is the whole registration check: a missing or mistyped slot is a compile error, and there is no partial tier — every one of the seventeen is required, because a document may reach any of them. That is the entire wiring; both shipped kits' `src/form.tsx` is this file and nothing else.

### Fields

Every field receives the same base props:

| Prop                            | Meaning                                                           |
| ------------------------------- | ----------------------------------------------------------------- |
| `data-field`, `data-field-type` | Spread onto your root so CSS, tests and e2e can find the field.   |
| `id`, `name`                    | `id` goes on the focusable control.                               |
| `label`, `description`          | `ReactNode`; `null`/`undefined` when the consumer passed none.    |
| `errors`, `invalid`             | Already normalised display strings; `errors` is empty when valid. |
| `onBlur`                        | Must reach the control — blur validation depends on it.           |
| `disabled`, `required`          | `boolean \| undefined`.                                           |

#### Per-kind props

On top of that, per kind:

| Component            | Value props                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `TextField`          | `value: string`, `onChange(value)`, `placeholder?`, `type?`                                                                    |
| `NumberField`        | `value: number \| undefined`, `onChange(value)`, `placeholder?`, `min/max/step?`                                               |
| `TextareaField`      | `value: string`, `onChange(value)`, `placeholder?`, `rows?`                                                                    |
| `SelectField`        | `value: string`, `onChange(value)`, `options`, `loading`, `search?`, `placeholder?`                                            |
| `MultiSelectField`   | `value: readonly string[]`, `onChange(value)`, `options`, `loading`, `search?`, `placeholder?`                                 |
| `CheckboxField`      | `checked: boolean`, `onChange(checked)`                                                                                        |
| `SwitchField`        | `checked: boolean`, `onChange(checked)`                                                                                        |
| `RadioGroupField`    | `value: string`, `onChange(value)`, `options`, `loading`                                                                       |
| `CheckboxGroupField` | `value: readonly string[]`, `onChange(value)`, `options`, `loading`                                                            |
| `SliderField`        | `value: number` — always concrete, never empty — `onChange(value)`, `min/max/step?`                                            |
| `DateField`          | `value: string \| undefined` (`YYYY-MM-DD`), `onChange(value)`, `placeholder?`, `min/max?`                                     |
| `DateRangeField`     | `value: DateRangeValue \| undefined` — reported only once both ends are picked — `onChange(value)`, `placeholder?`, `min/max?` |

<Callout type='warn'>
	`onChange` receives **the value**, not a DOM event. That is what keeps the contract identical across kits whose
	primitives disagree — some hand you an event, some a value, some a React Aria callback. Unwrapping is the kit's job.
</Callout>

### Form level

| Component | Props                            | Renders                      |
| --------- | -------------------------------- | ---------------------------- |
| `Button`  | `type?`, `disabled?`, `children` | The submit button.           |
| `Form`    | `<form>` props                   | The `<form>` element itself. |

### Layout and wizard

Three components the _document_ side leans on hardest, though `Section` and `GridItem` are equally reachable from JSX as `form.Section` / `form.GridItem` — see [Layout](/docs/form/layout).

| Component  | Props                                                                                                         | Renders                                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `Section`  | `title`, `description`, `columns`, `children`                                                                 | A heading plus a `columns`-wide grid. `columns` is `undefined` for one column; clamp it into 1–4 with `clampToGridRange`.         |
| `GridItem` | `colSpan`, `children`                                                                                         | One cell of that grid. `undefined` spans one column.                                                                              |
| `Wizard`   | `steps`, `currentIndex`, `canGoBack`, `canGoNext`, `isLastStep`, `goNext`, `goBack`, `submitting`, `children` | The stepper chrome around the current step's fields. Every step's `status` / `invalid` / `disabled` / `goTo` is already resolved. |

Tailwind extracts class names statically, so `grid-cols-${columns}` would drop the utility from your build — both shipped kits map the four supported counts to literal class names instead.

## Two shapes, two implementations

**Plain DOM (shadcn).** Chrome is siblings of the control, wired by explicit ids. Because that shape is uniform, the kit factors it into one internal `FieldShell` — but that is the _kit's_ choice, not the contract's:

```tsx
export function TextField({ value, onChange, id, name, onBlur, ...field }: TextFieldRenderProps) {
	return (
		<FieldShell
			id={id}
			{...field}
		>
			{(binding) => (
				<Input
					id={id}
					name={name}
					value={value}
					onBlur={onBlur}
					onChange={(event) => {
						onChange(event.target.value)
					}}
					aria-invalid={field.invalid}
					{...binding}
				/>
			)}
		</FieldShell>
	)
}
```

**React Aria (HeroUI).** Chrome is nested inside the root, and the library owns the ids:

```tsx
export function TextField({
	value,
	onChange,
	id,
	name,
	onBlur,
	label,
	description,
	errors,
	...field
}: TextFieldRenderProps) {
	return (
		<HeroTextField
			value={value}
			onChange={onChange}
			name={name}
			{...fieldRoot(field)}
		>
			<FieldLabel label={label} />
			<Input
				id={id}
				onBlur={onBlur}
			/>
			<FieldDescription description={description} />
			<FieldErrorText
				errors={errors}
				invalid={field.invalid}
			/>
		</HeroTextField>
	)
}
```

## What you must not forget

- **Spread `data-field` and `data-field-type` onto your root.** They are the only structural convention the contract keeps, and kit CSS, tests and e2e selectors rely on them.
- **Put `id` on the focusable control** and make sure a click on the label focuses it — via `htmlFor`, or via your library's own labelling.
- **Route `onBlur` to the control.** Dropping it silently disables `onBlur` validators.
- **Render errors only when `invalid`.** `errors` is empty otherwise.
- **Handle `loading` on the four option-bearing fields.** `SelectField`, `MultiSelectField`, `RadioGroupField` and `CheckboxGroupField` each receive `loading: boolean` — a plain boolean, never `undefined`, so there is no absent case to collapse. While it is true the list has not arrived and an empty `options` says nothing about what there will be to choose from: keep the control non-interactive and put a skeleton where its value would go. A widget with no trigger (radio group, checkbox group) has nowhere to put a single skeleton — the shipped kits render a short list of placeholder rows instead. There is intentionally **no** `error` or `onRetry` in the contract; a failed fetch is the consuming app's to report.
- **Map `invalid` to whatever your system wants** — `aria-invalid`, `isInvalid`, a `data-` attribute.
- **Render `Section`'s heading only when `title` is given.** A section without one is legal and means grouping alone; the same goes for `description`.

## Boolean props and `exactOptionalPropertyTypes`

The contract declares optional inputs as `T | undefined` rather than `?:`, so nothing is ever silently absent. Several third-party primitives reject an explicit `undefined` under `exactOptionalPropertyTypes` — spread conditionally at that edge:

```tsx
<Primitive {...(disabled !== undefined ? { disabled } : {})} />
```

## Worked examples

The two shipped kits are the reference implementations, and they deliberately solve the problem differently:

- [`packages/form/react/shadcn/src/blocks`](https://github.com/ez-kit/ez-kit/tree/main/packages/form/react/shadcn/src/blocks) — one shared `FieldShell` over Radix-based primitives.
- [`packages/form/react/heroui/src/blocks`](https://github.com/ez-kit/ez-kit/tree/main/packages/form/react/heroui/src/blocks) — React Aria compositions, chrome nested inside the field root.

Reading both is the fastest way to see which parts of the contract are load-bearing.
