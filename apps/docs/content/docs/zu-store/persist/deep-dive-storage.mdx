title: Deep dive — storage
description: Scoped records, independent schemas, automatic restoration, timeout, confirmed writes and full scope reset.

Storage adapters are ambient and do no I/O during server rendering. They share one engine queue with
custom sources, while the application keeps synchronous state in memory.

## Addressed records

The existing container still has a version v and a map s, but its keys now encode StoreId plus field.
Each value is a tagged envelope containing that record's version and parser-encoded payload. Scope
comes from the cache; another panel or page has a different logical address.

Normal writes patch only changed keys. Closed components, unrelated records and legacy keys survive.
Returning a changed field to default removes its override when clearOnDefault is enabled. The default
physical storageKey remains ez-kit; choose a separate key for an incompatible application rollout.

## Automatic restore and waiting

```tsx
import { useHydrated, usePersistStatus } from '@ez-kit/zu-store/persist'

withPersist({ restore: { timeoutMs: 2000 }, fields })

const store = prefsStore.useStore()
const status = usePersistStatus(store)
if (status.restore === 'pending') return <Skeleton />
```

No consumer effect is required to start restoration. The timeout is configurable and omitted by
default. A timeout leaves defaults for untouched records, never saves them, and closes that read's
right to apply. User changes can still be saved; a late result cannot alter memory or trigger migration.
A cache-hit preserves the existing state/status. An evicted instance starts a new operation.

useHydrated is false on the server and while initial sources wait. It becomes true when all initial
sources finish ready/error/timeout; inspect status for their actual outcomes and write errors.
Explicit handle.restore joins pending or starts a fresh retry after a terminal result, preserving edits.

## Restore policy per source

A store can use independent sources for settings and drafts while keeping shared defaults:

```ts
withPersist({
	restore: {
		timeoutMs: 2000,
		externalChanges: 'ignore',
		sources: {
			draftsApi: { timeoutMs: 10000, externalChanges: 'apply' },
		},
	},
	fields: (field) => [
		field((state) => state.layout, { source: 'settingsApi' }),
		field((state) => state.draft, { source: 'draftsApi' }),
	],
})
```

Both names must be registered. settingsApi inherits two seconds/ignore, while draftsApi waits ten
seconds and accepts external updates. These can be two endpoints of the same server. Map keys are
the effective names used by sources overrides. Overrides merge with shared defaults; omitted
settings retain existing behavior. Unknown override names fail before reading. Calling a handle's
restore while it is pending joins that source's existing deadline rather than extending it.

Use `timeoutMs: null` to wait without a deadline for a particular source even when the shared
configuration is finite. For example, `sources: { draftsApi: { timeoutMs: null } }` overrides a
shared 2000 ms timeout. Omitting a property inherits its shared value; zero ends async waiting
immediately. A terminal retry accepts `handle.restore({ timeoutMs: null })`. The per-call
`RestoreCallOptions` contains only timeoutMs; externalChanges is a lifecycle policy configured
under withPersist restore rather than a policy change hidden in a retry call.

## Write policy per source

Existing throttleMs and clearOnDefault are shared write defaults. Override either by source alias:

```ts
withPersist({
	throttleMs: 0,
	clearOnDefault: true,
	write: {
		sources: {
			draftsApi: { throttleMs: 500, clearOnDefault: false },
		},
	},
	fields: (field) => [
		field((state) => state.q, { source: 'url' }),
		field((state) => state.draft, { source: 'draftsApi' }),
	],
})
```

Here URL edits use the ordinary zero-delay schedule, while draftsApi batches its own edits for
500 ms and saves an explicit default value. Missing override members inherit the shared values.
Unknown write.sources aliases fail before any source is read; registered unused names are allowed.
These settings do not copy one field to another source. Flush explicitly collects the selected
binding immediately and still waits for acknowledgement.

## Independent schema versions

```ts
field((state) => state.layout, {
	source: 'localStorage',
	parser: paramJson(),
	schema: {
		version: 2,
		minVersion: 1,
		migrate: upgradeLayout,
		validate: (value) => layoutSchema.parse(value),
	},
})
```

The order is metadata check, decode, migrate if needed, validate, apply. The callbacks are synchronous
and perform no I/O. Validate returns the current typed value or throws. Zod belongs here, not in the
parser; the old zodParam integration was removed. Missing versions mean 0. Unsupported old or invalid
records are individually deleted. Future versions stay untouched and block normal writes/deletes,
including a write made before a timed-out read returned. Explicit reset can delete a future record.

## Container migrations

Adapter version/migrate still describes the whole packed container, independently of schema.version:

```ts
localStorageAdapter({
	storageKey: 'prefs-v2',
	version: 1,
	migrate: (stored) => new Map(stored),
})
```

Existing transformation rules remain: old without migrate passes through, a thrown migration falls
back to an empty container, missing/non-numeric container version is 0, and current/newer containers
pass through. A rewrite requested by engine get is staged into the same queue and guarded against
obsolete reads, rather than writing from a late get callback. Per-record minVersion does not change
these container rules. Legacy ownership is not inferred; transfer requires known address mappings.

## Reset and durability

```ts
const handle = persistHandle(prefsStore.useStore(), 'localStorage')
await handle.reset({ fields: [['layout']] })
await handle.flush()

const persistence = usePersistence()
const outcomes = await persistence.resetScope({ path: ['devices'], sources: ['localStorage'] })
```

Reset keeps the instance, restores its original defaults and deletes overrides. Scope reset includes
nested areas and persisted entries of closed/evicted components. Adapter capability preflight rejects
unsupported full deletion before partial work. Outcomes distinguish source failures; memory stays reset
if deletion fails and the pending deletion can be retried. Cache clear/remove remains eviction.

Writes and deletes are serialized per source. Each binding keeps its own throttle window, so an idle
slow panel does not delay a fast form sharing the source. Already-observed edits remain queued when
a context view disconnects. A sent old write precedes reset deletion, queued old
writes are dropped, and later user edits follow deletion. Flush waits for its revision fence and rejects
on failed/blocked persistence. Dirty state and current memory survive errors. Flush also waits for applicable container rewrites
and namespace deletions captured at its call. Repeated reset Promises do not acknowledge deletion
until the relevant delete succeeds; a failed scope blocks that scope rather than unrelated records.
A retained handle cannot report successful durability merely because its view disconnected. A call
to reset/resetScope after engine disposal rejects instead of waiting forever. Defaults for every
source are captured before any URL seed or ambient restoration, so a shared field's reset does not
adopt another source's restored value.

## External changes and errors

Ambient external changes are ignored by default. Set restore.externalChanges to apply explicitly for
cross-tab UI synchronization. The adapter reports only external storage events, never its own writes.
URL Back/Forward remains reactive independently of this storage policy. An async external read
protects edited records independently, so editing one panel does not discard another clean panel's
update. An authoritative deletion releases an obsolete future-version block; normal adapter-side
version guards still protect a later concurrent write.

Sync storage failures and async IndexedDB/backend rejections reach onError/onPersistError with source,
operation and address/addresses or scope. They do not stop the interface. Read failure is distinct from
missing data. Built-in adapters no longer hide quota failures behind a one-time console warning.

## IndexedDB and backend limits

indexedDbAdapter has the same addressed values, schemas and lifecycle. Patches and version checks use
one transaction; removeScope inspects the whole persistent namespace. All source mutations are ordered
by the engine, not an IndexedDB-only last-value queue. Multiple storeName values can share one
dbName: missing object stores are provisioned through schema upgrades without deleting existing
stores. Owned connections close/reopen on versionchange. Other tabs can block an upgrade; close
competing connections and retry. Adapter version/migrate still versions the stored container, not
the IndexedDB database schema.

The built-in IndexedDB adapter currently has no cross-tab change notifications. Another tab's
write does not trigger a read merely because externalChanges is apply; call that source's
`handle.restore()` explicitly. Web Storage events and custom adapters with subscribe have their
own external notification paths. Automatic IndexedDB notifications are not part of this change.

For a backend, implement full removeScope and conditional version checks. A mutation Promise must mean
acknowledgment. A lost response does not prove cancellation; server revisions/generations are needed
if an old request can commit after a network error. The client queue is not a distributed lock or a
cross-device synchronization protocol.
