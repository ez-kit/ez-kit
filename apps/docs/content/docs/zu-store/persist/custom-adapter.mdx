Every source — URL, localStorage, IndexedDB — is just an adapter over the same `SourcePort`. Writing your own (a cookie, a REST endpoint, a WebSocket, a test double) is the same small contract. Every live demo in these docs runs on a custom in-memory adapter.

An adapter is **manager-agnostic**: it speaks to the substrate, never to your store. The same adapter serves a Zustand store and a Valtio one — how a store is read and written is the store port's job, not the adapter's.

## The interchange: `Keyed`

The engine speaks exactly one language: `Keyed = Map<string, string>` — a logical key mapped to an **already-stringified** value. Parsers run inside the engine, so your adapter never sees typed values, Dates, or BigInts — only strings it can pack however the substrate needs.

## The port

```ts
import type { CommitCtx, Keyed, SourcePort } from '@ez-kit/zu-store/persist'

type SourcePort = {
	get(): Keyed | Promise<Keyed> // read the substrate (async allowed — IndexedDB)
	set(desired: Keyed, ctx: CommitCtx): void | Promise<void> // commit the store's keys
	subscribe?(onChange: () => void): () => void // external changes (ambient only)
}
```

`CommitCtx` gives `set` what it needs beyond the values: `fields` (the descriptors, to read per-field `key`/`meta`), `diff` (`{ set, removed }` — which keys to touch or delete, useful for granular or async writes), and `meta` (per-commit data, e.g. `{ history }` for the URL).

## Two shapes

There are two adapter families, unified only at the port:

|                  | Ambient (storage-like)       | Render-scoped (router-like)       |
| ---------------- | ---------------------------- | --------------------------------- |
| State location   | reachable anywhere           | only in render (hooks)            |
| You ship         | a ready `port`               | a `usePort()` hook                |
| External changes | `subscribe` (e.g. cross-tab) | provider re-renders → `changeKey` |

### Ambient adapters

Ship an object with `source` and a ready `port`. This complete in-memory adapter (one JSON blob) is what the storage demos use:

```tsx
import type { AmbientAdapter, CommitCtx, Keyed, SourcePort } from '@ez-kit/zu-store/persist'

function createMemoryStorageAdapter(source: string): AmbientAdapter {
	let blob = ''
	const port: SourcePort = {
		get(): Keyed {
			const keyed: Keyed = new Map()
			if (blob) for (const [k, v] of Object.entries(JSON.parse(blob) as Record<string, string>)) keyed.set(k, v)
			return keyed
		},
		set(desired: Keyed, _ctx: CommitCtx): void {
			blob = desired.size === 0 ? '' : JSON.stringify(Object.fromEntries(desired))
		},
		// Report only EXTERNAL changes; never notify your own writes or they echo back as a pull.
		subscribe: () => () => undefined,
	}
	return { source, port }
}
```

Then mount it and target it from a field whose `source` matches:

```tsx
const memory = createMemoryStorageAdapter('localStorage')
<StoreProvider persist={[memory]}>…</StoreProvider>
```

### Render-scoped (URL) adapters

When the substrate is only reachable through hooks (a router), ship a `usePort()` that returns a stable port plus a `changeKey` that changes when the substrate changes externally (so the provider knows to pull). The URL source provides `createUrlPort(driver)` so you only supply `read`/`commit`:

```tsx
import { createUrlPort, URL_SOURCE, UrlHistory, urlMetaMerge } from '@ez-kit/zu-store/persist/url'
import type { RenderScopedAdapter, SyncSourcePort } from '@ez-kit/zu-store/persist'

const myRouterAdapter: RenderScopedAdapter = {
	source: URL_SOURCE,
	mergeMeta: urlMetaMerge, // any `push` in a coalesced batch wins
	defaultMeta: { history: UrlHistory.Replace },
	usePort() {
		const router = useMyRouter()
		const portRef = useRef<SyncSourcePort | null>(null)
		portRef.current ??= createUrlPort({
			read: () => new URLSearchParams(router.search),
			commit: (next, history) => router.navigate(`?${next}`, { replace: history === UrlHistory.Replace }),
		})
		return { port: portRef.current, changeKey: router.search }
	},
}
```

Keep the port instance stable across renders (a `ref`); the provider reads `persist` once, so its length and order must be stable too.

## When the substrate fails

A synchronous source cannot fail into the engine: the URL port never throws, and the built-in storage adapter absorbs a quota or private-mode error behind a single `console.warn`. An **async** port can — a REST call 500s, an IndexedDB transaction aborts — and a rejected `get()` or `set()` reaches your app through the persist layer's error handler, tagged with the `source` that produced it:

```tsx
<StoreProvider
	persist={[remote]}
	onPersistError={(error, { source }) => {
		notify(`Could not sync ${source}`, error)
	}}
>
	…
</StoreProvider>
```

Mounting `PersistProvider` directly, the same handler is its `onError` prop; on `StoreProvider` it carries the layer's name because that provider mounts two. The handler is read at call time, so a fresh closure each render costs nothing — it does not re-create the engines.

Leave it unset and a rejection is swallowed, exactly as before: persistence is best-effort and the store stays the source of truth. An adapter that can recover on its own — a retry, a write queue — should still do that internally rather than push every transient failure at the application.

## Checklist

- `get()` returns the substrate as `Keyed`; unknown/foreign keys you don't own should be preserved on `set`.
- `set()` honors `ctx.diff.removed` to delete keys, and is best-effort (never throw into render); an async `set()` may reject, which surfaces as `onPersistError` rather than an unhandled rejection.
- `subscribe` reports **external** changes only — the writing context must not notify itself.
- Async (`Promise`) returns are fine; they keep that source's engine independent of the synchronous ones.
