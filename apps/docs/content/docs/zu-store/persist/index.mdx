# Persist

Mirror a Zustand store into an external substrate and back, in both directions. A `set()` writes the substrate; an external change (a deep link, Back/forward, another tab, a restored value) writes the store. The store stays **synchronous and snappy** — the substrate is a throttled, rehydratable projection of it.

```bash
pnpm add @ez-kit/zu-store zustand
```

Router, storage, and validator integrations are optional peers — install only what you use (`react-router`, `next`, `zod`).

## One engine, many sources

The core never imports React, `URLSearchParams`, or a storage API. Its only interchange language is `Keyed = Map<string, string>` — a logical key mapped to an already-stringified value. A **source adapter** teaches the engine how to read and write one substrate through a small port (`get` / `set` / `subscribe`). Everything else — typed codecs, key naming, throttling, loop-breaking, hydration — is shared.

| Source                        | Import                             | Sync?  |
| ----------------------------- | ---------------------------------- | ------ |
| URL search params             | `@ez-kit/zu-store/persist/url`     | sync   |
| localStorage / sessionStorage | `@ez-kit/zu-store/persist/storage` | sync   |
| IndexedDB                     | `@ez-kit/zu-store/persist/storage` | async  |
| your own                      | a `SourcePort` you write           | either |

Because each source is just an adapter, a single field can sync to **two** substrates at once (a shared `?q=` in the URL _and_ a cached copy in storage), and async sources (IndexedDB) never stall the synchronous URL.

## Mental model

The store is the **source of truth**; the substrate is a **mirror**.

- **store → substrate**: a `subscribe` watches the store; changed fields are coalesced into one commit per tick (throttled).
- **substrate → store**: an external change pushes the diff back in, writing only what changed — pulls never re-write the substrate, so Back/forward and other-tab writes are safe.
- **One `setState` per arrival**: fields are addressed by **path** (`filters.price.min`). A pull rebuilds only the touched paths into a new state object and issues **one** `setState` for the whole batch, so untouched branches keep their reference and an `Object.is`-comparing selector re-renders exactly the components that read a changed field.
- **Loop breaking**: each direction writes only when the value differs in normalized form. Parsers carry a round-trip contract so the feedback loop terminates.

## Declaring fields

You bring your own store and declare which fields sync, with the [accessor front](./persist/fields): `field((state) => state.q, urlField())`. The selectors are typed against the store's **state**, not its handle — `withPersist` reads `ExtractState` off the store `pipe` hands it.

<Callout type='info'>
	The decorator front (`@persistUrl()` on a class property) is deliberately Valtio-only: it is the "class inside
	`proxy()`" idiom, and Zustand state is a plain object rebuilt on every write. The accessor front is the same engine
	and the same descriptors — see [va-store → decorators](../va-store/persist/decorators) if you are comparing the two
	packages.
</Callout>

## The same engine as va-store

Both packages re-export `@ez-kit/store-persist` with their own store port bound, so codecs, adapters, key naming, migrations, `useHydrated` and the `$url` / `$persist` handles behave identically. Only two things are Zustand-specific: how a write happens (`set()`, a new state object) and how the capability is attached (`pipe(store, withPersist())` on the handle).
