# `persist`

`withPersist` binds a Zustand store to an external substrate: the store stays the synchronous source
of truth and the substrate is a rehydratable mirror. Deep links and Back/forward flow in; store
writes flow out, coalesced into one commit per flush.

## The three pieces

```tsx
import { createContextStore, pipe, StoreProvider } from '@ez-kit/zu-store'
import { type FieldsBuilder, withPersist } from '@ez-kit/zu-store/persist'
import { urlField } from '@ez-kit/zu-store/persist/url'
import { reactRouterAdapter } from '@ez-kit/zu-store/persist/url/react-router'
import { createStore } from 'zustand/vanilla'

type Filters = { q: string; page: number }

// 1. Declare which fields sync, and where. Primitives need no parser — it's auto-resolved.
const fields: FieldsBuilder<Filters> = (field) => [
	field((state) => state.q, urlField()),
	field((state) => state.page, urlField()),
]

// 2. Attach the capability to the store through `pipe`.
const filtersStore = createContextStore(() =>
	pipe(
		createStore<Filters>()(() => ({ q: '', page: 1 })),
		withPersist({ fields }),
	),
)

// 3. Mount the adapter once, app-level, and render the store under it.
function Page() {
	return (
		<StoreProvider persist={[reactRouterAdapter]}>
			<filtersStore.Provider>
				<FilterControls />
			</filtersStore.Provider>
		</StoreProvider>
	)
}
```

The `adapters` array is read once and may call hooks (router adapters do), so declare it at module
scope or memoize it — keep its length and order stable across renders.

`fields` selectors are typed against the store's **state**, not its handle: `withPersist` reads
`ExtractState` off the store `pipe` hands it, so `field((state) => state.q, …)` needs no annotation.
Anything no field selects — your actions, derived values, transient UI state — is never persisted.

## As a factory plugin

A capability can also be declared on the factory instead of on the store value, which is the form to
reach for when the store is built somewhere you don't control:

```tsx
import { persist } from '@ez-kit/zu-store/persist'

const filtersStore = createContextStore(() => createStore<Filters>()(() => ({ q: '', page: 1 })), {
	plugins: [persist({ fields })],
})
```

Both forms run the same plugin at the same moment. `plugins` is not persist-specific — it takes any
`StorePlugin`, and its entries run after whatever the factory chain attached to the store itself.

## Writes are one state change

A hydration that fills five fields is **one** `setState`, not five: the engine hands every changed
leaf to the store port in a single batch, and the port rebuilds only the touched paths into a new
state object. Untouched branches keep their reference, so an `Object.is`-comparing selector re-renders
exactly the components that read a changed field.

That is also why `withPersist` composes with [`withHistory`](./with-history): one hydration is one
history entry.

## Sources beyond the URL

`localStorage`, `sessionStorage` and IndexedDB are ambient adapters — no router involved:

```tsx
import { localStorageField } from '@ez-kit/zu-store/persist/storage'
import { localStorageAdapter } from '@ez-kit/zu-store/persist/storage'

const fields: FieldsBuilder<Prefs> = (field) => [field((state) => state.theme, localStorageField())]

;<StoreProvider persist={[localStorageAdapter()]}>…</StoreProvider>
```

Storage can't be read during render without breaking SSR, so a stored non-default value lands one
tick after mount. When that gap would flash, gate on `useHydrated(store)`.

## The rest of the surface

Codecs (`paramNumber`, `paramDate`, `paramArray`, `paramJson`, …), Zod-validated parsers, blob
migrations, the `$url` / `$persist` control handles, `clearOnDefault` and `throttleMs` behave
identically here and are documented once, under
[va-store → persist](../va-store/persist) — both packages re-export the same engine
(`@ez-kit/store-persist`) with their own store port bound. The only Zustand-specific parts are the
two on this page: how the capability is attached, and the fact that a write is a state replacement.
