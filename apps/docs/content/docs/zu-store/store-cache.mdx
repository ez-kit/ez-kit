# `createStoreCache`

`createContextStore` creates a fresh store on `Provider` mount and throws it away on unmount. That is exactly what you want for a modal or a one-off form — but not for a table whose filters and pagination should still be there when the user navigates away and back.

`createStoreCache` is a **separate, opt-in** primitive that keeps the whole live store instance alive in an in-memory cache, keyed by a name you choose. `createContextStore` is unchanged.

## Keep-alive in action

Switch to **Away** (the table unmounts) and back — the filter and page are preserved. The badge reads the same store from outside the table via `useFromCache`.

## Quick start

Three steps: create a cache, define a store group, mount the cache boundary once.

```tsx
import { createStoreCache } from '@ez-kit/zu-store'
import { createStore } from 'zustand/vanilla'

type TableState = {
	filter: string
	page: number
	setFilter: (filter: string) => void
}

// 1. Create the cache (usually one per app).
const cache = createStoreCache({ gcTime: 5 * 60_000 })

// 2. Define a named store group against it.
const usersTable = cache.defineStore('users-table', (defaultProps: { filter?: string }) =>
	createStore<TableState>((set) => ({
		filter: defaultProps.filter ?? 'all',
		page: 1,
		setFilter: (filter) => set({ filter }),
	})),
)

// 3. Mount the cache boundary once, high in the tree.
function App({ children }: { children: React.ReactNode }) {
	return <cache.Provider>{children}</cache.Provider>
}
```

Then mount the keyed `Provider` wherever the table lives. It survives unmount and is reused on remount:

```tsx
function UsersPage() {
	return (
		<usersTable.Provider
			cacheKey='users'
			defaultProps={{ filter: 'active' }}
		>
			<UsersTable />
		</usersTable.Provider>
	)
}

function UsersTable() {
	const filter = usersTable.useStore((s) => s.filter)
	const setFilter = usersTable.useStore((s) => s.setFilter)
	// reads/writes survive navigating away from UsersPage and back
	return (
		<FilterDropdown
			value={filter}
			onChange={setFilter}
		/>
	)
}
```

The read hooks (`useStore`, `useShallowStore`, `useContextStore`, `Item`) behave exactly like [`createContextStore`](./create-context-store).

## How it stays alive

Each `<Provider>` is counted as an observer. When the **last** one unmounts, the store is kept for `gcTime`, then evicted. Remount within that window and you get the same instance back.

```tsx
// gcTime resolution (first match wins):
<usersTable.Provider cacheKey='users' />              // cache default (5 min here)
<usersTable.Provider cacheKey='users' gcTime={30_000} /> // this entry: 30s after last unmount
<usersTable.Provider cacheKey='users' alwaysCache />  // never auto-evict
```

`gcTime` and `alwaysCache` are **birth-config**: they are fixed by the first mount that creates the entry. Later mounts attach to the existing store and ignore them.

## `defaultProps` seed once

`defaultProps` seeds the store **only when the key is first created**. On remount of a live entry it is ignored — that is the whole point of keep-alive.

```tsx
// First visit → store created as { filter: 'active' }
<usersTable.Provider cacheKey='users' defaultProps={{ filter: 'active' }} />

// User changes filter to 'archived', navigates away, comes back:
<usersTable.Provider cacheKey='users' defaultProps={{ filter: 'active' }} />
// → still 'archived'. The new defaultProps do nothing.
```

To open a page with pre-set state, drive it from the URL and seed from there, rather than mutating a cold store:

```tsx
<usersTable.Provider
	cacheKey='users'
	defaultProps={{ filter: searchParams.get('filter') ?? 'all' }}
/>
```

## Reading a store from anywhere

Reads are addressed by the **absolute** `{ path, key }` — `path` defaults to `[]` (root) when omitted. Writes inherit their path from `Scope`; reads, being "from elsewhere", state it explicitly.

### `fromCache({ path, key })` — imperative

Returns the live `StoreApi` or `undefined`. Never creates an entry. Use it in event handlers, actions, or non-React code:

```tsx
// A global "reset filters" button, even outside the table's subtree:
function ResetButton() {
	return (
		<button onClick={() => usersTable.fromCache({ path: ['page-1'], key: 'users' })?.setState({ filter: 'all', page: 1 })}>
			Reset
		</button>
	)
}

// A WebSocket pushing rows into the live store:
socket.on('row', (row) => usersTable.fromCache({ path: ['page-1'], key: 'users' })?.getState().addRow(row))
```

### `useFromCache({ path, key }, selector)` — reactive

Reactively read a cached store from **anywhere** — even a sidebar that is not inside the table's `Provider`. The selector receives the state, or `undefined` when no entry exists:

```tsx
function ActiveFiltersBadge() {
	const count = usersTable.useFromCache({ path: ['page-1'], key: 'users' }, (s) => s?.activeFilters.length ?? 0)
	return <span>{count} filters</span>
}
```

`useFromCache` is **passive** — it reflects the cache but does not keep the store alive. Once the owning `Provider` unmounts and `gcTime` elapses, the entry is evicted and the reader sees `undefined`. Use `alwaysCache` if a reader must keep it alive.

## Multiple keys and groups

One group, many keys — each `cacheKey` is an independent store:

```tsx
<usersTable.Provider cacheKey='active-users' />
<usersTable.Provider cacheKey='archived-users' /> // separate filters/pagination
```

Different groups never collide, even on the same key — the group `name` is the namespace:

```tsx
const usersTable = cache.defineStore('users', usersFactory)
const ordersTable = cache.defineStore('orders', ordersFactory)

usersTable.fromCache({ key: 'main' }) // ≠ ordersTable.fromCache({ key: 'main' })
```

## Namespacing with `Scope`

A cache entry's identity has three axes: a **`path`** (where in the app it lives), the **group** (the `defineStore` name), and the **`cacheKey`** (which instance). The `path` is the outer axis and it is _inherited_ from the surrounding `<cache.Scope>`.

This matters for **reusable** components. A `<UserTable userId>` mounted on two different pages computes the same `cacheKey` (`user-42`) under the same group — so without a path, the two mounts would share one store and leak filters between pages. Wrap each location in a `Scope` and the collision is gone, with no change to the leaf component:

<LivePreview
	path='zu-store/store-cache-scope'
	title='Same table under two scopes never collide'
/>

```tsx
// Reusable — knows only its own cacheKey, nothing about where it is mounted:
function UserTable({ userId }: { userId: string }) {
	return (
		<usersTable.Provider cacheKey={`user-${userId}`}>
			<Grid />
		</usersTable.Provider>
	)
}

// Each page namespaces its subtree. user-42 on page-1 ≠ user-42 on page-2:
<cache.Scope path={['page-1']}>
	<UserTable userId='42' />
</cache.Scope>
<cache.Scope path={['page-2']}>
	<UserTable userId='42' />
</cache.Scope>
```

Nested `Scope`s **concatenate** (outermost first), so `resolvedPath = [...inheritedScope, ...providerPath]`:

```tsx
<cache.Scope path={['page-1']}>
	<cache.Scope path={['section-1']}>
		<usersTable.Provider cacheKey='user-42' /> {/* path: ['page-1', 'section-1'] */}
		<usersTable.Provider cacheKey='user-42' path={['detail']} /> {/* ['page-1','section-1','detail'] */}
	</cache.Scope>
</cache.Scope>
```

The `path` prop on a `Provider` is appended _after_ the inherited scope — a local override for ad-hoc disambiguation. With no enclosing `Scope`, the path is `[]` (root), reproducing the flat behavior above.

### `path` prop without `Scope` — ad-hoc variants

When you don't want to lift a `Scope` boundary but still need to disambiguate two mountings of the same table, the `path` prop on the Provider is enough. A common case: the same data shown in the main view and inside a modal — different filters, no leakage:

```tsx
function CompanyView({ companyId }: { companyId: string }) {
	return (
		<>
			<usersTable.Provider cacheKey={`company-${companyId}`} path={['main']}>
				<UsersTable />
			</usersTable.Provider>

			<Modal title='Edit users'>
				<usersTable.Provider cacheKey={`company-${companyId}`} path={['modal']}>
					<UsersTable />
				</usersTable.Provider>
			</Modal>
		</>
	)
}
```

Both Providers share the same `cacheKey`, but their resolved paths are `['main']` and `['modal']` — two independent stores, two independent filters.

### One `Scope`, many groups

A `Scope` namespaces **every** descendant `defineStore`'s `Provider` — not just one group. So a page that mounts several different tables gets all of them namespaced together:

```tsx
const usersTable = cache.defineStore('users', usersFactory)
const ordersTable = cache.defineStore('orders', ordersFactory)
const invoicesTable = cache.defineStore('invoices', invoicesFactory)

function CustomerDetailPage({ customerId }: { customerId: string }) {
	return (
		<cache.Scope path={['customer', customerId]}>
			<usersTable.Provider cacheKey='list' />     {/* path: ['customer', '42'] */}
			<ordersTable.Provider cacheKey='list' />    {/* path: ['customer', '42'] */}
			<invoicesTable.Provider cacheKey='list' />  {/* path: ['customer', '42'] */}
		</cache.Scope>
	)
}
```

All three tables share the same `path`. `clear(['customer', '42'])` drops all of them in one call when the user leaves the customer page.

## Inspecting and clearing

`useCache()` exposes the active cache. `keys(prefix?)` is a flat list of coordinates (great for tests/iteration); the standalone `toTree(coords)` utility turns any coordinate list into a nested object view (great for logs/devtools). `tree` lives outside the cache instance — it's a pure function, not a method:

```tsx
import { toTree } from '@ez-kit/zu-store'

function CacheTools() {
	const { keys, clear } = cache.useCache()

	// keys() → [{ path: ['page-1'], group: 'users', key: 'main' }, { path: ['page-2'], group: 'orders', key: 'list' }]
	// toTree(keys()) → { 'page-1': { users: ['main'] }, 'page-2': { orders: ['list'] } }

	return (
		<>
			<button onClick={() => clear()}>Clear all cached tables</button>
			{/* Cross-group subtree eviction — drop everything page-1 created when leaving it: */}
			<button onClick={() => clear(['page-1'])}>Clear page-1</button>
		</>
	)
}

usersTable.remove({ path: ['page-1'], key: 'main' }) // drop a single entry (overrides alwaysCache)
```

`clear(path)` removes every entry whose resolved path is prefixed by `path`, **across all groups** — the natural "leave a page, drop its stores" lever. Both `remove` and `clear` override `alwaysCache`.

### Dev-tools tree inspector

`toTree` is a plain function — drop it into a debug overlay, a Storybook addon, or a `console.log` call without wiring anything reactive. Useful while you are still learning what your cache contains:

```tsx
import { toTree } from '@ez-kit/zu-store'

function CacheInspector() {
	const { keys } = cache.useCache()
	const [open, setOpen] = useState(false)

	if (!open) return <button onClick={() => setOpen(true)}>Show cache</button>

	return (
		<aside className='debug-overlay'>
			<button onClick={() => setOpen(false)}>Close</button>
			<pre>{JSON.stringify(toTree(keys()), null, 2)}</pre>
		</aside>
	)
}
```

Pass a prefix for a focused view of a subtree:

```tsx
const subtree = toTree(keys(['customer', customerId]))
```

### `clear(path)` on navigation

Pair `clear(path)` with a route-exit effect to release a page's stores on leave. `alwaysCache` entries living inside the subtree are released too — `clear` is the explicit lever, so it takes precedence:

```tsx
function CustomerDetailPage({ customerId }: { customerId: string }) {
	const { clear } = cache.useCache()

	useEffect(() => {
		return () => {
			// Effect cleanup runs on unmount or when customerId changes.
			clear(['customer', customerId])
		}
	}, [clear, customerId])

	return (
		<cache.Scope path={['customer', customerId]}>
			<usersTable.Provider cacheKey='list' />
			<ordersTable.Provider cacheKey='list' />
		</cache.Scope>
	)
}
```

For a single entry rather than a subtree, use the group's `remove({ path, key })`.

## API

### `createStoreCache(options?)`

```ts
createStoreCache(options?: { gcTime?: number }): {
	Provider // mount once; owns the cache storage for its React tree
	Scope // contributes inherited path segments to descendant Providers
	useCache: () => {
		keys(prefix?: string[]): { path: string[]; group: string; key: string }[]
		clear(prefix?: string[]): void
	}
	defineStore: (name, factory, options?) => StoreGroup
}

// Pure utility, exported alongside createStoreCache:
toTree(coords: { path: string[]; group: string; key: string }[]): CacheTree
```

`gcTime` (default 5 minutes) is the delay before an unobserved entry is evicted. `toTree` is a standalone pure function — it takes any coordinate list (e.g. the output of `keys()`) and returns the nested view. It is not a method on the cache instance.

### `cache.Scope`

Contributes path segments to every descendant store-group `Provider`. Takes a `path: string[]`; nested `Scope`s concatenate (outermost first). Reusable components stay location-agnostic — the surrounding `Scope` decides their namespace.

### `cache.Provider`

Owns the real storage, created per React tree — so SSR requests and tests are isolated by construction. Mount it once above your store groups; unmounting it drops the whole cache. Using a group hook/provider without a `cache.Provider` ancestor throws `Missing StoreCacheProvider for createStoreCache`.

### `cache.defineStore(name, factory, options?)`

Returns a store group. `name` is the group's namespace (visible in `useCache().keys()`) and must be unique within a cache. `options.gcTime` overrides the cache default for this group.

The returned group exposes:

| Member                                                      | Purpose                                                                                          |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `Provider`                                                  | Keyed observer: `cacheKey` (required), `path?`, `defaultProps`, `gcTime?`, `alwaysCache?`.        |
| `useStore` / `useShallowStore` / `useContextStore` / `Item` | Read the store under the `Provider` — same as `createContextStore`.                              |
| `fromCache({ path?, key })`                                 | Imperative get-if-alive → `StoreApi` or `undefined`.                                             |
| `useFromCache({ path?, key }, selector)`                    | Reactive, passive cross-tree read.                                                               |
| `remove({ path?, key })`                                    | Drop one entry immediately.                                                                       |

## Server-side rendering

The feature is client-only. On the server the group `Provider` behaves like `createContextStore` — a fresh store per request, seeded from `defaultProps` — and `fromCache` returns `undefined`. Because storage lives inside `cache.Provider` (per render tree), there is no cross-request leakage.

## Gotchas

- **Reads use the absolute path.** `fromCache`/`useFromCache`/`remove` address `{ path, key }` from outside, so pass the full resolved path (it defaults to `[]` root). A read with the wrong path silently misses.
- **`alwaysCache` + dynamic keys or paths leaks.** Pinned entries under unbounded keys (`order-${id}`) or unbounded paths never evict. Use `alwaysCache` only for a small, fixed set; rely on `gcTime` for dynamic ones, and `clear(path)` to drop a subtree on navigation.
- **`useFromCache` is passive.** It will not keep a store alive on its own.
- **Imperative access needs a mounted `cache.Provider`.** With multiple `cache.Provider`s, the active one is ambiguous — prefer `useCache()` inside the tree.
- **Group names must be unique within a cache.** Two groups sharing a name under the same `cache.Provider` collide on one keyspace.
