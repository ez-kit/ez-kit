# `createStoreCache`

`createContextStore` creates a fresh store on `Provider` mount and throws it away on unmount. That is exactly what you want for a modal or a one-off form — but not for a table whose filters and pagination should still be there when the user navigates away and back.

`createCachedStore` is a **separate, opt-in** primitive that keeps the whole live store instance alive in an in-memory cache, keyed by a name you choose. `createContextStore` is unchanged.

The package ships a **ready-made default cache** — import `CacheProvider` and `createCachedStore` directly and you are done; no instance to create. This page uses the default cache throughout. If you need an isolated cache or several independent caches, see [Custom or multiple caches](#custom-or-multiple-caches) at the end.

## Keep-alive in action

Switch to **Away** (the table unmounts) and back — the filter and page are preserved. The badge reads the same store from outside the table via `useFromCache`.

## Quick start

The package ships a ready-made default cache. Two steps: define a named store group, then mount the cache boundary once.

```tsx
import { type ContextStoreInit, CacheProvider, createCachedStore } from '@ez-kit/zu-store'
import { createStore } from 'zustand/vanilla'

type TableState = {
	filter: string
	page: number
	setFilter: (filter: string) => void
}

// 1. Define a named store group against the default cache.
const usersTable = createCachedStore(
	({ defaultValue }: ContextStoreInit<{ filter?: string }>) =>
		createStore<TableState>((set) => ({
			filter: defaultValue.filter ?? 'all',
			page: 1,
			setFilter: (filter) => set({ filter }),
		})),
	{ name: 'users-table' },
)

// 2. Mount the cache boundary once, high in the tree.
function App({ children }: { children: React.ReactNode }) {
	return <CacheProvider>{children}</CacheProvider>
}
```

Then mount the keyed `Provider` wherever the table lives. It survives unmount and is reused on remount:

```tsx
function UsersPage() {
	return (
		<usersTable.Provider
			id='users'
			defaultValue={{ filter: 'active' }}
		>
			<UsersTable />
		</usersTable.Provider>
	)
}

function UsersTable() {
	const filter = usersTable.useStore((s) => s.filter)
	const setFilter = usersTable.useStore((s) => s.setFilter)
	// reads/writes survive navigating away from UsersPage and back
	return (
		<FilterDropdown
			value={filter}
			onChange={setFilter}
		/>
	)
}
```

The read hooks (`useStore`, `useShallowStore`, `useContextStore`, `Item`) behave exactly like [`createContextStore`](./create-context-store).

## How it stays alive

Each `<Provider>` is counted as an observer. When the **last** one unmounts, the store is kept for `gcTime`, then evicted. Remount within that window and you get the same instance back.

```tsx
// gcTime resolution (first match wins):
<usersTable.Provider id='users' />              // cache default (5 min here)
<usersTable.Provider id='users' gcTime={30_000} /> // this entry: 30s after last unmount
<usersTable.Provider id='users' alwaysCache />  // never auto-evict
```

`gcTime` and `alwaysCache` are **birth-config**: they are fixed by the first mount that creates the entry. Later mounts attach to the existing store and ignore them.

## `defaultValue` seed once

`defaultValue` seeds the store **only when the key is first created**. On remount of a live entry it is ignored — that is the whole point of keep-alive.

```tsx
// First visit → store created as { filter: 'active' }
<usersTable.Provider id='users' defaultValue={{ filter: 'active' }} />

// User changes filter to 'archived', navigates away, comes back:
<usersTable.Provider id='users' defaultValue={{ filter: 'active' }} />
// → still 'archived'. The new defaultValue do nothing.
```

To open a page with pre-set state, drive it from the URL and seed from there, rather than mutating a cold store:

```tsx
<usersTable.Provider
	id='users'
	defaultValue={{ filter: searchParams.get('filter') ?? 'all' }}
/>
```

## Reading a store from anywhere

Reads are addressed by the **absolute** `{ path, id }` — `path` defaults to `[]` (root) when omitted. Writes inherit their path from `Scope`; reads, being "from elsewhere", state it explicitly.

### `fromCache({ path, id })` — imperative

Returns the live `StoreApi` or `undefined`. Never creates an entry. Use it in event handlers, actions, or non-React code:

```tsx
// A global "reset filters" button, even outside the table's subtree:
function ResetButton() {
	return (
		<button onClick={() => usersTable.fromCache({ path: ['page-1'], id: 'users' })?.setState({ filter: 'all', page: 1 })}>
			Reset
		</button>
	)
}

// A WebSocket pushing rows into the live store:
socket.on('row', (row) => usersTable.fromCache({ path: ['page-1'], id: 'users' })?.getState().addRow(row))
```

### `useFromCache({ path, id }, selector)` — reactive

Reactively read a cached store from **anywhere** — even a sidebar that is not inside the table's `Provider`. The selector receives the state, or `undefined` when no entry exists:

```tsx
function ActiveFiltersBadge() {
	const count = usersTable.useFromCache({ path: ['page-1'], id: 'users' }, (s) => s?.activeFilters.length ?? 0)
	return <span>{count} filters</span>
}
```

`useFromCache` is **passive** — it reflects the cache but does not keep the store alive. Once the owning `Provider` unmounts and `gcTime` elapses, the entry is evicted and the reader sees `undefined`. Use `alwaysCache` if a reader must keep it alive.

## Multiple keys and groups

One group, many keys — each `id` is an independent store:

```tsx
<usersTable.Provider id='active-users' />
<usersTable.Provider id='archived-users' /> // separate filters/pagination
```

Different groups never collide, even on the same key — the group `name` is the namespace:

```tsx
const usersTable = createCachedStore(usersFactory, { name: 'users' })
const ordersTable = createCachedStore(ordersFactory, { name: 'orders' })

usersTable.fromCache({ id: 'main' }) // ≠ ordersTable.fromCache({ id: 'main' })
```

## Namespacing with `Scope`

A cache entry's identity has three axes: a **`path`** (where in the app it lives), the **`name`** (the `createCachedStore` name of its store group), and the **`id`** (which instance). The `path` is the outer axis and it is _inherited_ from the surrounding `<CacheScope>`.

This matters for **reusable** components. A `<UserTable userId>` mounted on two different pages computes the same `id` (`user-42`) under the same group — so without a path, the two mounts would share one store and leak filters between pages. Wrap each location in a `Scope` and the collision is gone, with no change to the leaf component:

<LivePreview
	path='zu-store/store-cache-scope'
	title='Same table under two scopes never collide'
/>

```tsx
// Reusable — knows only its own id, nothing about where it is mounted:
function UserTable({ userId }: { userId: string }) {
	return (
		<usersTable.Provider id={`user-${userId}`}>
			<Grid />
		</usersTable.Provider>
	)
}

// Each page namespaces its subtree. user-42 on page-1 ≠ user-42 on page-2:
<CacheScope path={['page-1']}>
	<UserTable userId='42' />
</CacheScope>
<CacheScope path={['page-2']}>
	<UserTable userId='42' />
</CacheScope>
```

Nested `Scope`s **concatenate** (outermost first), so `resolvedPath = [...inheritedScope, ...providerPath]`:

```tsx
<CacheScope path={['page-1']}>
	<CacheScope path={['section-1']}>
		<usersTable.Provider id='user-42' /> {/* path: ['page-1', 'section-1'] */}
		<usersTable.Provider id='user-42' path={['detail']} /> {/* ['page-1','section-1','detail'] */}
	</CacheScope>
</CacheScope>
```

The `path` prop on a `Provider` is appended _after_ the inherited scope — a local override for ad-hoc disambiguation. With no enclosing `Scope`, the path is `[]` (root), reproducing the flat behavior above.

### `path` prop without `Scope` — ad-hoc variants

When you don't want to lift a `Scope` boundary but still need to disambiguate two mountings of the same table, the `path` prop on the Provider is enough. A common case: the same data shown in the main view and inside a modal — different filters, no leakage:

```tsx
function CompanyView({ companyId }: { companyId: string }) {
	return (
		<>
			<usersTable.Provider id={`company-${companyId}`} path={['main']}>
				<UsersTable />
			</usersTable.Provider>

			<Modal title='Edit users'>
				<usersTable.Provider id={`company-${companyId}`} path={['modal']}>
					<UsersTable />
				</usersTable.Provider>
			</Modal>
		</>
	)
}
```

Both Providers share the same `id`, but their resolved paths are `['main']` and `['modal']` — two independent stores, two independent filters.

### One `Scope`, many groups

A `Scope` namespaces **every** descendant `createCachedStore`'s `Provider` — not just one group. So a page that mounts several different tables gets all of them namespaced together:

```tsx
const usersTable = createCachedStore(usersFactory, { name: 'users' })
const ordersTable = createCachedStore(ordersFactory, { name: 'orders' })
const invoicesTable = createCachedStore(invoicesFactory, { name: 'invoices' })

function CustomerDetailPage({ customerId }: { customerId: string }) {
	return (
		<CacheScope path={['customer', customerId]}>
			<usersTable.Provider id='list' />     {/* path: ['customer', '42'] */}
			<ordersTable.Provider id='list' />    {/* path: ['customer', '42'] */}
			<invoicesTable.Provider id='list' />  {/* path: ['customer', '42'] */}
		</CacheScope>
	)
}
```

All three tables share the same `path`. `clear(['customer', '42'])` drops all of them in one call when the user leaves the customer page.

## Inspecting and clearing

`useCache()` exposes the active cache. `keys(prefix?)` is a flat list of coordinates (great for tests/iteration); the standalone `toTree(coords)` utility turns any coordinate list into a nested object view (great for logs/devtools). `tree` lives outside the cache instance — it's a pure function, not a method:

```tsx
import { toTree, useCache } from '@ez-kit/zu-store'

function CacheTools() {
	const { keys, clear } = useCache()

	// keys() → [{ path: ['page-1'], name: 'users', id: 'main' }, { path: ['page-2'], name: 'orders', id: 'list' }]
	// toTree(keys()) → { 'page-1': { users: ['main'] }, 'page-2': { orders: ['list'] } }

	return (
		<>
			<button onClick={() => clear()}>Clear all cached tables</button>
			{/* Cross-group subtree eviction — drop everything page-1 created when leaving it: */}
			<button onClick={() => clear(['page-1'])}>Clear page-1</button>
		</>
	)
}

usersTable.remove({ path: ['page-1'], id: 'main' }) // drop a single entry (overrides alwaysCache)
```

`clear(path)` removes every entry whose resolved path is prefixed by `path`, **across all groups** — the natural "leave a page, drop its stores" lever. Both `remove` and `clear` override `alwaysCache`.

### Reactive inspection — `useCacheKeys`

`useCacheKeys(prefix?)` is the one reactive inspection hook (the default cache's `useKeys`). It re-renders only when the cache **membership** changes (entries added or removed); internal state changes inside tracked stores do **not** trigger it, so a devtools panel built on `useCacheKeys` stays cheap even with chatty entries.

```tsx
import { useCacheKeys } from '@ez-kit/zu-store'

function CacheBadge() {
	const records = useCacheKeys() // [{ path, name, id }, ...]
	return <span>{records.length} cached</span>
}
```

For a nested view, compose the standalone `toTree` utility with `useCacheKeys`:

```tsx
import { toTree, useCache, useCacheKeys } from '@ez-kit/zu-store'

function CachePanel({ customerId }: { customerId: string }) {
	const records = useCacheKeys(['customer', customerId])
	const { clear } = useCache()
	const tree = toTree(records)
	return (
		<>
			<pre>{JSON.stringify(tree, null, 2)}</pre>
			<button onClick={() => clear(['customer', customerId])}>Clear customer</button>
		</>
	)
}
```

For one-off snapshots (tests, event handlers, logging in non-reactive code) use the non-reactive `useCache().keys()` paired with `toTree`.

### Dev-tools tree inspector

`toTree` is a plain function — drop it into a debug overlay, a Storybook addon, or a `console.log` call without wiring anything reactive. Useful while you are still learning what your cache contains:

```tsx
import { toTree, useCache } from '@ez-kit/zu-store'

function CacheInspector() {
	const { keys } = useCache()
	const [open, setOpen] = useState(false)

	if (!open) return <button onClick={() => setOpen(true)}>Show cache</button>

	return (
		<aside className='debug-overlay'>
			<button onClick={() => setOpen(false)}>Close</button>
			<pre>{JSON.stringify(toTree(keys()), null, 2)}</pre>
		</aside>
	)
}
```

Pass a prefix for a focused view of a subtree:

```tsx
const subtree = toTree(keys(['customer', customerId]))
```

### `clear(path)` on navigation

Pair `clear(path)` with a route-exit effect to release a page's stores on leave. `alwaysCache` entries living inside the subtree are released too — `clear` is the explicit lever, so it takes precedence:

```tsx
import { CacheScope, useCache } from '@ez-kit/zu-store'

function CustomerDetailPage({ customerId }: { customerId: string }) {
	const { clear } = useCache()

	useEffect(() => {
		return () => {
			// Effect cleanup runs on unmount or when customerId changes.
			clear(['customer', customerId])
		}
	}, [clear, customerId])

	return (
		<CacheScope path={['customer', customerId]}>
			<usersTable.Provider id='list' />
			<ordersTable.Provider id='list' />
		</CacheScope>
	)
}
```

For a single entry rather than a subtree, use the group's `remove({ path, id })`.

## API

The default cache is exposed as top-level exports — use these for the common one-cache-per-app case, no factory call required:

```ts
import {
	CacheProvider, // mount once; owns the cache storage for its React tree
	CacheScope, // contributes inherited path segments to descendant Providers
	useCache, // () => { keys(prefix?), clear(prefix?) }
	useCacheKeys, // (prefix?) => CacheRecord[] — reactive: re-renders on membership change
	createCachedStore, // (factory, { name, gcTime? }) => StoreGroup
	toTree, // pure utility: (records) => CacheTree
} from '@ez-kit/zu-store'

type CacheRecord = { path: string[]; name: string; id: string }
```

`Cache`-qualified names are used only where the bare member name would be too generic at package scope (`Provider`→`CacheProvider`, `Scope`→`CacheScope`, `useKeys`→`useCacheKeys`). `useCache` and `createCachedStore` are already specific and keep their names. `toTree` is a standalone pure function — it takes any coordinate list (e.g. the output of `keys()` or `useCacheKeys()`, or an array you assembled by hand for a test) and returns the nested view. For a reactive nested view, compose `toTree(useCacheKeys(prefix?))` at the call site.

### `CacheScope`

Contributes path segments to every descendant store-group `Provider`. Takes a `path: string[]`; nested `Scope`s concatenate (outermost first). Reusable components stay location-agnostic — the surrounding `Scope` decides their namespace.

### `CacheProvider`

Owns the real storage, created per React tree — so SSR requests and tests are isolated by construction. Mount it once above your store groups; unmounting it drops the whole cache. Using a group hook/provider without a `CacheProvider` ancestor throws `Missing StoreCacheProvider for createStoreCache`.

### `createCachedStore(factory, options)`

Returns a store group. `options.name` is the group's namespace (visible in `useCache().keys()`), is required, and must be unique within a cache. `options.gcTime` overrides the cache default for this group.

The returned group exposes:

| Member                                                      | Purpose                                                                                          |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `Provider`                                                  | Keyed observer: `id` (required), `path?`, `defaultValue`, `gcTime?`, `alwaysCache?`.       |
| `useStore` / `useShallowStore` / `useContextStore` / `Item` | Read the store under the `Provider` — same selector/shallow semantics as `createContextStore`.   |
| `fromCache({ path?, id })`                            | Imperative get-if-alive → `StoreApi` or `undefined`.                                             |
| `useFromCache({ path?, id }, selector)`               | Reactive, passive cross-tree read.                                                               |
| `remove({ path?, id })`                               | Drop one entry immediately.                                                                       |

## Server-side rendering

The feature is client-only. On the server the group `Provider` behaves like `createContextStore` — a fresh store per request, seeded from `defaultValue` — and `fromCache` returns `undefined`. Because storage lives inside `CacheProvider` (per render tree), there is no cross-request leakage.

## Custom or multiple caches

The default cache covers the common "one cache per app" case. When you need an **isolated** cache, **several independent** caches in one app, or a **custom default `gcTime`**, build your own with `createStoreCache`. It returns the same surface as the default — but as instance members instead of top-level exports:

```ts
createStoreCache(options?: { gcTime?: number }): {
	Provider // ↔ CacheProvider
	Scope // ↔ CacheScope
	useCache // ↔ useCache
	useKeys // ↔ useCacheKeys
	createCachedStore // ↔ createCachedStore
}
```

```tsx
import { createStoreCache } from '@ez-kit/zu-store'
import { createStore } from 'zustand/vanilla'

// Two independent caches with different defaults.
const sessionCache = createStoreCache({ gcTime: 30_000 })
const persistentCache = createStoreCache({ gcTime: Infinity })

const draft = sessionCache.createCachedStore(draftFactory, { name: 'draft' })
const settings = persistentCache.createCachedStore(settingsFactory, { name: 'settings' })

function App() {
	return (
		<sessionCache.Provider>
			<persistentCache.Provider>{/* … */}</persistentCache.Provider>
		</sessionCache.Provider>
	)
}
```

A store group is **bound to the cache that created it**. A group from the top-level `createCachedStore` works only under `<CacheProvider>`; a group from `sessionCache.createCachedStore` works only under `<sessionCache.Provider>`. Mounting a group under the wrong provider throws `Missing StoreCacheProvider for createStoreCache`. Everything else on this page applies unchanged — just read `sessionCache.Provider` / `sessionCache.Scope` / `sessionCache.useKeys` for `CacheProvider` / `CacheScope` / `useCacheKeys`.

## Gotchas

- **Reads use the absolute path.** `fromCache`/`useFromCache`/`remove` address `{ path, id }` from outside, so pass the full resolved path (it defaults to `[]` root). A read with the wrong path silently misses.
- **`alwaysCache` + dynamic keys or paths leaks.** Pinned entries under unbounded keys (`order-${id}`) or unbounded paths never evict. Use `alwaysCache` only for a small, fixed set; rely on `gcTime` for dynamic ones, and `clear(path)` to drop a subtree on navigation.
- **`useFromCache` is passive.** It will not keep a store alive on its own.
- **Imperative access needs a mounted `CacheProvider`.** With multiple `CacheProvider`s, the active one is ambiguous — prefer `useCache()` inside the tree.
- **Group names must be unique within a cache.** Two groups sharing a name under the same `CacheProvider` collide on one keyspace. The library emits a `console.warn` in development if `createCachedStore` is called twice with the same name on the same cache — usually a sign of `createCachedStore` being invoked inside a render.
- **Don't mount two `<CacheProvider>` for the same cache.** Imperative access via `fromCache`/`remove` targets the most recently activated cache and is ambiguous when both are mounted. The library emits a `console.warn` in development to make the collision visible at the moment it happens.
