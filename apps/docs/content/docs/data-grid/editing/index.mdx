title: Editing
description: Row, modal and cell editing — one handler, typed values, validation before commit.
---

Editing is one option and one handler. `editing.onSave` receives the row id, the row and the
edited values; supply it and the grid mounts the edit affordance, the form inputs and the commit
pipeline.

## Usage

<DataGridDocsExample exampleId='base-editing' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	editing={{
		mode: 'row',
		onSave: ({ rowId, values }) => {
			setData((prev) => prev.map((row) => (String(row.id) === rowId ? { ...row, ...values } : row)))
		},
	}}
/>
```

Editing only activates when you supply `onSave` — without it, no Edit button is mounted. This lets
a [defaults layer](/docs/data-grid/state/defaults) describe how editing should _look_ for a whole app while only the grids that supply `onSave` actually enable it.

## Modes

`mode` is what editing _does_, not how it looks.

| `mode`    | Behaviour                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------ |
| `'row'`   | The default. The row turns into inputs in place; the actions cell offers Save / Cancel.          |
| `'modal'` | A dialog collects the whole row. The grid mounts it for you when this mode is on.                |
| `'cell'`  | One cell at a time. Double-click a cell to open it; Enter or leaving it commits, Escape cancels. |

### Row

The row you picked turns into inputs in place, and the actions cell swaps Edit for Save / Cancel.

<DataGridDocsExample exampleId='editing-mode-row' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	editing={{ mode: 'row', onSave }}
/>
```

### Modal

The same form, collected in a dialog instead of in the row. The grid mounts the dialog itself —
nothing to place by hand. To replace it, or the form inside it, register a `FormModal`; see
[a form of your own](/docs/data-grid/editing/creating#a-form-of-your-own).

<DataGridDocsExample exampleId='editing-mode-modal' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	editing={{ mode: 'modal', onSave }}
/>
```

### Cell

One field at a time: double-click a cell to open it. Columns marked `editing: false` stay
read-only here too. `table.editing.startCell(rowId, columnId)` opens a cell programmatically.

The opened cell takes the focus. **Enter** commits that one field, **Escape** abandons it, and
clicking or tabbing anywhere outside the cell commits too — a control _inside_ it, a switch or a
select's popover, does not. Which is why this mode adds no Edit pencil and no Save / Cancel pair to
the [row actions](/docs/data-grid/row-actions) column — the pencil starts the _row_ flow, which
opens nothing here, and there is no row-wide form left to save. With nothing else switched on, the
actions column does not appear at all.

<DataGridDocsExample exampleId='editing-mode-cell' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	editing={{ mode: 'cell', onSave }}
/>
```

## Which inputs a row gets

From the columns, not from a second list. A column's `cell.type` decides the input its field
renders — a `date` column gets the kit's date picker, a `select` column its select. See
[Cell types](/docs/data-grid/columns/cell-types).

Per column, the edit form is tuned under `editing`:

```tsx
const columns = createColumns<User>([
	{ accessorKey: 'name', header: 'Name' },
	// Not editable: the field is left out of the form.
	{ accessorKey: 'createdAt', header: 'Created', editing: false },
	{
		accessorKey: 'email',
		header: 'Email',
		editing: {
			description: 'Used for sign-in',
			validateOn: 'blur',
		},
	},
	{
		accessorKey: 'rating',
		header: 'Rating',
		// Anything the built-in types do not cover.
		editing: { component: RatingInput },
	},
])
```

`editing.component` receives a `FieldState` — `value`, `onChange`, `onBlur`, `error`, `errors`,
`isValidating`, plus the column's `config`, `label` and `description` in form contexts.

## What `onSave` receives

`values` holds the fields of the edit form and nothing else: every column the form shows, but no
system column and no column with `editing: false`. In cell mode it holds the one edited column.
Everything else about the row — its id field, a column left read-only, a `version` no column
shows — is on `row`, the row as it is in `data`:

```ts
editing: {
	onSave: async ({ rowId, row, values, signal }) => {
		// Optimistic locking: the version is not a column, so it is not in `values`.
		await api.update(rowId, { ...values, version: row?.version }, { signal })
	},
}
```

`row` is read-only context: nothing in it is saved unless you put it in the request yourself. It
is `undefined` only when the row left `data` while the form was open.

Earlier versions seeded the form with every non-system column, `editing: false` ones included, so
those values reached `onSave` unchanged. Read them from `row` now.

## Options

| `editing` key | Type                                                        | Description                                                                                                |
| ------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `onSave`      | `({ rowId, row, values, signal }) => void \| Promise<void>` | Required. Commit the edit. `signal` aborts when the user cancels or the table unmounts.                    |
| `mode`        | `'row' \| 'modal' \| 'cell'`                                | What editing does. Default `'row'`.                                                                        |
| `validate`    | `ValidateConfig`                                            | A function, or `{ schema }` for any Standard Schema. See [Validation](/docs/data-grid/editing/validation). |
| `validateOn`  | `'submit' \| 'blur' \| 'change'`                            | When a field validates. Default `'submit'`. A column overrides it under its own `editing.validateOn`.      |
| `debounce`    | `number`                                                    | Debounce for `validateOn: 'change'`. Default `200`.                                                        |
| `enabled`     | `boolean`                                                   | Explicit off-switch for a config that came from a defaults layer.                                          |

## Reading and driving it yourself

`table.editing` is the whole pipeline, so a custom layout never has to re-implement it:

```ts
table.editing.start(rowId)
table.editing.setValue('email', next)
const result = await table.editing.commit() // { ok: true } | { ok: false, reason, … }
table.editing.cancel()
table.editing.getState() // { rowId, cellId, values, initialValues, errors, formError, commitStatus }
```

`commit({ values })` saves values collected elsewhere instead of the ones in the grid's state, and
`validateValues(values)` runs the validator without writing anything — the two halves a form of
your own needs. A rejected save resolves as `{ ok: false }` rather than throwing; only an error the
grid cannot interpret rejects the promise. See
[a form of your own](/docs/data-grid/editing/creating#a-form-of-your-own).

`row.getIsEditing()` answers whether a given row is the one being edited.

## Passing your own props to an input

An input has no separate props channel. Whatever it receives besides its `FieldState` comes from
one of three places.

**The column's `cell.config`.** One config serves every renderer of the column:

```
cell.config --+--> view        CellViewProps.config
              +--> editing     FieldState.config
              +--> creating    FieldState.config
              +--> filtering   FieldState.config / InputComponentProps.config
```

There is no `editing.config`. Put a setting here when it describes the column — a range, a step, a
list — and holds for display and editing alike. A key the column's type does not declare is a
compile error; to add one, [extend the type](/docs/data-grid/columns/custom-cell-types#extending-a-built-in-type).

**A closure in `editing.component`.** For a value only the input needs, and one that does not
change:

```tsx
{
	accessorKey: 'rating',
	header: 'Rating',
	editing: { component: (field: FieldState) => <RatingInput {...field} allowHalf /> },
}
```

The grid mounts `editing.component` as a component, by identity. A closure is a new component every
time the columns are rebuilt, and rebuilding them during an edit remounts the input — focus and the
half-typed value go with it. Keep the columns at module scope or under `useMemo` (see
[Hoist what does not change](/docs/data-grid/state/rendering#hoist-what-does-not-change)), and keep
anything that changes out of the closure.

**The grid context.** For values that change — a permission, the current locale, a callback that
closes over state — read the [grid context](/docs/data-grid/state/context) inside the input. A
selector re-renders the input when its slice changes and never remounts it:

```tsx
function RatingInput(field: FieldState) {
	const allowHalf = useGridContext((c) => c.ratings.allowHalf)
	return (
		<Stars
			value={Number(field.value)}
			onChange={field.onChange}
			allowHalf={allowHalf}
		/>
	)
}
```
