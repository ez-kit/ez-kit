`deleting.onDelete` removes one row. `deleting.bulk` extends the same feature to the current
selection. Both live here, next to each other, because they are the same operation over a
different number of rows.

## Usage

Select some rows to see the bulk prompt, or use a row's Delete action for the per-row one.

<DataGridDocsExample exampleId='delete-confirmation' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	selection
	deleting={{
		onDelete: ({ row }) => remove(row.original.id),
		confirmation: {
			title: 'Delete product?',
			description: (row) => `"${row.original.name}" will be permanently removed.`,
		},
		bulk: {
			onDelete: ({ rowIds }) => api.removeMany(rowIds),
			confirmation: {
				title: 'Delete products?',
				description: (rows) => `${rows.length} products will be permanently removed.`,
			},
		},
	}}
/>
```

## Bulk delete

Bulk deletion requires its own `onDelete` handler. Omit `bulk` or pass `false` to disable it.
The base grid rejects `bulk: true` and configurations without a bulk executor; it never
falls back to the single-row handler.

```tsx
// One call for the whole set — the shape a "delete these ids" endpoint wants.
deleting: { onDelete, bulk: { onDelete: ({ rowIds }) => api.removeMany(rowIds) } }
```

The Delete button appears in the [action bar](/docs/data-grid/selection/action-bar) as soon as
`bulk` resolves to on and row selection is enabled. The deleted ids leave the selection once the
handler resolves, so the bar never counts rows that no longer exist.

## Migrating an intentional per-row loop

Move the loop into the bulk handler if the API has no batch endpoint:

```tsx
deleting: {
  onDelete,
  bulk: {
    onDelete: async ({ rows, signal }) => {
      for (const row of rows) {
        await onDelete({ rowId: row.id, row, signal })
      }
    },
  },
}
```

The grid clears the resolved selection only when the whole handler resolves. It does not
interpret per-row statuses in a response or provide automatic partial-success handling.
With `withQuery`, `deleting: { bulk: true }` remains a shorthand when the source provides
`deleteMany`: the connector installs the required handler before the grid is configured.

## The prompt

`confirmation` is per level, and the two are independent — deleting twelve rows at once may
deserve a prompt where deleting one does not.

- `true` — default copy. Per row: "Delete this row?"; bulk: count-aware, "Delete 3 rows?".
- an object — `{ title?, description? }`. `description` may be a function: per row it receives
  that `row`, in bulk it receives the whole selection, which is what lets it say "3 products".

Without a prompt, the delete runs immediately.

## Rollback

Neither handler is optimistic for you, and the grid rolls nothing back — `onDelete` owns the data,
so restoring it is the handler's job. Snapshot, apply, and restore on failure if that is the UX
you want:

```tsx
bulk: {
	onDelete: async ({ rowIds }) => {
		const snapshot = data
		setData((d) => d.filter((r) => !rowIds.includes(String(r.id))))
		try {
			await api.bulkDelete(rowIds)
		} catch {
			setData(snapshot)
			toast.error('Delete failed')
		}
	},
}
```

`signal` on both contexts aborts when the user cancels a staged delete or a new delete starts.

## When the handler fails

Here are three important patterns to know when the delete handler fails:

<DataGridDocsExample exampleId='deleting-rollback' />

**An explicit loop stops at the first rejection.** The example's bulk handler calls the API
sequentially and awaits each call. The grid invokes that handler once; it does not create a loop.
If a later call fails, earlier deletions may already have succeeded. The application owns
reconciliation of those partial results and the remaining selection.

**Resolving is what clears the selection.** The deleted ids leave `state.rowSelection` after the
handler resolves, and only then. Reject and the whole selection stays, which is what lets the user
retry. The trap is the rollback pattern above: catching the error inside the handler makes it
_resolve_, so the grid treats the failed delete as a success and drops those rows from the
selection anyway. Notice the example clears all five ids in swallow mode even though one row is
still in the table.

**Nothing catches a rejection for you.** The grid calls the handler from a fire-and-forget path
(`void table.deleting.confirm()`), so a rethrow surfaces as an unhandled promise rejection in the
console. If you rethrow to keep the selection, still handle the error yourself — report it to the
user in the same handler, before rethrowing.

The dialog closes immediately after the user presses Delete, regardless of the handler's outcome.
If you need to show pending or error feedback, render it separately beside the grid.

## Options

### `deleting`

| `deleting` key | Type                                                | Description                                                       |
| -------------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| `onDelete`     | `({ rowId, row, signal }) => void \| Promise<void>` | Required. Delete one row.                                         |
| `confirmation` | `boolean \| { title?, description? }`               | Prompt before deleting one row. `description` receives that row.  |
| `bulk`         | `false \| BulkDeletingConfig`                       | Delete the selection with a required bulk executor.               |
| `enabled`      | `boolean`                                           | Explicit off-switch for a config that came from a defaults layer. |

### `deleting.bulk`

| `deleting.bulk` key | Type                                                  | Description                                                       |
| ------------------- | ----------------------------------------------------- | ----------------------------------------------------------------- |
| `onDelete`          | `({ rowIds, rows, signal }) => void \| Promise<void>` | Required. One call for the whole set; no single-delete fallback.  |
| `confirmation`      | `boolean \| { title?, description? }`                 | Prompt before deleting. `description` receives the selected rows. |
| `enabled`           | `boolean`                                             | Explicit off-switch.                                              |
