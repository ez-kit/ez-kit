The grid ships a "creating" flow: `<DataGrid.CreateTrigger>` renders the button, and clicking it
opens a draft row or a modal whose inputs come from the columns themselves — each field renders
the input its column's `cell.type` implies.

## Usage

The creating flow supports three modes. The default `mode: 'row'` opens an inline draft row at the
top of the body. Its save and cancel controls share the row-actions column when the grid has one —
`editing`, `deleting`, row `pinning` or `rowActions.actions` — and otherwise take the place of the
create trigger in the toolbar, so no column is mounted for a draft that is closed most of the time.
**Enter** commits the draft and **Escape** abandons it either way.

<DataGridDocsExample exampleId='creating-row' />

`mode: 'modal'` collects the new row in a dialog built from the same columns.

<DataGridDocsExample exampleId='creating-modal' />

`mode: 'pin-row'` keeps that draft row permanently open — there is no create trigger and nothing to
cancel; saving simply clears the row for the next entry. Its save button always has a row-actions
column to sit in, since the row is always there.

<DataGridDocsExample exampleId='creating-pin-row' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	creating={{
		mode: 'modal',
		onSave: ({ values }) => api.create(values),
	}}
>
	<DataGrid.CreateTrigger>New order</DataGrid.CreateTrigger>
</DataGrid>
```

The modal itself is mounted by the grid when `creating.mode` is `'modal'` — there is nothing to
place in a layout, and everything about the form comes from `creating` and the column defs. To
replace the dialog or the form, register a `FormModal` — see
[a form of your own](#a-form-of-your-own).

## Default values

The form opens empty unless you seed it. Two places do that, and they are resolved on **every**
`creating.start()` — not once at mount — so a function form sees the table as it is at the moment
the form opens.

Per column, next to the column it seeds:

```tsx
const columns = createColumns<Order>([
	{ accessorKey: 'status', header: 'Status', creating: { defaultValue: 'pending' } },
	{
		accessorKey: 'position',
		header: 'Position',
		creating: { defaultValue: ({ table }) => table.getRowModel().rows.length + 1 },
	},
])
```

<Callout type='warn'>
	`table` here is the real table, so what it offers depends on the features the grid registered. `getRowCount()` belongs
	to `rowPaginationFeature`, `getSortedRowModel()` to `rowSortingFeature`, and so on — call one the set omits and the
	default resolver throws a `TypeError` when the form opens. `getRowModel()` is core and is always there.
</Callout>

Or at table level, for values that span columns:

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	creating={{
		mode: 'modal',
		defaultValues: ({ table }) => ({ createdAt: new Date(), page: table.store.state.pagination.pageIndex }),
		onSave: ({ values }) => api.create(values),
	}}
/>
```

Both accept a plain value as well as a function. Rules:

- Column defaults are resolved first, in column order; `creating.defaultValues` is then merged over
  them, so the table level wins per key.
- A column with no `defaultValue` contributes **no key** at all to `state.creating.values` — not a
  key holding `undefined`.
- Both forms must be **synchronous**. An async default would open the form empty and make the field
  jump once the promise settled; load such values before calling `start()` and pass them through
  `creating.defaultValues`.
- The function form is detected with `typeof === 'function'`, so a default whose value is itself a
  function has to be wrapped: `defaultValue: () => myFn`.
- Column defaults receive only `{ table, columnId }` — not the values resolved before them. A
  default that could read its neighbours would depend on the order the columns happen to sit in the
  config. Cross-field seeding belongs in `creating.defaultValues`, which runs once, after all of
  them.

Seeding the create form through `initialState.creating` is a **type error** — see
[State model](/docs/data-grid/state).

## Validation

One validator for the whole form, exactly as in [editing](/docs/data-grid/editing/validation) — a
function, or `{ schema }` for any Standard Schema (zod, valibot, arktype, …). The modal stays open
until it passes, and a schema issue without a path — the example's "name and email must be
different" — shows in the form's banner rather than under a field.

<DataGridDocsExample exampleId='creating-validation' />

```tsx
creating: {
	mode: 'modal',
	validate: { schema: orderSchema },
	// Per field: `{ accessorKey: 'email', creating: { validateOn: 'blur' } }`
	onSave: ({ values }) => api.create(values),
}
```

Throw `ValidationError` from `onSave` to put a server's rejection back into the fields. Full
details in [Validation](/docs/data-grid/editing/validation).

## What `onSave` receives

`values` holds the create form's fields — the seed from `defaultValue` / `defaultValues`, as the
user left it. A form of your own that saves through `submit(values)` sends exactly what it passes,
keys no column declares included, so a field the grid does not show still reaches `onSave`. There
is no `row`: a row that is being created does not exist yet.

## A form of your own

The modal is the kit's `FormModal` component, and replacing that component is how the form is
replaced too — there is no second way. Register your own for one grid through `components`, or
for every grid through `createDataGrid({ components })`. One component serves both forms; `mode`
says which is open:

```tsx
<DataGrid
	columns={columns}
	data={data}
	creating={{ mode: 'modal', onSave: create }}
	editing={{ mode: 'modal', onSave: update }}
	components={{ editing: { FormModal: UserFormModal } }}
/>
```

Beside the dialog's own props — `title`, `formError`, `isPending`, `onSave`, `onCancel` and the
generated form as `children` — it receives the whole form contract:

- `fields` — the generated fields one by one, keyed by column id, each with its label, errors and
  `validateOn` behaviour, writing to the grid's state;
- `initialValues` — what the form opened with, for the fields the generated form shows only, and
  the same object for as long as it stays open;
- `row` — the row being edited as it is in `data`, read-only; `undefined` when creating;
- `submit(values?)` — saves through the grid: its `validate`, when one is configured, then
  `onSave`. It resolves rather than throwing on a refusal: `{ ok: true }`, or `ok: false` with a
  `reason` — `'rejected'` with the `errors` and `formError` the form now shows, `'cancelled'` when
  the form was closed mid-save, `'busy'` while the grid's own `validate()` runs, `'closed'` when no
  form is open. A second call while a save is in flight gets the first one's outcome;
- `validate(values)` — the grid's validator as a pure function, for a check on blur; it writes
  nothing to the grid's state. `null` means valid, or that the form has closed;
- `errors` — field errors from the last failed save.

### The generated fields in a layout of your own

Place the entries of `fields` wherever the dialog wants them and save with `onSave` — the fields
have already written their values into the grid's state:

<DataGridDocsExample exampleId='form-modal-fields-layout' />

```tsx
function UserFormModal({ title, fields, formError, isPending, onSave, onCancel }: FormModalProps) {
	return (
		<MyDialog
			title={title}
			onClose={onCancel}
		>
			{formError ? <p role='alert'>{formError}</p> : null}
			<div className='grid grid-cols-2 gap-4'>
				<div className='col-span-2'>{fields.name}</div>
				{fields.email}
				{fields.age}
			</div>
			<button
				disabled={isPending}
				onClick={() => void onSave()}
			>
				Save
			</button>
		</MyDialog>
	)
}
```

### A form library

Seed the library from `initialValues`, hand its values to `submit` and map a failed result back
onto its fields. The grid still owns opening, closing and the save — here with `@ez-kit/form`,
whose `onSubmitAsync` result is exactly that mapping:

<DataGridDocsExample exampleId='form-modal-own-form' />

The same with react-hook-form:

```tsx
import { useForm } from 'react-hook-form'

import type { FormModalProps } from '@ez-kit/data-grid-react'

function UserFormModal({ title, initialValues, submit, onCancel }: FormModalProps) {
	const { register, handleSubmit, setError, formState } = useForm({ defaultValues: initialValues })

	const onSubmit = handleSubmit(async (values) => {
		const result = await submit(values)
		if (result.ok || result.reason !== 'rejected') return
		for (const [field, messages] of Object.entries(result.errors)) {
			setError(field, { message: messages.join(', ') })
		}
		if (result.formError) setError('root', { message: result.formError })
	})

	return (
		<MyDialog
			title={title}
			onClose={onCancel}
		>
			<form onSubmit={onSubmit}>
				<input {...register('name')} />
				<input {...register('email')} />
				<button disabled={formState.isSubmitting}>Save</button>
			</form>
		</MyDialog>
	)
}
```

`submit(values)` saves exactly what it is given: keys no column declares reach `onSave` unchanged,
and nothing from `row` is added. If the grid has a `validate`, it runs on every `submit` as well —
so a form that validates itself and a grid that validates too check twice only when both were
configured to.

## Options

| `creating` key  | Type                                            | Description                                                                         |
| --------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------- |
| `onSave`        | `({ values, signal }) => void \| Promise<void>` | Required. Persist the new row. See [What `onSave` receives](#what-onsave-receives). |
| `mode`          | `'row' \| 'modal' \| 'pin-row'`                 | Where the draft appears. Default `'row'`.                                           |
| `defaultValues` | `Partial<TRow> \| ((ctx) => Partial<TRow>)`     | Seeds that span columns. Merged over the per-column `defaultValue`s.                |
| `validate`      | `ValidateConfig`                                | The form's validator.                                                               |
| `validateOn`    | `'submit' \| 'blur' \| 'change'`                | When a field validates. Default `'submit'`.                                         |
| `debounce`      | `number`                                        | Debounce for `'change'`. Default `200`.                                             |
| `enabled`       | `boolean`                                       | Explicit off-switch for a config that came from a defaults layer.                   |
