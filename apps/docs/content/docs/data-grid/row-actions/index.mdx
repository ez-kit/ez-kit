title: Row Actions
description: The per-row actions column that holds edit, delete, the row-pin menu and your own actions — inline buttons or a single overflow menu.
---

Edit, delete and row pinning all act on a single row, so they share one column at the right edge of
the grid. The column is injected automatically as soon as any of them is enabled — you never declare
it yourself.

Every option on this page is listed in the [API reference](/docs/data-grid/row-actions/api).

## Layout

`rowActions.placement` decides whether the built-in edit and delete spend the column's width on
buttons or collapse into one trigger. It is the only difference between the two grids below.

It governs the built-ins. The pin actions are always in a menu, and each of your own entries
carries [its own `placement`](#inline-entries).

### Inline

The default. Each action is its own icon button, side by side:

```tsx
<DataGrid
	data={data}
	columns={columns}
	editing={{ mode: 'modal', onSave }}
	deleting={{ onDelete }}
	pinning={{ row: { top: true, bottom: true } }}
/>
```

<DataGridDocsExample exampleId='row-actions-inline' />

The pin actions always live behind a menu — inline or not — because there are up to three of them
(`Pin Top`, `Pin Bottom`, `Unpin`) and only one applies at a time.

While a row is in **inline** edit mode, save and cancel are rendered as buttons regardless of the
placement: burying a pending commit inside a dropdown would hide it behind an extra click.

### Menu

Set `placement: 'menu'` and every action collapses into one overflow menu — the column narrows to a
single trigger, which is what a wide grid usually wants:

```tsx
<DataGrid
	data={data}
	columns={columns}
	editing={{ mode: 'modal', onSave }}
	deleting={{ onDelete }}
	pinning={{ row: { top: true, bottom: true } }}
	rowActions={{ placement: 'menu' }}
/>
```

## Custom actions

The built-in three are rarely the whole story — a row usually also wants a _Duplicate_, a _Send
invoice_, a _View history_. `rowActions.actions` is that slot, the per-row counterpart of
[`selection.bar.actions`](/docs/data-grid/selection/selection-bar#custom-actions) for bulk operations —
and the two take the **same** entry shape, so an action offered in both places is written once. It
is called per row, so a row's entries can depend on the row itself:

```tsx
<DataGrid
	data={data}
	columns={columns}
	editing={{ mode: 'modal', onSave }}
	deleting={{ onDelete }}
	rowActions={{
		actions: ({ row }) => [
			{
				id: 'duplicate',
				label: 'Duplicate',
				disabled: !row.original.active,
				onAction: () => duplicate(row.original),
			},
		],
	}}
/>
```

Return `[]` for a row that offers nothing extra.

<DataGridDocsExample exampleId='row-actions-custom' />

An entry lives in the **overflow menu** by default, whatever the column's placement is: with
`placement: 'menu'` there is only the one menu, and with `placement: 'inline'` your entries join the
menu that already carries the pin actions — so an inline grid with custom actions grows one trigger,
not one button per action. An entry that should be a button says so itself; see
[Inline entries](#inline-entries).

Every field an entry can carry is in the [entry shape table](/docs/data-grid/row-actions/api#entry-shape).
An entry's `icon` is your own element:

```tsx
rowActions: {
	actions: ({ row }) => [
		{ id: 'duplicate', label: 'Duplicate', icon: <Copy />, onAction: () => duplicate(row.original) },
		{ id: 'archive', label: 'Archive', icon: <Archive />, className: 'text-warning', onAction: () => archive(row.original) },
	],
}
```

The grid's own glyph names (`'edit'`, `'delete'`, `'pin-top'`, …) are deliberately not offered here.
That vocabulary is semantic — each kit maps a name to the icon it draws for _that grid affordance_ —
so lending `'delete'` to an application's _Archive_ hands it the glyph the kit means by the grid's
own Delete. An application action brings its own element, and a string is a **compile error**.

## Inline entries

An entry that should sit beside Edit and Delete as a button asks for it:

```tsx
rowActions={{
	column: { width: 172 },
	actions: ({ row }) => [
		{ id: 'duplicate', label: 'Duplicate', icon: <Copy />, placement: 'inline', onAction: () => duplicate(row.original) },
	],
}}
```

<DataGridDocsExample exampleId='row-actions-custom-inline' />

Three rules make this predictable:

- **`placement` on an entry defaults to `'menu'`** — always, including under a column with
  `placement: 'inline'`. Promotion is never implicit.
- **`icon` becomes required.** An icon button with no icon is a blank square, so this is a compile
  error rather than a runtime surprise.
- **The column's `width` becomes yours.** `actions` is a function of the row, so the grid cannot
  know how many buttons a row will render when it sizes the column — it budgets the built-ins and
  one overflow trigger, and nothing more. Set `rowActions.column.width`; in development the grid
  tells you the number it needs when a row overflows.

Under `placement: 'menu'` the column has no cell to put a button in, so an entry asking for one
there falls back to the menu and says so in development.

## Drawing an entry yourself

An entry may hand over its markup instead of describing itself: give it an `id` and a
`component`, and the kit contributes nothing around it — no glyph, no danger colour, no disabled
state, and the interaction is your component's own.

```tsx
rowActions: {
	actions: ({ row }) => [
		{ id: 'archive', label: 'Archive', icon: <Archive />, onAction: () => archive(row.original) },
		{ id: 'seats', component: <SeatStepper row={row.original} /> },
	],
}
```

<DataGridDocsExample exampleId='row-actions-component' />

Reach for the described form first: it is what makes an entry match the built-in Delete beside it
in every kit. This one is for the entry that shape cannot express — a split button, a picker, a
counter. Use the kit's own `Button` inside and it will still look native; what you render is on
you, including the widths — the menu sizes itself to its entries, so a control much wider than a
label makes the whole dropdown that wide.

The two hosts place it differently, because a menu is a collection and cannot hold loose nodes: in
the selection bar `component` **replaces** the entry's button, while in a row-actions menu it fills
a menu entry the kit still wraps, so keyboard navigation keeps working.

## The same action for the selection

`selection.bar.actions` takes the same entries, built from the selection instead of one row. Factor
the entry out and offer it in both — the kit renders it as a menu entry in the row and as a button
in the bar, with its own chrome either way:

```tsx
const exportAction = (rows: Row<Product>[]) => ({
	id: 'export',
	label: 'Export',
	onAction: () => exportRows(rows),
})

rowActions: { actions: ({ row }) => [exportAction([row])] },
selection: {
	bar: { actions: ({ selectedRows }) => [exportAction(selectedRows)] },
}
```

## Column width

The column sizes itself from the number of actions it renders, rather than falling back to the
150px default width TanStack gives a column with no `width`. Resize it like any other column when
`resizing` is enabled.

Supplying `rowActions.actions` reserves room for the overflow trigger, so an inline grid that had
none before widens by one button — and one that already showed the pin menu does not widen at all,
since the two share that trigger.

Entries promoted to inline buttons are **not** in that calculation — see
[Inline entries](#inline-entries) for why, and what to set instead.

Everything else about the column — its header, its own `width`, which edge it pins to — is
`rowActions.column`, documented under [The column itself](/docs/data-grid/row-actions/api#the-column-itself).
