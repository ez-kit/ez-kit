**Config states behaviour. JSX states composition.** An option answers "what does this grid do";
where a control goes and whether it is mounted is what the tree says. Eight options that answered
the second question with the first's vocabulary — `filtering.chips` / `.panel` / `.toolbar` /
`.variant`, `globalFiltering.toolbar`, `pagination.pageSizer`, `sorting.toolbar`,
`visibility.toolbar` — are gone, and this page is where their arrangements live now.

Every piece of a layout is a compound member you can place yourself, and each one degrades
gracefully: supply nothing and you get the built-in behaviour, supply something and you take over
exactly that piece.

## How the grid decides what to render

The body of a grid resolves in three steps:

```
children  ??  components.core.Layout  ??  <DataGrid.Table/>
```

- **`children`** win. A call site that wrote its own tree meant it.
- Otherwise a registered **`core.Layout`** renders.
- Otherwise the floor: a table and nothing else.

`core.Layout` is an _optional_ component slot — the tier beside the required ones, where
`core.TableWrapper` and `core.TableScroll` already live. A key belongs there only when the package
has a correct answer without it, and here that answer is the bare table. So
`@ez-kit/data-grid-react` ships no rich default at all: `<DataGrid data columns features />`
straight off the adapter renders a table.

**Each UI kit binds the rich default.** `@ez-kit/data-grid-shadcn` and `@ez-kit/data-grid-heroui`
register `DefaultLayout` as their `core.Layout`, so a `<DataGrid />` from a kit keeps rendering
toolbar, table and pagination with no children, exactly as before. A grid composed through
`createDataGrid` inherits nothing and pays for what it names.

Because it is the components registry rather than a prop, both forms come for free:

```tsx
// app-wide, or for one subtree
const components = { core: { Layout: InvoicesLayout } }

;<GridComponentsProvider components={components}>{children}</GridComponentsProvider>
```

```tsx
// one grid
<DataGrid
	features={features}
	data={data}
	columns={columns}
	components={components}
/>
```

<Callout type='info'>
	Define the object outside the render (or memoize it). The provider keys its merge on the object's identity, so a fresh
	literal every render re-renders every component that reads the registry.
</Callout>

A layout is an ordinary component reading the table from context, so it may be written inline as
`children` instead, which is what the examples on this site do:

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
>
	<BottomBarLayout />
</DataGrid>
```

Nested grids inherit `components`, and therefore inherit `Layout` with it — `components` describes
a subtree by design. There is no recursion risk: a layout renders `DataGrid.Table`, never
`DataGrid`.

## Layout presets

`@ez-kit/data-grid-react` exports four — `DefaultLayout`, `BottomBarLayout`,
`FilterPanelLayout`, `PopoverFiltersLayout` — as pure composition with no styling of
their own, so one set serves both kits. Each gates its controls on the feature being registered
and enabled, so a narrow grid renders a narrow toolbar rather than throwing.
[**Presets**](/docs/data-grid/layout/presets) has a live preview of each, on one grid, and which
to reach for.

All four render `<DataGrid.ActionBar />` **last**, which is where the default `floating` bar
belongs: it overlays the rows, and coming last in document order keeps it out of the tab order
until there is something to act on.

That is one bar with a section per concern — the current selection, and the pending draft. It
replaced a `SelectionBar` / `DraftBar` pair that each drew a whole bar and were kept apart by a
gate that did not re-run on a draft edit, so both could mount at the same sticky position.

Nothing places it for you; a layout renders it where it writes it, like every other member. The
consequence to know: `selection: { bar: 'inline' }` on one of these presets puts that in-flow strip
**below** the table, because the preset writes the bar last either way. An `inline` grid writes a
layout of its own with `<DataGrid.ActionBar />` first.

`FilterPanelLayout` is the arrangement that used to read:

```tsx
// before — five options describing an order the JSX shows at a glance
<DataGrid
	globalFiltering={{ toolbar: 'start' }}
	filtering={{ panel: 'toolbar', toolbar: true }}
	visibility={{ toolbar: true }}
	sorting={{ toolbar: true }}
	pagination={{ pageSizer: 'footer' }}
/>
```

```tsx
// after
<DataGrid
	features={features}
	data={data}
	columns={columns}
	globalFiltering
	filtering
	sorting
	visibility
>
	<FilterPanelLayout />
</DataGrid>
```

Note what that preset can do which no enum value could: the panel **adds** to the header's own
filter controls rather than replacing them, because the header cell still renders each column's
control. See [Where filters live](/docs/data-grid/filtering/variants#both-at-once).

## Writing a layout

A layout is a component that mounts compound members. Nothing more:

```tsx
function InvoicesLayout() {
	return (
		<>
			<DataGrid.Toolbar
				start={<DataGrid.GlobalFilterInput />}
				end={
					<>
						<DataGrid.ClearFiltersButton />
						<DataGrid.CreateTrigger />
						<DataGrid.SortMenuTrigger />
						<DataGrid.VisibilityTrigger />
					</>
				}
			/>
			<DataGrid.ActiveFiltersBar />
			<DataGrid.Table />
			<DataGrid.BottomBar />
			<DataGrid.ActionBar />
		</>
	)
}
```

Each control reads the table from context and renders nothing when it has nothing to show, so a
layout mounts them unconditionally — with one caveat worth knowing: a control whose **feature was
never registered** has no API to read and throws on render. Gate on the resolved bag
(`useDataGridTable().grid.sorting`) when one layout serves grids with different feature sets, which
is exactly what the shipped presets do.

## The full tree, written out

What `DefaultLayout` amounts to, for a grid with every feature on:

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
>
	<DataGrid.Toolbar
		start={<DataGrid.GlobalFilterInput />}
		end={
			<>
				<DataGrid.ClearFiltersButton />
				<DataGrid.CreateTrigger />
				<DataGrid.SortMenuTrigger />
				<DataGrid.VisibilityTrigger />
			</>
		}
	/>
	<DataGrid.Table />
	<DataGrid.Pagination />
	<DataGrid.ActionBar />
</DataGrid>
```

## Toolbar: a container and nothing else

`<DataGrid.Toolbar>` mounts no control of its own and reads no grid config. What goes in it is
what a layout writes. With nothing to show — no `children`, neither slot — it renders nothing
rather than an empty bar, so a layout can mount it unconditionally.

`start` and `end` are the two ends of the row. They are logical, not physical, so they swap sides
under RTL:

```tsx
<DataGrid.Toolbar
	start={<DataGrid.GlobalFilterInput />}
	end={<ExportButton />}
/>
```

`children` fills the bar as one run of controls instead of two groups, and is the answer to
**order** — each control is a compound member reading the table from context, so they come in the
order you write:

```tsx
<DataGrid.Toolbar>
	<span>Team members</span>
	<DataGrid.GlobalFilterInput />
	<DataGrid.ColumnFilter columnId='status' />
	<DataGrid.VisibilityTrigger />
	<DataGrid.CreateTrigger>Add new</DataGrid.CreateTrigger>
</DataGrid.Toolbar>
```

`className` classes the bar itself, with `children` or without. The kit **merges** it with its own
(`cn`, i.e. tailwind-merge), so a utility that collides with one of the kit's replaces it rather
than fighting it — which is what re-using the toolbar as a card's header bar needs, since both kits
give the bar an `mb-2` meant for a toolbar standing free above the table:

```tsx
<DataGrid.Toolbar className='mb-0 px-3 py-2.5'>{/* … */}</DataGrid.Toolbar>
```

## The bottom bar

`<DataGrid.BottomBar>` is the region below the table, the counterpart of the toolbar above it. It
is a container rather than a pagination control: what it holds is what it is given.

Given no children it is the page controls — the size selector and the pagination — which is what
`BottomBarLayout` mounts it for:

```tsx
<DataGrid.Table />
<DataGrid.BottomBar />
```

Given children it holds those instead, laid out as one row with two ends:

```tsx
<DataGrid.BottomBar>
	<span>{selectedCount} selected</span>
	<div style={{ display: 'flex', gap: '0.5rem' }}>
		<DataGrid.PageSizer />
		<DataGrid.Pagination />
	</div>
</DataGrid.BottomBar>
```

It takes `className` and `style`, both handed to the element as-is — a bar used as a card's own
footer usually wants the top margin off, since the kits keep one to separate a free-standing bar
from the table above it.

Not to be confused with `<DataGrid.Footer>`, which is the `<tfoot>` summary row built from each
column's `footer` — that one is part of the table, this one is part of the shell around it.

## Table: reorder, wrap, extend

`<DataGrid.Table />` renders `<DataGrid.Header />` and `<DataGrid.Body />` inside the kit's
`<table>`, wrapped in the scroll container that owns sticky headers, column pinning shadows and
virtualization. Supplying `children` replaces the header/body pair while keeping all of that
plumbing:

```tsx
<DataGrid.Table>
	<DataGrid.Header />
	<DataGrid.Body />
	<DataGrid.Footer />
</DataGrid.Table>
```

`<DataGrid.Footer />` is the footer row — the default layout mounts it for you, a custom body
does not. See [Column footers](#column-footers).

A render function gets the live table:

```tsx
<DataGrid.Table>
	{({ table, headerGroups, rows }) => (
		/* … */
	)}
</DataGrid.Table>
```

`<DataGrid.Header />` reads the grid's own `layout.stickyHeader` option, so it keeps working when placed
by hand.

## Body: compose the rows yourself

```tsx
<DataGrid.Body>
	{({ rows }) =>
		rows.map((row) => (
			<DataGrid.Row
				key={row.id}
				row={row}
			/>
		))
	}
</DataGrid.Body>
```

### Keep the built-in body and add to it

Returning `rows.map(...)` replaces the body's contents. When you only wanted to _add_ something,
take `content` instead — everything the built-in body would have rendered inside the `<tbody>`,
already composed:

```tsx
<DataGrid.Body>
	{({ content }) => (
		<>
			{content}
			<tr data-slot='tr'>
				<td colSpan={columns.length}>Σ {total}</td>
			</tr>
		</>
	)}
</DataGrid.Body>
```

`content` is the six parts below, in this order. Take them individually when you need to reorder
or drop one:

| Part               | What it is                                                           |
| ------------------ | -------------------------------------------------------------------- |
| `creatingRow`      | The draft row `creating` mounts above the data, or `null`.           |
| `pinnedTopRows`    | Rows pinned to the top, each with its expanded panel and pin offset. |
| `centerRows`       | The unpinned rows, each with its expanded panel.                     |
| `pinnedBottomRows` | Rows pinned to the bottom, measured like the top ones.               |
| `loadMoreFooter`   | The infinite-scroll sentinel or trigger.                             |
| `refetchOverlay`   | The overlay shown during a background refetch, or `null`.            |

Four branches are checked **before** your body, because each renders a `<tbody>` of its own rather
than something that goes inside one: the **virtualized** body, and the **loading**, **empty** and
**no-results** fallbacks. So a custom body does not replace the skeleton, and adding a summary row
does not cost you the empty state.

To own the body in one of those states, turn that state off where it is configured and read the
state inside `children`:

```tsx
<DataGrid
	fallbacks={{ loading: false }}
	…
>
	<DataGrid.Table>
		<DataGrid.Body>{({ content }) => (isPending ? <MySkeleton /> : content)}</DataGrid.Body>
	</DataGrid.Table>
</DataGrid>
```

<Callout type='warn'>
	Virtualization is the exception, and it has no opt-out: it renders and positions the rows itself, so it owns the
	body outright. `children` on a virtualized grid are **ignored**, with a development warning. Compose one level
	further down, at `<DataGrid.Row>`, or drop virtualization for that grid.
</Callout>

## Rows and cells: wrap the default instead of rebuilding it

`<DataGrid.Row>` and `<DataGrid.Cell>` hand back the same thing under the same name. A row's
`content` is its default cells; a cell's is whatever that cell would have rendered — its cell-type
view, the inline editor while it is open, or the selection checkbox and expand chevron on a system
column. Every lookup `cell.component`, `cell.type` and `editing.component` feed is already applied.

```tsx
<DataGrid.Row row={row}>
	{({ content }) => (
		<>
			<td data-slot='td'>
				<DragHandle />
			</td>
			{content}
		</>
	)}
</DataGrid.Row>
```

```tsx
<DataGrid.Cell
	cell={cell}
	row={row}
>
	{({ content, value }) => <Tooltip title={String(value)}>{content}</Tooltip>}
</DataGrid.Cell>
```

Both keep their shell either way — the row keeps its `data-*` attributes and `rowProps`, the cell
keeps its pinning offset, alignment and `cellClassName`.

<Callout type='info'>
	The two forms differ on one point. A cell whose `children` are a **static** node opts out of cell-editing — it has
	nowhere to put an editor, so it does not take one, and double-click does nothing. The render-function form stays in:
	its `content` **is** the editor while that cell is open, so it decides where the editor goes.
</Callout>

A column-wide change belongs on the column instead (`cell.component`), which also feeds the create
and edit forms; these slots are for one row or one cell in a hand-composed table.

### Typing the render arguments

Every compound child reads the table from context rather than from a prop, so it has nothing to
infer your row type from — `row.original` is `any` unless you say otherwise. Name the row type
once, as a type argument, and the whole render function is typed:

```tsx
<DataGrid.Body<Order>>{({ rows }) => rows.map((row) => <td>{row.original.total}</td>)}</DataGrid.Body>
```

The same argument is available on `Table`, `Header`, `HeaderRow`, `HeaderCell`, `Row`, `Cell`,
`Footer`, `FooterRow` and `FooterCell`, and on `useDataGridTable<Order>()` for a component of
your own.

## Header rows and cells: keep the chrome, change the markup

`<DataGrid.Header>` composes three slots below it. Reach for them when `column.header` is not
enough but you do not want to re-derive pinning, alignment, colSpan and the resize handle by hand.

`<DataGrid.HeaderRow>` gives you one header group's headers in column order, already reflecting
visibility and pinning:

```tsx
<DataGrid.Header>
	{({ headerGroups }) =>
		headerGroups.map((headerGroup) => (
			<DataGrid.HeaderRow
				key={headerGroup.id}
				headerGroup={headerGroup}
			/>
		))
	}
</DataGrid.Header>
```

`<DataGrid.HeaderCell>` hands you the assembled pieces of one `<th>` separately, so you can
rearrange them without rebuilding any of them — and, by leaving one out, drop it. Not rendering
`filter` is what takes a column's filter out of the header; rendering `filterPopover` instead puts
it behind an icon. Those two decisions replaced the `filtering.variant` enum — see
[Where filters live](/docs/data-grid/filtering/variants).

```tsx
<DataGrid.HeaderCell header={header}>
	{({ label, sortTrigger, menu, filter, sortDirection }) => (
		<div>
			<span>{sortTrigger}</span>
			{sortDirection !== 'none' && <PriorityBadge />}
			{menu}
			{filter}
		</div>
	)}
</DataGrid.HeaderCell>
```

| Render arg                 | What it is                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| `label`                    | The column's own `header` content, with no sorting behaviour attached.                           |
| `sortTrigger`              | `label` plus the sort indicator, in a `<button>` — or a plain box when the column does not sort. |
| `menu`                     | The column overflow menu (sort / pin / hide), or `null` when it has no sections.                 |
| `filter`                   | The column's filter control, or `null` when the column is not filterable.                        |
| `filterPopover`            | The same control behind the kit's popover trigger. Render this **or** `filter`.                  |
| `resizer`                  | The resize handle, or `null` when the column cannot be resized.                                  |
| `canSort`, `sortDirection` | The column's sort capability and current direction (`'asc' \| 'desc' \| 'none'`).                |
| `header`, `column`         | The underlying TanStack objects, for anything the above does not cover.                          |

`<DataGrid.Cell>` is the body-side equivalent: it keeps the `<td>`, its alignment, pinning
offsets and `cellClassName`, and lets you replace only what goes inside.

```tsx
<DataGrid.Row row={row}>
	{({ cells }) =>
		cells.map((cell) => (
			<DataGrid.Cell
				key={cell.id}
				cell={cell}
				row={row}
			>
				{({ value }) => <strong>{String(value)}</strong>}
			</DataGrid.Cell>
		))
	}
</DataGrid.Row>
```

## Fallbacks, modals and bars

The remaining slots take `children` for the same reason as everything above: replace the content,
keep the conditions under which it appears. A modal and a fallback row are mounted by their feature
rather than by a layout — neither has a position a layout could give it. `<DataGrid.ActionBar>` does:
a layout writes it where it wants it, and the four presets all write it last.

| Slot                                                   | Renders when                             | `children` receives                                             |
| ------------------------------------------------------ | ---------------------------------------- | --------------------------------------------------------------- |
| `<DataGrid.LoadingBody>`                               | `loading.isPending`                      | `{ columnCount }`                                               |
| `<DataGrid.EmptyStateRow>`                             | the data array is empty                  | `{ columnCount }`                                               |
| `<DataGrid.NoResultsRow>`                              | filters match nothing                    | `{ columnCount }`                                               |
| `<DataGrid.CreatingModal>` / `<DataGrid.EditingModal>` | `mode: 'modal'` and the form is open     | `{ open, form, title, formError, isPending, onSave, onCancel }` |
| `<DataGrid.ActionBar>`                                 | a row is selected, or the draft is dirty | `{ open, variant, selection, draft }`                           |
| `<DataGrid.PageSizer>`                                 | page-based pagination is on              | `{ pageSize, items, onPageSizeChange }`                         |

The three row-level fallbacks render their `children` **inside** the kit's
`<Tbody><Tr><Td colSpan>` scaffold, so the table markup stays valid and you supply only the
cell's content. The modals hand you `form` — the field set the columns already describe — so a
custom dialog does not have to rebuild the inputs:

```tsx
<DataGrid.EditingModal>
	{({ form, isPending, onSave, onCancel }) => (
		<MyDialog
			title='Edit order'
			onClose={onCancel}
		>
			{form}
			<button
				disabled={isPending}
				onClick={() => void onSave()}
			>
				Save
			</button>
		</MyDialog>
	)}
</DataGrid.EditingModal>
```

## Column headers

`column.header` takes a string or a render function, so a header can carry an icon, a tooltip or
a badge:

```tsx
createColumns<Row>([
	{
		accessorKey: 'total',
		header: () => (
			<span>
				Total <InfoIcon />
			</span>
		),
	},
])
```

**Keep that content non-interactive.** On a sortable column the header renders inside the sort
affordance, which is a `<button>` — so a button or a link placed there is a nested one: invalid
HTML, and the parser takes the header apart. An icon, a badge or a tooltip is fine.

A header that genuinely needs a control composes the cell and puts it beside the affordance
rather than inside it — `label` and `sortTrigger` are separate render args for exactly this:

```tsx
<DataGrid.HeaderCell header={header}>
	{({ sortTrigger }) => (
		<DataGrid.HeaderMain>
			{sortTrigger}
			<HelpButton />
		</DataGrid.HeaderMain>
	)}
</DataGrid.HeaderCell>
```

## Column footers

`column.footer` accepts the same shape as `column.header`, and a plain `<DataGrid />` renders it:
declaring it on any column mounts the footer row — see [Footer](/docs/data-grid/layout/footer) for `layout.footer` and
the sticky variant. This section is about the composed path, where `<DataGrid.Table>` children
replace the built-in pair and nothing is mounted for you.

`<DataGrid.Footer />` renders every column's `footer` in the same column order and with the same
colSpan, pinning and alignment as the header; `column.footerClassName` lands on the footer cell.
The archetypal case is a numeric column with a total. The render function gets the live table,
so summing over the _filtered_ rows keeps the total honest while a filter is on:

```tsx
const columns = createColumns<Row>([
	{ accessorKey: 'product', header: 'Product', footer: 'Total' },
	{
		accessorKey: 'amount',
		header: 'Amount',
		align: 'end',
		footerClassName: 'font-medium',
		footer: ({ table }) => table.getFilteredRowModel().rows.reduce((sum, row) => sum + row.original.amount, 0),
	},
])
```

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
>
	<DataGrid.Toolbar />
	<DataGrid.Table>
		<DataGrid.Header />
		<DataGrid.Body />
		<DataGrid.Footer />
	</DataGrid.Table>
	<DataGrid.Pagination />
</DataGrid>
```

Giving `<DataGrid.Footer>` `children` replaces the per-column row with your own markup inside
the kit's `<tfoot>` — a node, or a render function receiving `{ table, footerGroups }`:

```tsx
<DataGrid.Footer>
	{({ table }) => (
		<tr>
			<td colSpan={table.getVisibleLeafColumns().length}>{table.getRowModel().rows.length} rows</td>
		</tr>
	)}
</DataGrid.Footer>
```

`<DataGrid.FooterRow>` and `<DataGrid.FooterCell>` are the footer's counterparts to
`<DataGrid.HeaderRow>` and `<DataGrid.HeaderCell>`, for when only _one_ cell should differ. A
hand-written `<td>` would give up the `colSpan`, the pinning offset, the `align.footer` attribute
and the `footerClassName` that the default footer applies for you; these keep all of it:

```tsx
<DataGrid.Footer>
	{({ footerGroups }) =>
		footerGroups.map((group) => (
			<DataGrid.FooterRow
				key={group.id}
				footerGroup={group}
			>
				{({ headers }) =>
					headers.map((header) => (
						<DataGrid.FooterCell
							key={header.id}
							header={header}
						>
							{({ content }) => (header.column.id === 'amount' ? <strong>{content}</strong> : content)}
						</DataGrid.FooterCell>
					))
				}
			</DataGrid.FooterRow>
		))
	}
</DataGrid.Footer>
```

## Swapping a UI component for one grid

`components` on `<DataGrid>` merges over the kit's registry group by group, so an override
replaces one slot and leaves the rest of the kit intact:

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	components={{ sorting: { SortMenu: MySortMenu } }}
/>
```

<Callout type='info'>
	Define the object outside the render (or memoize it). The provider keys its merge on the object's identity, so a fresh
	literal every render re-renders every component that reads the registry.
</Callout>

For an app-wide swap, wrap a subtree in `GridComponentsProvider` instead — providers nest and
merge the same way.
