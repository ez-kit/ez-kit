---
title: Ordering
description: Let the user rearrange columns — from the header menu, or with `Alt+Arrow` on the focused header.
---

`ordering` lets the user decide where each column sits. It is grouped per axis, the way `pinning`
is: this page is `ordering.column`, and [`ordering.row`](/docs/data-grid/row-ordering) moves rows.

<DataGridDocsExample exampleId='column-ordering' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	ordering
/>
```

`ordering: true` means columns, and keeps meaning columns — the row axis turns on only by being
named, so this option cannot gain an affordance under you. `ordering={{ column: { onChange } }}`
also reports the new order, and [`{ row: true }`](/docs/data-grid/row-ordering) is the other
axis.

## What the user does

- **The header menu** grows a _Move left_ / _Move right_ pair. Both entries are always listed and
  disabled at the ends, so the menu never rearranges itself under the pointer.
- **`Alt+ArrowLeft` / `Alt+ArrowRight`** move the focused column one step, without reopening the
  menu each time. The menu closes on select in both kits, so this is the path for a column that
  has to travel several places. Not yet wired in the HeroUI kit — see the note below.
- **The Columns toggle**, once `visibilityMenu` asks for it — see below.
- **Dragging the header**, once a [drag adapter](/docs/data-grid/drag-and-drop/columns) is bound. That is the
  one affordance that moves a column several places in a single gesture; everything on this page
  moves it one step. With it, every header carries a grip and the menu drops its move pair.

A step swaps the column with its **visible** neighbour. Hidden columns keep their own places: a
column that is hidden and shown again comes back where it was, which is exactly why the order and
the visibility are two separate pieces of state rather than one list of visible columns.

## In the column panel

<DataGridDocsExample exampleId='column-panel-ordering' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	visibility
	ordering={{ column: { visibilityMenu: true } }}
/>
```

The toolbar's [Columns toggle](/docs/data-grid/columns/visibility) becomes a column panel: each row
carries the same two moves beside its visibility checkbox. It is opt-in, and off by default —
that control is a visibility control in every grid written so far, and a second job is not
something those grids asked for.

Turning it on changes the list as well as the row. The panel then lists **every** non-system
column rather than only the hideable ones, because a list that left some of them out could not be
read as the column order. A column locked with `visibility: false` is therefore listed, with its
checkbox disabled — it can never be hidden, and that is unchanged, but it does hold a place in the
order and it can still be moved.

A step lands on the row **next to it**, including hidden columns, because the panel shows the full order.

The panel's arrows point up and down. The two moves are logical — `start` and `end`, since the
column order flips under RTL — but this list runs from the start of the order at the top in either
writing direction, so up and down are what the arrows honestly point at. Their wording comes from
`messages.visibility.moveStart` / `moveEnd` (`Move up` / `Move down`).

### The arrows or the drag, not both

Rows of this panel can also be **dragged**, with nothing to compose, once a
[drag adapter](/docs/data-grid/drag-and-drop) is bound. It is the only surface where a hidden
column can be moved at all.

`visibilityMenu: true` then means **the drag and not the arrows**. The pair is a one-step
simplification of the same gesture — same axis, same state, same refusals — so a panel offering
both would offer the same move twice, and the drag is operable from the keyboard too
([pick-up, arrows, drop](/docs/data-grid/drag-and-drop/api#keyboard)), which is the one thing the pair
used to have to itself. With no adapter bound, `true` means the arrows, which is what every grid
written before drag existed already gets.

Name a mode to choose for yourself. The header takes the same values through
`ordering.column.header`:

```tsx
// Both, if a one-step control beside the grip is what the screen wants.
ordering={{ column: { visibilityMenu: 'both' } }}

// The arrows alone, in a grid whose rows and headers still drag.
ordering={{ column: { visibilityMenu: 'step' } }}
```

| Value             | With an adapter     | Without one |
| ----------------- | ------------------- | ----------- |
| `true`            | the grip            | the arrows  |
| `'drag'`          | the grip            | the arrows  |
| `'step'`          | the arrows          | the arrows  |
| `'both'`          | the grip and arrows | the arrows  |
| `false` / omitted | no panel            | no panel    |

The panel lists every column under any mode. A grip needs an adapter, so `'drag'` and `'both'` with
none bound fall back to the arrows, and the grid warns in development, naming the option.

A grid whose panel should offer something else entirely composes it:
`<DataGrid.VisibilityTrigger>` hands its render function the same `columns` the kits map — each item
carrying its `ordering` pair when the arrows are the chosen affordance — beside an `isColumnPanel`
flag, and `<DataGrid.VisibilityItem>` is the row the drag registers. Branch the panel's shape on the
flag and each control on the item: `col.ordering` for the arrows, `<ColumnDragHandle />`, which
self-hides, for the grip. The
options above exist because the kits' own panel is a list they map rather than markup you write; a
header you compose yourself places its grip the same way — see [A header you compose](/docs/data-grid/drag-and-drop/columns#a-header-you-compose).

## What cannot move

- **System columns** — selection, expansion and row actions have a fixed place in the layout.
- **`ordering: false` columns** — locked where they were declared. The menu offers them no move
  entries, and their neighbours cannot step over them either.
- **Across a pin band** — a move that crossed from the centre into the pinned edge would read as a
  pin, not a reorder. Pin the column instead.
- **Out of a header group** — a leaf dragged into a sibling group would split its parent's header
  cell in two, so moves stay between siblings.

## Reporting and restoring the order

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	ordering={{ column: { onChange: (columnOrder) => save(columnOrder) } }}
	initialState={{ columnOrder: restore() }}
/>
```

`onChange` receives the **complete** order as column ids, in visual order.

`columnOrder` is part of the persisted view state — see
[State persistence](/docs/data-grid/state/persistence), where it travels with `columnVisibility`
and `columnPinning` in the same deep link.

## HeroUI: keyboard shortcut not wired

The header menu works in both kits. `Alt+Arrow` works in the shadcn kit only: HeroUI's table is a
React Aria collection that builds the column header's own prop bag and spreads it after whatever it
was handed, so the handler the grid puts there is overwritten. Tracked in
[#223](https://github.com/ez-kit/ez-kit/issues/223); the menu path is unaffected.

## Options

| Option                           | Type                        | Description                                                                                                                                         |
| -------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ordering`                       | `boolean \| { column?: … }` | Reordering, per axis. `true` enables the column axis; `{ column: { onChange } }` reports the new order.                                             |
| `ordering.column.header`         | `boolean \| ReorderMode`    | How the header offers a move: `'drag'` a grip, `'step'` the menu pair, `'both'`, or `false` for neither. Default `true` — the grip with an adapter. |
| `ordering.column.visibilityMenu` | `boolean \| ReorderMode`    | Turn the Columns toggle into a column panel that lists every non-system column and offers that move affordance. Default `false`.                    |

## Migrating from `drag` / `moveControls`

The two flags on each surface are one option now, taking a `ReorderMode`
(`'drag' | 'step' | 'both'`). A combination that offered nothing is `false`.

| Before                                                   | After                                    |
| -------------------------------------------------------- | ---------------------------------------- |
| `ordering.column.drag: false`                            | `ordering.column.header: 'step'`         |
| `ordering.column.moveControls: true`                     | `ordering.column.header: 'both'`         |
| `ordering.column.drag: false, moveControls: false`       | `ordering.column.header: false`          |
| `ordering.column.visibilityMenu: { drag: false }`        | `ordering.column.visibilityMenu: 'step'` |
| `ordering.column.visibilityMenu: { moveControls: true }` | `ordering.column.visibilityMenu: 'both'` |
| `ordering.column.visibilityMenu: { drag: true }`         | `ordering.column.visibilityMenu: 'drag'` |
| `ordering.column.visibilityMenu: {}`                     | `ordering.column.visibilityMenu: true`   |

## Column options

| Option     | Type    | Description                                                                                |
| ---------- | ------- | ------------------------------------------------------------------------------------------ |
| `ordering` | `false` | Lock this column where it was declared. It cannot move, and its neighbours cannot pass it. |
