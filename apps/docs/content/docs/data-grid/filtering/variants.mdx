---
title: Where Filters Live
description: The filter control is one component; where it renders is the layout's decision — inline in the header, behind a header popover, collected into a panel, or a header and a panel at once.
---

A column's filter control does not change with where it sits: the same input, operator selector
and value list, chosen from the column's `cell.type` and its `filtering.operators`. What changes
is **where the JSX puts it**.

This used to be `filtering.variant`, a table-level enum with three values. It is gone, because it
decided two unrelated things at once — whether the header cell renders a filter, and what that
filter looks like — and could therefore never express the fourth arrangement on this page.

| Where the control lives             | How you say it                                                                     | Reach for it when                                                                         |
| ----------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| In the header cell, under the label | Nothing — the built-in header cell renders it. **The default.**                    | A few filterable columns, and filtering is the main thing the user does.                  |
| Behind a filter icon in the header  | The header cell renders `filterPopover` instead of `filter`.                       | Many columns, or controls too tall for a header — operator selectors, sliders, calendars. |
| Collected into one panel            | Mount `<DataGrid.FilterPanel />`; the header cell renders everything but `filter`. | The filter set is the interface: the user reads and edits several filters as one form.    |
| In the header **and** in a panel    | Mount the panel and keep rendering `filter`.                                       | A panel that summarises, with the header control still to hand.                           |

## In the header

The control sits in the header cell and is always visible, so an active filter is readable without
opening anything. It is also what costs header height — see
[Layout](/docs/data-grid/layout) if the header has to stay compact.

Nothing to write: this is what `<DataGrid.HeaderCell>` renders when it is given no children.

<DataGridDocsExample exampleId='base-filtering' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	filtering
/>
```

## Behind a header popover

A filter icon appears in each column header; clicking it opens the control in a popover. The icon
turns the primary colour while that column's filter is active, so the header still says _what_ is
filtered without saying what to.

`filterPopover` is the same control behind the kit's trigger. Render it **instead of** `filter`,
never both — they are one control in two presentations, and the pair would field one filter value
twice.

<DataGridDocsExample exampleId='filter-popover-basic' />

Writing out a table down to its header cell for one swap is four levels of JSX, so the package
ships that expansion as a preset. `PopoverFiltersLayout` is the default arrangement — toolbar,
table, pagination — with this one change:

```tsx
import { PopoverFiltersLayout } from '@ez-kit/data-grid-react'
;<DataGrid
	features={features}
	data={data}
	columns={columns}
	filtering
>
	<PopoverFiltersLayout />
</DataGrid>
```

Spelled out, the preset is:

```tsx
<DataGrid.Table>
	<DataGrid.Header>
		{({ headerGroups }) =>
			headerGroups.map((headerGroup) => (
				<DataGrid.HeaderRow
					key={headerGroup.id}
					headerGroup={headerGroup}
				>
					{({ headers }) =>
						headers.map((header) => (
							<DataGrid.HeaderCell
								key={header.id}
								header={header}
							>
								{({ sortTrigger, filterPopover, menu }) => (
									<DataGrid.HeaderMain>
										{sortTrigger}
										{filterPopover}
										{menu}
									</DataGrid.HeaderMain>
								)}
							</DataGrid.HeaderCell>
						))
					}
				</DataGrid.HeaderRow>
			))
		}
	</DataGrid.Header>
	<DataGrid.Body />
</DataGrid.Table>
```

This is the presentation to pair with richer comparisons: with `filtering: { operators }` on a
column the popover renders an operator selector above the input, which is where a `between` slider
or a date range gets the room it needs.

## In a panel

Every filterable column becomes a chip in one panel: `label: value`, or `Any` while empty. Clicking
a chip opens its control; the X clears it.

Two independent things make this arrangement, and separating them is the point of the change:

1. **Mount `<DataGrid.FilterPanel />`** — that is what puts the controls in a panel.
2. **Do not render `filter`** in the header cell — that is what takes them out of the headers,
   leaving them sortable and one line tall.

<DataGridDocsExample exampleId='filter-panel' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	filtering
>
	<DataGrid.FilterPanel />
	<DataGrid.Table>
		<DataGrid.Header>
			{({ headerGroups }) =>
				headerGroups.map((headerGroup) => (
					<DataGrid.HeaderRow
						key={headerGroup.id}
						headerGroup={headerGroup}
					>
						{({ headers }) =>
							headers.map((header) => (
								<DataGrid.HeaderCell
									key={header.id}
									header={header}
								>
									{({ sortTrigger, menu }) => (
										<DataGrid.HeaderMain>
											{sortTrigger}
											{menu}
										</DataGrid.HeaderMain>
									)}
								</DataGrid.HeaderCell>
							))
						}
					</DataGrid.HeaderRow>
				))
			}
		</DataGrid.Header>
		<DataGrid.Body />
	</DataGrid.Table>
</DataGrid>
```

### Where the panel goes

Wherever you write it. Above the table, under it, in a sidebar, or in the toolbar's leading slot
beside the search box — the faceted-toolbar arrangement:

```tsx
<DataGrid.Toolbar
	start={
		<>
			<DataGrid.GlobalFilterInput />
			<DataGrid.FilterPanel />
		</>
	}
/>
```

That whole arrangement — search leading, panel beside it, controls trailing, page sizer in the
bottom bar — is the `SearchFiltersActionsLayout` preset; see
[Composition](/docs/data-grid/layout/composition#layout-presets). The
[task board](/docs/data-grid/examples#task-board) is it in full.

The panel renders nothing when the grid has no filtered row model or no filterable column, so a
hand-placed panel is safe on a grid whose filtering a defaults layer switched off.

### One column at a time

`<DataGrid.ColumnFilter columnId='status' />` renders a single column's chip — same control, same
popover — wherever the layout wants it, so a grid can place two filters in its toolbar and leave
the rest out. Its children take a render function over the same per-column shape the panel hands
over (`label`, `valueDisplay`, `hasValue`, `input`, `onClear`).

It renders nothing for a column that is not filterable, so no guard is needed around it.

## Both at once

Mount the panel **and** keep rendering `filter`, and the grid has a filter control in both places.
This was inexpressible while one enum decided both questions — there was no value for it.

<DataGridDocsExample exampleId='filter-panel-and-header' />

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	filtering
>
	<DataGrid.FilterPanel />
	<DataGrid.Table />
</DataGrid>
```

Both write to the one `columnFilters` slice, so a column's two controls are two inputs bound to one
value: type in either and the other follows. That needed no coordination to build — it is what two
controls reading one state slice already do.
