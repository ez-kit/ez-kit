# Custom Cell Types

When the built-in cell types don't cover your needs, register your own. A custom cell type is an **id mapped to its renderers**; you write it once, then opt columns in with `cell: { type: '<id>' }`.

## Usage

This grid registers custom `rating` and `color` cell types via `extendDataGrid()` — click Edit on any row to try the custom inputs.

<DataGridDocsExample exampleId='custom-cell-types' />

A cell type is a `CellTypeDefinition` — up to four renderers, all optional:

```tsx
import type { CellTypeRegistry, CellViewProps, FieldState } from '@ez-kit/data-grid-react'

const TONE_MAP: Record<string, string> = { active: 'positive', cancelled: 'critical' }

const CELL_TYPES = {
	status: {
		view: ({ value }: CellViewProps) => <span data-tone={TONE_MAP[String(value)] ?? 'neutral'}>{String(value)}</span>,
		edit: ({ value, onChange }: FieldState) => (
			<input
				value={String(value ?? '')}
				onChange={(e) => {
					onChange(e.target.value)
				}}
			/>
		),
	},
} satisfies CellTypeRegistry
```

| Renderer   | Receives        | Used for                                                                       |
| ---------- | --------------- | ------------------------------------------------------------------------------ |
| `view`     | `CellViewProps` | Display mode.                                                                  |
| `edit`     | `FieldState`    | Editing input. **No fallback** — omit it and edit mode uses the default input. |
| `creating` | `FieldState`    | Create-row input. Falls back to `edit` when omitted.                           |
| `filter`   | `FieldState`    | Filter input. Falls back to `edit` when omitted.                               |

The fallbacks run one way only — `creating → edit` and `filter → edit`, never `edit → creating`. A definition with just `creating` leaves edit mode on the default input.

`CellTypeDefinition` also takes optional `operators` / `defaultOperator`, which seed the filter UI for columns of that type.

Register the whole map once for a grid module. `extendDataGrid` comes from your UI kit — `@ez-kit/data-grid-shadcn`, `-heroui`, or `-native` — not from the headless package:

```tsx
import { extendDataGrid } from '@ez-kit/data-grid-shadcn'

const grid = extendDataGrid(CELL_TYPES)

export const { DataGrid, useDataGrid, createColumns, createColumnHelper } = grid
```

…or per grid, with the `cellTypes` prop — registries nest, so this merges over the ones the kit already provides instead of replacing them:

```tsx
<DataGrid
	data={data}
	columns={createColumns<Order>([{ accessorKey: 'status', header: 'Status', cell: { type: 'status' } }])}
	cellTypes={CELL_TYPES}
/>
```

## Type-safety

The registry's **keys** are the source of truth. `extendDataGrid()` returns a bundle whose `createColumnHelper` is typed to those keys, so the builder gains a matching `createColumn.status({ … })` method and a typo in the method name is a TS error.

Hand-written `cell: { type: '…' }` is **not** id-checked — `CellType` keeps a `string & {}` tail so custom ids stay assignable. A typo there silently falls through to the raw, unstyled value instead of your renderer: no compile error, and no visibly broken cell to tip you off. One more reason to go through the helper.
