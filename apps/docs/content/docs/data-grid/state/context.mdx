title: Grid context
description: Carry application and kit values alongside a grid — the current user, a permission set, a tenant id — and read them from any component the grid renders.
---

A component the grid renders for you — a cell view, a custom toolbar control, a row-action menu —
sometimes needs to know something the grid has no opinion about. Whether the current user may edit.
Which tenant the page belongs to. What density the kit was told to use.

`context` is where that goes. You put an object on the grid; every component inside it reads the
object back. The grid never looks at what is in there.

The signed-in user goes into `context`, and three cells read it. _Name_ marks the user's own row.
_Salary_ is visible to an admin, and to a manager for their own department only. _Edit_ is enabled
for an admin. Switch the user and only those cells re-render; the department column, which reads
nothing from the context, does not.

```tsx
const table = useDataGrid({
	features,
	data: users,
	columns,
	context: { permissions },
})
```

```tsx
import { useGridContext } from '@ez-kit/data-grid-react'

function DeleteAction() {
	const canDelete = useGridContext((context) => context.permissions.canDelete)
	if (!canDelete) return null
	return <button type='button'>Delete</button>
}
```

## Type it once

`GridContext` ships **empty**. Declare its members once, anywhere in your app, and every call site
and every reader is typed from that declaration — there is no generic to thread through:

```ts
declare module '@ez-kit/data-grid-react' {
	interface GridContext {
		currentUser: { id: string; role: 'admin' | 'viewer' }
		permissions: { canEdit: boolean; canDelete: boolean }
	}
}
```

Until something extends it, `context` accepts `{}` and `useGridContext()` returns `{}`.

## Reading it

`useGridContext` reads the whole object or a slice of it, and which one you read decides what
re-renders.

| Form                                                           | Returns          | Re-renders when                 |
| -------------------------------------------------------------- | ---------------- | ------------------------------- |
| `useGridContext()`                                             | the whole object | any part of the context changes |
| `useGridContext((c) => c.some.value)`                          | that value       | **that value** changes          |
| `useGridContext((c) => ({ ...c.some }), { compare: shallow })` | a new object     | one of **its fields** changes   |

Prefer the selector form in anything the grid renders per row or per cell — a permission flag read
that way re-renders one cell when the flag flips, and stays quiet for every other change.

A selection is compared with strict equality, so field access and primitive computations need
nothing more. A selector that builds a new object or array (`(c) => ({ ...c.permissions })`) works
too, but a new object is never strictly equal to the last one, so on its own it re-renders on every
context change. Pass `compare: shallow` and it re-renders only when one of the object's fields does:

```tsx
import { shallow, useGridContext } from '@ez-kit/data-grid-react'

const { canEdit, canDelete } = useGridContext((context) => ({ ...context.permissions }), { compare: shallow })
```

This is the same contract as [`useDataGridState`](/docs/data-grid/state/controlled), which takes
the same `compare` option.

Like every other context-bound hook, `useGridContext` throws outside `<DataGrid>`.

## Values that change often

Every value in `context` lives in the host's state or props, so changing one re-renders the
component that renders `<DataGrid>` — and then the readers that select it. For a permission that
flips once a session that is nothing. For a value that changes many times a second — a live
selection elsewhere on the page, a hovered id, a ticker — pass a **store** instead of the value.

A store is an object whose identity never changes, so the grid's context never changes either.
Only the cells that subscribe to the store re-render when it does; the host does not re-render at
all.

```tsx
import { createStore } from '@tanstack/react-store'

import type { Store } from '@tanstack/react-store'

declare module '@ez-kit/data-grid-react' {
	interface GridContext {
		highlight: Store<{ id: string | null }>
	}
}

const highlight = createStore({ id: null as string | null })

const table = useDataGrid({ features, data, columns, context: { highlight } })

// anywhere — an event handler, a socket callback — with no React state involved
highlight.setState(() => ({ id: 'order_42' }))
```

The cell reads the store through the store library's own hook:

```tsx
import { useGridContext } from '@ez-kit/data-grid-react'
import { useSelector } from '@tanstack/react-store'

import type { CellViewCtx } from '@ez-kit/data-grid-react'

function OrderCell({ row, value }: CellViewCtx<Order, string>) {
	const highlight = useGridContext((context) => context.highlight)
	const isHighlighted = useSelector(highlight, (state) => state.id === row.id)
	return <span data-highlighted={isHighlighted}>{value}</span>
}

const columns = createColumns<Order>([{ accessorKey: 'id', cell: { component: OrderCell } }])
```

The grid does not care which library the store comes from. A Zustand store, a Valtio proxy or a
TanStack store all work the same way: put the store in `context`, read it with that library's hook.
In the example below each cell shows how many times it has rendered. **Allow editing** passes a
value through `context`; **Highlight next order** writes a store held in `context`, and only the two
cells whose highlight changed re-render. [Rendering](/docs/data-grid/state/rendering) explains the
arrangement in full.

## It merges like every other option

`context` travels the [three option layers](/docs/data-grid/state/defaults) unchanged — kit factory
under provider under instance, deep-merged, nearest to the grid wins:

```tsx
// in the kit
createDataGrid({ components, defaults: { context: { shadcn: { density: 'comfortable' } } } })

// in the app, over a subtree
<DataGridOptionsProvider defaults={{ context: { currentUser } }}>

// on one grid
useDataGrid({ features, data, columns, context: { permissions } })
```

That grid sees all three. Naming a key **replaces** it rather than adding to it: `permissions` at
the call site means those permissions, not a union with a provider's.

## Who owns which key

The interface is one namespace shared by your application and the UI kit you render through, and
nothing in the types keeps them apart. The convention is that **a kit writes only under its own
key** — `context.shadcn`, `context.heroui` — and leaves everything else to the application. Follow
it and a kit shipping a new setting cannot collide with a name you already use.

## When not to use it

`context` is not table state. It is never serialized, never part of `onStateChange`, and never
restored from a URL — a value that belongs in a deep link belongs in
[state](/docs/data-grid/state/persistence) instead.

It is also not a replacement for props. A value one component needs, and whose parent can hand it
over directly, should be a prop. `context` earns its place when the reader is a component the
**grid** renders, where there is no parent of yours in between.

## Options

| Option    | Type          | Default | Description                                                                          |
| --------- | ------------- | ------- | ------------------------------------------------------------------------------------ |
| `context` | `GridContext` | `{}`    | Application and kit values carried alongside the grid, read with `useGridContext()`. |
