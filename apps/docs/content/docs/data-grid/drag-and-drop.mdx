---
title: Drag and drop
description: Drag a row, a column header, or a row of the column panel — a fourth affordance over the same ordering state.
---

The grid already reorders rows and columns three ways: the [column menu](/docs/data-grid/columns/ordering),
the [row action menu](/docs/data-grid/row-ordering), and `Alt+Arrow` on either. All three move **one
step at a time**, which nobody uses to move a column six places. Drag is the fourth, over the same
`rowOrder` and `columnOrder` state, committing through the same rules.

It is **opt-in and composed** — there is no `<DataGrid dnd>` prop and neither kit's prebuilt grid
carries it, so a grid that does not name it pays nothing.

## Switching it on

### shadcn

The adapter is a [registry item of its own](/docs/data-grid/installation/shadcn), so the plain
`npx shadcn add …/r/data-grid.json` no longer brings it — or `@dnd-kit` with it. Add the drag item
instead, which copies `components/data-grid/dnd.tsx`, installs `@dnd-kit/react` and `@dnd-kit/dom`,
and — because it names the grid item as a registry dependency — installs the grid in the same run:

```bash
npx shadcn@latest add https://ez-kit-docs.vercel.app/r/data-grid-dnd.json
```

If you already have the grid from the plain command, this is still the command to run: it copies
the one file it owns and leaves the rest alone.

```tsx title="src/lib/data-grid.tsx"
import { allDataGridFeatures } from '@ez-kit/data-grid-core/features/all'
import { createDataGrid } from '@ez-kit/data-grid-react'

import { allComponents, cellTypes } from '@/components/data-grid/data-grid'
import { adapter } from '@/components/data-grid/dnd'

export const { DataGrid } = createDataGrid({
	components: allComponents,
	cellTypes,
	features: allDataGridFeatures,
	dnd: adapter,
})
```

If you change your mind, delete `dnd.tsx` and drop `@dnd-kit/react` and `@dnd-kit/dom` by hand —
nothing else in the block references any of them. By hand is the only way: `shadcn add` has no
uninstall, and a registry item carries one dependency list with no way to mark part of it optional.
That is exactly why drag is a separate item rather than a flag on the main one — so that choosing
not to drag is a choice you make before anything is installed. Unused, the adapter costs no bundle
bytes either way.

### HeroUI

`@dnd-kit/react` is an **optional peer** — install it only if you want drag:

```bash
pnpm add @dnd-kit/react
```

```tsx title="src/lib/data-grid.tsx"
import { allDataGridFeatures } from '@ez-kit/data-grid-core/features/all'
import { allComponents, cellTypes } from '@ez-kit/data-grid-heroui'
import { adapter } from '@ez-kit/data-grid-heroui/dnd'
import { createDataGrid } from '@ez-kit/data-grid-react'

export const { DataGrid } = createDataGrid({
	components: allComponents,
	cellTypes,
	features: allDataGridFeatures,
	dnd: adapter,
})
```

The peer range is pinned to `0.1.x` on purpose: the adapter reads shapes of that library which a
minor release before its own 1.0 is free to rename, and a version mismatch would otherwise fail
silently rather than at install.

### Then, either way

Turn the axis on as you always would. The two handles you place need no option of their own — a
row drags iff you rendered a row handle, a header drags iff you rendered a header one:

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	ordering={{ row: true, column: { visibilityMenu: true } }}
/>
```

The column panel is the exception, because its rows are a list the kit maps rather than markup you
write — so which affordance it carries is the one thing drag does put in the config. See
[The column panel](#the-column-panel).

## Rows

<DataGridDocsExample exampleId='row-drag' />

A row is dragged by a handle you place, in a column of its own:

```tsx
const columns = createColumns<Employee>([
	{ id: 'drag', header: '', width: 48, align: 'center', cell: { component: () => <RowDragHandle /> } },
	// …
])
```

`RowDragHandle` from your kit wears the kit's grip; `<DataGrid.RowDragHandle />` is the same control
with no glyph, for a call site that supplies its own content. It needs no arguments — it finds the
row it is in.

**Set `getRowId`.** The order is recorded as row ids, and without one a row falls back to its index,
which changes the moment it moves. The same requirement [row ordering](/docs/data-grid/row-ordering#getrowid-is-not-optional-here)
has, for the same reason.

### In a virtualized body

<DataGridDocsExample exampleId='virtualized-row-drag' />

A [virtualized](/docs/data-grid/virtualization) body needs no drag option of its own: the handle
column and the bound adapter are the ones from [Rows](#rows) above, and `virtualization` is the only
addition.

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns} // the same drag-handle column
	getRowId={(row) => String(row.id)}
	virtualization={{ row: { estimateSize: 49, overscan: 10 } }}
	ordering={{ row: true }}
/>
```

Four things make that work, and all of them are about the body rendering a **window** rather than the
whole list:

- **A row's drag index counts within the window, not within the row model.** The body declares the
  rows it renders and each row takes its index from that declaration, so the positions a drag sees
  run from zero with no gap — which is what the library behind the adapter requires, and what a row
  reporting its place in the whole model could never satisfy once the window had scrolled.
- **The row you are holding stays mounted when the window scrolls past it.** The body builds its list
  as the window _plus_ the held row, so the row keeps its registration — and therefore its place in
  that dense space — for as long as you hold it. Let it unmount and the gesture breaks without
  looking broken.
- **The window's rows are in normal flow, and the window is offset by the body's own band.** The body
  pads the space above and below the rows it renders rather than placing each row with a `transform`.
  That is what lets the drag library move a dragged row's neighbours aside: it reorders the rows and
  animates the layout change that follows, and out of flow there is no layout change to animate. The
  one row placed out of flow is the held row of the bullet above, once the window has scrolled past
  it, so that it does not displace a band it is no longer part of.
- **While you hold a row, the body renders the arrangement the drag is showing, not the saved
  order.** The body re-renders on every frame of a drag's auto-scroll, and the held row is
  wherever the pointer has carried it — so the body draws the saved order with that one row moved
  to its new place, and the drag and the body agree about where every row is however many times
  the window turns over. Nothing is saved until you release: the order you pass in, and
  `onOrderChange`, do not move mid-gesture, and `Escape` puts everything back.

The virtualizer is keyed by row id, so a row keeps its identity, its measured height and its element
across a commit: the order is rewritten underneath it, and nothing hands one row's measurement to
whichever row takes its slot.

So a virtualized body displaces a dragged row's neighbours exactly as a non-virtualized one does, and
a drag of one place commits wherever you release it.

## Column headers

<DataGridDocsExample exampleId='column-drag' />

The header cell's render function hands you a `dragHandle` beside the parts you already know:

```tsx
<DataGrid.HeaderCell header={header}>
	{({ dragHandle, sortTrigger, menu }) => (
		<DataGrid.HeaderMain>
			{dragHandle}
			{sortTrigger}
			{menu}
		</DataGrid.HeaderMain>
	)}
</DataGrid.HeaderCell>
```

Or place your kit's `<ColumnDragHandle />` inside the cell's body, which is what the example above
does — same handle, same sortable, one reads the context the other publishes.

**Not inside `column.header`.** That content renders within the sort trigger's `<button>`, and a
button inside a button is invalid HTML. Compose `<DataGrid.HeaderCell>` and put the handle outside
`sortTrigger`, exactly as the sort-trigger docs already ask.

The resizer is untouched: a drag starts from the handle element and nothing else, so the two
gestures on one header cell cannot be confused for each other.

## The column panel

<DataGridDocsExample exampleId='column-panel-drag' />

Under [`ordering.column.visibilityMenu`](/docs/data-grid/columns/ordering#in-the-column-panel) the
Columns toggle becomes a column panel, and its rows are draggable with nothing to compose:

```tsx
<DataGrid.Toolbar end={<DataGrid.VisibilityTrigger />} />
```

The panel is the **same axis** as the header — one `columnOrder` — and differs in one way that
matters: it lists the hidden columns, so a hidden column can be dragged there and has no header cell
to drag at all. In the example `joinedAt` starts hidden; move it in the panel and the visible order
rearranges around it.

**This is the one surface whose affordance is a config question, and the arrows step aside for the
drag.** A row handle and a header handle are there iff a call site wrote them, so for those two
surfaces the JSX already is the switch; a kit's panel maps its rows, so nobody writes that markup.
With an adapter bound, `visibilityMenu: true` therefore means the grip and not the
[one-step pair](/docs/data-grid/columns/ordering#in-the-column-panel) — the pair moves a column by
the same rules and the drag is keyboard-operable too, so offering both is the same move twice.
`{ moveControls: true }` asks for both and `{ drag: false }` keeps the pair alone, in a grid whose
rows and headers still drag.

A kit rendering its own panel composes the row from `<DataGrid.VisibilityItem>`. One obligation
comes with that: render one item per column the panel lists, all of them. Filtering the list — a
search box over a long panel — leaves a gap in the drag's index space, and a gap stops panel
dragging with no error. Filter what a row renders, not which rows exist.

## The three surfaces

| Surface       | Handle                                                      | Writes        | Scope                                                     |
| ------------- | ----------------------------------------------------------- | ------------- | --------------------------------------------------------- |
| Row           | `<RowDragHandle />` in a column's `cell.component`          | `rowOrder`    | The rows the body renders, pinned bands included          |
| Column header | `dragHandle` from `<DataGrid.HeaderCell>`, or the component | `columnOrder` | The **visible** leaf columns, in the order they are drawn |
| Column panel  | the component, inside `<DataGrid.VisibilityItem>`           | `columnOrder` | **Every** listed leaf column, hidden ones included        |

## Starting a drag

Both input paths start from the same element — the handle, and nothing else. That is the drag
library's own rule rather than ours: it compares the event's target to the handle before it activates
anything, which is what structurally keeps a pick-up away from the sort trigger beside it and from the
selection checkbox in the row.

### Pointer

A mouse drag begins once the pointer has **moved a little** from the handle, so a plain click on a
handle is a click and not a one-pixel reorder. A finger drag begins on a **press and hold**, and a
finger that strays before the hold is up is left to the scroller rather than taken for a drag. Any
other pointer — a pen — takes the hold or the movement, whichever comes first.

Every one of those thresholds is the drag library's own value, named in each kit's `dnd.tsx` so the
feel of the gesture no longer depends on a default a minor release is free to move.

### Keyboard

<DataGridDocsExample exampleId='keyboard-sensors' />

A drag handle is focusable, and a drag is operable from the keyboard alone — `Tab` to a grip in the
example above and try it:

| Key                 | While focused on a handle | Mid-drag                                              |
| ------------------- | ------------------------- | ----------------------------------------------------- |
| `Space` or `Enter`  | Picks the item up         | Drops it where it is                                  |
| `ArrowUp` / `Down`  | —                         | Moves a row                                           |
| `ArrowLeft`/`Right` | —                         | Moves a column                                        |
| `Escape`            | —                         | Cancels; nothing is written                           |
| `Tab`               | Moves focus as usual      | Ends the drag and **commits** at the position reached |

`Tab` committing rather than cancelling is the drag library's documented behaviour, and we did not
override it: a drag that ended because focus moved on has already shown the reader where the item
would land, and throwing that away silently is the worse of the two. `Escape` is the deliberate way
to abandon one.

The item being held reports the same state a pointer drag does — `data-row-dragging` on a row — so a
kit's stylesheet needs nothing keyboard-specific.

`Alt+Arrow` on a row or a header still moves it one step, as it always did, and the two do not
compound: while an item is being dragged with the keyboard, the arrows move it through the drag only.
Another row's `Alt+Arrow` is unaffected meanwhile.

Two differences here belong to HeroUI and both are React Aria's, listed in
[Kit parity](/docs/data-grid/kit-parity): `Alt+Arrow` row reordering does not reach that kit at all,
and on `Tab` mid-drag the shadcn kit keeps focus on the handle while HeroUI's focus leaves the table.

## Announcements

A keyboard drag is narrated. Focusing a handle reads its name and how to drive it from the keyboard —
and, in the shadcn kit, what the gesture is. The pick-up, the drop and a cancellation each reach a
polite live region as they happen, and so does the arrows' progress, so the gesture is followable
without seeing the rows move.

**Movement is announced as the position you settle on, not as every position you pass through.** The
drag library coalesces its move announcements: every arrow press records the sentence for where the
item now sits, and the region is written once the keys have been quiet for a moment. Tap `ArrowDown`
four times in quick succession and a screen reader reads the fourth position rather than all four.
That is the right output, not a shortfall — a region that spoke each intermediate step of a fast key
repeat would be a stream nobody can follow, every sentence cut off by the next, and the position a
user arrives at is the one they are deciding about. The pick-up, the drop and the cancellation are not
coalesced; each of those is said as it happens.

The sentences name things a user can act on rather than internals. A **column** is called by its
header text — or by its column id when the header is a React element, since flattening arbitrary JSX
to a string means rendering it out of tree, and a worse name is better than an invented one. A **row**
has no name, so it is given its place: both axes count **from one**, among the items the surface
actually lists, because the number is read aloud.

Every string is in the [message catalogue](/docs/data-grid/localization)'s `ordering` group and is
overridden like any other, per key:

```ts
const ru: PartialGridMessages = {
	ordering: {
		draggable: 'перетаскиваемый',
		instructions: 'Нажмите пробел, чтобы взять элемент…',
		rowPickedUp: ({ position, total }) => `Взята строка ${position} из ${total}.`,
		columnMovedTo: ({ name, position, total }) => `${name}: позиция ${position} из ${total}.`,
	},
}
```

Each key is a **whole sentence** taking named values, never a stem the grid completes: word order
differs between languages, and the row and column forms are separate keys for the same reason. The
keys are `draggable` and `instructions` for the handle itself, then `rowPickedUp` / `rowMovedTo` /
`rowDropped` / `rowCancelled` and their four `column*` counterparts.

Three things are deliberately true of this:

- **A pointer drag is not announced.** Whoever is moving a row with a mouse can see it move, and
  narrating every `dragover` of a pointer would talk over the gesture being made.
- **This is not the grid's own live region.** [`grid.rowCount`](/docs/data-grid/localization) reports
  how many rows a query matches and remains the one thing the grid announces about its contents; the
  drag's region is a sibling of it, created per grid, so several grids on one page never announce each
  other's drags.
- **The handle's `aria-roledescription` reaches shadcn and not HeroUI** — React Aria's attribute
  allow-list, not the kit's adapter, so there a screen reader says the drag library's English
  `draggable` rather than yours. In [Kit parity](/docs/data-grid/kit-parity), with the rest.

## What a drag will not do

The same boundaries the one-step affordances honour — drag adds none and removes none:

- **Cross a pin band.** A move from the centre into a pinned edge would read as a pin, not a reorder.
- **Leave a header group.** A leaf moves among its siblings.
- **Leave its own subtree**, with [tree data](/docs/data-grid/expanding/tree).
- **Move a locked item.** A system column, a column declared `ordering: false`, a synthetic group
  row: these render no handle at all, rather than one that does nothing.
- **Move anything while a sort or a grouping is applied**, on the row axis — both compute the order
  from the data, so a manual arrangement would be recomputed away.

**An illegal drop does not snap back.** The refused step simply never happens: the item travels as
far as its own group or band allows and commits there, which is also what was on screen the whole
time. Release outside the grid, or press `Escape`, and nothing is written.

One completed drag produces one change — the neighbours part by transform while you drag and no
state is touched until you let go.

## RTL

<DataGridDocsExample exampleId='column-drag-rtl' />

The column axis is logical, so under `dir="rtl"` the later a column sits in the order, the further
left it is drawn — and dragging leftwards moves a column later. Pass `direction='rtl'` to the grid
beside the `dir` on an ancestor, the same pair [column pinning](/docs/data-grid/pinning/columns) needs.

## Not built yet

Stated rather than left to be discovered:

- **The announcements have not been through a screen reader.** What is verified is that the right
  sentence reaches a correctly shaped live region at the right moment, in both kits, which is a
  different claim from "it reads well through NVDA or VoiceOver" — that one is untested. See
  [Announcements](#announcements) for what is said and the one attribute HeroUI drops.
- **Two HeroUI-specific limits**, both in [Kit parity](/docs/data-grid/kit-parity): a header column
  cannot be dragged while the column panel is open, and `Escape` during a panel drag can leave the
  order changed without reporting it.
