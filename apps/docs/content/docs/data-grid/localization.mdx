title: Localization
description: Every string the grid renders comes from one dictionary. Replace any subset of it with `messages` — per grid, or app-wide.
---

The grid holds no text of its own. Every user-facing string — visible labels, `placeholder`s and
`aria-label`s alike — lives in a single dictionary, `GridMessages`, whose English default is
`defaultMessages`. `messages` replaces any part of it.

That includes the accessible names. A grid whose buttons you translated but whose `aria-label`s
stayed English is not localized; it just hides the English where only a screen reader finds it.

## One string

```tsx
<DataGrid
	features={features}
	data={data}
	columns={columns}
	messages={{ pagination: { rowsPerPage: 'Строк на странице' } }}
/>
```

Overrides merge **per entry**, so naming one string keeps the rest of its group: the six other
`pagination` entries stay English until you say otherwise.

## App-wide

Set it once on `DataGridOptionsProvider` and every grid below it inherits the dictionary. A single
grid can still override one string of it — the provider, factory defaults and the instance are the
same three option layers everything else uses.

The package ships two complete dictionaries, English and Russian, one subpath each:

```tsx
import { ruMessages } from '@ez-kit/data-grid-core/messages/ru'
import { DataGridOptionsProvider } from '@ez-kit/data-grid-react'

export function Providers({ children }: { children: ReactNode }) {
	return <DataGridOptionsProvider defaults={{ messages: ruMessages }}>{children}</DataGridOptionsProvider>
}
```

`enMessages` (`@ez-kit/data-grid-core/messages/en`) is the default dictionary under the same kind
of name, so switching language reads `lang === 'ru' ? ruMessages : enMessages`. A dictionary you
do not import costs nothing.

For any other language, write your own — the whole dictionary or any part of it:

```ts
// grid-messages.de.ts
import type { PartialGridMessages } from '@ez-kit/data-grid-react'

export const de: PartialGridMessages = {
	selection: { selectRow: 'Zeile auswählen', selectAll: 'Alle Zeilen auswählen', clear: 'Auswahl aufheben' },
	pagination: { rowsPerPage: 'Zeilen pro Seite', page: 'Seite', of: 'von' },
	fallbacks: { empty: 'Keine Daten', noResults: 'Keine Treffer' },
}
```

`PartialGridMessages` types any subset, group by group, so a typo in a key is a compile error
rather than a string that silently stays English. A record inside a group — `filtering.presets`,
`operators.common` — merges entry by entry as well, so `presets: { today: 'Heute' }` keeps the
other presets.

## Strings that depend on the render

Entries whose text varies take a **typed context object** and return a string. They are ordinary
functions, which is the whole surface an `Intl.PluralRules` call or an ICU message needs:

```ts
const ru: PartialGridMessages = {
	filtering: { placeholder: ({ columnId }) => `Фильтр по ${columnId}` },
	selection: { count: ({ count }) => `Выбрано: ${count}` },
	draft: {
		sorts: ({ count }) => `${count} ${plural(count, ['сортировка', 'сортировки', 'сортировок'])}`,
	},
}
```

The grid ships no plural rules of its own — the English default writes `1 sort` / `2 sorts` and
stops there, because pluralization is the language's business, not the grid's.

`draft.summary` is the same idea one level up: it is handed the segments the entries above
produced, and joins them into the action bar's accessible name. The separators are in the
dictionary for the same reason the plurals are — a locale that does not list with `, ` has
nowhere else to say so.

```ts
const ru: PartialGridMessages = {
	draft: { summary: ({ label, parts }) => `${label}: ${parts.join('; ')}` },
}
```

## Filter operators

The ready-made operators are labelled from the dictionary, under `operators`. `common` names every
operator by its id; `date` and `boolean` hold only the wordings that differ from it — the date
set's `greaterThan` reads "After" where the number set's reads "Greater than", and the boolean set's
`equals` reads "Is":

```ts
const de: PartialGridMessages = {
	operators: {
		common: { contains: 'Enthält', equals: 'Gleich', greaterThan: 'Größer als' /* … */ },
		date: { greaterThan: 'Nach', lessThan: 'Vor' /* … */ },
	},
}
```

The group belongs to the definition, not to the column: a cell type of your own built from
`defaultOperators.byType.date` reads "After" too. An operator you wrote yourself is labelled by its
own `label`, which always wins over the dictionary — see
[Filter operators](/docs/data-grid/filtering/operators#labels).

The date presets are the dictionary's as well, under `filtering.presets`, and the preset menu's own
name is `filtering.presetMenu`:

```ts
const de: PartialGridMessages = {
	filtering: {
		presetMenu: 'Schnellauswahl',
		presets: { today: 'Heute', yesterday: 'Gestern', last7: 'Letzte 7 Tage' },
	},
}
```

## Reading the dictionary yourself

A custom cell renderer, toolbar control or kit component reads the resolved dictionary with
`useGridMessages()` — complete by construction, so no call site needs a fallback:

```tsx
import { useGridMessages } from '@ez-kit/data-grid-react'

function MyPageSizerLabel() {
	const messages = useGridMessages()
	return <span>{messages.pagination.rowsPerPage}</span>
}
```

Outside a `<DataGrid>` it returns `defaultMessages` rather than throwing, so a component of yours
still renders in a story or a test.

## Strings nobody sees

Some keys are never rendered visibly, and translating them is the whole point of their existing:

- `grid.label` names the table element.
- `grid.rowCount` is the grid's **live region** — the sentence a screen reader hears when a filter
  or a search term changes how many rows match. It is announced, never shown.
- `selection.columnHeader`, `expanding.columnHeader` and `rowActions.columnHeader` name the three
  system columns, whose `<th>` holds a control or nothing at all.
- The whole `ordering` group beyond `dragRow` / `dragColumn` is a
  [drag](/docs/data-grid/drag-and-drop/api#announcements) nobody can see being made: `draggable` is what a
  handle is called in place of its role, `instructions` is how to drive one from the keyboard, and
  `rowPickedUp` / `rowMovedTo` / `rowDropped` / `rowCancelled` with their four `column*` counterparts
  are the live-region sentences. Those eight take a context and return a **whole sentence** rather
  than a fragment the grid completes, for the reason the plurals above do. Left in English, so is the
  drag.

One limit inside that group is worth knowing before you translate it. `ordering.instructions` — the
sentence a screen reader reads when focus reaches a handle — is read **once, when the grid mounts**,
and does not follow a later change of language: the drag library builds that node from the string it
was handed at construction and never rewrites it. Everything else about the drag does follow, so a
locale switch mid-session re-translates the handle's name and all eight announcements and leaves only
the keyboard instructions in the language the page started in. If your app switches language without a
reload, remount the grid to pick the new sentence up.

A dictionary that leaves them in English leaves a screen-reader user in English.

## What the dictionary does not cover

A UI kit's own internals keep their own strings: HeroUI's icons, for instance, carry English
accessible names (`Search icon`, `Chevron down icon`) that come from `@heroui/react`, not from this
grid. Everything the grid itself renders — including every `aria-label` it writes — is in the
dictionary.

The calendar is the kit's too. Month and weekday names in a date filter come from the kit's own
locale, not from `messages`: on HeroUI wrap the app in React Aria's `I18nProvider` with
`locale="ru-RU"`; on shadcn the calendar is react-day-picker, which takes its `locale` from
`react-day-picker/locale`.

## What ships

**English and Russian**, as `enMessages` and `ruMessages`. Each is the whole dictionary, typed as
`GridMessages` rather than as a partial one, so a string added to the grid without its translation
fails the package's own type check — a shipped dictionary is never quietly half-translated. Other
languages are a `PartialGridMessages` of your own.

## Options

| Option     | Type                  | Description                                                                                                                                                       |
| ---------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `messages` | `PartialGridMessages` | Replaces any subset of the strings the grid renders, merged per entry onto `defaultMessages`. Set on the grid, or on `DataGridOptionsProvider` for the whole app. |
