# Composition

`<DataGrid />` with no children renders the full default layout. Every piece of that layout is
also a compound member you can place yourself, and each one degrades gracefully: supply nothing
and you get the built-in behaviour, supply something and you take over exactly that piece.

## The default layout

```tsx
<DataGrid
	data={data}
	columns={columns}
/>
```

is equivalent to writing the tree out:

```tsx
<DataGrid
	data={data}
	columns={columns}
>
	<DataGrid.Toolbar />
	<DataGrid.Table />
	<DataGrid.Pagination />
</DataGrid>
```

## Toolbar: add without replacing

The toolbar auto-mounts the controls the enabled features ask for — global search, Clear
filters, the create trigger, the multi-sort builder, column visibility, the page sizer.

`left` and `right` **append** to those, which is what "the default toolbar plus one button of
mine" needs:

```tsx
<DataGrid.Toolbar right={<ExportButton />} />
```

`children` **replaces** the whole bar — the kit's `left` / `right` slots go unused and nothing
auto-mounts:

```tsx
<DataGrid.Toolbar>
	<MyEntirelyCustomBar />
</DataGrid.Toolbar>
```

## Table: reorder, wrap, extend

`<DataGrid.Table />` renders `<DataGrid.Header />` and `<DataGrid.Body />` inside the kit's
`<table>`, wrapped in the scroll container that owns sticky headers, column pinning shadows and
virtualization. Supplying `children` replaces the header/body pair while keeping all of that
plumbing:

```tsx
<DataGrid.Table>
	<DataGrid.Header />
	<DataGrid.Body />
	<DataGrid.Footer />
</DataGrid.Table>
```

`<DataGrid.Footer />` is the footer row the default layout leaves out — see
[Column footers](#column-footers).

A render function gets the live table:

```tsx
<DataGrid.Table>
	{({ table, headerGroups, rows }) => (
		/* … */
	)}
</DataGrid.Table>
```

`<DataGrid.Header />` reads the grid's own `layout.stickyHeader` option, so it keeps working when placed
by hand.

## Body: compose the rows yourself

```tsx
<DataGrid.Body>
	{({ rows }) =>
		rows.map((row) => (
			<DataGrid.Row
				key={row.id}
				row={row}
			/>
		))
	}
</DataGrid.Body>
```

<Callout type='warn'>
	A custom body opts out of **everything** the built-in body does: pinned rows, the creating row, expanded sub-content,
	the loading / empty / no-results fallbacks, the infinite-scroll footer and the refetch overlay. That is the trade —
	full control in exchange for re-implementing what you still want. Omit `children` unless you need it.
</Callout>

## Column headers

`column.header` takes a string or a render function, so a header can carry an icon, a tooltip or
a badge:

```tsx
createColumns<Row>([
	{
		accessorKey: 'total',
		header: () => (
			<span>
				Total <InfoIcon />
			</span>
		),
	},
])
```

## Column footers

`column.footer` accepts the same shape as `column.header`. It is not part of the **default**
layout — a plain `<DataGrid />` renders no footer row — but you do not read it yourself either:
place `<DataGrid.Footer />` inside a custom `<DataGrid.Table>` body and it renders every
column's `footer`, in the same column order and with the same colSpan, pinning and alignment as
the header. `column.footerClassName` lands on the footer cell.

The archetypal case is a numeric column with a total. The render function gets the live table,
so summing over the _filtered_ rows keeps the total honest while a filter is on:

```tsx
const columns = createColumns<Row>([
	{ accessorKey: 'product', header: 'Product', footer: 'Total' },
	{
		accessorKey: 'amount',
		header: 'Amount',
		align: 'end',
		footerClassName: 'font-medium',
		footer: ({ table }) => table.getFilteredRowModel().rows.reduce((sum, row) => sum + row.original.amount, 0),
	},
])
```

```tsx
<DataGrid
	data={data}
	columns={columns}
>
	<DataGrid.Toolbar />
	<DataGrid.Table>
		<DataGrid.Header />
		<DataGrid.Body />
		<DataGrid.Footer />
	</DataGrid.Table>
	<DataGrid.Pagination />
</DataGrid>
```

Giving `<DataGrid.Footer>` `children` replaces the per-column row with your own markup inside
the kit's `<tfoot>` — a node, or a render function receiving `{ table, footerGroups }`:

```tsx
<DataGrid.Footer>
	{({ table }) => (
		<tr>
			<td colSpan={table.getVisibleLeafColumns().length}>{table.getRowModel().rows.length} rows</td>
		</tr>
	)}
</DataGrid.Footer>
```

## Swapping a UI component for one grid

`components` on `<DataGrid>` merges over the kit's registry group by group, so an override
replaces one slot and leaves the rest of the kit intact:

```tsx
<DataGrid
	data={data}
	columns={columns}
	components={{ sorting: { SortMenu: MySortMenu } }}
/>
```

<Callout type='info'>
	Define the object outside the render (or memoize it). The provider keys its merge on the object's identity, so a fresh
	literal every render re-renders every component that reads the registry.
</Callout>

For an app-wide swap, wrap a subtree in `GridComponentsProvider` instead — providers nest and
merge the same way.
