The grid's behaviour lives in `@ez-kit/data-grid-core` and `@ez-kit/data-grid-react`, and a kit
only draws it. So the two kits agree on almost everything: the same options, the same state, the
same `data-*` attributes, the same message dictionary. The whole browser test suite is written
once and run against both, which is how the short list below stays short — and honest.

This page is the complete list. If a divergence is not here, it is a bug rather than a
limitation: please [open an issue](https://github.com/ez-kit/ez-kit/issues/new).

## Known divergences

| Capability                                                                            | shadcn                          | HeroUI                                 | Why                                                                                       |
| ------------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------- |
| [Grouped headers](/docs/data-grid/columns/grouped-headers)                            | Full                            | Renders flat                           | React Aria removed nested columns from its collection before GA                           |
| [`Alt+Arrow` column reordering](/docs/data-grid/columns/ordering)                     | Works                           | Menu only                              | React Aria's column spreads its own props last, overwriting the handler                   |
| [`Alt+Arrow` row reordering](/docs/data-grid/row-ordering)                            | Works                           | Menu only                              | React Aria's row owns focus inside the grid and forwards no key handler                   |
| [Header drag while the column panel is open](/docs/data-grid/drag-and-drop)           | Works                           | Does not start                         | HeroUI's popover covers the header, so the pointer never reaches the handle               |
| [`Escape` during a panel drag](/docs/data-grid/drag-and-drop)                         | Reports nothing, writes nothing | Can write without reporting            | Unexplained; `Escape` is both the popover's dismiss key and the drag library's cancel key |
| [Focus after `Tab` ends a keyboard drag](/docs/data-grid/drag-and-drop#keyboard)      | Stays on the handle             | Leaves the table                       | React Aria's focus manager owns focus inside the grid                                     |
| [A drag handle's `aria-roledescription`](/docs/data-grid/drag-and-drop#announcements) | From the dictionary             | The drag library's English `draggable` | React Aria's button forwards an allow-list of ARIA attributes and this is not on it       |

None of these affect the data, state, or options you write — moving a grid between kits never
requires rewriting your config. The first three are upstream constraints; the last four are drag-specific.

### Grouped headers render flat in HeroUI

`columns[].columns` builds a header group. HeroUI renders the leaf columns directly without the
group row; the columns and all other features work normally. See [Grouped headers → Kit support](/docs/data-grid/columns/grouped-headers).

### `Alt+Arrow` reordering is shadcn-only

The shadcn kit supports `Alt+ArrowLeft` / `Alt+ArrowRight` on focused headers. HeroUI does not —
the menu entries still work in both kits, so the capability is present either way. Tracked in
[#223](https://github.com/ez-kit/ez-kit/issues/223).

### A header column does not drag while the column panel is open (HeroUI)

Both [drag surfaces of the column axis](/docs/data-grid/drag-and-drop) work in both kits. What
HeroUI cannot do is the two at once: with the Columns panel open, its popover covers the header, so a
pointer aimed at a header cell's grip never reaches it and no drag starts. In the shadcn kit the same
gesture works.

Measured rather than inferred — nothing overlays the handle in the accessibility sense, the element
is where it was and its `pointer-events` are `auto`; the popover's own overlay is simply in front. It
is a property of that kit's popover rather than of the drag layer, and it costs little: the panel is
itself the affordance for reordering while it is open. Drag a header column before opening the panel,
or drag inside the panel.

### `Escape` during a panel drag can write without reporting (HeroUI)

A known defect. In HeroUI, pressing `Escape` mid-drag in the column panel may change the order
without calling `onChange`. Applications persisting the order should read it from `state.columnOrder`
on the grid rather than relying on the callback alone.

### Where focus lands when `Tab` ends a keyboard drag (HeroUI)

In both kits, `Tab` ends a keyboard drag and commits. In shadcn, focus stays on the handle; in
HeroUI, focus leaves the table. The order is written identically either way.

### `Alt+Arrow` row reordering is shadcn-only

The shadcn kit supports `Alt+ArrowUp` / `Alt+ArrowDown` on rows with focus. HeroUI does not — the
menu entries still work in both kits, so the capability is present either way. Same upstream cause
as [#223](https://github.com/ez-kit/ez-kit/issues/223).

## Presentation, not capability

One more difference, listed because the promise above says everything is listed — but it costs a
reader nothing and changes no config:

The **column visibility control** in the toolbar is a popover of labelled checkboxes under shadcn
and a menu of checkable entries under HeroUI. Same columns, same toggles, same result; each kit
reaches for the overlay its own design system uses for this. It matters only if you are writing a
selector or an automated accessibility check against the control itself, in which case expect
`checkbox` under shadcn and `menuitemcheckbox` under HeroUI.

## What is deliberately the same

Worth stating, because these are the places two kits most often drift apart:

- **Options and state.** Nothing in a grid's config is kit-specific. The same `columns`, the same
  `sorting` / `filtering` / `pagination` / `editing` objects, the same controlled state.
- **The `data-*` contract.** `data-slot`, `data-row-id`, `data-column-id`, `data-pinned`,
  `data-align`, `data-sort-direction`, `data-row-selected`, `data-scrollport` and the rest are
  emitted by the shared React layer, so a stylesheet or a test written against them holds for
  every kit. See [Theming](/docs/data-grid/theming).
- **Every user-facing string.** One dictionary, one set of keys — see
  [Localization](/docs/data-grid/localization).
- **The delete confirmation is an `alertdialog` in both**, not a plain dialog: it asks something
  destructive and irreversible, so a stray click on the backdrop is not an answer.
- **Server rendering.** Both kits prerender. Nothing in either requires a client-only boundary.

## Picking a kit

Neither list above should decide it. Pick the one whose design system you are already in —
[shadcn](/docs/data-grid/installation/shadcn) if your app is built on Radix and Tailwind,
[HeroUI](/docs/data-grid/installation/heroui) if it is built on HeroUI — and treat grouped headers
as the one capability to check against your design before committing.
